# Other consoles

[Back to README](../README.md) · [The proof tools](../tools/README.md) · [The Dreamport standard](STANDARD.md)

A Dreamport can be of a game on any console, and the proof tools work the same way for each: the same recorded presses in the original and in the Dreamport, every frame compared, picture and sound. This page says what that rests on, how far each console has got, and what a console needs to be added.

## How a console is known

[`kit/consoles.js`](../kit/consoles.js) lists each console: its name, the size of its screen, how long a frame lasts, how many sound samples a second it mixes, the kinds of file a copy comes in, and its buttons. Games read it in the browser, and the tools read it too. [`tools/consoles.mjs`](../tools/consoles.mjs) adds what only the tools need: which emulator runs the original, and which of that emulator's buttons is each of the console's.

A game's `proof/original.json` names its console, and everything follows from that: `rom` tells a copy by what it holds, whichever console it's for, `prove` compares at that console's rate and frame time, and at the game's screen, `capture` opens a window with its buttons, and `new` starts a game on it.

A game that chooses its own screen says so in the same file, as `"screen": [256, 224]`, or as a list when it changes partway, `"screen": [[320, 224], [256, 224]]`, the size it starts at first. With none it's the console's size in `kit/consoles.js`. A Game Boy Advance game has no say, as its screen never changes.

## What runs the original

The Game Boy Advance runs in mGBA, as it always has ([Getting ready](../tools/README.md#getting-ready)). Every other console runs in a libretro core, a small emulator with one way of being driven, through [`tools/libretro/host.c`](../tools/libretro/host.c), a program of the tools' own that gives them the same pictures, sound and memory that mGBA's does.

The first time a game on a console needs its core, the tools fetch it from its makers' source, at a fixed commit, and build it on the contributor's computer, once. So everyone gets the same pictures, and the project publishes no programs of its own. Each runs with the settings that keep it the same for everyone, in `tools/consoles.mjs`, and with nothing saved from one run to the next. A console that can't start without a BIOS would find one a person has from their own console in `.dreamports/libretro/system/<console>/`, and nothing in the project helps get one. Gambatte and PCSX ReARMed are set to go without, so that a person's BIOS doesn't change what they show. A made-up file there does change Gambatte's frames when that setting is off. PCSX ReARMed's setting comes from reading its source, as no real BIOS has been tried.

| Game Boy, Game Boy Color | 59.7275 | 32,768 | 160 by 144 | 27 KB | 8 KB |
| Super Nintendo | 60.0988 | 32,040 | 256 by 224 | 823 KB | 128 KB |

| PlayStation 2 | 60 | 48,000 | 640 by 448 | 40 MB | 32 MB |

**Screens.** An emulator may not show the whole screen unless told to, as FCEUmm cuts the NES's to 224 lines, which is why it has settings for that. A game can also choose its own size: a Mega Drive game can use 256 or 320 across, a PlayStation game many sizes, and a Nintendo 64 game can show twice the lines. Such a game lists its sizes in its `proof/original.json`. Each frame is compared at the size it has, so it can change partway, and the same pixels in another shape are another picture. `prove` stops when the original shows a size the game doesn't list, and gives the line to write, leaving out frames only the original has, as nothing compares them. When the Dreamport's picture is another size than the original's, `prove` says at which frame. The stills and clips `prove` makes have room for the largest width and height listed, with a smaller picture filled with black on the right and below. A capture is cut to the size its moment shows, so no band of black reaches a game's card, and `capture` stops only at a picture too large for what the game lists, which would lose its edges. Genesis Plus GX showed a small program at 256 by 224 and then 320 by 224 as it chose, with 256 by 192 on its very first frame, which nothing compares. So far only the made-up console has proved a game at its own size, and the Super Nintendo's kit a program of the project's own at four, 256 or 512 across and 224 or 448 down.

**Names and regions.** FCEUmm reads a copy's region from words anywhere in its path, so `Games (a)/program (E).nes` ran as a European copy, at 50 frames a second. The tools now give an emulator the copy under a plain name of their own, except a disc's `.cue`, which names its tracks from where it is. A copy that really is for another region's consoles stops with a sentence saying so, as `prove` knows a region only by a frame's length.

**Sound.** A real console's sound isn't a clean wave. The NES's waves only ever go up from zero, and FCEUmm's filter then makes a thump in the lowest bands when a note stops, loud enough for `prove` to notice, so a Dreamport has to make that sound too. A Nintendo 64 game chooses its own rate, so `host.c` follows the emulator's notice of it and hears the sound at the kit's rate, on a straight line between samples. `prove` compares loudness by bands, so that's near enough, though the highest band loses a little.

**Frames.** On FCEUmm a game's frame shows in the next one, as `prove` assumes, and so does its sound. The others ran only a program that does nothing to show it.

**Save states and work memory.** Only `route` uses save states, the emulator's own, in memory as it searches for a recording's presses, and it keeps none of them ([Finding a route](../tools/README.md#finding-a-route)): it needs a core that can copy its state out and bring it back, and has been run on none of these consoles yet. `prove --state` says it can't compare on these consoles, so their sizes don't matter yet. A start point writes to work memory as the emulator keeps it. Going by their source, Genesis Plus GX keeps it in pairs of bytes swapped and Parallel N64 in fours, so a whole word lands as it should and a lone byte needs its address changed. Only the NES has tried a start point.

**Buttons.** The NES's were pressed in a recording. The Mega Drive's and Nintendo 64's agree with their emulators' source, and the rest are still only as chosen.

**Building.** Each builds with a compiler and `make` alone, but for Play!, which needs CMake too, and on Linux the headers of EGL and OpenGL ES and Mesa's drawing, which on Debian or Ubuntu `sudo apt install libegl-dev libgles-dev libegl-mesa0 libgl1-mesa-dri` installs. Parallel N64 is built with no recompiler and no OpenGL, so it needs no assembler or graphics libraries, only OpenGL's headers on Linux, which its `libretro.c` includes whatever it's built with and `sudo apt install libgl-dev` installs, and runs on its interpreter, with `-O2` in place of its makers' `-Ofast`, so its floating-point unit rounds as IEEE 754 asks, as the console's does.

## The PlayStation Portable

PPSSPP runs it, built from [its makers' source](https://github.com/hrydgard/ppsspp) at version 1.20.4, under the GPL, version 2 or later. It starts a program or a disc with its own stand-in for the console's system software, so nobody needs a file from their own console and everyone gets the same frames ([#1907](https://github.com/NahuelGenchi/dreamports/issues/1907)).

**Its pictures and its processor.** It's run with its software renderer, which draws on the computer's processor, so a picture depends on no graphics card and the tools give it no graphics context: it runs on Windows as on Linux and a Mac. Its renderer works out each pixel and texel with its own C++, as the tools' patch has it do on every computer: it has no code it compiles for Apple's chip, and the code it compiles for Intel's and AMD's didn't write a pixel with a write mask as its C++ does. Its processor is its interpreter, an instruction at a time, as the other consoles' are. It's built with CMake, without FFmpeg, which only a game's films and compressed music need, so those don't play yet, and with `-ffp-contract=off`, as Play! is, so a compiler for Apple's chip rounds each product and sum of the emulator's own as Intel's does. Of its source's many other projects the tools fetch only the ones it's built from.

**One frame at a time.** PPSSPP ended a frame of the tools only when the screen had changed, or after ten of the console's frames with nothing new, and decided by the computer's clock whether to skip one, so a still screen swallowed several of the console's frames into one of the tools', a different number from one run to the next. It also loaded the program on a thread of its own while the tools' first frames went by, more of them on a slower computer. So the tools patch its source as they build it, with [`tools/libretro/ppsspp.patch`](../tools/libretro/ppsspp.patch), whose hash is in the built core's name so a build without it is never used: each V-blank ends a frame, showing what the screen shows then, and nothing else does; no frame is skipped and none waits for the computer's clock; the console starts in the first frame the tools ask for, however long loading took; and its clock starts at the first second of 2005 in every run, and goes on by the console's own time.

**What the small program showed.** Its screen is 480 by 272 from the first frame. It paints the framebuffer itself and waits for each V-blank: the background shows on frame 1 and the square from frame 2, in its own place on every frame after. The console mixes 64 samples at a time, 44,100 a second, so a frame has 704 or 768 of them, and the program's square wave, played by a second thread a block of 1,024 at a time, comes out with every sample as loud as it was written. A button held from frame 100 shows from frame 101, as the console reads its buttons at the V-blank that ends a frame and the program paints what it read in the next. Both runs of 600 frames gave the same pictures and the same sound.

**Ending.** PPSSPP's threads are still running as the tools' program ends, and what it tidied away under them stopped the program with an error after everything was written, so the program that drives the emulators now ends at once when it has written everything, for every console.

**Its buttons.** PPSSPP's own front worked the stick's place out by dividing by how far over it is, which is zero by zero when nobody touches it, and what that became, all the way up and left, was the compiler's to choose. The tools' patch puts an untouched stick in its middle, as the console's is. The console samples its buttons as each V-blank ends, from what the emulator was given as the frame started, so a game's `proof/original.json` says `"keysAfterVBlank": true`.

**Its sound list.** The patch also keeps each frame's sound list, everything a game gives the sound channels and each block of 64 samples the console mixes, hashed as the kit in C hashes its own ([the kit](../kit/psp/c/README.md)), so a game's sound is proven by it and by every sample, as a PlayStation 2's is.

**Its function check.** The tools' patch also gives the core a call that runs one function of a game's program by the emulator's own interpreter, which `twin` calls beside the function's twin in C, from the same memory ([The function check on the PlayStation Portable](../tools/README.md#the-function-check-on-the-playstation-portable)), and the tools keep the console's proofs. `match` has no compiler for it: its games were built with Sony's or SN Systems', which no one can have freely.

**Its parts for tasks.** The tools' patch tells the program that drives the emulators of each instruction PPSSPP's interpreter runs, and which way each conditional branch went, and a function runs in a frame when its first instruction does, so `prove` keeps each part's functions in `proof/part-functions.json`, as on the NES, and a game's tasks can be its parts. Its code map names the program's start, `"start"`, which goes round the game's loop and never comes back, so no call can prove it and it's in no task. What ran isn't read into gameplay proven yet, as that needs each of the console's functions followed through its instructions, which the tools do for the Game Boy Advance, the NES, the Super Nintendo and the PlayStation 2 so far. `npm run test:psp-parts` takes a made-up program through the whole new way, from `proofs --start --parts` to a part done, on Linux, a Mac and Windows ([#1965](https://github.com/NahuelGenchi/dreamports/issues/1965)).

**Its graphics chip.** The kit runs a game's display lists as PPSSPP does, with the chip's time, its interrupts and its waits, and draws rectangles in the screen's own coordinates and copies blocks, pixel for pixel as the software renderer does ([#1945](https://github.com/NahuelGenchi/dreamports/issues/1945)). Each frame's draw list, every command the chip ran and what each draw read, is hashed in the kit and by the tools' patch alike, so a game can be proven by its draw lists as well as its pictures (`"provenBy": "draw lists"`). Triangles, textures and 3D are [#1980](https://github.com/NahuelGenchi/dreamports/issues/1980).

**Its processor's own instructions.** The kit's `psp.h` gives each of the Allegrex's instructions that C has no word for, and the floating-point unit's conversions to whole numbers, as PPSSPP's interpreter gives them, and the function check gives a function its floats in the unit's registers ([#1978](https://github.com/NahuelGenchi/dreamports/issues/1978)). The tools' patch has PPSSPP convert a float past what a word holds to the nearest it holds on every computer, as ARM's processors do and x86's didn't.

**Its semaphores and event flags, mutexes and callbacks.** The kit has semaphores, event flags, mutexes and lightweight mutexes as PPSSPP answers them, with their timeouts as it times them, and the callbacks a game makes as the console's SDK has it start ([#1979](https://github.com/NahuelGenchi/dreamports/issues/1979), [#2001](https://github.com/NahuelGenchi/dreamports/issues/2001)).

**Its vector unit.** The kit runs the vector unit's instructions as PPSSPP's interpreter does, ported from its source, with the tables PPSSPP measured on the console for the unit's sine and the rest, which the tools give PPSSPP too, so both work them out from the same files on every computer. A thread made with the unit has its own, as the system keeps it, and the function check gives a function the unit's registers and compares what it leaves there ([#1987](https://github.com/NahuelGenchi/dreamports/issues/1987)).

**Still to come.** A callback a game notifies, message boxes, interrupts, timers, files and the system's functions by number ([#1990](https://github.com/NahuelGenchi/dreamports/issues/1990)). Nothing has tried a disc, a save, a start point or a search for a route on it yet.

## The PlayStation 2

Play! runs it, built from [its makers' source](https://github.com/jpd002/Play-) under a BSD licence. It starts a game or a program with its own stand-in for the console's BIOS, so nobody needs a file from their own console and everyone gets the same frames. The other emulator with a libretro core, the libretro PCSX2, runs more games and draws on the processor, but it won't start without a BIOS, and a BIOS's version can change what a game shows.

**Its pictures.** Play! draws only with OpenGL, so `host.c` gives a core that asks a graphics context with no window, from EGL, and a framebuffer it reads each picture back from. It asks Mesa for llvmpipe, which draws on the processor, so the picture doesn't depend on the computer's graphics card, and stops with a sentence if it gets anything else. Play! is built for OpenGL ES 3, which needs no GLU or GLEW. That's on Linux. A Mac gets its context another way, below, and so does Windows, after it. Two computers with different versions of Mesa could still draw some things differently, which a 3D game will show (#618).

**On a Mac.** There `host.c` makes the context with CGL, on Apple's OpenGL, and asks for Apple's software renderer, which draws on the processor, so a picture is the same on every Mac whatever its graphics chip, as llvmpipe's is on Linux, and stops with a sentence if it gets anything else. Play! is built for OpenGL rather than OpenGL ES, which a Mac doesn't have, and for the processor Node.js runs as, arm64 on Apple's chip, with the host built for the same. Its JIT keeps the code it writes in memory mapped with `MAP_JIT`, and switches each thread between writing it and running it, as Apple's rules ask; the host isn't a hardened program, so it needs no entitlement for that. Play! is built with `-ffp-contract=off` everywhere, as a compiler for arm64 would otherwise fuse a product and a sum of the emulator's own C++ into one rounding where x86's can't, and its JIT writes each product and sum on its own on both. Apple's renderer and Mesa's can still draw a shaded triangle differently, which is why the PlayStation 2's 3D games are proven by their draw lists.

**On Windows.** Windows' own OpenGL draws on the graphics card, and with none it stops at OpenGL 1.1, so the tools fetch Mesa for Windows, [mesa-dist-win](https://github.com/pal1000/mesa-dist-win)'s build of it (MIT), about 66 MB, at a fixed version and checked against its hash, and keep its OpenGL library and what it draws with in `.dreamports/libretro/`, on your computer only. Nothing is installed, and Windows' own OpenGL stays as it is for everything else. `host.c` loads it before the emulator, makes a context with WGL on a window nobody sees, and asks for llvmpipe as on Linux, stopping with a sentence if it gets anything else ([#1909](https://github.com/NahuelGenchi/dreamports/issues/1909)). Play! is built there by the compiler `setup` gets, [w64devkit](https://github.com/skeeto/w64devkit)'s GCC, where its makers build it with Microsoft's, so the tools' patch has what GCC needs of it: a few headers named, Microsoft's own flags left to Microsoft's compiler, and a file opened by a wide name. Play! keeps its settings and memory cards in the Documents folder there, whatever the environment says, so the patch has it take the folder the tools name for a run instead, and nothing is left in a person's own. A memory card's folder that holds something isn't deleted, which GCC's library on Windows says another way than Play! looks for, so the patch looks first there. On 24 November 2026, on Windows 11, `npm run dp -- setup ps2` built it in under four minutes, and `npm run test:ps2-same` gave what Linux gives for every program: each frame's draw list, sound and memory, and each picture. The Mac workflow runs it on GitHub's Windows too and compares the two on every pull request that touches the PlayStation 2's files. Sony's own compiler isn't built on Windows yet, and the kit's own checks that build it for the computer need a C compiler there, named in `CC`.

The Mac workflow ([`.github/workflows/mac.yml`](../.github/workflows/mac.yml)) runs all of it on GitHub's Mac with Apple's chip, for pull requests that touch the PlayStation 2's files, after they merge and every week, on the newest macOS GitHub has: Getting ready with Homebrew's Node.js, GitHub CLI and CMake, `npm run dp -- setup` and `setup ps2`, which builds Play! there in about seven minutes, `npm run test:real-ps2`, `test:ps2-3d`, `test:ps2-kit`, `test:ps2-gs` and `test:ps2-sound`, and `npm run test:ps2-flow`, which goes through what `/dreamport` does with a new PlayStation 2 game, `rom`, `codemap`, `new`, `capture` and `prove`, on a small program, and then plays its page in Safari and in Chrome, with every picture and draw list the same in both. On 19 November 2026 all of it passed on macOS 26.7 with Safari 27.2, where Apple's software renderer is the only one GitHub's Mac has. A job on Linux and the Mac each run `npm run test:ps2-same` on the small programs, and a third compares the two: every frame's draw list, sound and memory the same on both, and every picture of the programs proven by their pictures. The test with this computer's graphics card in `test:ps2-3d` has nothing to compare there, and a person's Mac with Apple's chip is where it first will.

**Its own folder.** Play! keeps its settings and memory cards in the person's home folder, on a Mac in its Documents folder, so each run is given an empty one of its own, as every core's saves are, and nothing carries from one run to the next. On a Mac Play! asks Apple's CoreFoundation where that is, which `CFFIXED_USER_HOME` points at the run's folder.

**One frame at a time.** Play! runs the console on a thread of its own, which ran a frame or two ahead of what the tools asked for. It copied the buttons in at each V-blank from whatever the tools last gave, handed over a picture only when the console flipped one, so a still screen swallowed several of the console's frames into one of the tools', and kept only the latest of its 990-sample blocks of sound, losing the rest. On The Sims (USA), with Start held, one run of three parted from the others six frames after the press, and 3,000 frames gave 1,998,810 samples where they last 2,205,000.

So the tools patch Play!'s libretro front as they build it, with [`tools/libretro/play.patch`](../tools/libretro/play.patch), whose hash is in the built core's name so a build without it is never used. The console waits at each V-blank, before it reads the buttons, until the tools ask for the next frame, and the tools serve the GS's calls until it gets there, so each frame of the tools is one frame of the console and its buttons are read as it starts. Sound is handed over a block at a time, every block kept, so each frame has the samples it lasts, give or take a block: 45 samples at 44,100 a second then, and 48 at the chip's own 48,000 since #1612. The small program's first frame is now black, as the program draws once the first V-blank has started, where before Play! was already ahead. With the patch The Sims gave the same pictures and sound in three runs of 3,000 frames, two of them side by side with others, 2,204,910 samples each, reached its main menu by frame 2999 and played 5,000 frames in 50 seconds. A small program can't press buttons it doesn't read, so that a press lands on its frame is shown only by The Sims, whose copy stays on the computer it was run on.

**Draw lists.** The same patch keeps each frame's draw list: a hash of every register the console writes to the GS, every picture it sends it, and what the screen shows of the framebuffer, in the order given, with how many things that was. `host.c` writes them where the environment's `DP_DRAWS` says, and that's what a 3D game is proven by ([How progress is measured](STANDARD.md#how-progress-is-measured)). `npm run test:ps2-3d` tries it on a second small program, two shaded triangles that cross, one turning by float sums: the same list in every run, the same list from the program written again in JavaScript with the console's arithmetic, and the same list, with different pictures, when this computer's graphics card draws it where the tools ask for llvmpipe. A game whose `original.json` says `"provenBy": "draw lists"` is compared by them in `prove`, against what its Dreamport gives the kit's GS ([PlayStation 2 kit in C](../kit/ps2/c/README.md)), and `npm run test:ps2-kit` proves the small 3D program's Dreamport in C that way, every frame, and a program whose shapes come from a program on vector unit 1, through the kit's GIF and the unit's sums.

**Sound lists.** The patch keeps each frame's sound list too: a hash of every register the IOP writes to the SPU2, every block of sound data moved to or from it by DMA, and a mark for every block of 45 samples it mixes, in the order they came, so the list says which block each write came before. `host.c` writes them where `DP_SOUNDS` says, and each frame's samples as the emulator made them, 16 bits each, where `DP_SOUND_EXACT` says. A PlayStation 2 game's sound is proven by both, exactly, against the kit's SPU2 ([PlayStation 2 kit in C](../kit/ps2/c/README.md#the-iop-and-its-sound)), and `npm run test:ps2-sound` proves a program of the project's own whose IOP module plays sound that way. The emulator mixed at 44,100 samples a second on its own model of the chip. Since #1612 the tools build the kit's chip into it in place of its own, so both mix as the console does, 48,000 samples a second and 48 at a time, and `npm run test:ps2-spu2` checks that chip against PCSX2's own, sample for sample. `DP_SOUND_DATA` names a file for the bytes moved to the chip by DMA, which that check gives PCSX2.

**The console's floats.** Play! works out the EE's and the vector units' float sums with the computer's own floats, cut towards zero, which isn't what the console does: its sums drop all but one bit of the smaller number before they add, its largest float is one a computer calls NaN, it has no infinity, and it raises flags Play! doesn't keep. So the same patch gives Play! the console's rules, the multiplier's and the divider's circuits among them, held to what a real console printed for 1,098 sums (#1622), as one file that the PlayStation 2's kit in C uses too ([`kit/ps2/c/floats.c`](../kit/ps2/c/floats.c)), and `npm run check` checks that the two copies are the same, word for word. With it Play!'s FPU keeps its flags, its vector units have every MAC and status flag at the cycle the console has it, and SUBAq, which Play! left out, is there. A proof then compares a Dreamport with an emulator that follows the console, where the two used to share Play!'s shortcuts. It makes Play! slower in the tools, as each sum is a call. `npm run test:ps2-ee-vu` proves a program of the project's own against it, the kit's whole EE, vector units, VIFs, DMA controller and GIF ([the kit's README](../kit/ps2/c/README.md#how-its-checked)), with both vector units' memories compared every frame, which the patch writes where the environment's `DP_VU_DUMP` says.

**Buttons.** The emulator gives its pads a frame's buttons as the frame starts, and a game's pad module reads them in that same frame, so a PlayStation 2 game's `original.json` says `"keysAfterVBlank": true` ([Proving](../tools/README.md#proving)). Play!'s libretro front takes buttons as held or not and the left stick as the tools give it, all the way over or not at all, so the pressure it gives a game for a button is all or nothing: a recording can't hold how hard a button is pressed or how far a stick is pushed yet.

**A stricter reference for the kit's pictures.** Play! draws on a graphics card, which can't be exact for everything the GS does: a shaded triangle's colours, a texture sampled between texels, fog, dithering, smaller copies of a texture, points, lines and edges, and what it keeps on the card rather than in the GS's memory. So where the kit's drawing is checked against more than Play!, it's PCSX2's software renderer, built from [its makers' source](https://github.com/PCSX2/pcsx2) by `tools/ps2/pcsx2.mjs`, once, on Linux, with the libraries it needs beside it, and run through its GS runner. The kit's Dreamport runs on the computer, everything its GS was given goes into a GS dump, PCSX2 replays the dump and saves each frame's framebuffer straight from its memory, and every bit of every pixel is compared, alpha too (`tools/test/gs-reference.mjs`). PCSX2 is GPL-3.0-or-later and runs only as a tool, and its replay needs a graphics card with a Vulkan driver, as it shows its output through one, even with no window. PCSX2 draws what varies across a shape, such as a shaded triangle's colours, a step of colour apart on thousands of pixels between a processor with AVX2 and one without, so the check has it draw every program both ways, and only what comes out the same is taken as exact. Neither it nor Play! is known to be bit for bit the console's: the one free GS renderer that's written from scratch says so of itself, and no public test of the chip is exact enough to settle it, so a pixel that agrees with both is the strictest proof there is until one exists.

**What a game's lists hold.** `npm run dp -- draws <copy>` plays a game's original from power-on, with a list of presses if it's given one, and counts what the game gave the GS: its shapes and how they're drawn, its textures' formats and sizes, its blending and tests, what it draws into, and which of the console's paths the writes came by, which says whether vector unit 1 makes its shapes. That's what the kit has to draw, and do, for a Dreamport of that game ([Counting what a game draws](../tools/README.md#counting-what-a-game-draws)). For it the emulator writes each frame's whole list to a file, a picture's bytes left out, where the environment's `DP_DRAW_DUMP` says, which the tool removes once it has counted.

**What ran, and what was read.** The same patch has Play! tell the tools of every block of instructions it runs on the EE, the IOP and both vector units, with which way its branch went, and of every sector of the disc the game reads, so a PlayStation 2 game's gameplay proven counts its code and its disc's data, and `untouched` lists what's left of both ([On the PlayStation 2](../tools/README.md#the-code-map-and-the-two-numbers)). `npm run test:ps2-ledger` checks it on a disc of the project's own, then proves the program on it and asks `untouched`.

**What it holds.** The same patch says where Play! keeps the console's memories, the EE's, the IOP's and the sound chip's, and its memory cards, so `prove` compares a game's memory after every frame and what it saves to its cards, file by file ([The same-memory build](../tools/README.md#the-same-memory-build)). Play! read the computer's clock for the console's, and for the times of a card's files, so the patch gives it a clock of its own instead: midnight on 1 January 2001, Coordinated Universal Time, as the console starts, going on as its V-blanks do, the same in every run. A kit's clock starts at the same moment. `npm run test:ps2-memory` checks it on the real emulator.

## The Nintendo DS

[melonDS](https://github.com/melonDS-emu/melonDS) runs it, built from its makers' own source at a fixed commit, under the GNU General Public License, version 3 or later. It's fetched and built on the contributor's computer, as every emulator here is, and the project publishes nothing built from it. Of the emulators anyone can build, it follows the console most closely: both processors on one clock, each instruction with its own length, a software renderer for the 3D that's written to give the console's pixels, and the sound's mixer as the hardware runs it. DeSmuME is older and looser in its timing, and NooDS and the two libretro cores named melonDS follow older versions of it or are other people's ports. So the tools build melonDS itself, with a small front of their own, [`tools/nds/melonds/libretro.cpp`](../tools/nds/melonds/libretro.cpp), that drives it the one way `host.c` drives every emulator.

**No window, no settings, nothing of the computer's.** The front builds only melonDS's console: its interpreter and not its recompiler, whose blocks would change when an interrupt lands, its software renderer and not OpenGL, and no thread but the one it runs on. It gives the console no files, no network, no camera, no microphone and no clock of the computer's, so a frame depends on the program and its presses alone. It builds with a compiler and CMake on Linux, a Mac and Windows, where the tools get both for themselves, as they do for mGBA.

**How it starts.** With melonDS's free BIOS and the firmware it writes itself, and the program started directly, as the console's firmware would have left it, so nobody needs a file from their own console and everyone gets the same frames. A game that checks the BIOS's or the firmware's own bytes would see the free ones. The clock starts at midnight on 1 January 2000 and goes on only as the console runs.

**Two screens, one of them touched.** A frame's picture is both screens, the upper above the lower with nothing between them, 256 by 384, and `kit/consoles.js` says where each is. A recording keeps a touch beside the buttons, as `"TOUCH@200,150"`, the lower screen's pixel, 0 to 255 across and 0 to 191 down, from the frame it's listed until the next change, as a button is. The tools give it to the emulator in the same 32 bits as the buttons, and the front gives it to melonDS as a touch on that pixel, which the game's ARM7 program reads from the touch screen's chip as the pixel times 16. The made-up program shows a button the frame after it's held and a touch two frames after, as its ARM7 takes most of a frame to ask the chip.

**A game's page.** The page shows the picture as it is, the upper screen above the lower, at a whole number of the display's pixels. A finger or the mouse held on the lower screen touches the pixel it's on, and one that slides off still touches the nearest pixel of its edge until it's let go. The game reads it once a frame, as `input.touch` in JavaScript and `kit_touch` in C. Under the proof tools the touch is the recording's, and in record mode the page keeps each frame's touch beside its buttons. The touch from a recording is proven by `npm run test:real-nds`. The finger's own path, on the page, hasn't been tried in a browser by a test yet.

**Its sound.** The console's mixer makes a pair of samples every 1,024 ticks of its 33,513,982 Hz clock, 32,728.498046875 pairs a second, which is why `sound` in `kit/consoles.js` isn't a whole number. melonDS then resamples that for a computer's speakers. The tools' patch, [`tools/libretro/melonds.patch`](../tools/libretro/melonds.patch), takes each pair as the mixer leaves it, before that, cut to the 10 bits the console's speakers get, so a frame's samples are the console's own. A frame's sound is what the mixer made from one V-blank's start to the next's, as what a frame shows and plays follows from what a game writes in the V-blank before it. melonDS's own frame runs from line 0 to line 262, with the V-blank 73% of the way through, so the front keeps what's mixed from line 192 on for the next frame.

**Its colours.** The console shows 18 bits of colour, 6 for each of red, green and blue, and the tools compare a picture at 15, as they do on every console. A game's 2D colours are 15 bits, which lose nothing. What 3D, blending and the master brightness add in the sixth bit isn't compared yet, and the kit's own check of its 3D will have to compare all 18.

**What's left out.** The microphone hears nothing, the lid stays open, and nothing is in the slot for Game Boy Advance cartridges. A recording can't hold any of them yet. Wireless play isn't there either. The Nintendo DSi's own games aren't run.

**What ran.** The tools' patch has melonDS tell the front of each place either processor is sent to, by a call, a branch or a return, and the front says which of the code map's functions ran in each frame: one whose processor was sent to its address while the memory there held the function's first 8 bytes. A Nintendo DS game's code is all in memory, and two overlays can have the same place, so the bytes say which one is there. So `prove` lists the functions that ran in matching play, the ARM7's and an overlay's among them. It doesn't follow each instruction, so `untouched` and gameplay proven by instructions aren't there yet, and a function the processor only falls into from the one before it isn't counted.

**A Nintendo DS game's proof.** Since [#1936](https://github.com/NahuelGenchi/dreamports/issues/1936) a function of a Nintendo DS game can be proven by the same memory, `twin` on the Nintendo DS, which calls the twin and the original from the same memory, the original in melonDS's own ARM946E-S or ARM7TDMI, in ARM or in Thumb code, the processors the reference emulator runs every game on, and keeps the proof in the version's `proofs.json` ([The function check on the Nintendo DS](../tools/README.md#the-function-check-on-the-nintendo-ds)). It compares the console's main memory and what a function gives back, and sets aside, saying why, a call that reaches the rest of the console's memory, the BIOS or the system control coprocessor. Not by the same bytes yet: `match` has no compiler for the Nintendo DS.

**A game made the new way.** `npm run test:nds-flow` takes a made-up Nintendo DS game of the project's own through the new way of making a game, a part at a time, each part a task of the functions the original runs in it ([#1955](https://github.com/NahuelGenchi/dreamports/issues/1955)): `proofs --start --parts`, a recording with two parts, `prove` matching it in melonDS on every frame and writing which functions each part runs, `tasks` opening a task for each part against a stand-in for GitHub, `find --take` handing the first out, `twin` proving the functions in melonDS's own processor, and `ready --task` failing while a part's function has no proof, failing while its frames don't match, and passing once both hold. Its Dreamport is on what every console's kit in C shares, as the Nintendo DS has no kit of its own yet. A program's start and its main loop, which never come back, run in no part and can't be proven by the same memory, as on the other consoles.

**Its memory.** The tools read and write the console's main memory, 4 MB at `0x02000000`, by its own addresses. The emulator's front says where it starts, and `host.c` counts from there.

The workflow [`.github/workflows/nds.yml`](../.github/workflows/nds.yml) runs `npm run test:real-nds` on Linux, on GitHub's Mac with Apple's chip and on Windows, for pull requests that touch the Nintendo DS's files or what its emulator is built with, after they merge and every week.

## What's different from the Game Boy Advance

A few things the tools do rest on mGBA, and stay with it for now.

Code ported counts only the port map's names on every console, the Game Boy Advance too since [#1452](https://github.com/NahuelGenchi/dreamports/issues/1452). So its number rises as the Dreamport's code names functions from its code map, and a recording doesn't add to it. A libretro core doesn't say which of the original's functions ran, so on another console `prove` can't list those that ran in matching play and still have no twin. The Game Boy and the Game Boy Color are exceptions too, since [#1959](https://github.com/NahuelGenchi/dreamports/issues/1959): the tools build Gambatte with a change of their own that tells them of every instruction, so `prove` lists the functions that ran and what each part runs, and gameplay proven stays their parts' share. The NES is the first: the tools build FCEUmm with a small change of their own that tells them of every instruction it runs, so an NES game's code map says which functions ran, `codemap --fill` finds those only play reaches, and `untouched` lists the instructions and branch ways nobody has played, while its gameplay proven stays its parts' share until the tools follow its data too ([On the NES](../tools/README.md#the-code-map-and-the-two-numbers)). The PlayStation 2 is the other: Play!, with the tools' patch, tells them of every block of instructions it runs and every sector of the disc it reads, so its gameplay proven counts its code and its disc ([On the PlayStation 2](../tools/README.md#the-code-map-and-the-two-numbers)).

The tools find the functions themselves in Game Boy Advance, NES, Game Boy, Game Boy Color, Super Nintendo, PlayStation, Nintendo 64, PlayStation 2 and Nintendo DS code. On any other console the code map comes from a list, with `codemap --from`, a decompilation's symbols or a disassembler's list of functions. `read` knows the Game Boy Advance's instructions, through mGBA's decoder, the NES's, through a table of the tools' own ([`tools/nes/6502.mjs`](../tools/nes/6502.mjs)), with each address's bank taken from what the function finder knows, the Super Nintendo's 65816 and its sound processor's SPC700, through two more ([`tools/snes/65816.mjs`](../tools/snes/65816.mjs), [`tools/snes/spc700.mjs`](../tools/snes/spc700.mjs)), with each instruction's length taken from the mode the finder knows, and the PlayStation's, through another, which reads the Nintendo 64's VR4300 and RSP too ([`tools/lib/mips.mjs`](../tools/lib/mips.mjs)) ([Reading the original's instructions](../tools/README.md#on-the-nes)). On another console a disassembler on the person's own computer does that job. What it prints stays there, by the same rules as `read`. `prove --state` compares what the console holds through the kit's video, so on another console it says that it can't, and the picture and sound are still compared.

**NES addresses.** An NES game's program is in banks of 16 KB. On the cartridges the tools read, NROM, MMC1, UNROM and CNROM, the last bank is always at $C000-$FFFF, and the cartridge switches any of the others in at $8000-$BFFF, so an address there means nothing until the bank is known. The code map numbers each function by its offset in the program, past the file's 16-byte header: bank n's $8000 is n × 0x4000, so $923F in bank 4 is `0001123F`, and $C39C in the last of Mega Man's 8 banks is `0001C39C`. A game's code names a function as a label with its bank: `sub_04_923F` is $923F with bank 4 switched in, the bank in two hexadecimal digits, and `sub_C39C`, with no bank, is in the last one. A program of 32 KB or less never switches, so a label there needs no bank anywhere. The port map works out how many banks there are from the code map, as the last always has code. A list for `codemap --from` gives each address as an offset in the program or as such a label.

[`tools/nes/functions.mjs`](../tools/nes/functions.mjs) finds the functions by following the code from the three vectors at the end of the last bank, through every call, branch and jump. Code in a switched bank sees itself at $8000. Code in the last bank sees what its caller left there, or what it switched in itself, by writing a number it loaded to the cartridge or by calling a routine that writes the number it's given. An address at $8000 reached with no bank known is taken in the one bank where it reads as code, if that bank has code already. It also follows the three ways NES games jump through a table: a list of addresses after a JSR to a routine that pulls its own return address off the stack and reads the list, two tables of low and high bytes pushed before an RTS, and a pointer built from a table for JMP ($xx). Since #1170 it follows three more, which Ghosts'n Goblins uses: a task's start copied from a table into the task's own stack, in the stack page, for an RTS much later; a pointer built in one routine and jumped through in another, a JMP ($xx) alone that the first one calls; and a table read through a pointer the code makes from its own numbers. Last, it takes what reads as code between the functions of a bank that has some. On Mega Man (USA) it finds 530 functions in 30,744 bytes, in banks 4 to 7, where a plain walk from the vectors found about 15 KB, and on Ghosts'n Goblins (USA) 378 functions in 26,888 bytes. Nothing has checked it against a disassembly of the game, so it can still miss code only a table it doesn't follow leads to.

**Game Boy addresses.** A Game Boy or Game Boy Color game's program is in banks of 16 KB too. The first is always at $0000-$3FFF, and the cartridge's chip switches any of the others in at $4000-$7FFF. The code map numbers each function by its place in the program, the whole file: bank n's $4000 is n × 0x4000, so $4123 in bank 2 is `00008123`. A game's code names a function as a label with its bank: `sub_02_4123` is $4123 with bank 2 switched in, the bank in two hexadecimal digits, or three in a program of more than 256 banks, and `sub_0150`, with no bank, is in the first one.

[`tools/gbc/functions.mjs`](../tools/gbc/functions.mjs) finds the functions by following the code from where the console starts a game, $0100, and from each of the interrupts' five places that holds code, through every call, jump and RST. Code in a switched bank sees itself at $4000. Code in the first bank sees what its caller left there, or what it switched in itself, by writing a number it loaded to the cartridge's chip, on a cartridge with an MBC1, an MBC3 or an MBC5, or by calling a routine that writes the number it's given. An address at $4000 reached with no bank known is taken in the one bank where it reads as code, if that bank has code already. It follows two ways the console's games jump through a table: a table of addresses a register pair was loaded with before a `JP (HL)`, and a list of addresses after a call or an RST to a routine that pops its own return address and jumps through what it reads there. Code a game copies into its memory and runs there, as the routine that waits for the sprites' copy is, has no place of its own in the program and isn't found, and nothing is taken for code only because it reads as code: `codemap --from` takes the rest from a list. The processor's instructions are in a table of the tools' own, [`tools/gbc/sm83.mjs`](../tools/gbc/sm83.mjs).

**A Game Boy game's proof.** A Game Boy or Game Boy Color game's functions are proven by the same memory, `twin` on the Game Boy ([#1948](https://github.com/NahuelGenchi/dreamports/issues/1948)), which calls the twin and the original from the same memory and registers in Gambatte's own processor, built from its makers' source, with each twin's registers and flags said by a contract line beside it, as on the NES ([The function check on the Game Boy](../tools/README.md#the-function-check-on-the-game-boy)). No compiler gives their bytes back, so `match` has nothing to say there. A version's proofs are kept, and a twin is proven only when its calls took every instruction of the original's function and both ways of each jump with a condition. A call can't start from a memory of play yet.

**A PlayStation game's proof.** Since [#1558](https://github.com/NahuelGenchi/dreamports/issues/1558) a PlayStation game can have both proofs of a function and the proof of its frames. A function is proven by the same memory, `twin` on the PlayStation, which calls the twin and the original from the same memory in PCSX ReARMed's own interpreter, and by the same bytes, `match` on the PlayStation, which builds the twin with GCC 2.7.2 and Sony's assembler's ways (maspsx's rules) and compares it with the program the disc boots, a switch's table and texts included ([The PlayStation's compiler](../tools/README.md#the-playstations-compiler)). A twin keeps every value at the console's address, `0x80000000` and up, which a pass over the built module folds to its low 26 bits ([The function check on the PlayStation](../tools/README.md#the-function-check-on-the-playstation)). Its frames are proven by `prove`, picture and sound, on [the PlayStation's kit in C](../kit/ps1/c/README.md), as far as the kit goes: everything the GPU draws, polygons, lines, rectangles and textures with their shading, dithering and mixing, as psx_gpu, the emulator's own GPU, draws them, the sound chip, mixed by dfsound, the emulator's own, a digital pad read through its serial port, and the console's clock with its root counters and interrupts, with the CD drive still to come. Each of these has been run on programs of the project's own and on no real game yet, and Sony's PsyQ libraries are named in `kit/ps1/c/lib/` without a twin of any of their functions.

**A Nintendo 64 game's proof.** Since [#1644](https://github.com/NahuelGenchi/dreamports/issues/1644) a function of a game built with IDO, Silicon Graphics' compiler, which most of the console's games were, Nintendo's own among them, can be proven both ways. By the same bytes, `match` on the Nintendo 64, which builds the twin with IDO 5.3 or 7.1, translated into C from IDO's own programs and built on the contributor's computer, and compares it with the code the cartridge starts, its values included ([The Nintendo 64's compiler](../tools/README.md#the-nintendo-64s-compiler)). And by the same memory, `twin` on the Nintendo 64, which calls the twin and the original from the same memory in Parallel N64's own processor, on the cached interpreter `prove` runs the game on. A twin keeps every value at the console's address, `0x80000000` and up, and the hardware's at `0xA4000000` and up, which a pass over the built module folds to its low 27 bits, and it reads and writes each number as the console keeps it, highest byte first, which the same pass does by turning round the bytes of every number outside the module's own values; a float or a double too small for an ordinary number becomes zero, as the console's floating-point unit makes it with the FS bit games set ([The function check on the Nintendo 64](../tools/README.md#the-function-check-on-the-nintendo-64)). Since [#1929](https://github.com/NahuelGenchi/dreamports/issues/1929) a version made a function at a time keeps each proof in its `proofs.json`, as on the other consoles whose functions the tools prove, and the function check runs on Linux, a Mac and Windows; `match` runs where IDO is built, on Linux and a Mac. Since [#1932](https://github.com/NahuelGenchi/dreamports/issues/1932) the tools change Parallel N64's source before building it ([`tools/libretro/parallel-n64.patch`](../tools/libretro/parallel-n64.patch)), so its cached interpreter tells them where the processor is before each instruction: that says which functions ran in each frame, which is what a part's functions are read from, and no more, so gameplay proven by instructions and branches isn't there on this console yet. The same change clears a flag Parallel N64 left set after its first frame when built with no dynarec for Windows or for arm64, which kept it from ever ending a second frame there. A game built with GCC, as KMC shipped it, or with SN Systems' compiler, has the same memory for each function and not yet the same bytes. Its frames are proven by `prove`, picture and sound, on [the Nintendo 64's kit in C](../kit/n64/c/README.md), as far as the kit goes: its RSP runs any microcode, as cxd4 does, its RDP fills rectangles and its video interface shows 16-bit and 32-bit pictures as angrylion's do, with triangles, textures, the video interface's anti-aliasing, sound, the controllers and the save chips still to come. Code a game copies from its cartridge as it runs isn't in the code map yet, and each of these has been run on programs of the project's own and on no real game yet.

**A PlayStation 2 game's functions.** Its EE functions can be proven by the same memory, `twin` on the PlayStation 2, since [#1591](https://github.com/NahuelGenchi/dreamports/issues/1591), against Play!'s own processor code, the code `prove` runs the game on. A twin keeps every value at the console's address, `0x00100000` and up, the scratchpad at `0x70000000` and the hardware at `0x10000000` and `0x12000000`, which a pass over the built module folds by each address's top byte ([The function check on the PlayStation 2](../tools/README.md#the-function-check-on-the-playstation-2)). Since [#1628](https://github.com/NahuelGenchi/dreamports/issues/1628) a twin can also name a function by its code map's key, as `0x00000120@SOUND.IRX`: a function of one of the game's own modules for the IOP, which the check loads as the console's loader does and calls as the IOP's compiler does, or of another EE program on the disc. And a function that works on vector unit 0 in macro mode is compared with the unit's registers and flags. A vector unit's microprogram is written again in C too, on the kit's unit (`vu_program`, `vu_sum`, `vu1_kick`), named by its key with `~vu`, and compared with the original's run in Play!'s vector unit: every register and flag, the unit's data memory, each packet it sends the GS, and where it stops.

**A Super Nintendo game's proof.** A Super Nintendo game's functions can be proven by the same memory, and not by the same bytes. By the same memory: `twin` on the Super Nintendo, since [#1641](https://github.com/NahuelGenchi/dreamports/issues/1641), calls the twin and the original from the same memory, the original in Snes9x's own 65816, the processor `prove` runs the game on. Its functions take their values in the processor's registers and flags, so a twin has a contract beside it, a `dp:twin` line as an NES twin has, which says what it's given, the mode it starts and ends in, and what it gives back. A twin keeps every value at the console's own 24-bit address, and a pass over the built module folds the banks that show the same memory onto one ([The function check on the Super Nintendo](../tools/README.md#the-function-check-on-the-super-nintendo)). It reads and writes the hardware through [the Super Nintendo's kit in C](../kit/snes/c/README.md), which notes each read and write for the check. Since [#1908](https://github.com/NahuelGenchi/dreamports/issues/1908) a version made a function at a time keeps each proof in its `proofs.json`, as on the other consoles whose functions the tools prove, and the check runs on Linux, a Mac and Windows.

Not by the same bytes: `match` has no compiler for the Super Nintendo, and says so. Its games were written by hand in the 65816's own language, so their bytes were never a compiler's to give back, and an assembler given a twin's instructions would only copy the original, which proves nothing of the C. A few are said to have been written in C, Sutte Hakkun with the Zardoz compiler, which Western Design Center keeps today as WDC816CC, and others are guessed at from how their code reads, but none of it is known for sure, no game is known to have kept the compiler's version and settings it was built with, and the compilers of the time, Zardoz's, ORCA/C for the Apple IIGS and a port of lcc, aren't ones the tools can fetch and build on a contributor's computer. So a Super Nintendo game's function is proven by the same memory, over every path of the original's, and its frames by `prove`, picture and sound, on the kit, as far as the kit goes.

**PlayStation code.** [`tools/ps1/functions.mjs`](../tools/ps1/functions.mjs) reads the program a disc boots, as the `BOOT` line of its SYSTEM.CNF names it, in the disc's top folder or in one of its folders, or `PSX.EXE` when it has none, or a program given alone, and maps it at the address its PS-X EXE header says it's loaded at. Such a program keeps its code and its values together with nothing to tell them apart, so its functions are found by reading it: its start, every call's target, every opening of a stack right after a return, and every word of the program that holds the address of an opening, as a table of functions does. A function ends at its last return or jump away that none of its own branches goes past, so a switch's cases, reached through a table, stay its own, and so does a jump to a fixed address, as a call to the BIOS is made. What's left between two functions is a function too when every word of it is an instruction and it ends as one does, which finds a function nothing calls, and leaves out the program's values. On the made-up program of the tools' tests it finds every function with its size ([`test/ps1-functions.test.mjs`](../tools/test/ps1-functions.test.mjs)). A game's code that a list or nothing reaches this way, a function reached only through a pointer with no opening of its own, and code a game loads from its disc as it runs, which [#1451](https://github.com/NahuelGenchi/dreamports/issues/1451) met in Mega Man 8, aren't mapped yet.

**Super Nintendo code.** [`tools/snes/functions.mjs`](../tools/snes/functions.mjs) reads a plain cartridge, LoROM, HiROM or ExHiROM, and numbers each function by its offset in the ROM, past a copier's header, so the banks that show the same ROM twice name it once; a game's code names one by the address it runs at, as `sub_808123`, in any bank that shows that ROM. How long one of the 65816's instructions is depends on two of its flags, M and X, which make A and X 8 bits or 16, and which the program changes as it goes, so reading can't tell where one ends from its bytes alone. The finder follows the code from the console's vectors, the reset in the 6502's mode and each interrupt's handler with its flags not known until its own REP or SEP, with the flags carried along through every instruction, branch, jump and call, and through a table of addresses a JSR or a JMP goes through, read until it runs into code or into something another instruction names. A function starts where something calls it, in its caller's mode, and the code map keeps that mode beside it, as `"modes"`. Where the flags can't be known by reading, after PLP or an XCE with its carry not known, the path stops, and where two callers give one function two modes, the finder says so. What reading can't reach, it learns from play: with [`libretro/snes9x.patch`](../tools/libretro/snes9x.patch), Snes9x tells the tools of every instruction it runs and the mode it ran in, and each place a call, a jump through a pointer or a return sent the processor to, so `codemap --fill` follows the code again from there, as it ran ([#1641](https://github.com/NahuelGenchi/dreamports/issues/1641)). A map made this way holds what was played, and grows with the recordings. On Yoshi's Cookie (USA) reading alone finds 48 functions in 3,794 bytes, as [#1451](https://github.com/NahuelGenchi/dreamports/issues/1451)'s trial found 44 in 3,540, and on Mega Man Soccer (USA) 541 in 53,838 bytes. A cartridge with a chip of its own beside the ROM, such as the Super FX or the SA-1, isn't read yet.

**Nintendo 64 code.** [`tools/n64/functions.mjs`](../tools/n64/functions.mjs) reads a cartridge in any of the three byte orders copies come in, turned to the console's own, and maps the code it starts: the megabyte after its boot code, which the boot code copies to the address the header names, or 1 MB or 2 MB lower for the kinds of cartridge whose boot code does that. The tools take, of those three, the place where most of the code's calls land on a function's opening, as a call names its target's address. It's found by reading, as the PlayStation's is, through the same finder ([`tools/lib/mips-functions.mjs`](../tools/lib/mips-functions.mjs)) with the VR4300's instructions: its likely branches stay a function's own, an `eret` ends one, and a word that sets a field its instruction keeps zero isn't one, as GNU's and LLVM's tools read it, so a value such as a float isn't read as code. Run on the owner's copies for counts, nothing of them kept: Super Mario 64 (USA) has 4,194 functions in its first megabyte, 3,148 of them opening a stack, against the 3,046 [#1451](https://github.com/NahuelGenchi/dreamports/issues/1451)'s trial found; Diddy Kong Racing and Super Smash Bros. run a megabyte lower than their headers say, and Yoshi's Story two, and the finder places them so. Ocarina of Time, Majora's Mask and Perfect Dark start with a small program that copies or unpacks the rest, so their first megabyte has 199, 539 and 115 functions. Mario Tennis's boot code puts its code somewhere else again, where at none of the three places do a tenth of its calls land on an opening, and the finder says it can't tell rather than map it in the wrong place: such a game's map comes from a list. Code a game copies from the rest of its cartridge as it runs, and code it runs through the TLB, as GoldenEye 007 does, aren't mapped yet.

**Nintendo DS code.** [`tools/nds/functions.mjs`](../tools/nds/functions.mjs) reads a cartridge a piece at a time, as one can be half a gigabyte, and maps each of its programs on its own: the ARM9's, which is most of a game, the ARM7's, and the overlays, the code a game loads as it plays, each a file of the cartridge with a place in memory of its own. Two overlays can have the same place, as only one is there at a time, so a function's key says which program it's in: `02380000@ARM7`, `02100000@OVERLAY9_0003` for the ARM9's overlay 3, and a plain address for the ARM9's own program. The console's makers' tools pack the ARM9's program and its overlays from the end backwards, which the finder unpacks, and the ARM9's program holds the code it copies elsewhere as it starts, such as into its fast memory at `0x01FF8000`, which the finder places where it runs. The code is followed from where each program starts, and from the functions an overlay runs as it's loaded, through every call and branch, in ARM code and in Thumb code: a call says which kind it calls, and an address the code loads says it by its lowest bit. A switch's branches and its table of addresses stay their function's own. Then what opens as a function does, saving its return address, between the functions it has, is one too, which is how most of an overlay's functions are found, as nothing says where they start. The code map keeps which functions are Thumb code, as `"modes"`. On the made-up cartridge of the tools' tests it finds every function with its size ([`test/nds-functions.test.mjs`](../tools/test/nds-functions.test.mjs)). It hasn't been run on a real game, and it can miss a function nothing calls that opens another way, can't tell which overlay a call into an overlay's place means, and doesn't read code a game unpacks from its own files as it plays.

**PlayStation 2 code.** [`tools/ps2/functions.mjs`](../tools/ps2/functions.mjs) reads the program a disc boots, as its SYSTEM.CNF names it, off the player's copy, so a disc of gigabytes is never read whole, and maps it at the addresses where it runs, which a list from Ghidra has too. A program that kept its symbol table says where each of its functions starts and how long it is, and the map takes those addresses and sizes, never the names, which are the game's own words. The rest, or all of a program without symbols, is found by reading it: its start, every call's target, and every function's opening right after the end of the one before. On The Sims (USA), whose program kept its symbols, the map has 11,254 functions in 2,430,360 of its 2,464,156 bytes of code. With its symbols hidden, reading alone found 8,861 starts, every one of them a function's start in the symbols.

**PlayStation Portable code.** [`tools/psp/functions.mjs`](../tools/psp/functions.mjs) reads the program a disc boots, `PSP_GAME/SYSDIR/EBOOT.BIN`, or the plain `BOOT.BIN` some discs keep beside an encrypted one, off the player's copy, or the program in a PBP, the file a download comes as, or a program given alone. A program built to run at fixed addresses is mapped where it says. Most games' are relocatable, a PRX, with a list of every place in it that holds an address: the tools put it where their emulator puts a game's first program, 0x08804000, and put each of those places right as the emulator does, which was checked by reading the emulator's memory back, word for word, for a made-up program of each kind ([#1947](https://github.com/NahuelGenchi/dreamports/issues/1947)). The functions are found by reading it, as every MIPS console's program is, with the Allegrex's own instructions (`tools/lib/allegrex.mjs`), from its start, what it exports to the system, every call's target, every opening after the end of the one before, and every word that holds the address of one, within the sections the file says are code. A file that names no sections has its code end where what it keeps for the system starts, and values right after its code that read as instructions are then mapped as a function. The two instructions the program leaves for each of the system's functions it calls, which the system writes its call into, are kept out: they're not the game's code. A program a publisher encrypted, which starts with `~PSP`, can't be mapped yet, and the tools say so.

In JavaScript there's no kit of its own for another console yet. A game starts on what's general in `kit/gba/`, its start screen, input, clock, settings and touch screen, as `npm run dp -- new` writes it, drawing its own picture at the game's size, which `createGame` can change by giving `size`, and giving `proof?.listen` how long its frame lasts. What a second game on a console turns out to share becomes that console's kit, `kit/<console>/`. A game in C on another console starts on what every console's kit in C shares, [`kit/c/`](../kit/c/README.md), the same way: `npm run dp -- new <game>/c` writes it, drawing its own picture at the game's size and making its own sound at the console's rate, with the console's buttons as bits in `console.h`, which the build writes from `kit/consoles.js`. On the NES it starts on the NES's kit in C, [`kit/nes/c/`](../kit/nes/c/README.md), the console's picture and sound hardware, and draws and plays by writing that hardware as its original does. On the Game Boy and the Game Boy Color it starts on [`kit/gbc/c/`](../kit/gbc/c/README.md), one kit for both, and reads and writes the console's memory as its original does, at the cycle its original does. On the Super Nintendo it starts on [`kit/snes/c/`](../kit/snes/c/README.md), and draws by writing the picture's registers as its original does. On the PlayStation it starts on [`kit/ps1/c/`](../kit/ps1/c/README.md), and draws by writing the GPU's two ports as its original does. On the PlayStation 2 it starts on [`kit/ps2/c/`](../kit/ps2/c/README.md), and draws by writing the GS as its original does. On the Nintendo DS it starts on [`kit/nds/c/`](../kit/nds/c/README.md), with its two processors' programs side by side, each writing the hardware as its original does. On the Nintendo 64 it starts on [`kit/n64/c/`](../kit/n64/c/README.md), and reads and writes the console at its original's addresses, the RSP running the microcode it gives it. A disc, which can be larger than a browser can hold in memory, is read a few sectors at a time as the game asks for them, from the file the player chose, an ISO, a BIN and its `.cue`, a CHD or a CSO: a game in C through [`kit/c/disc.h`](../kit/c/README.md#the-players-disc), as the console's drive gives them, and one in JavaScript through [`kit/copy/`](../kit/copy/README.md).

## Adding a console

Add it to `kit/consoles.js` and to `CORES` in `tools/consoles.mjs`, with a core whose source is at a fixed commit and whose license lets anyone build it, the settings that make it the same on every computer, and what tells a copy of its games in `tools/lib/read-copy.mjs`. Then make a game's first recording and run `prove`, which checks the numbers.
