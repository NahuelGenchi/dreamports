# History

Every decision that shaped how Dreamports works, one line each, by the issue that made it, in the order they were added here. Agents read `AGENTS.md` on every request, so what only matters when changing that part of the project lives here: search this file for a word before changing how something behaves, rather than reading all of it, and add a line here when a change should outlast its pull request.

Dreamports is the source code for dreamports.net, a home for enhanced fan ports of classic games. A Dreamport is "the port fans always dreamed of: the game you remember, with the extras you wished it had"; use that wording rather than "dream means fan". The site lists the owner's own Dreamports (for example Sonic Advance Dreamport). Every Dreamport keeps the rules in `docs/STANDARD.md`, whoever makes it (#73).

- Since #74 the games made here live in `games/`, one folder each, and play at `/play/<game>/` (`games/README.md`); since #75 that includes Sonic Advance Dreamport, in `games/sonic-advance/` with its history.
- Since #76 what every game on one console shares lives in that console's kit, `kit/<console>/`, served at `/kit/<console>/`; the first is the Game Boy Advance kit, `kit/gba/` (`kit/gba/README.md`), taken out of Sonic Advance Dreamport.
- Since #77 the proof tools in `tools/`, started with `npm run dp -- <tool>`, play the same recorded button presses in the original game and in a Dreamport on the contributor's computer, compare every frame and measure the game's % (`tools/README.md`); what they keep in the repository is JSON in each game's `proof/` folder, and everything taken from the game stays in the ignored `.dreamports/`.
- Since #78, `npm run dp -- share` publishes a contributor's preview on GitHub Pages from their own fork, never on dreamports.net (`docs/PREVIEWS.md`).

- Since #80, a New Dreamport issue claims a whole game for its lead and a Task issue is one piece of it, which one person claims at a time with a `/claim` comment. The claims workflow answers both, gives each game a label and a milestone, and releases a claim after 14 days without activity, and `npm run dp -- find` and `npm run dp -- team` show where a game stands and gather the team's pieces in the lead's team build (`docs/TEAMS.md`).
- Since #140, each game's New Dreamport issue is its game's issue, which its entry names as `issue`, and the claims workflow puts every new Task issue under it as a sub-issue, so it lists every piece of the game, and `find` and `team` read the pieces from there.
- Since #124 every Dreamport has a progress map, a picture of both numbers drawn from its `proof/` folder by `src/lib/progress-map.mjs` with the same code as the numbers: a rectangle for each function of the original, green once it counts toward code ported, and a block for each part, green once it's proven.
- Since #126 it's only on GitHub, never on the site, where it could puzzle players: the proof tools keep it in `.github/readme/progress/<game>.svg` and write it with the README's table, which links it. The whole game is mapped first: a Dreamport's code map comes before any of its code, and the build, `npm run check` and the proof tools stop without one (`docs/STANDARD.md#how-progress-is-measured`).

- Since #134, `npm run dp -- read <game> <function>` prints one of the original's functions, its ARM or Thumb instructions, from the contributor's copy with mGBA's own decoder, for code a decompilation has no C for; since #169 it follows the code from the whole code map, so that data and ARM inside Thumb show as they are, and says when a label may be the wrong function.
