# Agent instructions

## The project

Dreamports is the source code for dreamports.net, a home for enhanced fan ports of classic games. A Dreamport is "the port fans always dreamed of: the game you remember, with the extras you wished it had"; use that wording rather than "dream means fan". The site lists the owner's own Dreamports (for example Sonic Advance Dreamport), external ports made by other people (links and credits only), and other fan games that aren't ports (for example Kirby's Dead Land). Every Dreamport keeps the rules in `docs/STANDARD.md`, whoever makes it (#73). Since #74 the games made here live in `games/`, one folder each, and play at `/play/<game>/` (`games/README.md`); since #75 that includes Sonic Advance Dreamport, in `games/sonic-advance/` with its history. Since #76 what every game on one console shares lives in that console's kit, `kit/<console>/`, served at `/kit/<console>/`; the first is the Game Boy Advance kit, `kit/gba/` (`kit/gba/README.md`), taken out of Sonic Advance Dreamport. Since #77 the proof tools in `tools/`, started with `npm run dp -- <tool>`, play the same recorded button presses in the original game and in a Dreamport on the contributor's computer, compare every frame and measure the game's % (`tools/README.md`); what they keep in the repository is JSON in each game's `proof/` folder, and everything taken from the game stays in the ignored `.dreamports/`. Since #78, `npm run dp -- share` publishes a contributor's preview on GitHub Pages from their own fork, never on dreamports.net, and posts in the game's progress thread in the repository's Discussions (`docs/PREVIEWS.md`). Since #79 every Dreamport has one entry, `games/<game>/entry.md`, which makes its page on the site, and the launcher, its page and the README's table of Dreamports show its two numbers from its `proof/` folder, never typed by hand: code ported, from the port map of the original's functions its code names and the code that ran in matching play, and gameplay proven, the share of the game's parts a recording plays through with every frame matching (`docs/STANDARD.md#how-progress-is-measured`, `games/README.md#the-entry`). Since #80, a New Dreamport issue claims a whole game for its lead and a Task issue is one piece of it, which one person claims at a time with a `/claim` comment. The claims workflow answers both, gives each game a label and a milestone, and releases a claim after 14 days without activity, and `npm run dp -- find` and `npm run dp -- team` show where a game stands and gather the team's pieces in the lead's team build (`docs/TEAMS.md`). Since #140, each game's New Dreamport issue is its game's issue, which its entry names as `issue`, and the claims workflow puts every new Task issue under it as a sub-issue, so it lists every piece of the game, and `find` and `team` read the pieces from there. Since #124 every Dreamport has a progress map, a picture of both numbers drawn from its `proof/` folder by `src/lib/progress-map.mjs` with the same code as the numbers: a rectangle for each function of the original, green once it counts toward code ported, and a block for each part, green once it's proven. Since #126 it's only on GitHub, never on the site, where it could puzzle players: the proof tools keep it in `.github/readme/progress/<game>.svg` and write it with the README's table, which links it, and `share` adds a copy to each progress post. The whole game is mapped first: a Dreamport's code map comes before any of its code, and the build, `npm run check` and the proof tools stop without one (`docs/STANDARD.md#how-progress-is-measured`). Since #82 the About page has a section for rights holders, `docs/RIGHTS.md` says how a notice is handled, and clips that show the original game may appear in pull requests and progress posts, and nowhere else. Since #81, seven `/dreamport` commands guide a newcomer's coding agent through making a Dreamport, as the README's Make a Dreamport section teaches; each is written once in `tools/commands/` and copied by `npm run dp -- commands` into the form each agent reads, and `dreamports.net/code` redirects to this repository (`public/_redirects`). Since #141 one sentence pasted into any coding agent, such as `Set up https://dreamports.net/code and help me make Sonic Battle Dreamport.`, gets the person's Dreamports folder, the tools and, after their yes, their fork ready, then starts `/dreamport <game>`, which only reads and explains; the README's Make a Dreamport section starts from it. Since #129 the Dreamports bot moderates what people write on GitHub on its own, by the team's decision that people never moderate here: the moderation workflow applies plain rules first, asks OpenCode's free model, in a step with no token, only about what they leave, carries out a fixed plan for each verdict, and keeps a log in an issue (`docs/MODERATION.md`). The site is a static Astro site (#3); hosting it on Cloudflare is #4. Since #68 a small Worker adds players' profiles, signed in with Google, Discord, Steam or GitHub, and keeps the achievements games send through `/dreamports.js` (`docs/ACCOUNTS.md`). Since #23 the whole site is one screen that works like a game launcher: every page shows the menu, with that page's card open. Since #59 a card takes the menu's place as a full screen instead of opening over it.

Never describe something as working or complete unless a recorded check establishes it. A build is not a browser check.

Commands: `npm run dev`, `npm run check` (the site, the Worker, the port maps, the README's table of Dreamports and the moderation bot's tests), `npm run build`, `npm run preview`, `npm run worker` (the built site with the Worker and a local database, at `http://localhost:8787`), and `npm run dp -- <tool>` (the proof tools: `setup`, `rom`, `play`, `prove`, `codemap`, `portmap`, `share`, `find`, `team`, `readme`, which writes the README's table of Dreamports, and `commands`, which writes the `/dreamport` commands' copies). `npm run check` also checks that those copies match `tools/commands/`. Site text uses normal capitals: sentences and labels start with one, and names keep theirs (games, platforms, people, Dreamports); key hints are written as on a keyboard (`Esc`, `Enter`). Play and download links live only in a game's `ownCopy.links`, behind the own-copy tick on the game's page.

## Working well here

- Start from the active issue, then read only the files involved.
- Keep the README and site text plain enough for someone who has never used GitHub.
- The site never hosts ROMs, game files or extracted game assets, and only links to projects that require players to bring their own legal copy.
- Pictures of games on the site come only from the owner's own recordings, where the owner decides. The one exception is clips that show the original game, made by `npm run dp -- prove` to show a match: they may appear in pull requests and progress posts, and nowhere else, never on the site, in a game's files or in a commit (`docs/STANDARD.md#clips`). Never use publishers' logos, box art or characters in the site's own design.

## Working on a Dreamport

This part is for an agent helping someone make a Dreamport, or a piece of one, usually through the `/dreamport` commands. `docs/STANDARD.md` holds the rules every Dreamport keeps, `docs/TEAMS.md` how claims and team builds work, and `tools/README.md` the tools.

**Who you're helping.** Often someone who has never written code and talks to you in their own words. Do the technical work yourself, explain it plainly, one step at a time, and ask only what they have to decide.

**The commands.** `/dreamport <game>`, `/dreamport-claim <task>`, `/dreamport-clip`, `/dreamport-play`, `/dreamport-fix <what feels wrong>`, `/dreamport-share` and `/dreamport-send` (`$` instead of `/` in Codex). Each does one thing, and only when the person types it, except `/dreamport`, which the sentence in Getting ready starts too, since it only reads and explains. When they type one you haven't loaded as a command, as in a session opened outside this folder, read its file in `tools/commands/` and follow it. Between them, do what they ask in their own words, but never claim, share or send because of plain words: if they say "send it" or "post it", say which command does that and wait for them to type it. To change a command, change its file in `tools/commands/` and run `npm run dp -- commands`.

**Before anything leaves this computer.** An issue, a comment, a fork, a push, a preview, a post or a pull request is public and in the person's name. Say exactly what it is and where it goes, and wait for their yes. The tools ask too: run `share` and `team` without `--yes` first, and add `--yes` only after that yes, for that one action. Installing a program waits for a yes as well. The person signs in to GitHub themselves, with `gh auth login` on GitHub's own page: never ask for, read or type a password or token.

**Their copy of the game.** It stays on their computer: `npm run dp -- rom` finds and checks it, and nothing from it, no file, picture, sound, text or table, goes in a commit or an issue. The one exception is the clips `prove` makes, which may go in a pull request or a progress post. Never help anyone get a copy other than from their own cartridge or disc, and never break a lock.

**Getting ready.** Most people start by pasting one sentence into an agent opened in an empty folder: `Set up https://dreamports.net/code and help me make <game> Dreamport.`, or `Set up https://dreamports.net/code and help me start a Dreamport.` for a game they haven't named yet. If you aren't in a Dreamports folder already, and the folder you were opened in has none, clone `https://github.com/NahuelGenchi/dreamports.git` into a folder called `dreamports` there, read its `AGENTS.md`, and work in it from then on. A Dreamports folder made earlier is brought up to date with `git pull` when it's on `main` with nothing changed. Then follow `/dreamport` from its file, `tools/commands/dreamport.md`: it checks what the tools need, which `tools/README.md` lists, offers the person's fork and makes it only after their yes, says where the game stands, and tells them how to open their agent in the folder next time. A folder cloned from `https://dreamports.net/code` keeps that address as `origin`: point it at `https://github.com/NahuelGenchi/dreamports.git`, since the tools and the GitHub CLI only know GitHub's. Previews and pieces go through the person's own fork, which `gh repo fork --remote` makes after their yes, renaming this repository's remote to `upstream`.

**Building.** The whole game is mapped first, before any of its code: its `proof/original.json` and its code map, with `npm run dp -- codemap`, so its progress map shows all of it (`docs/STANDARD.md#how-progress-is-measured`). A game is made on its console's kit (`kit/gba/README.md` for the Game Boy Advance), in `games/<game>/`, with its entry (`games/README.md`). Start where a player starts, keep it playable after every step, and follow the order a player meets things. Rewrite the original's logic as readable JavaScript from how the original does it, through its decompilation, disassembly or code map, never by guessing numbers, and name the original's function in a comment wherever code rewrites one, so the port map counts it. Code whose license allows it can come in, with its notice and its authors' names; code with no license is only read. The entry lists every source with its license.

**Proving.** Every step gets a recording and `npm run dp -- prove`, and `portmap` runs after the code changes. Never type a number, and never say something matches the original unless `prove` found every frame the same. A step that makes anything that matched before differ isn't done.

**Its issue and branch.** The claim's issue, New Dreamport or Task, is the work item, and the claims workflow gives it a milestone. Its branch is `feat/<issue>-<slug>`, from the team build (`npm run dp -- team <game> join`) when the game has one, or else from the latest `main`. A pull request to this repository fills in `.github/pull_request_template.md`, with its part for a Dreamport.

## Private data

ROMs, game files, saves, extracted assets, private email addresses, Cloudflare account IDs, tokens and other credentials stay out of commits, issues and PRs.

## Tracking and delivery

Every change (code, bug fixes, enhancements, docs, research and repository operations) belongs to an issue with a milestone in `NahuelGenchi/dreamports`, reused or created before editing. Every work item gets its own new branch created from the latest `origin/main`: `<type>/<issue>-<slug>` (`feat`, `fix`, `enh`, `docs`, `research`, `ops`). Never reuse a branch for a second item, never mix two issues on one branch, and never push to `main`. Use `type: summary (#N)` commits. Delete the branch after its PR merges. PRs follow `.github/pull_request_template.md`: a standalone `Closes #N` line, the issue's milestone, and `Refs #N` for unfinished parent work. Decisions, exact changed paths and blockers go in the issue or PR. See `CONTRIBUTING.md` and `docs/TRACKING.md`.

## Final report

Report the issue, the PR and what changed. Keep these separate: site builds and browser checks (exact commands, pages, widths and outcomes, or "none run"), and source/diff review scope.
