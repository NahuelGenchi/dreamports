# PlayStation Portable kit in C

[Back to the kits in C](../../c/README.md) · [Other consoles](../../../docs/CONSOLES.md) · [The Dreamport standard](../../../docs/STANDARD.md) · [Written in: #1926](https://github.com/NahuelGenchi/dreamports/issues/1926)

This folder is the PlayStation Portable's kit for games written in C, on what [every console's kit in C](../../c/README.md) shares. A game keeps the console's memory at the console's own addresses, runs in the console's threads and time, and asks the system for what its original asks, by the same names. The kit answers as the console's emulator in the proof tools does, PPSSPP ([Other consoles](../../../docs/CONSOLES.md#the-playstation-portable)), down to the cycle a thread is woken on.

Like the rest of the kits it's under [GPL-3.0-or-later](../LICENSE), and nothing from any game is in it. It's written from how the console is documented to behave and from how PPSSPP, under the GPL too, answers a program.

## What's in it

| File | What it does |
| :--- | :--- |
| `psp.h` | What a game sees of the console: its memory by address, its time, and the system's functions by their names, for threads, the screen, the buttons and the sound channels |
| `memory.c` | The scratchpad, the video memory and the main memory, each where the processor sees it |
| `kernel.c` | The console's time, what's due at a time, and its threads: made, started, put to wait and woken in the order the system keeps them |
| `display.c` | The screen: its frames and V-blanks, the framebuffer a game names in each of the four pixel formats, and the waits for a V-blank |
| `ctrl.c` | The buttons and the stick, sampled as each V-blank ends into a ring of 64 samples a game peeks at or reads |
| `audio.c` | The eight sound channels, mixed 64 samples at a time, and each frame's sound list |
| `sync.c` | Semaphores and event flags: made, signalled or set, waited for with their timeouts, polled, looked at and deleted |
| `mutex.c` | Mutexes and lightweight mutexes, locked, tried and let go with their timeouts, and callbacks, made and registered as the exit callback |
| `vfpu.c` | The vector unit: every instruction of the emulator's interpreter, ported to C, with the emulator's own tables for its sine, cosine, roots, powers and logarithms in `vfpu/` |
| `ge.c` | The graphics chip: the display lists a game hands it, run a command at a time with the time the chip takes, each frame's draw list, and the rectangles it draws |
| `psp.c` | What the page calls to start the game, run its frames, draw them and hear them |
| `psp-kit.h` | What those files share, which a game doesn't need |

## Writing a game on it

A game includes `"psp.h"` and defines the four functions every game in C does ([A game on a console with no kit of its own](../../c/README.md#a-game-on-a-console-with-no-kit-of-its-own)). `npm run dp -- new <game>/c` writes a starting point that paints the screen blue, and green while a button is held.

**`game_start` is the program's first thread.** It runs as the original's does from its start, asks the system for what the original asks, waits where the original waits, and needn't come back. A frame of the page is a frame of the console, from one V-blank's start to the next, in which whichever of the game's threads has its turn runs. `game_step` isn't called on this console. `game_draw` calls `psp_show()`. So a game on this kit runs as WebAssembly only, as any game that waits from inside a function does.

**The console's first frame**, from power-on to its first V-blank, runs as the game starts, and the page's first frame is the console's second: the proof tools compare a Dreamport's frame with the original's next one. The console samples its buttons as each V-blank ends, from what the emulator was given as the frame started, so a PlayStation Portable game's `proof/original.json` says `"keysAfterVBlank": true`, or its original reads each press a frame before its Dreamport does.

**Memory.** As WebAssembly the console's memory is at the console's own addresses in the game's memory: the scratchpad's 16 KB from `0x00010000`, the video memory's 2 MB from `0x04000000` and the main memory's 64 MB from `0x08000000`, with a game's own values above them all. `psp_memory(address)` gives where an address is, whichever mirror it's in, the uncached one at `0x4xxxxxxx` or the kernel's at `0x8xxxxxxx`, and `psp_read32`, `psp_write32` and their kin read and write there. Where the system takes an address, as for a framebuffer, a block of samples or the pad's sample, a game gives the console's.

**Time.** The console's time is counted in the processor's cycles, 222 million a second. The emulator counts one for each instruction the original runs, and two for one of the vector unit's. The kit's own answers take the cycles the emulator takes for them: the two instructions every call of the system goes through, what a call is known to cost, such as 32,000 for making a thread, and 1,200 or 2,700 for changing the thread that runs. A game's own C takes none unless it says so, with `psp_time_pass(cycles)`: the instructions its original ran since the game last said so or last asked the system for something. That's right while its original's work is short beside a frame, and where it isn't, what's due meanwhile, a V-blank, a block of sound mixed, a better thread woken, happens partway through, as it does under the original. `psp_time()` is the time now.

**Threads.** `sceKernelCreateThread` takes the thread's function, a C function, and `sceKernelStartThread` starts it. The thread with the best priority, the lowest number, that is ready runs; among equals the one ready first; and a thread that runs keeps running until a better one is ready or it waits. A thread waits in `sceKernelSleepThread`, `sceKernelDelayThread`, the screen's waits, a read of the pad with no sample yet, and a block of sound handed to a channel that still has some. Each thread has a stack of its own and stops wherever it waits, by the same pass that lets a game wait for the screen from inside a function ([`kit/c/pause.c`](../../c/pause.c)). The numbers the system gives threads start where the emulator's do for a program run from its file.

**Semaphores and event flags.** `sceKernelCreateSema`, `sceKernelSignalSema`, `sceKernelWaitSema` and their kin, and `sceKernelCreateEventFlag`, `sceKernelSetEventFlag`, `sceKernelWaitEventFlag` and theirs, each take the time the emulator's take and wake their threads as it does: in the order they came, or by their priorities for a semaphore made with `PSP_SEMA_PRIORITY`, and a thread woken by one with a better priority than the one running runs at once. A wait's timeout is the address of a word saying how many microseconds, as the console has it: a short one is longer, as the console times it, the word is written with what was left as the wait ends, and a wait that runs out gives back `0x800201A8`. A thread whose wait ran out stays in the list until a signal or a look at it passes over it, as in the emulator, so it counts where the emulator counts it. The numbers the system gives them are counted with the threads'.

**Mutexes, lightweight mutexes and callbacks.** `sceKernelCreateMutex`, `sceKernelLockMutex`, `sceKernelUnlockMutex` and their kin, and `sceKernelCreateLwMutex`, `sceKernelLockLwMutex`, `sceKernelTryLockLwMutex` and `sceKernelUnlockLwMutex`, take the time the emulator's take and hand a mutex on as it does: to the first thread waiting, or the one with the best priority for one made with `PSP_MUTEX_PRIORITY`, again and again by its own thread for one made with `PSP_MUTEX_RECURSIVE`, with each lock's timeout timed as the console times a short one. A lightweight mutex keeps its state in the 32 bytes of work area the game gives it, in the console's memory, as the console does. A thread that ends lets go of the mutexes it holds. A game starts as the console's SDK has it start: `sceKernelCreateCallback`, `sceKernelRegisterExitCallback` and a thread that sleeps in `sceKernelSleepThreadCB` are there, and so are the other waits that take callbacks, `sceKernelDelayThreadCB`, `sceKernelWaitSemaCB`, `sceKernelWaitEventFlagCB`, `sceKernelLockMutexCB` and `sceKernelLockLwMutexCB`, which wait as the others do while no callback is notified, as in the emulator.

**The screen.** `sceDisplaySetMode` waits for a V-blank, as the system's does. `sceDisplaySetFrameBuf` names the framebuffer, its line's length and its format, 16 bits as 565, 5551 or 4444, or 32 bits, shown at once or from the next V-blank. A game paints it by writing the console's memory, or through the graphics chip. `sceDisplayWaitVblankStart`, `sceDisplayWaitVblank`, `sceDisplayGetVcount` and `sceDisplayIsVblank` are the system's. `psp_show()` paints the page's picture from what the screen shows, each colour's 4, 5 or 6 bits widened to 8 as the emulator widens them.

**The buttons and the stick.** `sceCtrlPeekBufferPositive` and its kin write the pad's samples at the address they're given, 16 bytes each: the time it was taken in microseconds, the buttons as the console's own bits (`PSP_CTRL_CROSS` and the rest), and the stick. The proof tools hold the stick all the way over or not at all, so it reads 0, 128 or 255 each way, and only once a game has asked for it with `sceCtrlSetSamplingMode(1)`.

**Sound.** A game reserves a channel, `sceAudioChReserve`, and hands it blocks of 16-bit samples from the console's memory, `sceAudioOutputBlocking` and its kin, each with its two volumes. The console takes 64 samples from every channel 44,100 times a second and adds them up. A thread that hands a block to a channel that still has some waits until what was there has gone, so a thread that plays one block after another keeps the console's pace.

**The graphics chip.** A game writes a display list in the console's memory, a command a word, `PSP_GE(command, value)`, and hands it to the chip with `sceGeListEnQueue`, as far as a stall address it moves on with `sceGeListUpdateStallAddr`, or to its end. The chip runs it as soon as it has it, a command at a time, as the emulator runs it: the jumps, calls and returns within a list, its base and origin, and its end. The chip's time isn't the processor's, so a list takes none of the calling thread's own: it's done when the chip would be, two cycles a command, sixty more each time it starts and as it ends, twenty a vertex, and a block copied takes its bytes' worth. Then its end's interrupt comes, which takes 2,400 cycles from a thread that's running, as the system changes to its idle thread and back, and a thread waiting in `sceGeListSync` or `sceGeDrawSync` is woken, each wait taking what the system's takes. The numbers lists get are the system's. The chip draws rectangles in the screen's own coordinates (`PSP_GE_THROUGH`): the screen and its depth cleared, or rectangles of one colour, from vertices with 16-bit or floating-point places and a colour of any format, by index or not, each pixel tested by its alpha, colour, stencil and depth, blended in any of the chip's ways, dithered, put through a logic op and written only where the masks let it, into a framebuffer of any of the four formats. Where the emulator's software renderer takes a shortcut that changes what it draws, the kit takes it too: a sprite with nothing but blending by alpha is written straight, skipping an alpha test that could only fail where blending changes nothing, and a rectangle blended by an alpha of zero isn't drawn. And it copies blocks of memory, `PSP_GE_TRANSFERSTART`.

**The draw list.** Every command the chip runs in a frame, and the vertices and indices each draw reads, are hashed in the order run, the same way the proof tools hash what the original gives its chip in the emulator ([`tools/libretro/ppsspp.patch`](../../../tools/libretro/ppsspp.patch)). A PlayStation Portable game is proven by its pictures, which the emulator's software renderer draws the same on every computer, and one whose `original.json` says `"provenBy": "draw lists"` by its draw lists, which find a command that differs even where the picture doesn't show it. The whole list isn't kept, so the tools can't yet say which command of a list that differs isn't the original's.

**The processor's own instructions.** A twin's C is the original's instructions in C's own words, sums, shifts, comparisons, loads and stores, and the floating-point unit's sums, square roots and comparisons, which give what the console gives. Where C has no word for an instruction, or leaves what it gives to the computer it runs on, `psp.h` has a function that gives what the emulator's interpreter gives: `psp_clz` and `psp_clo`, `psp_bitrev`, `psp_wsbh` and `psp_wsbw`, `psp_rotr`, `psp_ext` and `psp_ins`, the multiplies and divides into HI and LO (`psp_mult`, `psp_madd`, `psp_msub`, `psp_div` and their kin, with what a division by zero gives), and the floating-point unit's conversions to whole numbers (`psp_round_w_s`, `psp_trunc_w_s`, `psp_ceil_w_s`, `psp_floor_w_s`, and `psp_cvt_w_s` in the rounding its control register names), which give the nearest a word holds for a number past it, the most for one that isn't a number, and the least for minus infinity. `psp_mul_s` multiplies as the unit does, infinity by zero giving the console's own not-a-number, with no sign. A float that isn't a number made by any other sum has the sign the computer's processor gives it, in the original as in a twin.

**The vector unit.** A twin runs one of the vector unit's instructions by its word, as the original has it and as `read` shows it: `psp_vfpu(word)` for any of its own sums, prefixes and moves between its registers, `psp_vfpu_load` and `psp_vfpu_store` for `lv` and `sv` with the value of the instruction's base register, `psp_vfpu_get` and `psp_vfpu_set` for `mfv` and `mtv`, and `psp_vfpu_branch` for whether a `bvt` or `bvf` goes to its target. They are the emulator's interpreter ported to C, from PPSSPP's own source, so every register and condition bit comes out to the bit as the emulator gives it, and the sine, cosine, arcsine, reciprocal, powers and logarithms of two are worked out from the same tables the emulator reads, which PPSSPP measured on the console: the kit has them in `vfpu/`, and the tools give the emulator the same files, so it never falls back on the computer's own. The unit's 128 registers and its 16 control registers are `psp_vfpu_state`. A thread made with `PSP_THREAD_ATTR_VFPU` has a unit of its own, which the system puts away as it stops and gives back as it runs again, and every register of it starts not a number; a thread made without it, as the program's first thread is, finds the unit as the last thread left it. Each of the unit's instructions takes the emulator two cycles. A float that isn't a number made by a sum of two that are has the sign the computer's processor gives it, in the original as in a twin.

**The sound list.** Everything a game gives the channels in a frame is hashed in the order given, the same way the proof tools hash what the original gives them in its emulator ([`tools/libretro/ppsspp.patch`](../../../tools/libretro/ppsspp.patch)): each block handed over as its channel, its volumes, its format, how many samples and their bytes, and each block of 64 the console mixes. A PlayStation Portable game's sound is proven by its sound list and by every sample the kit mixes being the original's ([How sound is compared](../../../tools/README.md#how-sound-is-compared)). The mixed blocks are what makes the time a block is handed over part of the list.

## What it doesn't do yet

Of what the graphics chip draws there are rectangles in the screen's own coordinates and blocks copied: triangles, lines and points, textures, and the chip's own transform of 3D vertices with its lighting, fog, morphing, skinning and curved surfaces come next ([#1980](https://github.com/NahuelGenchi/dreamports/issues/1980)), and their commands are run and hashed in the draw list but draw nothing yet. A rectangle whose corners fall between pixels is drawn as the emulator draws it only where the emulator draws it in one piece, as its renderer splits the screen into parts it draws apart; a list's handlers of a game's own aren't called (`sceGeSetCallback`), and a list a signal pauses waits for `sceGeContinue`, which isn't there yet; a list's saved state (`args`' context) isn't kept; and the system's version a program names is taken to be none, as for a program run from its file. A callback a game notifies, message boxes, interrupts, timers, files and the system's functions by their numbers [#1990](https://github.com/NahuelGenchi/dreamports/issues/1990). Of the system's functions there are the ones above and no others: a callback a game notifies itself, which the console would run on its thread, isn't run, and there are no message boxes or interrupts of a game's own, no files, no memory blocks, no modules loaded after the first, no sound decoders and no network. A game that runs any of the vector unit's instructions takes in all of its tables, 4.6 MB, as `psp_vfpu` can run any of them. The program's first thread can't be given a vector unit of its own, as the console gives it one when the program's module names it (`module_start_thread_attr`). Where both of a sum's floats aren't numbers, the one it gives is the one the emulator's build for Windows takes, which its build for a Mac may take the other way round; `vsgn` on fewer than four lanes takes the lanes it doesn't have as 0, where the emulator takes what its stack held. A thread's stack isn't in the console's memory, so a game that reads its own stack's address, or what the system leaves on it, doesn't find the original's. The sound channel for a rate of a game's choice (`sceAudioSRC`) and the second output aren't there. A memory of 32 MB, as a game from a disc has, isn't told apart from the 64 MB a program run from its file gets, which only what the system places from the top of the memory would show.

What comes due while a game's own code runs comes one cycle after its time, as it does in the emulator after an instruction that isn't a branch. Under the original it comes two after when the instruction that reaches it is a branch, which runs with the one after it: a twin can't know which, and it shows only where a game asks the time to the microsecond on that cycle.

## How it's checked

`npm run test:psp-kit` writes the small program of [`tools/test/made-up-psp.mjs`](../../../tools/test/made-up-psp.mjs) as a Dreamport in C ([`psp-kit/main.c`](../../../tools/test/psp-kit/main.c)) and proves it against the console's real emulator. The program paints its framebuffer, moves a square, plays a square wave from a second thread a block at a time, and shows what the system answers as bars: the number the system gave its thread, the buttons, the stick, and the system's time in microseconds twice a frame, which is a different width as soon as anything is 222 cycles early or late. Its Dreamport says how many cycles each stretch of the program's instructions took. All 300 frames have to be the same, pixel for pixel, with every sample the console mixes and everything given to the channels in the frame it was given. What `new` writes, a square a shade off, a first block of sound handed over 64 samples' time late and a thread a microsecond late are each found, the last two by nothing but the kit's time. A second recording holds each button and each way of the stick in turn: all 300 frames match, and a Dreamport that doesn't see one button, or never reads how far down the stick is, is found at the first frame it's held.

A fifth, [`tools/test/made-up-psp-vfpu.mjs`](../../../tools/test/made-up-psp-vfpu.mjs) with its Dreamport in [`psp-vfpu/main.c`](../../../tools/test/psp-vfpu/main.c), does the vector unit's sums in two threads that have a unit of their own and use the same registers: each frame the first turns numbers from the frame's into floats and runs a prefix, sums, products, a dot product, the unit's sine, cosine, reciprocals, roots, powers, logarithms and arcsine, a matrix by a matrix and by a vector, a conversion back, a comparison and a move by it, and keeps a sum from frame to frame, and the second uses the same registers for its own. A bar for each word they make folds its four bytes into its width, so a bit of any of them shows. All 300 frames have to match by their pictures and by their draw lists, and a Dreamport whose reciprocals are worked out as C divides, where the unit gives its own, or whose first thread has no unit of its own, is found.

A fourth, [`tools/test/made-up-psp-mutex.mjs`](../../../tools/test/made-up-psp-mutex.mjs) with its Dreamport in [`psp-mutex/main.c`](../../../tools/test/psp-mutex/main.c), starts as the console's SDK has a game start, with a thread that makes the exit callback and sleeps, and has two threads that lock a mutex and a recursive lightweight mutex against each other: the first holds them for a while every fourth frame, so the second's lock runs out and its try fails. Bars show what each lock gave back, what was left of its timeout, and when each thread let go, to the microsecond. All 300 frames have to match by their pictures and by their draw lists, and a Dreamport whose lock's timeout is a microsecond longer, that holds the mutexes every frame, or that lets go a microsecond late is found.

A third program, [`tools/test/made-up-psp-sync.mjs`](../../../tools/test/made-up-psp-sync.mjs) with its Dreamport in [`psp-sync/main.c`](../../../tools/test/psp-sync/main.c), has two threads that wait for each other: each frame the first signals a semaphore the second waits for with a timeout, but every eighth frame, when the timeout runs out, and the second sets an event flag the first waits for with a timeout, but every fourth frame. Bars show what each wait gave back, what was left of its timeout, and when each ended, to the microsecond. All 300 frames have to match by their pictures and by their draw lists, and a Dreamport whose timeout is a microsecond longer, whose flag is set every frame, or that waits a microsecond late is found.

A second program, [`tools/test/made-up-psp-ge.mjs`](../../../tools/test/made-up-psp-ge.mjs) with its Dreamport in [`psp-ge/main.c`](../../../tools/test/psp-ge/main.c), draws through the graphics chip: each frame a tiny list whose end's interrupt comes while the program runs, a main list handed over stalled and let go, which clears the screen, moves a square, blends a see-through rectangle over it and a dithered one, draws two in 16-bit colour by indices and one through a call with a write mask, jumps over a command, and copies a block of the screen, and a list of bars as wide as the times its waits for the chip ended. All 300 frames have to match by their pictures and by their draw lists. A Dreamport with its see-through rectangle a shade off, a value of its dithering the other way, or its wait for the chip a microsecond late is found by its pictures, and one whose list differs only in a command that draws nothing is found by its draw lists, which its pictures can't show. The tools compare pictures in 15-bit colour, as a page shows them, so a colour a step off in its eight bits can be the same in the picture, and the draw lists find it.

It isn't part of Check, as the emulator takes a long while to build. The PlayStation Portable's workflow runs it on Linux, on a Mac with Apple's chip and on Windows, for pull requests that touch the console's files ([Other consoles](../../../docs/CONSOLES.md#the-playstation-portable)).
