# NES kit in C

[Back to the kits in C](../../c/README.md) · [Other consoles](../../../docs/CONSOLES.md) · [The Dreamport standard](../../../docs/STANDARD.md) · [Written in: #619](https://github.com/NahuelGenchi/dreamports/issues/619)

This folder is the NES's kit for games written in C, on what [every console's kit in C](../../c/README.md) shares. It's the console's picture and sound hardware, the PPU and the APU, with the cartridge and the controller, written from how the console is documented to behave, so a game in C draws and sounds as the console does by writing the hardware as its original does. A game in C runs in the browser with nothing to install: it's built to WebAssembly, and its page is the one every console's games share, with the same start screen, settings, controller drawn on touch screens and proof mode. The same C also builds for a computer, with no browser.

Like the rest of the kits it's under [GPL-3.0-or-later](../LICENSE), and nothing from any game is in it.

## What's in it

| File | What it does |
| :--- | :--- |
| `nes.h` | What a game sees of the console: the CPU's reads and writes of the hardware, work memory, the cartridge's program, tiles and battery memory, how its name tables are wired, time in the frame, and the buttons |
| `ppu.c` | The picture hardware: the registers, name tables, colours and sprites, and the drawing of each line at the time each write happens |
| `apu.c` | The sound hardware: the two pulse channels, the triangle, the noise and the samples channel, their envelopes, sweeps and length counters, the frame counter, the console's mix and the emulator's filter |
| `nes.c` | What the page calls to run the game: its start, with the cartridge from the copy's iNES header, its frames, the drawing and the sound, and the controller |
| `nes-kit.h` | What the kit's own files share, which a game doesn't need |

The page's side is the base's: [`kit/c/game.js`](../../c/game.js) loads the game and hands it the copy, and its sound plays on the base's audio thread ([`kit/c/worklet.js`](../../c/worklet.js)). On a computer the game runs with the base's [`native.c`](../../c/native.c).

It draws the background with its fine and coarse scroll, both pattern tables, the four name tables as the cartridge wires them, the attribute colours, the left column's hiding, greyscale, and 64 sprites, 8 by 8 or 8 by 16, flipped either way, in front of or behind the background, up to 8 a line, with sprite 0's hit. A write partway down the screen, as a game that splits its screen makes, changes the picture from the pixel it happens at. The colours are the 64 the proof tools see FCEUmm show, measured from it a colour at a time with a program of the project's own. Colour emphasis isn't drawn yet. It plays every channel of the console's own sound, mixed as the console's resistors weigh them and then filtered as FCEUmm filters its output, which only goes up from zero and thumps when a note stops ([Other consoles](../../../docs/CONSOLES.md)). A cartridge's own sound chip, interrupts from the frame counter or the samples channel, and a mapper's interrupts aren't in it yet. A game whose cartridge switches its banks does so itself, with `nes_chr_bank` and `nes_mirroring`. A game that needs one adds it here.

## A game in C

A game includes `"nes.h"` and defines two functions. `game_start()` runs once, with the player's copy in `kit_copy` and the cartridge read from it: its program in `nes_prg`, read as the CPU sees it with `nes_prg_byte(address)`, its tiles in `nes_chr`, or 8 KB of tile memory when it has none, and its name tables wired as its header says. `game_step(buttons)` runs every frame, with the buttons held as bits, `BUTTON_A` and the rest from `console.h`, in the order the controller sends them, which `nes_read(0x4016)` also gives a bit at a time. Each step is what the original's CPU does from one V-blank to the next: it writes the hardware with `nes_write(address, value)` and reads it with `nes_read(address)`, as the original's stores and loads of `$2000` to `$4017` do, and keeps its variables in `nes_ram`, the console's work memory, where the original keeps them, so a start point finds them there. A battery-backed cartridge's memory is `nes_wram`, which `nes_wram_write()` keeps in the browser.

A step's writes happen as V-blank starts. A game that changes the picture partway down the screen says when, as its original's timing does: `nes_wait_line(line)` moves the frame on to a visible line, `nes_wait_sprite0()` to where `$2002` first shows sprite 0's hit, and `nes_spend(cycles)` on by as many of the CPU's cycles. A game whose original times its own code, as one that waits for V-blank by reading `$2002` or runs on across frames with the interrupt off does, counts the original's cycles itself: `nes_frame_length(frame)` says how long each frame is, `NES_VBLANK_DOT` when `$2002` shows V-blank, and `NES_NMI_DOT` when the PPU asks for the interrupt, and `nes_spend` moves the frame on to the original's time before each write, as [Mega Man Dreamport's](../../../games/mega-man/c/src/main.c) does. `nes_frame()` counts the frames from power-on as the proof tools do: in frame 0 the PPU is warming up, its screen is grey and V-blank never starts, so the original's power-on, which waits for two V-blanks, gets through its first in frame 1. A start point (`kit_start_point`) begins later: `nes_start_at(frame)` in `game_start` makes the console as if that many frames had run, and the writes after it set the hardware up as the original had it there.

The kit's frame is the one the proof tools compare it with, as the emulator lays its frames out: each starts with V-blank, and its picture is drawn after it, so what a step writes in V-blank shows in the same frame, and its sound is that frame's time. The emulator's first frame, before frame 0, is left out, as the tools compare the Dreamport's frame f with the emulator's f + 1.

Its folder, `games/<game>/c/`, holds its page and its code, with its C in `src/`. `npm run dp -- new <game>/c` on an NES game writes the starting point on this kit, from `tools/libretro/new-game/c/nes.c.template`, whose `main.c` writes the backdrop's colour as an NES game does: blue, and green while a button is held. `buildGame(folder)` in [`tools/lib/c.mjs`](../../../tools/lib/c.mjs) builds it with the base and this folder, as the game's `proof/original.json` names the NES.

## How it's checked

`npm run test:real-console` proves a Dreamport in C of a small NES program of the project's own ([`tools/test/made-up-nes.c`](../../../tools/test/made-up-nes.c)) on the real FCEUmm, every frame, picture and sound, from power-on and from a start point, and checks that a sprite moved a pixel too far is found where it first shows. Its program scrolls a background of four tiles in four colours, moves a sprite and plays a pulse and a triangle, so that runs on every pull request. `npm run test:c-kit` builds that Dreamport and the NES's starting point for the computer and as WebAssembly, and fails on any frame or sound sample that differs between the two, and on the starting point's colours. `npm run test:game` tries the starting point's page on the NES, as on every console. What the program doesn't use, such as 8 by 16 sprites, sprite 0's hit, the noise and the samples channel, is checked by the NES games proven on it. The first is [Mega Man Dreamport](../../../games/mega-man/), whose title screen matches FCEUmm's every frame, picture and sound, with its tiles, its screen and its colours written with the picture off, partway down frames, as the original writes them.
