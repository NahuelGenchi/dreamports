# Game Boy kit in C

[Back to the kits in C](../../c/README.md) · [Other consoles](../../../docs/CONSOLES.md) · [The Dreamport standard](../../../docs/STANDARD.md) · [Written in: #1911](https://github.com/NahuelGenchi/dreamports/issues/1911)

This folder is the kit for Game Boy and Game Boy Color games written in C, on what [every console's kit in C](../../c/README.md) shares. The two consoles share a processor and nearly all their hardware, so they share one kit, which is the Game Boy Color's when the player's copy says it's a Game Boy Color game, as the console itself decides. It's the console around its processor: its memory with the cartridge's banks, the screen, the sound's four channels, the buttons, the timer and the interrupts, written from how the console is documented to behave, so a game in C draws and sounds as the console does by writing the hardware as its original does. A game in C runs in the browser with nothing to install: it's built to WebAssembly, and its page is the one every console's games share, with the same start screen, settings, controller drawn on touch screens and proof mode. The same C also builds for a computer, with no browser.

Like the rest of the kits it's under [GPL-3.0-or-later](../LICENSE), and nothing from any game is in it. The numbers of the filter its sound goes through are blipper's, by Hans-Kristian Arntzen, under the MIT licence `blip.h` carries.

## What's in it

| File | What it does |
| :--- | :--- |
| `gb.h` | What a game sees of the console: the processor's reads and writes of its memory, the cartridge, the time, the interrupts and the buttons |
| `gb.c` | The memory's map, the cartridge's chip and its banks, the buttons, the timer, the interrupts, the time and the frames, and what the page calls to run the game |
| `lcd.c` | The picture hardware: the background, the window and the sprites, the Game Boy's shades and the Game Boy Color's palettes, drawn a line at a time as far as the time has got, and the screen's interrupts |
| `apu.c` | The sound hardware: the two square channels, the wave and the noise, their lengths, envelopes and sweep, the mix, and the emulator's filter |
| `blip.h` | That filter's numbers |
| `gb-kit.h` | What the kit's own files share, which a game doesn't need |

The page's side is the base's: [`kit/c/game.js`](../../c/game.js) loads the game and hands it the copy, and its sound plays on the base's audio thread ([`kit/c/worklet.js`](../../c/worklet.js)). On a computer the game runs with the base's [`native.c`](../../c/native.c).

It keeps the console's memory by its addresses: the cartridge's program, with the banks a write to `$0000`-`$7FFF` switches, as a cartridge with no chip, an MBC1, an MBC3 or an MBC5 does, the cartridge's own memory, which the browser keeps when it has a battery, the picture memory, in two banks on a Game Boy Color, the work memory, in eight banks there, the sprites and the high memory. It draws the background with its scroll, the window, with its own count of lines, and 40 sprites of 8 by 8 or 8 by 16, flipped either way, ten to a line, in front of or behind the background: with the Game Boy's three palettes of four shades, where the sprite furthest left is on top, or the Game Boy Color's sixteen palettes of four colours, its second bank of tiles and each tile's own palette, flips and priority, where the first sprite in the list is. The shades and the colours are the ones the proof tools see Gambatte show, with its colour correction off, which is the console's own 15 bits. It plays the four channels of the console's sound as two million samples a second, each the sum of the four, and filters them down as Gambatte does. Where Gambatte catches the noise channel's register up after a silence, 15 steps at once, its last bit isn't the one 15 single steps would give, and the kit takes Gambatte's, as that is what a Dreamport is proven against. The timer counts and runs over at the cycles the console's does, and the screen and the timer ask for their interrupts when the console's do. The buttons are the console's eight lines, so two opposite arrows can be held at once, as Gambatte is set to allow.

What isn't in it yet: the Game Boy Color's double speed and its copies of memory to the picture memory (`$FF51`-`$FF55`), a second console at the other end of the link cable, the infrared port, an MBC3's clock, and the other kinds of cartridge. The console's own start-up isn't run, so the picture memory starts empty, without the logo it leaves there, and the work memory starts as zeros. A write that lands while a line is being drawn shows from the pixel the kit works out the console had reached, which isn't always where Gambatte shows it: the console reads the scroll again for each tile it fetches, and the kit doesn't yet. A write before a line's drawing starts, 83 cycles into the line, or after it ends shows as Gambatte shows it, which is when most games change their picture partway down the screen. A line's mode 0 starts when the documented cost of its sprites and window says, which isn't measured against Gambatte either. A game that needs one adds it here.

## A game in C

A game includes `"gb.h"` and defines two functions. `game_start()` runs once, at power-on, with the player's copy in `kit_copy` and the cartridge in `gb_rom`. `game_step(buttons)` runs every frame, with the buttons held as bits, `BUTTON_A` and the rest from `console.h`. Each does what the original's processor does in that time: it reads and writes the console's memory with `gb_read(address)` and `gb_write(address, value)`, as the original's loads and stores do, and it can keep its variables in `gb_wram`, the work memory, where the original keeps them, so a start point finds them there.

The kit counts the processor's cycles, 4,194,304 a second, four to each of its machine cycles. A write happens at the time the console has reached, so a game says how long its original's code takes: `gb_spend(cycles)` moves the console on. `gb_halt()` is the processor's HALT with interrupts on: the console runs on until an interrupt `$FFFF` has on is requested, and the processor takes it, in 20 cycles. It returns the interrupt's bit, `GB_VBLANK`, `GB_STAT`, `GB_TIMER`, `GB_SERIAL` or `GB_JOYPAD`, and the game runs that interrupt's code. `gb_interrupt()` is what the processor does between two instructions with interrupts on, such as after an interrupt's code returns: it takes one that is waiting, or returns 0. A game whose original waits in a loop of its own, and never halts, counts that loop's cycles with `gb_spend` and reads what it waits for, as its original does.

A frame is what the emulator plays in one go: up to when a picture is complete, as its V-blank starts, or, with the screen off, a picture's time after the last. So a step starts as V-blank does, and what it writes then shows in that frame's picture. When the frame ends, `gb_halt()` returns 0 and `gb_interrupt()` returns -1, and `game_step` returns: the next frame's buttons aren't known yet, and its call goes on from there, so a game keeps where its original's processor was. `game_start` and a step can also run on past a frame's end, as an original that spends several frames setting up with the screen off does: the frames they ran through are over, and the page gets each one's picture in turn, the last eight of them. The emulator's own first frame, from power-on to the first picture, is left out, as the tools compare the Dreamport's frame f with the emulator's f + 1: `game_start` runs through it. Its sound is left out too, up to where the emulator's processor stopped as the picture was complete: at the end of the instruction it was in, or, waiting in HALT, on its own four-cycle step after the picture, and after taking an interrupt asked for by then, as V-blank's is. A game that spends its time an instruction at a time, or waits in HALT, has that end exactly, and the whole of its sound is then the emulator's sample for sample.

Nearly every game reads its buttons in the code its V-blank interrupt runs, which is where the emulator's frame starts, so a game's `proof/original.json` says `"keysAfterVBlank": true`, and `prove` gives the original each frame's buttons in the frame the Dreamport gets them ([Proving](../../../tools/README.md#proving)).

For a start point (`kit_start_point`), `gb_play_ahead(frames)` in `game_start` plays that many frames of the game with no button held and nothing shown or heard, as the recording has the original do, and the game then sets what the start point names. The tools count a recording's `sets` from the start of the work memory: address 0 is `$C000`.

Its folder, `games/<game>/c/`, holds its page and its code, with its C in `src/`. `npm run dp -- new <game>/c` on a Game Boy or Game Boy Color game writes the starting point on this kit, from `tools/libretro/new-game/c/gb.c.template`, whose `main.c` writes the background's first colour: on a Game Boy Color blue, and green while a button is held, and on a Game Boy, which has four shades of one colour, light, and dark while a button is held. `buildGame(folder)` in [`tools/lib/c.mjs`](../../../tools/lib/c.mjs) builds it with the base and this folder, as the game's `proof/original.json` names the console.

## How it's checked

`npm run test:real-gb` proves a Dreamport in C of a small program of the project's own ([`tools/test/made-up-gb.c`](../../../tools/test/made-up-gb.c)) on the real Gambatte, as a Game Boy game and as a Game Boy Color one: `prove` finds every frame the same, picture and sound, from power-on and from a start point, and finds a sprite moved a pixel too far where it first shows. As `prove` hears sound by how loud it is in each band of pitches, the test then runs the same WebAssembly beside the emulator itself and compares every pixel of every frame and every sample of the sound, all 16 bits, with no tolerance: with the recording's presses, and with 900 frames of presses drawn from a seed, any buttons at once, pressed again before their sounds have ended.

The program is written out an instruction at a time, with each one's cycles, so its Dreamport makes each write at the cycle the program does. It switches the cartridge's banks for its tiles, its colours and a byte it reads every frame, writes the cartridge's own memory, scrolls a background of four tiles, with each tile's palette on a Game Boy Color, shows a window and two sprites, one of them behind the background, flipped and in the second palette, copies its sprites as the hardware does, reads the buttons, and scrolls the lower half of the screen the other way from an interrupt at a line LYC names, which two lines before switches the timer's interrupt off, so the scroll is always written before the line is drawn. Its buttons start each of the four sound channels: a square with a sweep and an envelope, one with a length, the wave and the noise, and its timer's interrupt changes a pitch while a button is held. `npm run test:c-kit` builds that Dreamport and the starting point for the computer and as WebAssembly, and fails on any frame or sound sample that differs between the two. `npm run test:game` tries the starting point's page on both consoles, as on every console.

What the program doesn't use isn't checked against the emulator: 8 by 16 sprites, more than ten sprites on a line, the mode 0 and mode 2 interrupts, MBC1 and MBC3, the work memory's banks, the link cable's interrupt, and what the sound does when a channel is written in ways the program's buttons never do. Those are written from how the console is documented to behave, and the first game that uses one proves it.
