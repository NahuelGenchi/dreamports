# Game Boy Advance kit in C

[Back to the kit](../README.md) · [The Dreamport standard](../../../docs/STANDARD.md) · [Written in: #595](https://github.com/NahuelGenchi/dreamports/issues/595)

This folder is the [Game Boy Advance kit](../README.md) for games written in C, on what [every console's kit in C](../../c/README.md) shares. It holds the same hardware layer as the JavaScript kit, and draws every frame to the same pixel, so a game can move between the two languages with nothing else changing. A game in C still runs in the browser with nothing to install: it's built to WebAssembly, and its page is the JavaScript kit's, with the same start screen, settings, controller drawn on touch screens, achievements and proof mode. The same C also builds for a computer, with no browser.

Like the rest of the kit it's under [GPL-3.0-or-later](../LICENSE), and nothing from any game is in it.

## What's in it

| File | What it does |
| :--- | :--- |
| `gba.h` | What a game sees of the console: VRAM, the colours, OAM and the display registers, the buttons, and, from [`kit/c/kit.h`](../../c/kit.h), the player's copy, the save memory, the start point's words and memory of its own |
| `video.c` | The video hardware's drawing, written from [`video.js`](../video.js) a function at a time, so it draws as mGBA does too |
| `gba.c` | What the page calls to run the game: its start, its frames, their drawing, and where the video hardware is for the proof tools |
| `game.js` | The page's side: on [`kit/c/game.js`](../../c/game.js), which loads the game's WebAssembly and hands it the copy, it hands it the buttons and gives the page the `video` and `step` a JavaScript game gives it |
| `apu.c` | The sound hardware: the four Game Boy channels, the two DirectSound FIFOs and the mix, written from [`sound/apu.js`](../sound/apu.js) |
| `m4a.c`, `sound.h` | Nintendo's sound engine (MusicPlayer2000, or "m4a"), written from [`sound/m4a.js`](../sound/m4a.js) |
| `sound.c` | The engine and the hardware on one clock, from [`sound/synth.js`](../sound/synth.js), the game's sound calls, and what the page calls to play them |
| `worklet.js` | The sound's audio thread for a player: a second copy of the game's WebAssembly, of which only the sound runs |
| `native.c` | The game on a computer: it plays a list of button presses, with the words of a start point if it's given them, and writes every frame, and its sound if asked, for tests |

The widescreen view, the mosaic and the OBJ window aren't drawn in C yet. Of the sound, a music manager of the game's own, the sound of every GBA after the first on a page with several, `countCycles` and the Sonic Rush and Sonic Advance 2 sounds Sonic Advance's extras play aren't in C yet. A game that needs one adds it here and to the JavaScript kit alike.

## A game in C

A game defines two functions. `game_start()` runs once, with the player's copy in `gba_rom`, and `game_step(keys)` runs every frame, with the buttons held as the console's KEYINPUT bits, a bit set for each button down. Each frame it writes the video hardware, `gba_vram`, `gba_pal`, `gba_oam` and the registers through `gba_write`, as the original does, and the kit draws the frame once the step is over. `gba_on_hblank()` gives the kit a function to run after each line, for a game that changes registers between lines. `gba_save(size)` gives the cartridge's save memory with what the browser kept of it, and `gba_save_write()` keeps it, when the original writes it.

`gba_sound_start(players, channels, volume, rate, reverb)` finds the sound engine's tables in the player's copy and starts it with the game's sound mode, from its decompilation's `DEFAULT_SOUND_MODE`, as the JavaScript kit's `soundLayout()` does. After it, `gba_sound_play(song)` and the other `gba_sound_` calls in `gba.h` each stand for one of the sound library's functions, and play at the start of the next sound frame, as the original's calls during a frame are sequenced on the next. The engine, the hardware and the clock that joins them are the JavaScript kit's `sound/` written in C a function at a time, so a song sounds the same to the sample in both, and the same as on the console wherever the JavaScript one does. For a player, the game hands its calls over after each frame, and `game.js` sends them to a second copy of the same WebAssembly on an audio thread of its own (`worklet.js`), which keeps its own time, so the music keeps time when the page's frames stall. Under the proof tools the sound plays on the page instead, a frame of it after each of the game's frames, as `proof.js` hears a JavaScript game's. `loadGame()` gives the page `sound`, with `muted`, and `held` for while the settings are open, and with `heard: false` the game plays none, as each GBA after the first does on a page that runs several, each a WebAssembly of its own, on a link cable the page carries between them (Sonic Advance's `c/src/link.c` and `c/src/main.js`). `gba_sound_start_layout()` starts the engine with its music players' table at a known place, as `soundLayout()` takes it, for a game whose table the kit can't find, such as Sonic Battle's, which points into IWRAM. For a game whose picture depends on how long the console's sound work takes, `gba_sound_count_cycles()` runs a silent engine of its own, a frame as each of the game's ends, as the JavaScript kit's `countCycles` does, so `gba_sound_frame_cycles()` says the same in a player's browser, where the audio thread plays the sound, as under the proof tools, and `gba_sound_frames_gone_by()` moves it on for a start point. A start point that plays frames of its own on the page, such as a fight's opening, moves the sound engine itself with the game's `dp_sound_skip_frames(frames)`, as the JavaScript kit's `skipFrames`.

Its folder, `games/<game>/c/`, holds its page and its code, with its C in `src/`: `src/main.c` and any other `.c` files there, which include the kit as `"gba.h"`. `src/main.js` is the page's script, which is the JavaScript starting point's with `loadGame()` from `game.js` in place of the game's own code, and it runs `src/game.wasm`. `npm run dp -- new <game>/c` writes that starting point, from `startingFiles(game, original, { language: 'c' })` in [`tools/lib/new-game.mjs`](../../../tools/lib/new-game.mjs), whose `main.c` paints the backdrop blue, and green while a button is held, as the JavaScript one does.

`buildGame(folder)` in [`tools/lib/c.mjs`](../../../tools/lib/c.mjs) builds `src/game.wasm` from the game's C and the kit's, this folder and [`kit/c/`](../../c/README.md), as the game's `proof/original.json` names the Game Boy Advance. It uses Clang and its linker built as WebAssembly themselves, from npm ([`@yowasp/clang`](https://yowasp.org)), so `npm ci` is all it needs, the same on every computer. `buildNative()` builds the same C for the computer it runs on, with that computer's C compiler, the one the proof tools already need. `game.wasm` isn't kept in the repository: the site builds it as it copies the games, and the proof tools before they open one. A game's C is its [version in C](../../../games/README.md#versions-in-other-languages), in `games/<game>/c/`, beside its JavaScript, which `npm run dp -- new <game>/c` starts.

## How it's checked

`npm run test:c-kit` draws 400 made-up scenes, with every mode, layer, window, colour effect and kind of sprite, and H-blanks that change registers and colours between lines, with `video.c` built for the computer and as WebAssembly, and with `video.js`, and fails on any pixel that differs. `SEED` and `SCENES` choose other scenes, and a failure names the scene to draw again. Then it builds the C starting point and plays 240 frames of made-up presses, on the computer and in Chrome a frame at a time as the proof tools play a game, and fails on any frame whose picture or video hardware differs from the JavaScript starting point's. It also checks that the save memory lasts from one run, and one visit, to the next. Then it plays songs on both sound engines, the C one as WebAssembly, a frame at a time with the same calls, and fails on any sample that differs: made-up songs on made-up cartridges, with every kind of voice and the commands that change them, each alone and with a game's calls between frames (`SONG_RUNS` says how many runs), and, with a copy of Sonic Advance here, every one of its songs (`COPY_FRAMES` frames of each). Its copy is read where it is, and nothing from it is kept. `npm run test:game` tries the C starting point's page as it tries the JavaScript one's: the start screen, the keys, a controller, the settings and the touch screen.
