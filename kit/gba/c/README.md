# Game Boy Advance kit in C

[Back to the kit](../README.md) · [The Dreamport standard](../../../docs/STANDARD.md) · [Written in: #595](https://github.com/NahuelGenchi/dreamports/issues/595)

This folder is the [Game Boy Advance kit](../README.md) for games written in C, on what [every console's kit in C](../../c/README.md) shares. It holds the same hardware layer as the JavaScript kit, and draws every frame to the same pixel, so a game can move between the two languages with nothing else changing. A game in C still runs in the browser with nothing to install: it's built to WebAssembly, and its page is the JavaScript kit's, with the same start screen, settings, controller drawn on touch screens, achievements and proof mode. The same C also builds for a computer, with no browser.

Like the rest of the kit it's under [GPL-3.0-or-later](../LICENSE), and nothing from any game is in it.

## What's in it

| File | What it does |
| :--- | :--- |
| `gba.h` | What a game sees of the console: VRAM, the colours, OAM and the display registers, the buttons, and, from [`kit/c/kit.h`](../../c/kit.h), the player's copy, the save memory, the start point's words and memory of its own |
| `video.c` | The video hardware's drawing, written from [`video.js`](../video.js) a function at a time, so it draws as mGBA does too |
| `gba.c` | What the page calls to run the game: its start, its frames, their drawing, and where the video hardware is for the proof tools |
| `game.js` | The page's side: on [`kit/c/game.js`](../../c/game.js), which loads the game's WebAssembly and hands it the copy, it hands it the buttons and gives the page the `video` and `step` a JavaScript game gives it |
| `apu.c` | The sound hardware: the four Game Boy channels, the two DirectSound FIFOs and the mix, written from [`sound/apu.js`](../sound/apu.js) |
| `m4a.c`, `sound.h` | Nintendo's sound engine (MusicPlayer2000, or "m4a"), written from [`sound/m4a.js`](../sound/m4a.js) |
| `sound.c` | The engine and the hardware on one clock, from [`sound/synth.js`](../sound/synth.js), the game's sound calls, and what the page calls to play them |
| `memory.c` | The console's memory at the console's own addresses, for a game whose every function is a twin of one of the original's: `gba_console_memory()` makes its work memory real at `0x02000000` and `0x03000000`, and its cartridge at `0x08000000` if asked, and `gba_vram_write8()` writes a byte to video memory as the console does ([the same-memory build](../../../tools/README.md#the-same-memory-build)). A game that calls neither has none of it |
| `clock.c`, `clock.h` | The console's time, to the cycle, as the reference emulator keeps it, for a game that ends its frames where the console does in the middle of its work ([The console's time](#the-consoles-time)) |
| `worklet.js` | The sound's audio thread for a player: a second copy of the game's WebAssembly, of which only the sound runs |
| `native.c` | The game on a computer: it plays a list of button presses, with the words of a start point if it's given them, and writes every frame, and its sound if asked, for tests |

The widescreen view, the mosaic and the OBJ window aren't drawn in C yet. Of the sound, the sound of every GBA after the first on a page with several, `countCycles` and the Sonic Rush and Sonic Advance 2 sounds Sonic Advance's extras play aren't in C yet. A game that needs one adds it here and to the JavaScript kit alike.

## A game in C

A game defines two functions. `game_start()` runs once, with the player's copy in `gba_rom`, and `game_step(keys)` runs every frame, with the buttons held as the console's KEYINPUT bits, a bit set for each button down. Each frame it writes the video hardware, `gba_vram`, `gba_pal`, `gba_oam` and the registers through `gba_write`, as the original does, and the kit draws the frame once the step is over. `gba_on_hblank()` gives the kit a function to run after each line, for a game that changes registers between lines. `gba_vblank_keys()` gives the buttons held at the V-blank that ends the frame, which the proof tools give as the next frame's, for a game that reads them there too, as a soft reset does. `gba_save(size)` gives the cartridge's save memory with what the browser kept of it, and `gba_save_write()` keeps it, when the original writes it.

`gba_sound_start(players, channels, volume, rate, reverb)` finds the sound engine's tables in the player's copy and starts it with the game's sound mode, from its decompilation's `DEFAULT_SOUND_MODE`, as the JavaScript kit's `soundLayout()` does. After it, `gba_sound_play(song)` and the other `gba_sound_` calls in `gba.h` each stand for one of the sound library's functions, and play at the start of the next sound frame, as the original's calls during a frame are sequenced on the next. The engine, the hardware and the clock that joins them are the JavaScript kit's `sound/` written in C a function at a time, so a song sounds the same to the sample in both, and the same as on the console wherever the JavaScript one does. For a player, the game hands its calls over after each frame, and `game.js` sends them to a second copy of the same WebAssembly on an audio thread of its own (`worklet.js`), which keeps its own time, so the music keeps time when the page's frames stall. Under the proof tools the sound plays on the page instead, a frame of it after each of the game's frames, as `proof.js` hears a JavaScript game's. `loadGame()` gives the page `sound`, with `muted`, and `held` for while the settings are open, and with `heard: false` the game plays none, as each GBA after the first does on a page that runs several, each a WebAssembly of its own, on a link cable the page carries between them (Sonic Advance's `c/src/link.c` and `c/src/main.js`). `gba_sound_start_layout()` starts the engine with its music players' table at a known place, as `soundLayout()` takes it, for a game whose table the kit can't find, such as Sonic Battle's, which points into IWRAM. For a game whose picture depends on how long the console's sound work takes, `gba_sound_count_cycles()` runs a silent engine of its own, a frame as each of the game's ends, as the JavaScript kit's `countCycles` does, so `gba_sound_frame_cycles()` says the same in a player's browser, where the audio thread plays the sound, as under the proof tools, and `gba_sound_frames_gone_by()` moves it on for a start point. `gba_sound_player_status(player)` reads a music player's status in that engine, for a screen that watches whether a song still plays, such as Sonic Advance's sound test. `gba_sound_start_program()` is for a game that soft resets into a program it unpacked into the work RAM with a sound engine of its own, as Sonic Advance does into Tiny Chao Garden: the engine starts again with the program's tables and reads its songs from the unpacked copy, which the audio thread's copy unpacks too. The JavaScript kit's engine reads the cartridge alone so far, and gets the same with the first JavaScript game that needs it. `gba_lz77()` and `gba_lz77_vram()` are the BIOS's LZ77 unpacking, into memory or into VRAM a halfword at a time, whatever the header's first byte, which the BIOS never checks, and `gba_sqrt()` and `gba_arctan2()` its Sqrt and ArcTan2, worked out as the console does. `gba_sound_missed(frames)` is for a loop held up past V-blanks by a long piece of work: SoundMain misses those frames, the chip goes on with its last notes, and the DMA plays again the samples it holds from some frames before. A game with a music manager of its own, as the JavaScript kit's `manager()` in `sound/synth.js`, defines `game_sound_frame()` (`sound.h`), which gets each sound frame's calls in place of the engine, runs them on it and then decides what plays, and queues its own calls with `gba_sound_manager_call()`; it runs where the sound does, on the audio thread for a player (Sonic Advance's `c/src/music.c`). A start point that plays frames of its own on the page, such as a fight's opening, moves the sound engine itself with the game's `dp_sound_skip_frames(frames)`, as the JavaScript kit's `skipFrames`. `gba_sound_played_for()` does the same for the sound that's heard: at a start point that leaves out a song's first frames, the engine plays them at once, unheard, so the music goes on from where the original's is.

Its folder, `games/<game>/c/`, holds its page and its code, with its C in `src/`: `src/main.c` and any other `.c` files there, which include the kit as `"gba.h"`. `src/main.js` is the page's script, which is the JavaScript starting point's with `loadGame()` from `game.js` in place of the game's own code, and it runs `src/game.wasm`. `npm run dp -- new <game>/c` writes that starting point, from `startingFiles(game, original, { language: 'c' })` in [`tools/lib/new-game.mjs`](../../../tools/lib/new-game.mjs), whose `main.c` paints the backdrop blue, and green while a button is held, as the JavaScript one does.

`buildGame(folder)` in [`tools/lib/c.mjs`](../../../tools/lib/c.mjs) builds `src/game.wasm` from the game's C and the kit's, this folder and [`kit/c/`](../../c/README.md), as the game's `proof/original.json` names the Game Boy Advance. It uses Clang and its linker built as WebAssembly themselves, from npm ([`@yowasp/clang`](https://yowasp.org)), so `npm ci` is all it needs, the same on every computer. `buildNative()` builds the same C for the computer it runs on, with that computer's C compiler, the one the proof tools already need. `game.wasm` isn't kept in the repository: the site builds it as it copies the games, and the proof tools before they open one. A game's C is its [version in C](../../../games/README.md#versions-in-other-languages), in `games/<game>/c/`, beside its JavaScript, which `npm run dp -- new <game>/c` starts.

## The console's time

Most of a game's frames end while it waits for the V-blank, and the kit ends a Dreamport's there. A game's power-on is different: interrupts are off, and the console's first frames end in the middle of its work, inside a DMA, the BIOS's CpuSet or a loop. A Dreamport that has to match the console's work memory after every frame, as one made [the stricter way](../../../docs/STANDARD.md) does, has to end those frames at the same instruction. `clock.c` keeps the console's time for that, on the rules of mGBA 0.10.5, the emulator `prove` plays the original in, and it is the one place a cycle is counted. Each instruction takes one cycle and the wait for its fetch, then its own: a load or a store the wait states of the memory it reaches, from WAITCNT for the cartridge, less what the cartridge's prefetch saved; a jump the fetches of the pipeline again; a multiply its own. Between instructions come the events: DMA units, which hold the processor, the timers, and the sound's two FIFOs, which take a sample at a timer's overflow and ask their DMA for four words when half empty. The BIOS's own code for power-on and for CpuSet is timed as the emulator's BIOS runs it, a step at a time, and CpuSet calls the game back for each halfword or word, as its store runs. A frame ends after the first instruction, or step of the BIOS, that starts at or after the frame's end: 40,997 cycles after power-on, where the display reaches line 160, and every 280,896 after.

A game does the work of a run of the original's instructions, then tells the clock with `gba_clock_run(from, to, next, at, count)`: the original's Thumb instructions from `from` to `to`, read from the player's copy, the last going on to `next`, and, in `at`, the addresses of the loads and stores the clock can't read from the instruction, the pool's and the stack's being plain, and what a multiply multiplies by. What the game writes to the DMA channels, the timers, the sound and WAITCNT goes to `gba_clock_written`, and waits there for the run's store of it, which takes it at that store's own time. A frame that ends inside a run ends after it, where `gba_clock_on_frame_end(kit_wait_frame)` ends the Dreamport's: so a run should end with the last store to the work memory a frame's end can come before, and `gba_clock_late()` counts those that came after one. `gba_clock_run_arm` is the same for ARM code, and `gba_clock_swi` takes a swi, CpuSet calling the game back for each unit. The clock is for a game's power-on: once the game waits for an interrupt, its own wait ends its frames, and `gba_clock_stop` makes every run cost nothing from there. `gba_clock_resume(time)` takes the time up again for a stretch a game has to time later, as its work in the V-blank, which asks the display whether the blank lines are over: the timers and the sound's DMA are brought up to `time`, an event at a time, and a register written while the time was stopped is written as it stood. The frames whose ends went by meanwhile count as over, so a game that waits for a frame resumes at `gba_clock_frame_end(gba_clock_frame())`, and `gba_clock_running()` says whether the time is going.

A few things spare a game's C from saying what the clock can work out. A run whose last instruction goes back from a call can name `GBA_CLOCK_BACK` as its `next`: the clock keeps where each timed `bl` goes back to, as the link register and the stack do, so a function called from several places goes back to the right one. `gba_clock_registers` gives the clock the game's own copy of the registers, for a store to a register nobody told `gba_clock_written` of, as a library that writes them directly does; a DMA channel's address that points into that copy, as a sound channel's to its FIFO does, is the console's register there. `gba_clock_divsi3` is a division by the compiler's own library, whose path through its loops the two numbers decide, and `gba_clock_vcount` the line the display is on by the console's time, for a game that waits for one.

The m4a sound library says which of the original's instructions each of its power-on's runs was, for a game whose `twins.h` names its functions ([`lib/m4a/m4a_console.h`](lib/m4a/m4a_console.h)), so a game made the stricter way times its sound's start without a line of its own.

`npm run test:clock` measures it against mGBA with a program of the project's own, [`tools/test/clock/power-on.s`](../../../tools/test/clock/power-on.s), in a made-up cartridge: `tools/gba/clock-check.c` runs it in the emulator and the clock beside it, an instruction at a time, and every instruction has to start at the same time by both, every frame end after the same instruction, one while a DMA holds the processor and one inside the BIOS's CpuSet. It then leaves a frame untimed and resumes the clock after it, and every instruction from there has to start at the emulator's time too. On 19 November 2026 it gave the same for all 162,163 instructions and 8 frames of that program, and, with a copy of Sonic Advance (USA) here, for all 380,138 instructions outside the BIOS of its power-on, frames 0 to 5, whose ends fall inside a video memory fill by DMA, the BIOS's CpuSet, the sound engine's MPlayOpen, TasksInit and a delay loop. The same day its stricter-way trial, timed as above, ended each of those six frames on the same instruction and cycle as the emulator, which no count of its own decides: the division's path, the line count and the calls only say which instructions ran, and the test above times each one.

## The console's stack

A game that keeps the console's memory can also keep its stack as the original's functions leave it (`stack.c`), for a function that reads stack it never set. The build adds the calls from the game's own C (tools/README.md, The console's stack): `gba_stack_start(sp)` where the console's start leaves the stack pointer, `gba_stack_call(return_address)` and `gba_stack_reg(reg, value)` before a call, `gba_stack_enter(&frame)` at a function's start, which writes its pushes below the stack pointer, and `gba_stack_leave`, run as it returns, which leaves them there. `gba_stack_local(at)` is where the function's local at `at` from its frame's start is, at the console's own address. A push whose value nothing gave leaves the bytes as they were, and `gba_stack_gaps()` counts them. A frame's `unproven` is `GBA_STACK_UNPROVEN` for a function whose code isn't the original's, which takes its frame's room and writes nothing, and `GBA_STACK_START_PROVEN` for one whose start is: its pushes are written, and the registers it doesn't push keep their values in it. A game that keeps some of the console's memory away from the console's address, as the kit keeps a save's flash, gives `gba_stack_addresses(console)` a function that turns a pointer of its own into the console's address, and a pointer goes on the stack through `gba_stack_address`. A build that never calls `gba_stack_start`, as the function check's, has every call cost nothing.

## The console's own sound engine

A game whose every function is a twin of the original's runs the console's sound engine itself, in the console's memory, and the kit's own engine has nothing to do. `gba_sound_console()` makes the kit only the sound hardware: the game gives it each sound register as it writes it, `gba_sound_console_write(reg, value)` for `0x60` to `0x9F`, and once a frame the samples the console's DMA feeds FIFO A and FIFO B during it, `gba_sound_console_samples(a, b, count)`. The m4a library says each register it writes, `console_wrote(where, bytes)`, for a version that plays its sound to hand on ([`lib/m4a/m4a_console.h`](lib/m4a/m4a_console.h)). `npm run test:sound-console` tries it with a program of the project's own: a FIFO's samples at their level, silence in a frame with none, a square wave started through the chip's registers, and silence with the sound off. It plays with the game, as the proof tools take it; a player's browser, where the audio thread plays the sound, doesn't have it yet.

## How it's checked

`npm run test:c-kit` draws 400 made-up scenes, with every mode, layer, window, colour effect and kind of sprite, and H-blanks that change registers and colours between lines, with `video.c` built for the computer and as WebAssembly, and with `video.js`, and fails on any pixel that differs. `SEED` and `SCENES` choose other scenes, and a failure names the scene to draw again. Then it builds the C starting point and plays 240 frames of made-up presses, on the computer and in Chrome a frame at a time as the proof tools play a game, and fails on any frame whose picture or video hardware differs from the JavaScript starting point's. It also checks that the save memory lasts from one run, and one visit, to the next. Then it plays songs on both sound engines, the C one as WebAssembly, a frame at a time with the same calls, and fails on any sample that differs: made-up songs on made-up cartridges, with every kind of voice and the commands that change them, each alone and with a game's calls between frames (`SONG_RUNS` says how many runs), and, with a copy of Sonic Advance here, every one of its songs (`COPY_FRAMES` frames of each). Its copy is read where it is, and nothing from it is kept. `npm run test:game` tries the C starting point's page as it tries the JavaScript one's: the start screen, the keys, a controller, the settings and the touch screen.
