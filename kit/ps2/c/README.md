# PlayStation 2 kit in C

[Back to the kits in C](../../c/README.md) · [Other consoles](../../../docs/CONSOLES.md) · [The Dreamport standard](../../../docs/STANDARD.md) · [Written in: #618](https://github.com/NahuelGenchi/dreamports/issues/618)

This folder is the PlayStation 2's kit for games written in C, on what [every console's kit in C](../../c/README.md) shares. A game writes the console's graphics chip, the GS, as its original does, and does its float sums as the console's processor, the EE, does them. A game made [the stricter way](../../../docs/STANDARD.md), each function a twin of one of its original's, builds its original's DMA chains and writes the console's registers where its original does, and the kit's DMA controller, VIFs, vector units and GIF do what the console's do with them. What it writes each frame is its **draw list**, which is what a 3D game is proven by ([How progress is measured](../../../docs/STANDARD.md#how-progress-is-measured)), and the kit draws that list for the page. Its twins of the game's own modules for the second processor, the IOP, write the sound chip, the SPU2, as the original's do, and the kit mixes the chip's sound as the console's emulator does, sample for sample.

Like the rest of the kits it's under [GPL-3.0-or-later](../LICENSE), and nothing from any game is in it. It's written from how the console is documented to behave.

## Writing a game on it

A game includes `"ps2.h"` and defines the four functions every game in C does ([A game on a console with no kit of its own](../../c/README.md#a-game-on-a-console-with-no-kit-of-its-own)). `npm run dp -- new <game>/c` writes a starting point that shows a blue screen through the GS.

`gs_write(reg, value)` writes one of the GS's registers, as a GIF packet's address and data does: `GS_PRIM`, `GS_RGBAQ`, `GS_XYZ2` and the rest. `gs_image(data, length)` sends it a picture's data. `gs_screen(address, value)` writes half of one of the registers that say what the screen shows, at the address the EE sees it. `game_draw` calls `gs_show()`.

**Pictures read back.** A game that reads a picture back from the GS, as a screenshot or a buffer used as data does, starts the transfer as on the console, BITBLTBUF's source, TRXPOS, TRXREG and TRXDIR = 1, and takes its bytes with `gs_read_image(data, length)`, as VIF1's DMA does once BUSDIR is 1. They come in the console's order, each pixel's bits after the last's, so a 24-bit picture is three bytes a pixel and a 4-bit one two pixels a byte.

**The GS's status.** `gs_screen_read(address)` reads CSR, IMR or SIGLBLID as the EE does, and `gs_screen` writes them, a 1 in CSR's low bits clearing that event. SIGNAL and LABEL put their IDs into SIGLBLID where their masks say, and SIGNAL and FINISH set their bits in CSR. `gs_on_interrupt(handler)` gives the GS's interrupt the game's handler for INTC_GS, which the kit calls as SIGNAL or FINISH is written, or as a V-blank starts, when IMR lets the bit through, and when IMR unmasks an event already in CSR, as the emulator does. Each frame starts with a V-blank: VSINT and HSINT are set, and FIELD is the field it starts. Where the console's values are unknown, they are the emulator's: revision 7 and no ID in CSR, every event masked in IMR at first, and 0xCCCCCCCC from a register the EE can't read. A SIGNAL written while CSR's SIGNAL is still set holds the console's GIF up until the game clears it, which the kit, drawing as it's written, doesn't. HSINT comes once a frame rather than at every line's end, and FIELD turns over as the next frame starts, where the console turns it once the V-blank ends: the kit's GS keeps no time within a frame.

**Packets.** A game that builds GIF packets, as nearly every real one does, hands them over as they are: `gif_send(data, bytes)` as a DMA transfer to the GIF does, and `gif_packet(data, most)` for one packet to the tag that ends it, as a vector unit program's XGKICK does. The kit turns each tag's PACKED, REGLIST or IMAGE data into the GS's writes the way the console's GIF does, so the draw list is the same as the original's, down to the Q an ST leaves for the next RGBA and the corners written without drawing.

**The EE's memory and registers.** `ee_memory()` is the EE's main memory, 32 MB, and `ps2_scratchpad()` its scratchpad. `ps2_read32`, `ps2_write32` and their 64 and 128-bit kin read and write what the EE's code reaches at an address: that memory, the vector units' memories, and the registers of the DMA controller, the VIFs, the GIF and the GS's screen, by the names `ps2.h` gives them (`DMA_VIF1 + DMA_TADR`, `VIF1_STAT`, `GIF_FIFO`). A DMA address is an offset into main memory, as on the console, so a game builds its chains there and gives the controller their offsets.

**DMA.** Writing a channel's CHCR with STR set starts it, and it runs then and there: QWC quadwords from MADR in normal mode, or in chain mode the tags from TADR, each kind of them (CNT, NEXT, REF, REFS, CALL, RET, END, REFE), with a tag's second half sent on when TTE is set and a tag's interrupt bit ending the chain when TIE is. What holds a transfer up on the console holds it up here, such as PATH3 masked, and it goes on when that's gone. The channels to the scratchpad copy to and from it, interleaved too. The channels to the IPU and the second processor keep what's written to them and move nothing.

**A unit's program in C.** A Dreamport runs no microcode of its original's: each program a game uploads to a vector unit is written again in C, and `vu_program(unit, address, program)` gives the kit that C for the program's place in the unit's code memory. From then on the VIF's MSCAL, MSCALF and MSCNT, VCALLMS and a write to CMSAR1 run the C there in place of the unit's own program, and the C gives back where the program stops. Until a game gives one, the kit runs what is in the unit's code memory, which is how the kit itself is proven. The C works on the unit's own registers and memory (`vu_vf`, `vu_acc`, `vu_vi` and `vu_set_vi`, `vu_q`, `vu_p`, `vu_i`, `vu_r`, `vu_data`), with the unit's sums and their flags (`vu_sum`, `vu_sum_with`, `vu_outer`, `vu_clip`, `vu_div`, `vu_sqrt`, `vu_rsqrt`), `vu1_kick` for XGKICK, and `vu1_xtop` and `vu_xitop`. It has no pipeline: each line's result and flags are there for the next, so a program that reads a flag or Q before its instruction's result is there keeps the value from before itself. `npm run dp -- twin` checks each against the original's program ([the function check](../../../tools/README.md#the-function-check-on-the-playstation-2)). Not there yet for a program in C: the EFU's sums, the random number's instructions and FSSET.

**The VIFs.** VIF0 feeds vector unit 0 and VIF1 vector unit 1, from their DMA channels or their FIFOs. Every code is here: UNPACK in every format, signed and not, through the mask, the row and the column, adding the row or keeping a running sum as STMOD says, written, skipped and filled as STCYCL says, and at TOPS when it's asked; MPG; MSCAL, MSCALF and MSCNT; BASE, OFFSET and ITOP, with the two buffers TOPS turns between; DIRECT and DIRECTHL, which send packets to the GIF; MSKPATH3; FLUSHE, FLUSH and FLUSHA; MARK, and the stall a code's interrupt bit asks for. A command whose data runs over the end of one transfer goes on in the next.

**The vector units.** A program put in a unit's code memory runs as the console runs it, an instruction pair at a time: every upper and lower instruction, with RSQRT, CLIP, the EFU's sums, the whole-number sums, branches with their delay slot, XGKICK, XTOP and XITOP. What a program can see of the unit's pipeline is kept: a float result is there four cycles after its instruction, and one that reads it sooner waits; the MAC, status and clip flags are as the instructions four cycles before left them, FSSET's and FCSET's too; Q changes seven cycles after a division or thirteen after RSQRT, with the status flag's division and invalid bits, and P when an EFU sum ends, and one read sooner is the old one; WAITQ and WAITP take the cycles they wait; and a branch right after a sum on its register tests the register as it was. XGKICK's packet goes to the GIF once the pair after it has run. A program runs to its end as it's started, so what it gives the GS comes where the console's comes among the rest.

Vector unit 0 also takes the EE's COP2 instructions one at a time: `vu0_macro(instruction)` with the original's 32-bit word, `vu0_vf(n)` for a register as QMFC2, QMTC2, LQC2 and SQC2 reach it, and `vu0_cfc2` and `vu0_ctc2` for its control registers.

A Dreamport can instead write a unit's program again in C, an instruction a line, with `vu_vector` for its registers and `vu_add`, `vu_madd`, `vu_mulf`, `vu_ftoi` and the rest for its sums, each on the fields its instruction names (`VU_XYZ`, `VU_XYZW`), and hand its packet to `gif_packet`. An instruction that takes one field, Q or I, such as MULAx or MULq, is the `f` form with that float. DIV is `ee_div`, SQRT `ee_sqrt`.

**The GIF's paths.** Packets reach the GIF by three paths: PATH1 from vector unit 1's memory, as XGKICK sends one, PATH2 from the VIF's DIRECT, and PATH3 from the GIF's own DMA channel or its FIFO. While one path is partway through a packet the others wait, PATH3's data in the FIFO, and PATH3 can be masked, by MSKPATH3 or GIF_MODE. The kit orders them as the console's emulator does, down to the one packet it lets through as PATH3 is unmasked, so the draw list has the three paths' writes in the original's order.

**The draw list.** Everything a game writes in a frame is hashed in the order written, the same way the proof tools hash what the original gives the GS in its emulator ([`tools/libretro/play.patch`](../../../tools/libretro/play.patch)): each register write as its register and its 64 bits, each picture's bytes, and each half written of PMODE, SMODE2, DISPFB and DISPLAY. A game whose `proof/original.json` says `"provenBy": "draw lists"` is compared by that hash, frame for frame, where another game is compared by its picture. So the order matters as much as the values: a game writes what its original writes, when it writes it. The kit also keeps each frame's whole list, up to 16 MB, which `prove` compares with the original's to say which write of a frame differs ([Proving](../../../tools/README.md#proving)). What a game writes in `game_start`, as it sets up its screen, is in no frame's list.

**The console's floats.** The EE's FPU and the vector units don't follow the rules a computer's floats do, and a Dreamport that used plain `+` and `*` would have a model's corner a sixteenth of a pixel out within a hundred frames. On the console there is no infinity and no NaN: a float whose exponent is all ones is an ordinary number, and a result too large is the largest float there is, 0x7FFFFFFF with its sign. A float tinier than the smallest ordinary one counts as zero. A sum is cut towards zero, never rounded, and keeps only one bit of the smaller number below the larger's last, so 1 minus something tiny is 1. A product comes from the multiplier's own circuit, which drops low bits on its way, so 1 times 0x3FFFFFFF is 0x3FFFFFFE. A quotient and a root come a digit a step from the divider's circuit, and their last bit is what its digits leave. A division by zero gives the largest float. `floats.c` has these rules, and says where each comes from: Sony's manuals, the circuits as PCSX2's soft-float work models them, and what a console itself gives.

So a twin of the EE's code does its float sums with `ee_add`, `ee_sub`, `ee_mul`, `ee_div`, `ee_sqrt` and `ee_rsqrt`, the accumulator's with `ee_adda`, `ee_madd` and their kin, compares with `ee_c_eq`, `ee_c_lt` and `ee_c_le`, and turns a float into a whole number with `ee_to_int`. Each keeps the FPU's flags in `ee_fcsr` as the console keeps them in FCSR: overflow, underflow, division by zero and invalid, each with the sticky flag that stays until the game clears it, and the condition bit.

**The EE's 128-bit integers.** `mmi.h` has a function for each of the EE's multimedia instructions, named after it (`ee_paddsw`, `ee_pextlh`, `ee_pmaddh`, `ee_qfsrv`), on an `ee_quad`, with HI, LO and SA kept as the console keeps them.

## The IOP and its sound

A game's own modules for the IOP, such as its sound driver, are written again as twins that write the IOP's hardware at the addresses the original's do: `iop_write16(0xBF900000 + register, value)` for a register of the SPU2, `iop_write32` for a DMA channel's, and `iop_read16` for what the chip says, with `iop_memory()` the IOP's 4 MB, as the emulator has them. A transfer to the chip goes through channel 4 for core 0 and channel 7 for core 1, from the IOP's memory, as the original's does.

**The sound list.** Everything the chip is given in a frame is hashed in the order given, the same way the proof tools hash what the original gives it in its emulator ([`tools/libretro/play.patch`](../../../tools/libretro/play.patch)): each register write as its address and the value written, each DMA transfer as its core, its mode and its bytes, and each block of 48 samples the chip mixes. A PlayStation 2 game's sound is proven by its sound list and by every sample the kit mixes from it being the original's ([How sound is compared](../../../tools/README.md#how-sound-is-compared)). The blocks in the list are what makes the time a write lands part of it.

**The time.** The emulator runs the console in slices of 4,800 of the EE's ticks, and mixes 48 samples, a thousandth of a second, at the top of a slice when their time has come: 16 or 17 blocks a frame, 15 in the first. The kit keeps the same time from power-on, so its blocks fall where the emulator's do. What a game's IOP code writes as a frame starts, as a driver woken by the V-blank does, comes before the frame's first block, and `ps2_time_pass(ticks)` lets the EE's ticks pass first for one that writes later.

**The chip.** `spu2.c` mixes the chip as the console is known to mix it, 48,000 samples a second. Each voice's ADPCM is decoded four samples at a time from the chip's memory as it's read, so what a game writes is heard from the next samples decoded, and a voice nothing has keyed on still moves through the memory, setting its end flag and tripping the interrupt address as it goes. Between samples a voice is stepped by the chip's own four-point table. Its envelope and its two volumes move by a counter, a step each time it fills, linear or exponential, up or down. Every volume is a product shifted fifteen bits. A core's noise generator steps at the pace its control sets, and a voice can bend the next one's pitch. Each voice has four mixing switches, dry and reverb, left and right, and each core twelve more for its voices, its sound input and, on core 1, core 0's output. The reverb works in whole numbers at half the rate, one side each sample, through two filters of 39 weights. A core's sound input is read from its buffer in the chip's memory, and the chip writes back into its memory what voices 1 and 3 and each core's sums give, where the interrupt address can be. The chip's memory starts as the console's own start-up leaves it, with a block that ends and loops at once where every voice begins.

The tools' emulator, Play!, mixed the chip its own way: 44,100 samples a second, straight lines between samples, tables of its own for envelopes, a reverb in floats, and decoded blocks it kept after a write. So the tools build this file into Play! in place of its chip ([`tools/libretro/play.patch`](../../../tools/libretro/play.patch)), and the original and a Dreamport are mixed by the same code: what a proof compares is what each gave the chip and when, and every sample that came of it. What the IOP sees of the chip stays as Play! has it, since a game's own sound driver runs against that in a proof: the registers' places, the data port, DMA and when a core takes it, and the interrupt flags.

**Checked against a second emulator.** The mixing follows PCSX2's SPU2, under the GPL as the kit is, and `npm run test:ps2-spu2` runs PCSX2's own source beside the kit's chip on what the sound test's program gives the chip: all 239,904 samples of 300 frames are the same, and so is every word the two leave in the chip's memory. Four things are not PCSX2's, each for the console's sake. PCSX2 keeps one decoded copy of a block for every voice on it, so a voice keyed on again and one that looped to the same block hear each other's decoding; the kit decodes for each voice, as the console does, and the test's voices each have their own copy of the tone so the two can be compared. PCSX2's reverb filters are compared in its plain version, which it keeps beside faster ones that round each weight. PCSX2 starts core 1 with core 0's output going to its reverb and not to its dry mix until a game sets the switches, where its own note of the console's register says the other; the kit starts from the register. And a core's mute bit and the modes that pass sound straight to the digital output aren't done, in either.

## The SIF

A game's EE code reaches the IOP through the SIF, as the console's emulator, Play!, has it: what the EE sends to the IOP's command buffer is read as a command, and the IOP's replies queue up and reach the EE's memory one at a time as the EE's ticks pass, each once the EE says it took the last. A twin of a game's SIF library calls the EE kernel's calls as the original does: `sif_set_dma` for SifSetDma, `sif_dma_stat`, `sif_set_dchain`, `sif_get_reg` and `sif_set_reg`, with what it sends in `ee_memory()`, the EE's 32 MB, at its own addresses, and `sif_ee_handler` for what runs as a packet arrives, the EE's DMA channel 5 handler. A twin that waits for the IOP lets the EE's time pass, `ps2_time_to_slice()`, as the IOP only runs at the end of the emulator's slice.

On the IOP, the kit stands in for the loader, as Play! does: when the EE has it load a module, by the path or from the IOP's memory, it starts the Dreamport's twin of that module, registered with `iop_module_twin(name, start)` by the name the module's file gives itself or the path it's loaded from. A twin's thread that waits for each V-blank, `iop_each_vblank`, runs when the IOP first runs in each frame, before the frame's first block of sound, and a twin's own RPC server, `sif_register_rpc(id, function, buffer)`, is called as Play! calls a module's: the arguments copied into its buffer in the IOP's memory, its function run when the IOP next runs, and the answer copied back from where it says. A server number the kit already answers stays the kit's, as in Play!, where a game's own memory card server never takes over from Play!'s.

## The pads

A game's own pad modules reach the pads through the SIO2, at 0x1F808200 on the IOP, a command a byte at a time or by DMA on channels 11 and 12, and the kit answers as Play!'s SIO2 does: a DualShock 2 in each of the two ports, which says what it is, goes into its configuration, is set to digital, analog or pressure mode, and is read for its buttons, both sticks and the pressure on each of twelve buttons. Play! is given each frame's buttons by the tools as held or not, and the left stick as all the way over or not at all, so a button's pressure is all or nothing and the right stick stays in the middle, and the kit gives the same from the buttons `dp_step` is given. There's no multitap, as Play! says, and a memory card asked for on the SIO2 answers as Play!'s does, which reads back nothing real: memory cards go through Play!'s own server.

The emulator gives the pad a frame's buttons as the frame starts, so a PlayStation 2 game's `original.json` says `"keysAfterVBlank": true`, or its original reads each press a frame before its Dreamport does.

## The disc

A game's EE code reads its disc through the IOP's RPC servers, which Play! answers itself, so the kit answers them the same way (`cdvd.c`): the drive set up, the kind of disc, the clock, the layers, the drive's status, the disc ready, a file searched for by its path, and sectors read into the EE's memory or the IOP's, in a chain, or streamed. A read is answered after the time Play! gives it, 100 microseconds and 500 for each sector, and the rest after a sixtieth of a second, and a read's bytes are in memory only then. A file is found as Play! finds it: its folders through the disc's path table, and its name as the start of an entry's, whatever its case. The sectors come from the player's disc a few at a time ([The player's disc](../../c/README.md#the-players-disc)), so a game that reads its disc runs under `kit_run`, in `game_start` and `game_step` alike, and `ps2_disc_sectors` reads sectors for what the console's loader does before a game's own code runs, such as putting its program in memory.

The clock is the console's as the tools' emulator keeps it, the same in every run: from the first second of 2001, on by its V-blanks. A disc's kind is the disc's own: a CD kept as an ISO file is a CD, where Play! took any file of 2048-byte sectors for a DVD, which the tools' patch puts right in it too.

## The memory cards

A game's EE code reaches its memory cards through an RPC server too, which Play! answers itself even when a game loads its own memory card modules, so the kit answers it the same way (`mc.c`). A card is always in each port, formatted, with 8 MB free. Files are opened, made, read, written, moved in, flushed and closed, five open at once at most; folders are made, gone into and listed, a few entries at a time, by a pattern with `?` and `*`; entries are renamed and deleted. Each answer comes back 100,000 of the IOP's ticks after the call, and what Play! gets wrong it gets wrong here too: a name with `:` or `\` in it is found when it's opened and not when it's deleted, as Play! keeps such a name another way and only looks for it that way in some calls.

An entry's time is the console's clock at the call that last changed it, and what was on the card as the game started has the clock's first second. The tools' patch makes Play! list a folder in the order of its names, where it took the computer's own order, which differs from one computer to the next.

The cards are the player's: the page keeps them in the browser, as the same bytes the proof tools compare with the original's ([`kit/ps2/card.js`](../card.js)), and gives them back to the game the next time it starts.

## What it doesn't do yet

The draw list is whole: anything a game writes is in it. What the kit draws of it is most of what a game's screens need, not all of it.

**Its memory.** The GS's 4 MB are kept as the chip keeps them: 8 KB pages, each 32 blocks of 256 bytes, each block 4 columns, with every format's pixels in its own order in each, 32, 24 and 16-bit colours, 32, 24 and 16-bit depths, and 8 and 4-bit indices, alone or in a 32-bit pixel's top byte. So a buffer written in one format and read in another holds what the console's would, as a game's own picture used as a texture, a depth buffer read as colours or a palette in a picture's corner do.

**What it draws.** Points, lines and line strips, sprites, and triangles as lists, strips and fans, in one colour or shaded between their corners, into a framebuffer of 32, 24 or 16 bits, with a depth buffer of 32, 24 or 16 bits, inside the scissor. Pictures move into its memory as a game sends them, out of it and from one place in it to another, in the order TRXPOS's DIR says. Points are the pixel their place is nearest. A shape in the fog (FGE) goes towards FOGCOL by its corner's fog, FOG's or the last XYZF's, and into a 16-bit framebuffer DTHE adds DIMX's numbers to each colour before COLCLAMP keeps it in range. PRMODE gives a shape its attributes when PRMODECONT says, FBMSK and ZMSK keep bits of the framebuffer and the depths, and SCANMSK keeps a shape off every even or every odd line. Textures are 32, 24 or 16-bit, or 8 or 4-bit with a 32 or 16-bit palette, which TEX0 or TEX2 loads into the palette buffer as its CLD says, from a block or a row, into the place CSA names. A texture is placed by whole texels or by floats over Q, sampled nearest or between the four nearest as TEX1 says, meets its edges in the four ways CLAMP says, and meets the shape's colour by any of the four texture functions, with TEXA giving 24 and 16-bit texels their alpha. Pixels go through the depth test, the alpha test with what's written of one that fails, the test of the framebuffer's alpha, and blending, with PABE, FBA, COLCLAMP and the framebuffer's mask.

**Matched pixel for pixel.** Sprites, flat or textured: at their size, larger, repeating, by floats, with 8 and 4-bit palettes, as a decal, blended, and with the alpha test, into a 16-bit framebuffer. The memory's layout: pictures moved in in nine formats and read as textures in eight, and as pictures read back in eight, three of them depths, palettes of 32 and 16 bits in blocks and in a row, in the buffer's places and loaded by every CLD. A sprite drawn through context 2 by PRMODE, FBMSK by whole bytes, and ZMSK under the depth test. A shaded triangle isn't: on the test's 3D program about a tenth of the still triangle's pixels are a step of colour away from the emulator's. A texture sampled between texels isn't either, as the emulator's graphics card weighs them its own way.

**Textures by their size.** A texture is sampled nearest or between its four nearest texels, by sixteenths as the chip weighs them, and from its smaller copies (mipmaps), whose places MIPTBP1 and MIPTBP2 give, up to MXL of them. The level of detail is K where LCM says so, or the logarithm of 1/Q shifted by L, plus K: at 0 or less MMAG filters the texture itself, and above it MMIN picks the copy the level rounds to or mixes the two it's between.

**Antialiasing.** With AA1 a line's or a triangle's edge pixels take how much of them is covered as their alpha and are blended in by it, whether ABE says so or not, and write no depth. Which pixels a line has, which an edge has and how much is covered follow PCSX2's software renderer, written again here, as do copies of a picture onto itself.

**What the screen shows.** Both read circuits, each with DISPFB's buffer in DISPLAY's rectangle, circuit 1 over circuit 2 or over BGCOLOR (SLBG), by ALP or by its own alpha (MMOD), with BGCOLOR wherever neither shows. On a screen interlaced in frame mode each of the buffer's lines is shown on two.

**Not done.** MTBA, which works the smaller copies' places out by itself, PMODE's AMOD and CRTMD, which the picture doesn't change with, and the feedback write circuit. Between two copies with the level fixed by K, the kit mixes them as the GS's manual has it; PCSX2 there mixes red and green and leaves blue, and paraLLEl-GS takes the larger alone.

**The strict reference.** Where the emulator, Play!, can't draw exactly, the kit's pictures are checked against PCSX2's software renderer too, the strictest free GS there is ([Other consoles](../../../docs/CONSOLES.md#the-playstation-2)): the Dreamport runs on the computer, everything its GS was given is replayed by PCSX2, and each frame's framebuffer has to be the same in every bit, alpha too. PCSX2 has to draw it the same whichever of the processor's instructions it's told to use, as well, since what varies across a shape, a shaded triangle's colours and depths, it draws a step of colour apart on thousands of pixels from one to another: only what it draws the same is an exact reference.

**What varies across a shape.** For that no free GS is exact: PCSX2 differs from itself, Play! more, and paraLLEl-GS from both. So the proof there, the owner's choice (#1590), is the same pixels covered as PCSX2's software renderer and every channel of every pixel within one step of it, which is as far as PCSX2 is from itself, with the draw list still exact. Proven that way, all 300 frames with no pixel further: lines every way round and line strips, triangles in lists, strips and fans, shaded and in one colour, in the fog, blended, textured by whole texels and by floats over Q, under the depth test, all of them antialiased too, a sprite placed by floats between texels, and triangles whose level of detail comes from Q. Two things stay outside it. Where two triangles cross in depth a pixel can go to either, as it does between PCSX2 and itself. And a place worked out in floats on the border of two texels can take either, so those checks use a texture a step of colour from texel to texel; what's placed by whole texels, sprites magnified between texels and drawn from every smaller copy, is checked on a texture of every colour and is exact. Matched that way, all 300 frames: both memory programs, the events and modes programs, SCANMSK and FBMSK bit by bit, which Play! doesn't do, and what Play! keeps on its graphics card: a picture the GS drew and its 16-bit depths read as textures in seven other formats and read back, the 16-bit depths' two layouts, and pictures copied within memory, onto themselves in each of TRXPOS's orders, before and after their source and more than a page away, and into another layout. Sprites in the fog, dithered and blended past a byte's range with COLCLAMP on and off, and points at every sixteenth of a pixel, flat, textured and in the fog, into 32 bits and 16. A copy onto itself follows the order PCSX2 found games to need, as the chip copies through a buffer: backwards when its destination starts after its source within the source's page.

**Held to a console's own results.** The last bit of a float sum is what Sony's manuals leave unsaid, so the kit's are held to what a console printed: the [ps2autotests](https://github.com/unknownbrackets/ps2autotests) project's programs, run on a PlayStation 2, with 1,098 sums of the FPU and the EFU and their results ([`tools/test/ps2-console-floats/`](../../../tools/test/ps2-console-floats), under its ISC licence). `npm run test:ps2-ee-vu` gives the kit each one first, and 1,094 come out with the console's bits ([#1622](https://github.com/NahuelGenchi/dreamports/issues/1622)). What made them so: the multiplier and the divider as circuits, which PCSX2's soft-float work models ([PCSX2/pcsx2#12001](https://github.com/PCSX2/pcsx2/pull/12001), GPL-3.0-or-later, written again in `floats.c`) and the console's results bear out in every product, quotient, root and RSQRT; the sum's one guard bit, which Tri-Ace's sums bear out; a product too large in MADD and MSUB, which gives the largest float whatever ACC holds; the FPU's MAX and MIN, which put minus zero under zero; and the order ESIN, EEXP and the arctangents work their series out in, found by trying the orders against the console's results, as no document gives them. Against the exact answer cut, which the kit gave before, a product is a last bit away once in 900, a quotient in 38 of 100 and a root in 24 of 100.

**Still not the console's.** EATAN of zero, four results: the console gives 0x33E60000 and the kit 0x34000000, and no order of the manual's formula gives the console's. EEXP's 16 results are the same whether its powers are made by multiplying by the number again or by squaring, so they don't say which the unit does: the kit multiplies again. The root of minus zero raises nothing here, where PCSX2's model raises invalid, and no console result in hand says which. The vector units' MAX and MINI order as Play! has them, with nothing from a console to hold them to. PCSX2's own soft-float code hasn't been run beside the kit: its circuits were read and written again, and it is the console's results that the kit is checked against.

The console's emulator in the proof tools is given the same float rules, the flags and the timing above (`tools/libretro/play.patch`), so a proof compares like with like. Three things it still does its own way, which a proof of a game that leans on one would show: a vector unit's EATAN, which it doesn't have; how far back a branch looks for its register as it was, which it counts as four instructions and no further than the start of its own run of code, where the kit counts four cycles; and a float result's wait worked out from where an instruction is in its block, which can be a cycle or two out right after WAITQ or WAITP when the next instruction reads a result made just before the wait.

Eight of the EE's multimedia instructions the emulator leaves out, PMADDW, PMSUBW, PMSUBH, PADSBH, PMADDUW, PDIVUW, PMFHL.SLW and PMTHL.LW: `mmi.h` does them as Sony's manual says, and a game that uses one can't be proven on it until the emulator has it. The DMA controller's ring buffer (MFIFO) and stall control are written as the emulator does them and haven't been tried against it, and GIF_MODE's mask of PATH3 is the console's, which the emulator doesn't have. A vector unit's program runs whole as it's started, so EE code that reads VPU_STAT or a VIF's status to wait for one finds it done, and a write to SIGNAL that the GS hasn't been asked about doesn't hold the GIF up. A picture read back from the GS through VIF1's channel is moved as the emulator moves it, which this check doesn't try.

On the IOP there's its memory, the sound chip and its DMA, the SIF and the loader, but not yet the rest of its kernel (semaphores, events, timers, interrupts and threads other than those that wait for the V-blank or serve calls), files opened by name through the IOP (`fileio`), a memory card read with the fast read some games' libraries use (call 0x16), cards bigger than the few megabytes the browser keeps of them as they're kept now, a file searched for on a DVD's second layer, nor a reset of the IOP with a game's own replacement modules. The order the IOP's threads run in within a slice is the V-blank's, then the servers', where Play! runs them by their priority. The PlayStation's own sound chip registers, which the emulator also lets a game reach, are in the sound list but don't play. A game can still add sound of its own with `game_sound`, which no proof hears.

## How it's checked

`npm run test:ps2-kit` writes the two small programs of [`tools/test/made-up-ps2.mjs`](../../../tools/test/made-up-ps2.mjs) as Dreamports in C ([`made-up-ps2.c`](../../../tools/test/made-up-ps2.c)) and proves them against the console's real emulator. The one in three dimensions is proven by its draw list, all 300 frames, and one that does a sum with a computer's rounding is found, at frame 81. The one whose square a program on vector unit 1 turns, divides by its depth and kicks to the GS as a PACKED packet is proven by its draw list too, all 300 frames, its Dreamport being that program written again in C with `vu_*` and `gif_packet`, and one that divides with a computer's rounding is found at once. With the 3D Dreamport's one sum done a computer's way, `prove` names the write that differs at frame 81: write 20 of 24, the turning triangle's first corner, a sixteenth of a pixel across from the original's. The textured one sends its textures, palettes and sprites as packets, and its Dreamport sends the same through the kit, so its pictures, proven pixel for pixel on all 300 frames, are the kit's drawing against the emulator's: with the palette's layout broken it differs at once. The flat one is proven by its pictures, pixel for pixel.

`npm run test:ps2-gs` does the same for the programs of [`tools/test/made-up-ps2-gs.mjs`](../../../tools/test/made-up-ps2-gs.mjs), each a list of steps its Dreamport in C does through the kit ([`made-up-ps2-gs.c`](../../../tools/test/made-up-ps2-gs.c)), proven by draw list and by pictures, all 300 frames. The memory programs move pictures in in one format and read them in others, as textures into a 32-bit framebuffer and a 16-bit one, and read 32 by 32 pixels back in eight formats every frame, which go back in as pictures, so the draw list holds every byte read: one whose Dreamport doesn't read back differs at once. They come in two because the emulator widens a 16-bit colour to 32 bits its own way, and so draws a 16-bit colour exactly only into a 16-bit framebuffer. The events program sends SIGNAL, LABEL and FINISH every frame, with a handler for the GS's interrupt that clears SIGNAL and counts it, and draws a sprite in the colour of each value it reads of CSR, SIGLBLID and IMR, and of the count, so the draw list holds them all. The modes program draws through context 2 by PRMODE, with FBMSK and with ZMSK.

`npm run test:ps2-sound` does the same for the IOP: a program of the project's own whose EE loads its own IOP module through the SIF, and the module plays a tone and a click on both of the chip's cores, with envelopes, a pitch that moves every frame, two volume sweeps, the reverb, a voice of noise, a voice bent by the one before it, master and effect volumes with a master sweep, and keys let go of and keyed on again, has an RPC server of its own that the EE calls every frame, and reads the pad through the SIO2 every frame, writing what it says where the sound chip takes no notice, so the sound list carries it. The EE writes everything the SIF gives it into GS LABEL writes, so its draw list carries them: what SifGetReg says of the SIF's registers, the ids SifSetDma gives and what SifDmaStat says, every word of the IOP's replies, and the server's answers. Its Dreamport in C, the EE's code and the module written again with the kit's SIF and IOP, has the same draw list and the same sound list, and the kit mixes every sample the emulator does, all 300 frames. One with its pitch a step out on one frame is found on that frame by its sound list, and one that asks SifDmaStat before the IOP has answered is found at once by its draw list. A second recording holds every button and each way of the left stick in turn: all 300 frames match, and a Dreamport that doesn't read the pressure is found on the first frame a button is held.

`npm run test:ps2-spu2` checks the chip itself against PCSX2's, as [The IOP and its sound](#the-iop-and-its-sound) says: the sound test's program runs on the tools' emulator, which keeps every register write and every byte moved to the chip, and a small program gives them to the kit's chip and to PCSX2's mixer, built from PCSX2's own source at a commit the test names. Every sample and every word of the chip's memory is the same, and a chip that divides by a volume's top in place of the console's shift is found on the first frame.

`npm run test:ps2-disc` does the same for the disc drive, on a disc of the project's own whose program asks the drive's servers about the disc, finds a file and reads one of its sectors each frame, keeping every answer in its draw list: its Dreamport, reading the same disc through the kit, matches on all 300 frames, and one that reads the sector after the one asked for is found at once.

`npm run test:ps2-cards` does the same for the memory cards: a program of the project's own sets the server up, finds the card, makes folders and files, writes and reads them back, lists a folder a few entries at a time and by a pattern, renames, deletes, and each frame writes a file again and lists its folder, keeping every answer in its draw list. Its Dreamport matches on all 300 frames, each entry's time moving with the console's clock, and its cards hold what the emulator's do, byte for byte. One that writes the next frame's number gives every answer the same and is found by the card it leaves. The program's start takes eight frames of calls, which showed how the emulator runs a program's wait for the IOP: a reply that comes later is seen a slice after it arrives.

`npm run test:ps2-ee-vu` checks the EE and the vector units against the same emulator, with a program of the project's own ([`tools/test/made-up-ps2-ee-vu.mjs`](../../../tools/test/made-up-ps2-ee-vu.mjs)) and its Dreamport, a twin of its EE code ([`made-up-ps2-ee-vu.c`](../../../tools/test/made-up-ps2-ee-vu.c)). `tools/test/ps2-console-floats.mjs` runs first: the kit's sums against a console's own, above. Each frame the program does the FPU's sums and the multimedia instructions on numbers that change, among them the floats the console treats its own way, with the flags each leaves; runs vector unit 0 an instruction at a time; sends DMA chains with every kind of tag to VIF1, with every UNPACK format and both of the unit's programs, one of which does every instruction and reads the flags, Q and P at the cycle they change and the one before; and sends packets by all three of the GIF's paths, PATH3 held back and let go. The draw list and both vector units' memories, code and data, have to be the same as the emulator's on all 120 frames, byte for byte, and where they aren't it names the write, or the memory and the quadword. Forty-one rules broken on purpose in the kit, one at a time, were each found by it.

They aren't part of Check, as the emulator takes minutes to build, and they run on Linux and macOS alone, where the Mac workflow runs them on GitHub's Mac with Apple's chip for pull requests that touch the PlayStation 2's files ([Other consoles](../../../docs/CONSOLES.md#the-playstation-2)). The strict reference's part of `test:ps2-gs` runs on Linux alone, where PCSX2's runner is built, on a computer with a graphics card: a Mac and GitHub's computers leave it out and say so.
