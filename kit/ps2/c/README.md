# PlayStation 2 kit in C

[Back to the kits in C](../../c/README.md) · [Other consoles](../../../docs/CONSOLES.md) · [The Dreamport standard](../../../docs/STANDARD.md) · [Written in: #618](https://github.com/NahuelGenchi/dreamports/issues/618)

This folder is the PlayStation 2's kit for games written in C, on what [every console's kit in C](../../c/README.md) shares. A game writes the console's graphics chip, the GS, as its original does, and does its float sums as the console's processor, the EE, does them. What it writes each frame is its **draw list**, which is what a 3D game is proven by ([How progress is measured](../../../docs/STANDARD.md#how-progress-is-measured)), and the kit draws that list for the page. Its twins of the game's own modules for the second processor, the IOP, write the sound chip, the SPU2, as the original's do, and the kit mixes the chip's sound as the console's emulator does, sample for sample.

Like the rest of the kits it's under [GPL-3.0-or-later](../LICENSE), and nothing from any game is in it. It's written from how the console is documented to behave.

## What's in it

| File | What it does |
| :--- | :--- |
| `ps2.h` | What a game sees of the console: the GS's registers by name, `gs_write`, `gs_image` and `gs_screen` to write them, `gs_read_image` to read a picture back, `gs_show` to paint the page's picture, and the EE's sums |
| `gs.c` | The GS: its registers, each frame's draw list, the drawing of the list into its memory, in software, textures and blending too, and its privileged registers: what the screen shows, which paints the page's picture, and its status, CSR and SIGLBLID, with IMR and the GS's interrupt |
| `gs-memory.c` | The GS's memory, laid out in pages, blocks and columns as the chip lays out each format, pictures moved into it, out of it and within it, and the palette buffer |
| `gs-kit.h` | What the GS's files share |
| `gif.c` | The GIF: packets, as a game or a vector unit program builds them, turned into the GS's register writes |
| `ee.c` | The EE's float sums, each cut towards zero, with its division and square root |
| `vu.c` | The vector units' sums, four floats at a time, on the fields an instruction names |
| `iop.c` | The IOP's memory and its hardware as a module's loads and stores reach it, the sound chip's DMA channels, and the console's time, which says when the sound chip mixes |
| `spu2.c` | The SPU2, both cores as the console's emulator mixes them, and each frame's sound list |
| `sif.c` | The SIF, which carries data and calls between the EE and the IOP, and the EE's memory |
| `pad.c` | The pads on the SIO2, a DualShock 2 in each port as the console's emulator answers for it |
| `iop-bios.c` | What the kit answers of the IOP's kernel: its loader, which starts a twin of a game's module, and the threads that wait for the V-blank |
| `ps2.c` | What the page calls to start the game, run its frames, draw them and hear them, and to ask for a frame's draw list and sound list |
| `ps2-kit.h` | What those files share, which a game doesn't need |

## Writing a game on it

A game includes `"ps2.h"` and defines the four functions every game in C does ([A game on a console with no kit of its own](../../c/README.md#a-game-on-a-console-with-no-kit-of-its-own)). `npm run dp -- new <game>/c` writes a starting point that shows a blue screen through the GS.

`gs_write(reg, value)` writes one of the GS's registers, as a GIF packet's address and data does: `GS_PRIM`, `GS_RGBAQ`, `GS_XYZ2` and the rest. `gs_image(data, length)` sends it a picture's data. `gs_screen(address, value)` writes half of one of the registers that say what the screen shows, at the address the EE sees it. `game_draw` calls `gs_show()`.

**Pictures read back.** A game that reads a picture back from the GS, as a screenshot or a buffer used as data does, starts the transfer as on the console, BITBLTBUF's source, TRXPOS, TRXREG and TRXDIR = 1, and takes its bytes with `gs_read_image(data, length)`, as VIF1's DMA does once BUSDIR is 1. They come in the console's order, each pixel's bits after the last's, so a 24-bit picture is three bytes a pixel and a 4-bit one two pixels a byte.

**The GS's status.** `gs_screen_read(address)` reads CSR, IMR or SIGLBLID as the EE does, and `gs_screen` writes them, a 1 in CSR's low bits clearing that event. SIGNAL and LABEL put their IDs into SIGLBLID where their masks say, and SIGNAL and FINISH set their bits in CSR. `gs_on_interrupt(handler)` gives the GS's interrupt the game's handler for INTC_GS, which the kit calls as SIGNAL or FINISH is written, or as a V-blank starts, when IMR lets the bit through, and when IMR unmasks an event already in CSR, as the emulator does. Each frame starts with a V-blank: VSINT and HSINT are set, and FIELD is the field it starts. Where the console's values are unknown, they are the emulator's: revision 7 and no ID in CSR, every event masked in IMR at first, and 0xCCCCCCCC from a register the EE can't read. A SIGNAL written while CSR's SIGNAL is still set holds the console's GIF up until the game clears it, which the kit, drawing as it's written, doesn't. HSINT comes once a frame rather than at every line's end, and FIELD turns over as the next frame starts, where the console turns it once the V-blank ends: the kit's GS keeps no time within a frame.

**Packets.** A game that builds GIF packets, as nearly every real one does, hands them over as they are: `gif_send(data, bytes)` as a DMA transfer to the GIF does, and `gif_packet(data, most)` for one packet to the tag that ends it, as a vector unit program's XGKICK does. The kit turns each tag's PACKED, REGLIST or IMAGE data into the GS's writes the way the console's GIF does, so the draw list is the same as the original's, down to the Q an ST leaves for the next RGBA and the corners written without drawing.

**Vector unit 1.** On a real game nearly everything drawn comes from programs on vector unit 1: 99.9% of The Sims' writes on a 3D screen (#1282). A Dreamport writes such a program again in C, an instruction a line, with `vu_vector` for its registers and `vu_add`, `vu_madd`, `vu_mulf`, `vu_ftoi` and the rest for its sums, each on the fields its instruction names (`VU_XYZ`, `VU_XYZW`). An instruction that takes one field, Q or I, such as MULAx or MULq, is the `f` form with that float. DIV is `ee_div`, SQRT `ee_sqrt`.

**The draw list.** Everything a game writes in a frame is hashed in the order written, the same way the proof tools hash what the original gives the GS in its emulator ([`tools/libretro/play.patch`](../../../tools/libretro/play.patch)): each register write as its register and its 64 bits, each picture's bytes, and each half written of PMODE, SMODE2, DISPFB and DISPLAY. A game whose `proof/original.json` says `"provenBy": "draw lists"` is compared by that hash, frame for frame, where another game is compared by its picture. So the order matters as much as the values: a game writes what its original writes, when it writes it. The kit also keeps each frame's whole list, up to 16 MB, which `prove` compares with the original's to say which write of a frame differs ([Proving](../../../tools/README.md#proving)). What a game writes in `game_start`, as it sets up its screen, is in no frame's list.

**The EE's sums.** The EE cuts each float result towards zero, where a computer and WebAssembly round to the nearest. A model turned with plain `+` and `*` has a corner a sixteenth of a pixel out within a hundred frames, and its draw list parts from the original's there. So a game does its sums with `ee_add`, `ee_sub` and `ee_mul`, and turns a float into a whole number with `ee_to_int`.

## The IOP and its sound

A game's own modules for the IOP, such as its sound driver, are written again as twins that write the IOP's hardware at the addresses the original's do: `iop_write16(0xBF900000 + register, value)` for a register of the SPU2, `iop_write32` for a DMA channel's, and `iop_read16` for what the chip says, with `iop_memory()` the IOP's 4 MB, as the emulator has them. A transfer to the chip goes through channel 4 for core 0 and channel 7 for core 1, from the IOP's memory, as the original's does.

**The sound list.** Everything the chip is given in a frame is hashed in the order given, the same way the proof tools hash what the original gives it in its emulator ([`tools/libretro/play.patch`](../../../tools/libretro/play.patch)): each register write as its address and the value written, each DMA transfer as its core, its mode and its bytes, and each block of 45 samples the chip mixes. A PlayStation 2 game's sound is proven by its sound list and by every sample the kit mixes from it being the original's ([How sound is compared](../../../tools/README.md#how-sound-is-compared)). The blocks in the list are what makes the time a write lands part of it.

**The time.** The emulator runs the console in slices of 4,800 of the EE's ticks, and mixes 45 samples at the top of a slice when their time has come: 16 or 17 blocks a frame, 14 in the first. The kit keeps the same time from power-on, so its blocks fall where the emulator's do. What a game's IOP code writes as a frame starts, as a driver woken by the V-blank does, comes before the frame's first block, and `ps2_time_pass(ticks)` lets the EE's ticks pass first for one that writes later.

**The chip.** `spu2.c` follows the emulator's own model of the chip, Play!'s, step for step, as that's what a Dreamport is proven against, and keeps its copyright notice: its ADPCM with the decoded blocks it keeps, its envelope and volume sweep tables, its pitch over 44,100 samples a second, its reverb in floats cut towards zero, its sound input blocks, core 0 mixed into core 1 and its interrupt address. Four things Play! leaves out are done as the console does them, in the kit and, through the tools' patch, in Play! too, so the two still match: noise, at the rate the core's control says, pitch modulation, where a voice bends the next, the master volume over everything a core gives, and the effect volume on what the reverb gives. They were checked against PCSX2's SPU2. Three things were written Play!'s way where PCSX2 does otherwise, to stay one model until the whole chip is the console's ([#1612](https://github.com/NahuelGenchi/dreamports/issues/1612)): a volume divides by 32,767 where PCSX2 shifts by 15 bits, a master volume sweeps as Play!'s voices do, and the noise steps 44,100 times a second, Play!'s rate, not 48,000. A chip nothing has reset has no master volume, as on the console, so a game that never sets it is silent.

## The SIF

A game's EE code reaches the IOP through the SIF, as the console's emulator, Play!, has it: what the EE sends to the IOP's command buffer is read as a command, and the IOP's replies queue up and reach the EE's memory one at a time as the EE's ticks pass, each once the EE says it took the last. A twin of a game's SIF library calls the EE kernel's calls as the original does: `sif_set_dma` for SifSetDma, `sif_dma_stat`, `sif_set_dchain`, `sif_get_reg` and `sif_set_reg`, with what it sends in `ee_memory()`, the EE's 32 MB, at its own addresses, and `sif_ee_handler` for what runs as a packet arrives, the EE's DMA channel 5 handler. A twin that waits for the IOP lets the EE's time pass, `ps2_time_to_slice()`, as the IOP only runs at the end of the emulator's slice.

On the IOP, the kit stands in for the loader, as Play! does: when the EE has it load a module, by the path or from the IOP's memory, it starts the Dreamport's twin of that module, registered with `iop_module_twin(name, start)` by the name the module's file gives itself or the path it's loaded from. A twin's thread that waits for each V-blank, `iop_each_vblank`, runs when the IOP first runs in each frame, before the frame's first block of sound, and a twin's own RPC server, `sif_register_rpc(id, function, buffer)`, is called as Play! calls a module's: the arguments copied into its buffer in the IOP's memory, its function run when the IOP next runs, and the answer copied back from where it says. A server number the kit already answers stays the kit's, as in Play!, where a game's own memory card server never takes over from Play!'s.

## The pads

A game's own pad modules reach the pads through the SIO2, at 0x1F808200 on the IOP, a command a byte at a time or by DMA on channels 11 and 12, and the kit answers as Play!'s SIO2 does: a DualShock 2 in each of the two ports, which says what it is, goes into its configuration, is set to digital, analog or pressure mode, and is read for its buttons, both sticks and the pressure on each of twelve buttons. Play! is given each frame's buttons by the tools as held or not, and the left stick as all the way over or not at all, so a button's pressure is all or nothing and the right stick stays in the middle, and the kit gives the same from the buttons `dp_step` is given. There's no multitap, as Play! says, and a memory card asked for on the SIO2 answers as Play!'s does, which reads back nothing real: memory cards go through Play!'s own server.

The emulator gives the pad a frame's buttons as the frame starts, so a PlayStation 2 game's `original.json` says `"keysAfterVBlank": true`, or its original reads each press a frame before its Dreamport does.

## What it doesn't do yet

The draw list is whole: anything a game writes is in it. What the kit draws of it is most of what a game's screens need, not all of it.

**Its memory.** The GS's 4 MB are kept as the chip keeps them: 8 KB pages, each 32 blocks of 256 bytes, each block 4 columns, with every format's pixels in its own order in each, 32, 24 and 16-bit colours, 32, 24 and 16-bit depths, and 8 and 4-bit indices, alone or in a 32-bit pixel's top byte. So a buffer written in one format and read in another holds what the console's would, as a game's own picture used as a texture, a depth buffer read as colours or a palette in a picture's corner do.

**What it draws.** Sprites and triangles, as lists, strips and fans, in one colour or shaded between their corners, into a framebuffer of 32, 24 or 16 bits, with a depth buffer of 32, 24 or 16 bits, inside the scissor. Pictures move into its memory as a game sends them, out of it and from one place in it to another, in the order TRXPOS's DIR says. Points are the pixel their place is nearest. A shape in the fog (FGE) goes towards FOGCOL by its corner's fog, FOG's or the last XYZF's, and into a 16-bit framebuffer DTHE adds DIMX's numbers to each colour before COLCLAMP keeps it in range. PRMODE gives a shape its attributes when PRMODECONT says, FBMSK and ZMSK keep bits of the framebuffer and the depths, and SCANMSK keeps a shape off every even or every odd line. Textures are 32, 24 or 16-bit, or 8 or 4-bit with a 32 or 16-bit palette, which TEX0 or TEX2 loads into the palette buffer as its CLD says, from a block or a row, into the place CSA names. A texture is placed by whole texels or by floats over Q, sampled nearest or between the four nearest as TEX1 says, meets its edges in the four ways CLAMP says, and meets the shape's colour by any of the four texture functions, with TEXA giving 24 and 16-bit texels their alpha. Pixels go through the depth test, the alpha test with what's written of one that fails, the test of the framebuffer's alpha, and blending, with PABE, FBA, COLCLAMP and the framebuffer's mask.

**Matched pixel for pixel.** Sprites, flat or textured: at their size, larger, repeating, by floats, with 8 and 4-bit palettes, as a decal, blended, and with the alpha test, into a 16-bit framebuffer. The memory's layout: pictures moved in in nine formats and read as textures in eight, and as pictures read back in eight, three of them depths, palettes of 32 and 16 bits in blocks and in a row, in the buffer's places and loaded by every CLD. A sprite drawn through context 2 by PRMODE, FBMSK by whole bytes, and ZMSK under the depth test. A shaded triangle isn't: on the test's 3D program about a tenth of the still triangle's pixels are a step of colour away from the emulator's. A texture sampled between texels isn't either, as the emulator's graphics card weighs them its own way.

**Not drawn yet.** Smaller copies of a texture (mipmaps), lines, and antialiased edges. A triangle's fog runs between its corners the kit's own way, as its colours do.

**The strict reference.** Where the emulator, Play!, can't draw exactly, the kit's pictures are checked against PCSX2's software renderer too, the strictest free GS there is ([Other consoles](../../../docs/CONSOLES.md#the-playstation-2)): the Dreamport runs on the computer, everything its GS was given is replayed by PCSX2, and each frame's framebuffer has to be the same in every bit, alpha too. PCSX2 has to draw it the same whichever of the processor's instructions it's told to use, as well, since what varies across a shape, a shaded triangle's colours and depths, it draws a step of colour apart on thousands of pixels from one to another: only what it draws the same is an exact reference. Matched that way so far, all 300 frames: both memory programs, the events and modes programs, SCANMSK and FBMSK bit by bit, which Play! doesn't do, and what Play! keeps on its graphics card: a picture the GS drew and its 16-bit depths read as textures in seven other formats and read back, the 16-bit depths' two layouts, and pictures copied within memory, onto themselves in each of TRXPOS's orders, before and after their source and more than a page away, and into another layout. Sprites in the fog, dithered and blended past a byte's range with COLCLAMP on and off, and points at every sixteenth of a pixel, flat, textured and in the fog, into 32 bits and 16. A copy onto itself follows the order PCSX2 found games to need, as the chip copies through a buffer: backwards when its destination starts after its source within the source's page.

Sums that overflow aren't done the console's way yet, and RSQRT, the clip test, the flags a sum sets and the units' integer sums aren't in `vu.c` yet. The interface that feeds vector unit 1, the VIF, isn't here: a Dreamport writes the unit's program again and fills its packets itself, so it needs only what the program does, not how its data got there. A SIGNAL written while the GS hasn't been asked about the last holds the console's GIF up, which the kit doesn't. On the IOP there's its memory, the sound chip and its DMA, the SIF and the loader, but not yet the rest of its kernel (semaphores, events, timers, interrupts and threads other than those that wait for the V-blank or serve calls), its memory cards or its disc drive, nor a reset of the IOP with a game's own replacement modules. The order the IOP's threads run in within a slice is the V-blank's, then the servers', where Play! runs them by their priority. The PlayStation's own sound chip registers, which the emulator also lets a game reach, are in the sound list but don't play. A game can still add sound of its own with `game_sound`, which no proof hears.

## How it's checked

`npm run test:ps2-kit` writes the two small programs of [`tools/test/made-up-ps2.mjs`](../../../tools/test/made-up-ps2.mjs) as Dreamports in C ([`made-up-ps2.c`](../../../tools/test/made-up-ps2.c)) and proves them against the console's real emulator. The one in three dimensions is proven by its draw list, all 300 frames, and one that does a sum with a computer's rounding is found, at frame 81. The one whose square a program on vector unit 1 turns, divides by its depth and kicks to the GS as a PACKED packet is proven by its draw list too, all 300 frames, its Dreamport being that program written again in C with `vu_*` and `gif_packet`, and one that divides with a computer's rounding is found at once. With the 3D Dreamport's one sum done a computer's way, `prove` names the write that differs at frame 81: write 20 of 24, the turning triangle's first corner, a sixteenth of a pixel across from the original's. The textured one sends its textures, palettes and sprites as packets, and its Dreamport sends the same through the kit, so its pictures, proven pixel for pixel on all 300 frames, are the kit's drawing against the emulator's: with the palette's layout broken it differs at once. The flat one is proven by its pictures, pixel for pixel.

`npm run test:ps2-gs` does the same for the programs of [`tools/test/made-up-ps2-gs.mjs`](../../../tools/test/made-up-ps2-gs.mjs), each a list of steps its Dreamport in C does through the kit ([`made-up-ps2-gs.c`](../../../tools/test/made-up-ps2-gs.c)), proven by draw list and by pictures, all 300 frames. The memory programs move pictures in in one format and read them in others, as textures into a 32-bit framebuffer and a 16-bit one, and read 32 by 32 pixels back in eight formats every frame, which go back in as pictures, so the draw list holds every byte read: one whose Dreamport doesn't read back differs at once. They come in two because the emulator widens a 16-bit colour to 32 bits its own way, and so draws a 16-bit colour exactly only into a 16-bit framebuffer. The events program sends SIGNAL, LABEL and FINISH every frame, with a handler for the GS's interrupt that clears SIGNAL and counts it, and draws a sprite in the colour of each value it reads of CSR, SIGLBLID and IMR, and of the count, so the draw list holds them all. The modes program draws through context 2 by PRMODE, with FBMSK and with ZMSK.

`npm run test:ps2-sound` does the same for the IOP: a program of the project's own whose EE loads its own IOP module through the SIF, and the module plays a tone and a click on both of the chip's cores, with envelopes, a pitch that moves every frame, two volume sweeps, the reverb, a voice of noise, a voice bent by the one before it, master and effect volumes with a master sweep, and keys let go of and keyed on again, has an RPC server of its own that the EE calls every frame, and reads the pad through the SIO2 every frame, writing what it says where the sound chip takes no notice, so the sound list carries it. The EE writes everything the SIF gives it into GS LABEL writes, so its draw list carries them: what SifGetReg says of the SIF's registers, the ids SifSetDma gives and what SifDmaStat says, every word of the IOP's replies, and the server's answers. Its Dreamport in C, the EE's code and the module written again with the kit's SIF and IOP, has the same draw list and the same sound list, and the kit mixes every sample the emulator does, all 300 frames. One with its pitch a step out on one frame is found on that frame by its sound list, and one that asks SifDmaStat before the IOP has answered is found at once by its draw list. A second recording holds every button and each way of the left stick in turn: all 300 frames match, and a Dreamport that doesn't read the pressure is found on the first frame a button is held. With the voices' samples interpolated the textbook way, in one sum rather than the emulator's two, every frame differs by its samples.

They aren't part of Check, as the emulator takes minutes to build, and they run on Linux and macOS alone, where the Mac workflow runs them on GitHub's Mac with Apple's chip for pull requests that touch the PlayStation 2's files ([Other consoles](../../../docs/CONSOLES.md#the-playstation-2)). The strict reference's part of `test:ps2-gs` runs on Linux alone, where PCSX2's runner is built, on a computer with a graphics card: a Mac and GitHub's computers leave it out and say so.
