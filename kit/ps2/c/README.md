# PlayStation 2 kit in C

[Back to the kits in C](../../c/README.md) · [Other consoles](../../../docs/CONSOLES.md) · [The Dreamport standard](../../../docs/STANDARD.md) · [Written in: #618](https://github.com/NahuelGenchi/dreamports/issues/618)

This folder is the PlayStation 2's kit for games written in C, on what [every console's kit in C](../../c/README.md) shares. A game writes the console's graphics chip, the GS, as its original does, and does its float sums as the console's processor, the EE, does them. A game made [the stricter way](../../../docs/STANDARD.md), each function a twin of one of its original's, builds its original's DMA chains and writes the console's registers where its original does, and the kit's DMA controller, VIFs, vector units and GIF do what the console's do with them. What it writes each frame is its **draw list**, which is what a 3D game is proven by ([How progress is measured](../../../docs/STANDARD.md#how-progress-is-measured)), and the kit draws that list for the page. Its twins of the game's own modules for the second processor, the IOP, write the sound chip, the SPU2, as the original's do, and the kit mixes the chip's sound as the console's emulator does, sample for sample.

Like the rest of the kits it's under [GPL-3.0-or-later](../LICENSE), and nothing from any game is in it. It's written from how the console is documented to behave.

## What's in it

| File | What it does |
| :--- | :--- |
| `ps2.h` | What a game sees of the console: the GS's registers by name, `gs_write`, `gs_image` and `gs_screen` to write them, `gs_read_image` to read a picture back, `gs_show` to paint the page's picture, the EE's memory and registers by address, its FPU and the vector units |
| `gs.c` | The GS: its registers, each frame's draw list, and the drawing of the list into its memory, in software, textures and blending too |
| `gs-memory.c` | The GS's memory, laid out in pages, blocks and columns as the chip lays out each format, pictures moved into it, out of it and within it, and the palette buffer |
| `gs-kit.h` | What the GS's files share |
| `gif.c` | The GIF: packets turned into the GS's register writes, from its three paths in the order the console takes them, with its FIFO and PATH3's mask |
| `floats.c`, `floats.h` | The console's float rules, on a float's bits, which the EE's FPU and the vector units share. The console's emulator in the proof tools is given this same file |
| `ee.c` | The EE's FPU: its instructions on those rules, its accumulator and its flags |
| `mmi.h`, `mmi.c` | The EE's 128-bit integer instructions, a function each, with HI, LO and SA |
| `vu.c` | The vector units: their memories and registers, their programs run an instruction pair at a time, vector unit 0 an instruction at a time from the EE, and the sums for a program written again in C |
| `vif.c` | The VIFs, which feed the vector units: every code, UNPACK in every format, and the programs they start |
| `dmac.c` | The DMA controller: its channels to the VIFs, the GIF and the scratchpad, in normal, chain and interleaved mode |
| `bus.c` | What the EE's code reaches at an address: main memory, the scratchpad, the vector units' memories and the registers of all of these |
| `iop.c` | The IOP's memory and its hardware as a module's loads and stores reach it, the sound chip's DMA channels, and the console's time, which says when the sound chip mixes |
| `spu2.c` | The SPU2, both cores as the console's emulator mixes them, and each frame's sound list |
| `sif.c` | The SIF, which carries data and calls between the EE and the IOP, and the EE's memory |
| `iop-bios.c` | What the kit answers of the IOP's kernel: its loader, which starts a twin of a game's module, and the threads that wait for the V-blank |
| `ps2.c` | What the page calls to start the game, run its frames, draw them and hear them, and to ask for a frame's draw list and sound list |
| `ps2-kit.h` | What those files share, which a game doesn't need |

## Writing a game on it

A game includes `"ps2.h"` and defines the four functions every game in C does ([A game on a console with no kit of its own](../../c/README.md#a-game-on-a-console-with-no-kit-of-its-own)). `npm run dp -- new <game>/c` writes a starting point that shows a blue screen through the GS.

`gs_write(reg, value)` writes one of the GS's registers, as a GIF packet's address and data does: `GS_PRIM`, `GS_RGBAQ`, `GS_XYZ2` and the rest. `gs_image(data, length)` sends it a picture's data. `gs_screen(address, value)` writes half of one of the registers that say what the screen shows, at the address the EE sees it. `game_draw` calls `gs_show()`.

**Pictures read back.** A game that reads a picture back from the GS, as a screenshot or a buffer used as data does, starts the transfer as on the console, BITBLTBUF's source, TRXPOS, TRXREG and TRXDIR = 1, and takes its bytes with `gs_read_image(data, length)`, as VIF1's DMA does once BUSDIR is 1. They come in the console's order, each pixel's bits after the last's, so a 24-bit picture is three bytes a pixel and a 4-bit one two pixels a byte.

**Packets.** A game that builds GIF packets, as nearly every real one does, hands them over as they are: `gif_send(data, bytes)` as a DMA transfer to the GIF does, and `gif_packet(data, most)` for one packet to the tag that ends it, as a vector unit program's XGKICK does. The kit turns each tag's PACKED, REGLIST or IMAGE data into the GS's writes the way the console's GIF does, so the draw list is the same as the original's, down to the Q an ST leaves for the next RGBA and the corners written without drawing.

**The EE's memory and registers.** `ee_memory()` is the EE's main memory, 32 MB, and `ps2_scratchpad()` its scratchpad. `ps2_read32`, `ps2_write32` and their 64 and 128-bit kin read and write what the EE's code reaches at an address: that memory, the vector units' memories, and the registers of the DMA controller, the VIFs, the GIF and the GS's screen, by the names `ps2.h` gives them (`DMA_VIF1 + DMA_TADR`, `VIF1_STAT`, `GIF_FIFO`). A DMA address is an offset into main memory, as on the console, so a game builds its chains there and gives the controller their offsets.

**DMA.** Writing a channel's CHCR with STR set starts it, and it runs then and there: QWC quadwords from MADR in normal mode, or in chain mode the tags from TADR, each kind of them (CNT, NEXT, REF, REFS, CALL, RET, END, REFE), with a tag's second half sent on when TTE is set and a tag's interrupt bit ending the chain when TIE is. What holds a transfer up on the console holds it up here, such as PATH3 masked, and it goes on when that's gone. The channels to the scratchpad copy to and from it, interleaved too. The channels to the IPU and the second processor keep what's written to them and move nothing.

**The VIFs.** VIF0 feeds vector unit 0 and VIF1 vector unit 1, from their DMA channels or their FIFOs. Every code is here: UNPACK in every format, signed and not, through the mask, the row and the column, adding the row or keeping a running sum as STMOD says, written, skipped and filled as STCYCL says, and at TOPS when it's asked; MPG; MSCAL, MSCALF and MSCNT; BASE, OFFSET and ITOP, with the two buffers TOPS turns between; DIRECT and DIRECTHL, which send packets to the GIF; MSKPATH3; FLUSHE, FLUSH and FLUSHA; MARK, and the stall a code's interrupt bit asks for. A command whose data runs over the end of one transfer goes on in the next.

**The vector units.** A program put in a unit's code memory runs as the console runs it, an instruction pair at a time: every upper and lower instruction, with RSQRT, CLIP, the EFU's sums, the whole-number sums, branches with their delay slot, XGKICK, XTOP and XITOP. What a program can see of the unit's pipeline is kept: a float result is there four cycles after its instruction, and one that reads it sooner waits; the MAC, status and clip flags are as the instructions four cycles before left them, FSSET's and FCSET's too; Q changes seven cycles after a division or thirteen after RSQRT, with the status flag's division and invalid bits, and P when an EFU sum ends, and one read sooner is the old one; WAITQ and WAITP take the cycles they wait; and a branch right after a sum on its register tests the register as it was. XGKICK's packet goes to the GIF once the pair after it has run. A program runs to its end as it's started, so what it gives the GS comes where the console's comes among the rest.

Vector unit 0 also takes the EE's COP2 instructions one at a time: `vu0_macro(instruction)` with the original's 32-bit word, `vu0_vf(n)` for a register as QMFC2, QMTC2, LQC2 and SQC2 reach it, and `vu0_cfc2` and `vu0_ctc2` for its control registers.

A Dreamport can instead write a unit's program again in C, an instruction a line, with `vu_vector` for its registers and `vu_add`, `vu_madd`, `vu_mulf`, `vu_ftoi` and the rest for its sums, each on the fields its instruction names (`VU_XYZ`, `VU_XYZW`), and hand its packet to `gif_packet`. An instruction that takes one field, Q or I, such as MULAx or MULq, is the `f` form with that float. DIV is `ee_div`, SQRT `ee_sqrt`.

**The GIF's paths.** Packets reach the GIF by three paths: PATH1 from vector unit 1's memory, as XGKICK sends one, PATH2 from the VIF's DIRECT, and PATH3 from the GIF's own DMA channel or its FIFO. While one path is partway through a packet the others wait, PATH3's data in the FIFO, and PATH3 can be masked, by MSKPATH3 or GIF_MODE. The kit orders them as the console's emulator does, down to the one packet it lets through as PATH3 is unmasked, so the draw list has the three paths' writes in the original's order.

**The draw list.** Everything a game writes in a frame is hashed in the order written, the same way the proof tools hash what the original gives the GS in its emulator ([`tools/libretro/play.patch`](../../../tools/libretro/play.patch)): each register write as its register and its 64 bits, each picture's bytes, and each half written of PMODE, SMODE2, DISPFB and DISPLAY. A game whose `proof/original.json` says `"provenBy": "draw lists"` is compared by that hash, frame for frame, where another game is compared by its picture. So the order matters as much as the values: a game writes what its original writes, when it writes it. The kit also keeps each frame's whole list, up to 16 MB, which `prove` compares with the original's to say which write of a frame differs ([Proving](../../../tools/README.md#proving)). What a game writes in `game_start`, as it sets up its screen, is in no frame's list.

**The console's floats.** The EE's FPU and the vector units don't follow the rules a computer's floats do, and a Dreamport that used plain `+` and `*` would have a model's corner a sixteenth of a pixel out within a hundred frames. On the console there is no infinity and no NaN: a float whose exponent is all ones is an ordinary number, and a result too large is the largest float there is, 0x7FFFFFFF with its sign. A float tinier than the smallest ordinary one counts as zero. A result is cut towards zero, never rounded, and a sum keeps only one bit of the smaller number below the larger's last, so 1 minus something tiny is 1. A division by zero gives the largest float. `floats.c` has these rules, and says where each comes from: Sony's manuals, and for the last bit of a sum, what the two emulators that have measured the console agree on.

So a twin of the EE's code does its float sums with `ee_add`, `ee_sub`, `ee_mul`, `ee_div`, `ee_sqrt` and `ee_rsqrt`, the accumulator's with `ee_adda`, `ee_madd` and their kin, compares with `ee_c_eq`, `ee_c_lt` and `ee_c_le`, and turns a float into a whole number with `ee_to_int`. Each keeps the FPU's flags in `ee_fcsr` as the console keeps them in FCSR: overflow, underflow, division by zero and invalid, each with the sticky flag that stays until the game clears it, and the condition bit.

**The EE's 128-bit integers.** `mmi.h` has a function for each of the EE's multimedia instructions, named after it (`ee_paddsw`, `ee_pextlh`, `ee_pmaddh`, `ee_qfsrv`), on an `ee_quad`, with HI, LO and SA kept as the console keeps them.

## The IOP and its sound

A game's own modules for the IOP, such as its sound driver, are written again as twins that write the IOP's hardware at the addresses the original's do: `iop_write16(0xBF900000 + register, value)` for a register of the SPU2, `iop_write32` for a DMA channel's, and `iop_read16` for what the chip says, with `iop_memory()` the IOP's 4 MB, as the emulator has them. A transfer to the chip goes through channel 4 for core 0 and channel 7 for core 1, from the IOP's memory, as the original's does.

**The sound list.** Everything the chip is given in a frame is hashed in the order given, the same way the proof tools hash what the original gives it in its emulator ([`tools/libretro/play.patch`](../../../tools/libretro/play.patch)): each register write as its address and the value written, each DMA transfer as its core, its mode and its bytes, and each block of 45 samples the chip mixes. A PlayStation 2 game's sound is proven by its sound list and by every sample the kit mixes from it being the original's ([How sound is compared](../../../tools/README.md#how-sound-is-compared)). The blocks in the list are what makes the time a write lands part of it.

**The time.** The emulator runs the console in slices of 4,800 of the EE's ticks, and mixes 45 samples at the top of a slice when their time has come: 16 or 17 blocks a frame, 14 in the first. The kit keeps the same time from power-on, so its blocks fall where the emulator's do. What a game's IOP code writes as a frame starts, as a driver woken by the V-blank does, comes before the frame's first block, and `ps2_time_pass(ticks)` lets the EE's ticks pass first for one that writes later.

**The chip.** `spu2.c` follows the emulator's own model of the chip, Play!'s, step for step, as that's what a Dreamport is proven against, and keeps its copyright notice: its ADPCM with the decoded blocks it keeps, its envelope and volume sweep tables, its pitch over 44,100 samples a second, its reverb in floats cut towards zero, its sound input blocks, core 0 mixed into core 1 and its interrupt address. So it leaves out what the emulator does: noise, pitch modulation and the master and effect volumes.

## The SIF

A game's EE code reaches the IOP through the SIF, as the console's emulator, Play!, has it: what the EE sends to the IOP's command buffer is read as a command, and the IOP's replies queue up and reach the EE's memory one at a time as the EE's ticks pass, each once the EE says it took the last. A twin of a game's SIF library calls the EE kernel's calls as the original does: `sif_set_dma` for SifSetDma, `sif_dma_stat`, `sif_set_dchain`, `sif_get_reg` and `sif_set_reg`, with what it sends in `ee_memory()`, the EE's 32 MB, at its own addresses, and `sif_ee_handler` for what runs as a packet arrives, the EE's DMA channel 5 handler. A twin that waits for the IOP lets the EE's time pass, `ps2_time_to_slice()`, as the IOP only runs at the end of the emulator's slice.

On the IOP, the kit stands in for the loader, as Play! does: when the EE has it load a module, by the path or from the IOP's memory, it starts the Dreamport's twin of that module, registered with `iop_module_twin(name, start)` by the name the module's file gives itself or the path it's loaded from. A twin's thread that waits for each V-blank, `iop_each_vblank`, runs when the IOP first runs in each frame, before the frame's first block of sound, and a twin's own RPC server, `sif_register_rpc(id, function, buffer)`, is called as Play! calls a module's: the arguments copied into its buffer in the IOP's memory, its function run when the IOP next runs, and the answer copied back from where it says. A server number the kit already answers stays the kit's, as in Play!, where a game's own memory card server never takes over from Play!'s.

## What it doesn't do yet

The draw list is whole: anything a game writes is in it. What the kit draws of it is most of what a game's screens need, not all of it.

**Its memory.** The GS's 4 MB are kept as the chip keeps them: 8 KB pages, each 32 blocks of 256 bytes, each block 4 columns, with every format's pixels in its own order in each, 32, 24 and 16-bit colours, 32, 24 and 16-bit depths, and 8 and 4-bit indices, alone or in a 32-bit pixel's top byte. So a buffer written in one format and read in another holds what the console's would, as a game's own picture used as a texture, a depth buffer read as colours or a palette in a picture's corner do.

**What it draws.** Sprites and triangles, as lists, strips and fans, in one colour or shaded between their corners, into a framebuffer of 32, 24 or 16 bits, with a depth buffer of 32, 24 or 16 bits, inside the scissor. Pictures move into its memory as a game sends them, out of it and from one place in it to another, in the order TRXPOS's DIR says. Textures are 32, 24 or 16-bit, or 8 or 4-bit with a 32 or 16-bit palette, which TEX0 or TEX2 loads into the palette buffer as its CLD says, from a block or a row, into the place CSA names. A texture is placed by whole texels or by floats over Q, sampled nearest or between the four nearest as TEX1 says, meets its edges in the four ways CLAMP says, and meets the shape's colour by any of the four texture functions, with TEXA giving 24 and 16-bit texels their alpha. Pixels go through the depth test, the alpha test with what's written of one that fails, the test of the framebuffer's alpha, and blending, with PABE, FBA, COLCLAMP and the framebuffer's mask.

**Matched pixel for pixel.** Sprites, flat or textured: at their size, larger, repeating, by floats, with 8 and 4-bit palettes, as a decal, blended, and with the alpha test, into a 16-bit framebuffer. The memory's layout: pictures moved in in nine formats and read as textures in eight, and as pictures read back in eight, three of them depths, palettes of 32 and 16 bits in blocks and in a row, in the buffer's places and loaded by every CLD. A shaded triangle isn't: on the test's 3D program about a tenth of the still triangle's pixels are a step of colour away from the emulator's. A texture sampled between texels isn't either, as the emulator's graphics card weighs them its own way.

**Not drawn yet.** Fog, dithering, smaller copies of a texture (mipmaps), points and lines. **Not checked yet**, as the emulator can't do them exactly: a copy from one place in memory to another, the 16-bit depth's layout, and a picture the GS drew read as a texture in another format or read back, which the emulator keeps on its graphics card. The kit does them by the same layout, which is proven everywhere else.

**In the EE and the vector units.** A few things the console's makers left unsaid, and the emulators disagree on, follow the choice `floats.c` and `vu.c` name where they make it: the last bit of a product, a quotient and a root, which are the exact ones cut; RSQRT, which is the root cut and then the division cut; the order an EFU sum adds in; and the root of minus zero, which raises nothing. Only a console could settle them, and nobody has measured them on one yet.

The console's emulator in the proof tools is given the same float rules, the flags and the timing above (`tools/libretro/play.patch`), so a proof compares like with like. Three things it still does its own way, which a proof of a game that leans on one would show: a vector unit's EATAN, which it doesn't have; how far back a branch looks for its register as it was, which it counts as four instructions and no further than the start of its own run of code, where the kit counts four cycles; and a float result's wait worked out from where an instruction is in its block, which can be a cycle or two out right after WAITQ or WAITP when the next instruction reads a result made just before the wait.

Eight of the EE's multimedia instructions the emulator leaves out, PMADDW, PMSUBW, PMSUBH, PADSBH, PMADDUW, PDIVUW, PMFHL.SLW and PMTHL.LW: `mmi.h` does them as Sony's manual says, and a game that uses one can't be proven on it until the emulator has it. The DMA controller's ring buffer (MFIFO) and stall control are written as the emulator does them and haven't been tried against it, and GIF_MODE's mask of PATH3 is the console's, which the emulator doesn't have. A vector unit's program runs whole as it's started, so EE code that reads VPU_STAT or a VIF's status to wait for one finds it done, and a write to SIGNAL that the GS hasn't been asked about doesn't hold the GIF up. A picture read back from the GS through VIF1's channel is moved as the emulator moves it, which this check doesn't try.

On the IOP there's its memory, the sound chip and its DMA, the SIF and the loader, but not yet the rest of its kernel (semaphores, events, timers, interrupts and threads other than those that wait for the V-blank or serve calls), its pads, its memory cards or its disc drive, nor a reset of the IOP with a game's own replacement modules. The order the IOP's threads run in within a slice is the V-blank's, then the servers', where Play! runs them by their priority. The PlayStation's own sound chip registers, which the emulator also lets a game reach, are in the sound list but don't play. A game can still add sound of its own with `game_sound`, which no proof hears.

## How it's checked

`npm run test:ps2-kit` writes the two small programs of [`tools/test/made-up-ps2.mjs`](../../../tools/test/made-up-ps2.mjs) as Dreamports in C ([`made-up-ps2.c`](../../../tools/test/made-up-ps2.c)) and proves them against the console's real emulator. The one in three dimensions is proven by its draw list, all 300 frames, and one that does a sum with a computer's rounding is found, at frame 81. The one whose square a program on vector unit 1 turns, divides by its depth and kicks to the GS as a PACKED packet is proven by its draw list too, all 300 frames, its Dreamport being that program written again in C with `vu_*` and `gif_packet`, and one that divides with a computer's rounding is found at once. With the 3D Dreamport's one sum done a computer's way, `prove` names the write that differs at frame 81: write 20 of 24, the turning triangle's first corner, a sixteenth of a pixel across from the original's. The textured one sends its textures, palettes and sprites as packets, and its Dreamport sends the same through the kit, so its pictures, proven pixel for pixel on all 300 frames, are the kit's drawing against the emulator's: with the palette's layout broken it differs at once. The flat one is proven by its pictures, pixel for pixel.

`npm run test:ps2-gs` does the same for the programs of [`tools/test/made-up-ps2-gs.mjs`](../../../tools/test/made-up-ps2-gs.mjs), each a list of steps its Dreamport in C does through the kit ([`made-up-ps2-gs.c`](../../../tools/test/made-up-ps2-gs.c)), proven by draw list and by pictures, all 300 frames. The memory programs move pictures in in one format and read them in others, as textures into a 32-bit framebuffer and a 16-bit one, and read 32 by 32 pixels back in eight formats every frame, which go back in as pictures, so the draw list holds every byte read: one whose Dreamport doesn't read back differs at once. They come in two because the emulator widens a 16-bit colour to 32 bits its own way, and so draws a 16-bit colour exactly only into a 16-bit framebuffer.

`npm run test:ps2-sound` does the same for the IOP: a program of the project's own whose EE loads its own IOP module through the SIF, and the module plays a tone and a click on both of the chip's cores, with envelopes, a pitch that moves every frame, two volume sweeps, the reverb and keys let go of and keyed on again, and has an RPC server of its own that the EE calls every frame. The EE writes everything the SIF gives it into GS LABEL writes, so its draw list carries them: what SifGetReg says of the SIF's registers, the ids SifSetDma gives and what SifDmaStat says, every word of the IOP's replies, and the server's answers. Its Dreamport in C, the EE's code and the module written again with the kit's SIF and IOP, has the same draw list and the same sound list, and the kit mixes every sample the emulator does, all 300 frames. One with its pitch a step out on one frame is found on that frame by its sound list, and one that asks SifDmaStat before the IOP has answered is found at once by its draw list. With the voices' samples interpolated the textbook way, in one sum rather than the emulator's two, every frame differs by its samples.

`npm run test:ps2-ee-vu` checks the EE and the vector units against the same emulator, with a program of the project's own ([`tools/test/made-up-ps2-ee-vu.mjs`](../../../tools/test/made-up-ps2-ee-vu.mjs)) and its Dreamport, a twin of its EE code ([`made-up-ps2-ee-vu.c`](../../../tools/test/made-up-ps2-ee-vu.c)). Each frame the program does the FPU's sums and the multimedia instructions on numbers that change, among them the floats the console treats its own way, with the flags each leaves; runs vector unit 0 an instruction at a time; sends DMA chains with every kind of tag to VIF1, with every UNPACK format and both of the unit's programs, one of which does every instruction and reads the flags, Q and P at the cycle they change and the one before; and sends packets by all three of the GIF's paths, PATH3 held back and let go. The draw list and both vector units' memories, code and data, have to be the same as the emulator's on all 120 frames, byte for byte, and where they aren't it names the write, or the memory and the quadword. Forty-one rules broken on purpose in the kit, one at a time, were each found by it.

They aren't run on every pull request, as the emulator takes minutes to build, and they run on Linux and macOS alone ([Other consoles](../../../docs/CONSOLES.md#the-playstation-2)).
