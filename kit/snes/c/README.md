# The Super Nintendo's kit in C

[Back to README](../../../README.md) · [The kits in C](../../c/README.md) · [Other consoles](../../../docs/CONSOLES.md) · [Written in: #1641](https://github.com/NahuelGenchi/dreamports/issues/1641)

A Super Nintendo game in C runs on this kit, on top of what every console's kit in C shares ([`kit/c/`](../../c/README.md)). Its C keeps every value where its original does, at the console's own 24-bit addresses, and reads and writes the console's hardware registers through the kit, as its original's loads and stores do. Like the rest of the kits it's under [GPL-3.0-or-later](../LICENSE), and nothing from any game is in it, nor from the console: the sound processor's start-up program is the kit's own, written as what it does.

## What's in it

| File | What it does |
| :--- | :--- |
| `snes.h` | What a game includes: where the work memory and the registers are, the two functions that read and write the hardware, the picture's memories, the cartridge, the sound processor's memory and registers, the four functions every game defines, and `game_spc`, which a game with a sound program defines |
| `snes.c` | The registers: the work memory's port, the multiply and divide unit, the two flags a read clears, and the rest kept as the last value written; and the cartridge, LoROM or HiROM, with its save memory, as DMA reads it |
| `ppu.c` | The picture unit: its registers and memories, and each frame's lines drawn from them, with windows and colour maths |
| `dma.c` | DMA, as a write to `$420B` starts it, and HDMA, line by line |
| `apu.c` | The sound side: the sound processor's memory and registers, the four ports, its three timers, the console's start-up program, and the time its turns and the sound chip's samples come at |
| `dsp.c` | The sound chip, its DSP: Shay Green's of snes_spc 0.9.0 ([LGPL-2.1-or-later](http://www.slack.net/~ant/)), written again in C as Snes9x runs it ([libretro/snes9x](https://github.com/libretro/snes9x) at `fae2fea0`) |
| `frame.c` | What the page calls to start a game, run its frames, draw them and hear them |
| `snes-kit.h` | What the kit's own files share |

## Writing a game on it

A game's C keeps its values at the console's addresses: the work memory at `$7E0000`, `SNES_RAM`, which its original also sees at `$0000` to `$1FFF` of the low banks; its save memory and its cartridge's ROM where the cartridge's map puts them. Where its original stores to a register, `$2100` to `$21FF` or `$4000` to `$43FF`, the game calls `snes_write(address, value)`, and where it loads one, `snes_read(address)`, in the same order, so a Dreamport's hardware work is its original's, write for write.

Beside drawing, the registers do what the console does with memory and sums: a write to `$2180` puts its byte in the work memory where `$2181` to `$2183` point and moves them on, and a read there reads one; a write to `$4203` multiplies it by `$4202` into `$4216` and `$4217`, and one to `$4206` divides `$4204` and `$4205` by it, the quotient into `$4214` and `$4215` and what's left into `$4216` and `$4217`, with the results there at once, as Snes9x has them, the reference the proof tools run the original on; reading `$4210` or `$4211` clears its top bit; and the sound processor's four ports are seen again every four bytes up to `$217F`. Reading `$2134` to `$2136` gives mode 7's product, and a write to the picture unit's registers from `$2134` on, which are only read, does nothing. Every other register keeps what was last written to it. A game keeps its own values above the console's 16 MB, as its build links it, so the console's addresses below are free for its C. `npm run dp -- new <game>/c` writes a game on this kit that shows the backdrop in blue.

## The sound program

The console's sound processor, an SPC700, runs a program of its own, which the main program sends it through four ports, `$2140` to `$2143`, as the game starts, and its sound chip plays samples from the sound processor's 64 KB of memory as the program tells it. A Dreamport has that program's twins too. The kit's own start-up program does what the console's does: it says `$AA` and `$BB`, takes the bytes the main program sends, each one's count said back, and sends the sound processor where the main program says, to `game_spc(address)`, the game's twin of what runs from there. That twin keeps its values in `snes_aram`, the sound processor's memory, at the original's addresses, and reads and writes the sound processor's registers, `$F0` to `$FF`, through `snes_spc_read` and `snes_spc_write`, as its original's loads and stores do: the sound chip through `$F2` and `$F3`, the ports at `$F4` to `$F7`, and the timers. Where its original waits in a loop for a timer or a port, it calls `snes_spc_wait()` in the same loop, and goes on from there at its next turn. A game with no sound program leaves `game_spc` out.

The kit runs the sound program beside the game's step, in turns, as its original runs beside the main processor: as one of its timers counts, and when the main program, having written a port, reads one. Time is the sound processor's cycles, 32 to each sample and 32,040 samples a second, as Snes9x has them, and a turn takes none of it, as its original's work after a timer's count is a few hundred of the thousands between two; the sound chip runs up to each turn first, so what the program writes to it lands to the timer's count. The main program's frame takes none either: what it writes to the ports is there at the frame's start. A main program that waits for an answer, reading a port that doesn't change a third time, waits as the console's does, to the sound program's next turn; reading one twice, as games do to be sure of it, doesn't wait. A turn runs from inside `snes_read`, under the same pass as `kit_wait_frame()`, with a stack of its own ([`kit_run_beside()`](../../c/README.md)), so the build of every game on this kit gets that pass.

The sound chip is the console's, as Snes9x has it: eight voices, each a BRR sample from the sound processor's memory at its pitch, with its envelope, ADSR or GAIN, its volume each side, noise, the pitch bent by the voice before, and the echo, with its filter of eight steps and its feedback, in the sound processor's memory; run a cycle at a time, 32 to a sample, so a register written partway through one plays as the console plays it. Its gaussian interpolation is the console's, which Snes9x uses unless told otherwise. Reading the start-up program's ROM itself, at `$FFC0`, reads the memory there instead, as the ROM never leaves the console.

## What it draws so far

Each frame the kit runs the game's step, what its original does from a V-blank to the next, and then draws the frame's 224 lines from the registers as the step left them, from line 1, as the console shows no line 0. So far it draws the screen off and on and its sixteen brightnesses; the 128 sprites, each of the eight pairs of sizes `$2101` chooses, from both of their tables of tiles, with their palettes, flips and four priorities among the backgrounds', the first sprite in the table's order in front where two meet, and on each line the first 32 sprites and, of their tiles across the screen, the last 34, as Snes9x keeps them, from the first sprite `$2103`'s priority bit chooses, or from it moved on by one for each line when the table's address is odd; their table through its port, `$2102` to `$2104`, a word at a time, with its address back where it was last written as each V-blank starts; each colour's 5 bits times the brightness over 15, rounded, as Snes9x has it; the backgrounds of modes 0 to 4, with tiles of 8 or 16 pixels and 2, 4 or 8 bits, maps of 32 or 64 tiles across and down, each tile's palette, flips and priority, mode 1's third background in front when `$2105` says, and each background's scrolling, with the byte the scroll registers share; modes 2 and 4's scroll for each column of tiles from BG3's map, across and down from two rows or from one word by its top bit, none for the leftmost column, read again at the start of each of Snes9x's spans of a line, as Snes9x does; 256-colour tiles through the palette or as direct colours, with the map's palette bits; mode 7, its field of 1024 by 1024 pixels turned, stretched and moved by its matrix, wrapped, nothing or tile 0 outside it, flipped either way, as Snes9x works each line out, flipping each of its spans by itself, with its second background of 7 bits and a priority, direct colours and mosaic, and its product of A and B's top byte read back at `$2134` to `$2136`; mosaic, each block of pixels as its top left one, the blocks from the screen's top left; which of them the main screen and the sub screen show; the two windows, each layer's and the colours' own, on or off and inside out, two combined by or, and, xor or xnor, hiding a layer on either screen where `$212E` and `$212F` say; the colour window turning the main screen black and keeping maths off, inside it, outside it or everywhere; and colour maths, adding or taking away the sub screen, where it shows a layer, or the fixed colour, by half or not, for each layer `$2131` names, the backdrop, and the sprites of palettes 4 to 7, worked on Snes9x's 16-bit pixels with its own sums, so each result is Snes9x's to the bit: below brightness 15 an addition keeps to the brightest the screen shows, a pixel the colour window made black is never halved, and the sub screen counts only when Snes9x draws it, when maths can use it; video memory written through its port, with its address turned round and moved on as `$2115` says; and the colours through theirs. DMA moves bytes between the console's memories and the picture's and the sound's registers, in all eight of its patterns, either way. HDMA starts at line 0 on the channels `$420C` turns on and writes in each line's H-blank, from its tables in the console's memory, directly or through the addresses they give, once or on every line, in every transfer mode and either way, keeping each channel's place in its registers as the console does; what it writes shows from the next line down. The kit draws the frame a line at a time, the sprites' lines found again and the windows' spans cut again when their registers change, and the fixed colour made again for each line. Mosaic is drawn as Snes9x draws it, which depends on where Snes9x starts each stretch of lines it draws, up to a write that changes how they're drawn: the kit notes the same writes, keeps each line's scrolls and mode 7's values as Snes9x does, and starts a mosaic's blocks from the line it was written on, and in a background's spans after its first from the stretch's first line, as Snes9x does. A game's step's writes all happen before the frame's lines are drawn.

## What it doesn't do yet

Modes 5 and 6, hi-res and interlace, mosaic on a background with offsets, the picture unit's other registers read back from `$2137` on, and the main processor's own writes partway down the screen, from an interrupt at a line, which #1641's last step brings, and so a frame of anything else differs, which `prove` finds. A sound program that goes back to the start-up program, or a main program that sends one while the sound processor's own program runs, isn't here either.

## How it's checked

`npm run test:snes-kit` proves it on every pull request with programs of the project's own, run in Snes9x, the console's reference emulator, and each the same in C on the kit: every frame of 300 is the same, pixel for pixel, and so is its sound. One fills video memory, the colours and two maps by DMA, shows two backgrounds of mode 1, scrolls them both ways and steps the brightness through every value; another shows 128 sprites over a background, every size in turn, more than 32 on a line and more than 34 of their tiles, moves some each frame and turns the priority rotation on and off; a third goes through modes 0 to 4, with offsets for each column, 256-colour tiles, direct colours, mosaic, and windows cutting a line with offsets into spans; another runs seven HDMA channels at once, scrolls, the brightness through an indirect table, window 1 from a table in the work memory the program changes each frame, the backdrop's colour, mosaic switched on partway down, the fixed colour and the mode, and turns one channel off and on; another turns mode 7's field a step each frame through 16 settings of its own, reading its product back each frame; a fifth goes through 16 settings of windows and colour maths, a new one every 16 frames, with the windows moving and the fixed colour changing each frame; and the last sends the sound processor a program with two samples, waits for its answer, and gives it the frame's count each frame, and that program plays a square wave, a ramp of BRR's three filters bent by it and into the echo, and noise, changes the pitch and the noise as its timer counts, and keys the square off and on. The sound is within 2 dB of the original's in every band of every frame, well inside the 10 dB `prove` allows. A Dreamport of any of them with one thing a little off, a background behind, a scroll or a sprite a pixel off, a brightness a step off, a sprite's priority, the sprites' second table moved, BG3 a pixel across under a background with offsets, the 256-colour tiles a tile off, no direct colours, the mosaic a pixel bigger, mode 7's matrix a step off, its product's bytes mixed up, its field never flipped, an HDMA channel on the wrong register, an indirect table read as it stands, the work memory's table's first count off, a channel never turned off, taking away where it adds, the fixed colour's green a step off, no sub screen, a window a pixel wider, the noise slower, the square keyed off at once or the echo never written, is found where it's first seen or heard.

The function check builds a game's twins on this kit with `DP_TWIN_CHECK`, so `snes.c` notes each read and write of the hardware in order, and compares the list with the original's, as Snes9x's own 65816 runs it ([The function check on the Super Nintendo](../../../tools/README.md#the-function-check-on-the-super-nintendo)), and keeps the picture's registers and DMA's as memory, as the original's side does. `npm run test:snes-twin` does that on every pull request with a made-up cartridge of the project's own.
