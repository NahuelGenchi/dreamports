# Games

[Back to README](../README.md) · [Contribution workflow](../CONTRIBUTING.md) · [The Dreamport standard](../docs/STANDARD.md) · [Written in: #74](https://github.com/NahuelGenchi/dreamports/issues/74)

Every Dreamport made in this repository lives in this folder, one folder per game. A game plays on dreamports.net at the address that matches its folder's name, so `games/sonic-advance/` plays at `dreamports.net/play/sonic-advance/`, on the same site as the player's profile. Every game here keeps the rules in [the Dreamport standard](../docs/STANDARD.md).

## What a game's folder holds

A game is plain HTML, CSS and JavaScript that runs in the browser as it is, with no build step, and its [version in C](#versions-in-other-languages), if it has one, is the only thing built. When the site is built, each game's folder is copied to `/play/<game>/` exactly as it is, but for its notes, so the files in the folder are the files players get. On dreamports.net they are served as plain files, like the site's own pages, without running the site's Worker.

Every folder needs three files at its top: `index.html`, the page the game starts from, which a game that [started in C](#versions-in-other-languages) has in `c/` instead; `entry.md`, the game's [entry](#the-entry); and the license for the game's code, in a file named `LICENSE` or `COPYING` (it may end in `.md` or `.txt`). Dreamports use GPL-3.0-or-later, as [the standard explains](../docs/STANDARD.md#licenses). The rest of the game can be in any files and folders it needs. Its pages load them with addresses relative to the page, such as `src/main.js`, and load the site's own files, such as [`/dreamports.js`](../docs/ACCOUNTS.md#for-a-game-dreamportsjs) for achievements, from the site's root. A Dreamport's `proof/` folder holds what the [proof tools](../tools/README.md) measure it with: which copy of the original it's compared with, its recorded play, its code map and its progress, all as JSON. Its `notes/` folder holds what people found while making it, one small file each, for the next person, as [Notes](../docs/NOTES.md) explains: the site's build leaves it out, and stops on a note that breaks the rules for notes.

The folder's name is the game's address, so it has only lowercase letters, numbers and single dashes, such as `sonic-advance`. Files and folders whose names start with a dot stay out of the site, and links to files somewhere else (symlinks) aren't allowed.

Nothing from the original game ever goes here: no ROM, no game files, and no music, pictures or data taken from them. Players bring their own copy, and the game reads it on their device.

## Versions in other languages

A Dreamport can be written in more than one language, each version with its own progress, and its JavaScript version stays where it always was, in the game's folder. A version in another language is a page of its own in a folder named after the language, so Sonic Battle Dreamport in C is `games/sonic-battle/c/`, played at `dreamports.net/play/sonic-battle/c/`. A new Dreamport starts in C, its only version, written from the original: its folder has its entry, license, notes and `proof/` but no `index.html`, and its page is in `c/`. Its own address, `dreamports.net/play/<game>/`, sends players on to `c/`, a page the site writes as it's built, and a JavaScript version can still be added later with `npm run dp -- new <game>`. C is the only other language so far, on its console's [kit in C](../kit/c/README.md): the [Game Boy Advance's](../kit/gba/c/README.md), or on any other console what every console's kit in C shares.

A version's folder holds its `index.html`, its code in `src/`, with its C in `.c` files that the site builds to `src/game.wasm` as it copies the games, and its own `proof/`, with only its `progress.json` and `port-map.json`. Everything else is the game's and stays in the game's folder: its entry, its license, its notes, and in its `proof/` the copy, the code map, the parts and the recordings, which are the same in every language. A version's numbers come from its own files measured against the game's, so its page in the Make row shows them under the heading **C**, first, with the other languages folded under **Other languages**, the game's own page shows two numbers only, those of the version Play opens, which is C until the player picks another language, and `docs/STATUS.md` has a row and a progress map for it, `.github/readme/progress/<game>-c.svg`. Each map names its language, and the game's issue shows its version in C's first, with the others folded under it.

The proof tools name a version by its folder, as in `npm run dp -- prove sonic-battle/c`. `npm run dp -- new sonic-battle/c` starts one, with the game's first files too in a game that hasn't started, and `npm run dp -- tasks sonic-battle/c` opens its tasks, each named after the part with the language after it, as *Task: Title screen in C*. A game's **main version** is its JavaScript one when it has one, or else its version in C, which is also what a game counts as before its first files reach `main`, so its tasks in C go under the game's own issue. Its numbers are the game's first, named after their language when it's C, as **Code ported in C**. Every version is written from the original, so a task in one language never waits for the same part in another ([What a task needs](../docs/TEAMS.md#what-a-task-needs)), and a version in C can follow the JavaScript where it has a part already. It keeps the player's copy and touch layout with the JavaScript version's, and its saves apart, unless its save is the same bytes as the JavaScript version's, as Sonic Advance's is, when the two share it so a player keeps theirs whichever they play. A game's card plays its C version first, as C is the default language, and the player can pick another beside the box to tick, which the card keeps.

## The entry

Every Dreamport has one entry, `entry.md` in its folder, which says everything about it: the game and the exact copy it needs, who makes it, what it's built with, and where to follow it. The site makes the game's page from it, at `dreamports.net/dreamports/<game>-dreamport/`, where `<game>` is the folder's name, and its page in the Make row, at `dreamports.net/make/<game>/`, for the people making it, until every part of it is proven. Its page, its place in the Make row and `docs/STATUS.md` show its two numbers, code ported and gameplay proven, and the table shows its lead too. [Sonic Advance Dreamport's entry](sonic-advance/entry.md) is an example.

A game's [capture](../docs/STANDARD.md#a-games-capture) gives it a place in the Make row, and only there at first, as what `npm run dp -- new` writes has no code of the original's yet. With no `screen`, or once it's taken down, it has none, and its files still build. Its place in the Dreamports row and its own page, for players, come with its first reviewed step that names code of the original, when its code ported rises above 0.

`npm run dp -- new <game>` writes a new game's entry, with its first code ([Starting a game](../tools/README.md#starting-a-game)). An entry is a Markdown file. Its fields go at its top, between two `---` lines, and the text below them, such as the credits, shows at the end of the game's page. Write them as normal sentences and labels, with a capital at the start. `npm run check` and `npm run build` stop and say what's wrong when a field is missing or wrong.

| Field | What to write |
| :--- | :--- |
| `title` | The Dreamport's name, such as `Sonic Advance Dreamport` |
| `platform` | The console, such as `Game Boy Advance`, shown under the name in the menu |
| `year` | Optional: the year the original came out |
| `added` | The day the Dreamport was added, written as `2026-10-27` |
| `summary` | A few words on what it is, up to 80 characters and without the game's name, shown under that name when its page is shared |
| `needs` | The exact copy players need, such as `A Sonic Advance (USA) ROM (.gba)`. It names the same copy as `proof/original.json` |
| `controls` | The ways to play: any of `keyboard`, `controller` and `touch` |
| `issue` | The number of its game's issue, the [New Dreamport](../docs/TEAMS.md#start-a-dreamport) issue that claimed it, such as `123` for Sonic Battle Dreamport's. Every piece of the game is a sub-issue of it, and it's where people talk about the game |
| `lead` | The GitHub account of whoever leads the work on it, such as `NahuelGenchi`, shown in `docs/STATUS.md`. A new game's lead is whoever claimed it with a [New Dreamport](../docs/TEAMS.md#start-a-dreamport) issue |
| `team` | Optional: the GitHub accounts of everyone else working on it |
| `kit` | Its console's kit, a folder in [`kit/`](../kit/), such as `gba` |
| `sources` | Every source of its code, each with a `name`, an `href`, its `license` (such as `MIT`, or `none`) and its `use`: `code` when code came in from it, or `guide` when it was only read. Code brought in without a license that allows it also needs `agreement`, a link to its authors' agreement, as [the standard](../docs/STANDARD.md#fair-to-everyone-who-helped) asks |
| `preview` | Optional: the lead's [team preview](../docs/TEAMS.md#team-builds), which `npm run dp -- team <game> add` updates with each piece, and which the page shows with a reminder that nobody has reviewed it |
| `ownCopy`, `extras`, `screen`, `share`, `glow` | The game's page, as for [every game on the site](../CONTRIBUTING.md#add-a-game). `npm run dp -- capture` writes `screen` and `share` ([The proof tools](../tools/README.md#a-games-capture)) |
| `facts` | Optional: more lines for the game's details, each with a `label` and a `value`, or a link of its own, with a `label` and an `href`, such as an article about it |

The rest of the game's page comes from its folder, not from the entry:

- **Code ported** comes from `proof/port-map.json`, which `npm run dp -- portmap` writes from the names of the original's functions in the game's code, and from `proof/progress.json`, which only `npm run dp -- prove` writes, from recorded play that matched the original ([How progress is measured](../docs/STANDARD.md#how-progress-is-measured)).
- **Gameplay proven** comes from `proof/parts.json`, the game's parts, each counting the same, written by its lead. A part names the recording that proves it and the first and last of that recording's frames it covers, and it's proven when `prove` found every one of those frames matching, picture and sound. A part that names [what it reaches](../tools/README.md#what-a-part-reaches), as an act names its end, also needs the original to get there within those frames. [Proving a part](../tools/README.md#proving-a-part) says how to record a whole part and find its first and last frames. On the page its line opens to list every part, with the links to the evidence: a part links its recording once it has one, and until it's proven, says what its frames found.
- `npm run check` and the build check that both numbers add up with the code map, the port map, the parts and what `prove` found, so neither can be typed by hand. They also stop when a Dreamport has no code map, since the whole game is mapped before anything else.
- **The achievements** come from the game's list, if it keeps them on players' profiles ([Profiles and achievements](../docs/ACCOUNTS.md#for-a-game-dreamportsjs)): how many the visitor has earned, and a row of trophies that opens the game's Achievements page, with every one. Until it keeps some, the page says none yet.
- **The source code** is the folder itself, on GitHub.

The game's tasks are the sub-issues of its game's issue, each also with the game's label, which is its folder's name. One person works on a task at a time, and a comment saying `/claim` takes a free one, as [Claims and teams](../docs/TEAMS.md) explains. `npm run dp -- find <game>` lists who has which, what's free to start, and what the others wait on.

The table of Dreamports in `docs/STATUS.md` comes from the entries too, with each Dreamport's **progress map**, which its numbers link: a picture of both, with a rectangle for each function in `proof/code-map.json`, green when it counts toward code ported, and a block for each part, green once it's proven ([How progress is measured](../docs/STANDARD.md#how-progress-is-measured)). The map is kept in `.github/readme/progress/<game>.svg` and shown only on GitHub, never on the site. Pull requests leave the table and the maps alone, so they can't conflict over them: the Readme workflow writes them on `main` from what's merged, every three hours, with `npm run dp -- readme`, which also shows them on your computer. A new game's first entry is the exception, and brings its own row and map. `npm run check` says when a port map is out of date.

## The kits games start from

What every game on the same console shares, such as reading the player's copy, drawing, sound, controls, settings and saves, is that console's kit, in a folder of its own in [`kit/`](../kit/). The first is the Game Boy Advance kit, [`kit/gba/`](../kit/gba/README.md), whose guide shows how a new Game Boy Advance game starts from it. When the site is built, each kit is copied as it is to `/kit/<console>/`, next to the games, so a game's pages load it with addresses relative to the page, such as `../../kit/gba/styles/kit.css`. Those addresses work the same on dreamports.net and on a file server run in the repository's folder.

A kit's folder follows a game's rules, but it isn't a page of its own, so it needs no `index.html`, only its license: kits use GPL-3.0-or-later, like the games. A kit holds only what any game on its console can use. What only one game needs stays in that game's folder, and nothing from any game ever goes in a kit.

## Trying a game on your computer

After [setting up the site on your computer](../CONTRIBUTING.md#run-the-site-on-your-computer), `npm run worker` builds it with every game in it and opens it at `http://localhost:8787`, with its profiles and a database on your computer. There, `http://localhost:8787/play/<game>/` plays the game the way dreamports.net does. `npm run build` followed by `npm run preview` shows the games too, without profiles. `npm run dev` shows only the site's own pages, not the games. While you work on a game, any static file server run in the repository's folder also plays it, at `/games/<game>/`, without the site's own files such as `/dreamports.js`, as [Sonic Advance Dreamport's README](sonic-advance/README.md#run-it-on-your-own-computer) shows. The server runs in the repository's folder rather than the game's so the game can load its kit. To let others try your work before it's merged, `npm run dp -- share` puts a preview of it online, as [Previews](../docs/PREVIEWS.md) explains.

The build stops and says what's wrong if a game's or a kit's folder breaks one of these rules, or if the site grows past what Cloudflare's free plan takes: 20,000 files at most, and none bigger than 25 MiB.

## Removing a game

A game comes off the site in one commit: delete its folder, entry included, any recordings of it in `public/media/`, any picture of it in `.github/readme/`, and write the table in `docs/STATUS.md` again with `npm run dp -- readme`, which also removes the game's progress map. It's how a rights holder's notice is answered, as [Notices from rights holders](../docs/RIGHTS.md) says.
