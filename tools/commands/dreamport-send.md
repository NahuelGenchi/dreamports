---
name: dreamport-send
description: Sends your finished piece to the game's lead, or to the Dreamports team if you're the lead.
---

1. Find the game, the work's branch and its task, from the branch's name, `feat/<issue>-<a few words>`, and run `npm run dp -- find <game>` for its lead and team build, and `npm run dp -- notes <game>` for what people already found.
2. Leave the next person what this step found. Think over what they'd otherwise have to find again: why something in the original surprised you, where a function really starts, what a difference turned out to be. Write each as a note in `games/<game>/notes/`, or in `kit/<console>/notes/` when it's true of every game on the console, unless a note already says it, as `docs/NOTES.md` shows: what was found and what proves it, never what to do, and nothing taken from the game. A step that found nothing of the kind needs none.
3. Check it's ready. Commit what's left on the branch. Run `npm run dp -- portmap <game>`, `npm run dp -- prove <game>`, `npm run check` and `npm run build`. Stop if anything that matched the original before differs now, or a check fails, and say what.
4. Work out where it goes:
   - **To the Dreamports repository as a first entry**, when the branch holds only what `npm run dp -- new` and `npm run dp -- capture` wrote for the game they lead: skip the notes, `prove` and the template's Clips, and write `Refs #<game's issue>` in its pull request, never `Closes`, as the game's issue stays open. The Dreamports bot writes it all again and compares, and asks the Dreamports team about its capture, so it comes in with no review of its code. It says so in a comment, and why not if it can't. If it has no capture yet, as its `games/<game>/entry.md` has no `screen`, ask whether to open the window where they choose one, as `/dreamport-claim` says, and send nothing until they have, as the game has no place on the site without it.
   - **To the lead's team build**, when someone else leads the game and has one: `npm run dp -- team <game> send --task <issue>`, with `--as <preview>` when they shared a preview of the piece. Run it without `--yes` first: it shows the pull request it would open and where, and stops.
   - **To the Dreamports repository**, when they lead the game, or nobody else does: a pull request from their fork's branch, or their team build, `team/<game>`, to `main` in NahuelGenchi/dreamports, for the Dreamports team to review. Fill in `.github/pull_request_template.md`, with its part for a Dreamport: the clips, as the lines `share` printed for each; code ported and gameplay proven before, from `main`'s README, and after, from this branch's; the preview or team preview; and every source used, with its license and whether code came in from it. Add `Closes #<issue>` for each task it finishes.
   - **When the game's lead has no team build yet**: say so. The lead makes one with `npm run dp -- team <game> start`, and a comment on the task's issue can ask them to. Ask whether to send it to the Dreamports repository instead, naming the lead in the pull request.
5. A pull request to the Dreamports repository shows the step's clips, unless it's a first entry. GitHub can't attach a file to a pull request from the command line, so only `share` can put a clip where the pull request shows it. Work out which recordings show what this step changed, and whether you have the lines `share` printed for the clip of each, from `/dreamport-share` in this conversation or from them. If any are missing, stop here, before anything is pushed or opened, and don't run `share` yourself. Name those recordings, say in plain words that their clips have to go online first and that the command for it runs only when they type it, and ask them to type `/dreamport-share`, then `/dreamport-send` again. If they shared them in an earlier session, typing it again prints the lines again. Only if they say they don't want to share, or can't, go on without the lines: under Clips, write which recordings' clips they'll add themselves, and remember them for the last step.
6. Say exactly where it's going, such as `Knuckles, to @bea's team build of Sonic Battle, as a pull request from your fork, with its numbers and your preview`, the title of each note it adds, that it's public and in their name, and wait for their yes. Nothing is sent without it.
7. Send it. For the team build, run the same command with `--yes`. For the Dreamports repository, push the branch to their fork, then run `gh pr create --repo NahuelGenchi/dreamports --base main --head <their account>:<branch> --title "<what it is>" --body-file <the filled-in template>`. Someone who can push to the Dreamports repository itself, such as its owner, who can't fork it, pushes the branch there instead and gives `--head <branch>`.
8. Give them the pull request's link, and say GitHub emails them when someone answers. If they chose not to share the clips, give them each clip's full path too, `.dreamports/results/<game>/<recording>/clip.mp4`, and say to drag each into the description on the pull request's page, the one way to add them without `share`.
