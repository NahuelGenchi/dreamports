# The proof tools

[Back to README](../README.md) · [Contribution workflow](../CONTRIBUTING.md) · [The Dreamport standard](../docs/STANDARD.md) · [Written in: #77](https://github.com/NahuelGenchi/dreamports/issues/77)

The proof tools show that each step of a Dreamport plays like the original game, so its progress is measured instead of guessed. They play the same button presses in the original and in the Dreamport, compare every frame, what it shows and what it sounds like, work out the game's [two numbers](../docs/STANDARD.md#how-progress-is-measured), code ported and gameplay proven, and make short clips of both side by side. They run on your own computer, with your own copy of the game, and everything they take from the game stays there.

You start each one from a terminal in the repository's folder, with `npm run dp -- <tool>`. `npm run dp` on its own lists them.

| Tool | What it does |
| :--- | :--- |
| `setup` | Builds the reference emulator the original runs in, and the Game Boy Advance's compiler |
| `rom` | Checks a copy of a game, says which game and which version it is, and remembers where it is |
| `play` | Opens a game in a browser with your copy, and with `--record` keeps what you play as a recording, after another recording's presses with `--from` |
| `route` | Finds the presses that take the original from where a recording leaves it to a goal, such as an act's end, and writes them as a recording, with nobody playing ([Finding a route](#finding-a-route)) |
| `prove` | Plays each recording in the original and in the Dreamport, compares every frame, its picture and its sound, says what the console holds that differs, updates the numbers, and with `--stills` keeps pictures of the frames you name |
| `capture` | Lets you play the original in a window, and keeps a real moment of it for the game's card, or with `--open`, `--pick` and `--from` does that while the game is being made, with nothing waiting for anyone |
| `codemap` | Makes the code map: every function in the original, with its address and size |
| `new` | Writes a claimed game's first files: its page, its code on the kit with everything wired in, its license and its entry |
| `untouched` | Lists what gameplay proven leaves untouched in a version: functions never played, branches gone one way only, and data never used |
| `portmap` | Makes the port map: each function of the original the Dreamport's code names, and where, and each path it says it hasn't ported |
| `read` | Prints one of the original's functions, its instructions, from your copy, for code its decompilation has no C for, on the Game Boy Advance and the NES |
| `match` | Builds a Game Boy Advance game's C with the compiler the original was built with, and says which functions come out as the original's bytes ([Matching the original's bytes](#matching-the-originals-bytes)) |
| `twin` | Calls a function of the original and its twin from the same memory, thousands of times, and says whether both leave the same memory, on the Game Boy Advance ([Checking a twin against the original's memory](#checking-a-twin-against-the-originals-memory)) and on the NES ([The function check on the NES](#the-function-check-on-the-nes)) |
| `proofs` | Lists where each function of a version stands, its twin and its proof, for a version made a function at a time ([A function's proof](#a-functions-proof-and-a-game-made-a-function-at-a-time)) |
| `libraries` | Says how much of each console's shared code, the libraries its games share, is proven, and with a version where each function it takes from them stands, finds them in a version's copy with `--find`, and lists what two games share with `--shared` ([Shared libraries](#shared-libraries)) |
| `share` | Publishes a preview of a game on GitHub Pages from your own fork, with the clips of what the step changed for its pull request |
| `find` | Shows where a game stands: its lead, its two numbers, its team build, who has claimed which task, the tasks free to start, and what the others wait on |
| `tasks` | Opens a Task issue for each of a game's foundations and parts that has none yet, its foundations first and then in the order a player meets them, or for each group of functions in a version made a function at a time |
| `notes` | Shows what people found while making a game or its console's kit, so nobody has to find it again |
| `team` | The game's team build, the lead's branch with the team's finished pieces: `start` makes it, `join` starts a piece from it, `send` sends a piece to the lead, and `add` proves a piece and takes it in |
| `readme` | Writes the table of Dreamports in `docs/STATUS.md`, with each one's numbers and lead, from their [entries](../games/README.md#the-entry), and each one's progress map. A workflow runs it on `main`, so a pull request doesn't need it |
| `commands` | Writes the `/dreamport` command, from `tools/commands/`, in the form each coding agent reads |
| `ready` | Everything a step has to pass before it goes out, in one go: the port map, every recording, `npm run check` and the build, printing only what's wrong |
| `update` | Brings a branch up to date with `main`, and with any pull request it's built on: merges it, settles conflicts in files the tools write, runs `ready` and commits ([Bringing a branch up to date](#bringing-a-branch-up-to-date)) |
| `help` | Prints one section of these documents, the ones whose headings have the words you give, so that nobody has to read a whole one |

They've been used with real games only on the Game Boy Advance, and they work the same way for any other console, each in a small emulator built on your computer, as far as [Other consoles](../docs/CONSOLES.md) says. They've been used with real games only on Linux. On a Mac, Apple silicon or Intel, on Windows with only Node.js and git added, and on Windows inside WSL 2, `setup`, `rom`, `notes`, `read`, `play --record`, `prove` and `portmap` work as they do on Linux, with the same results to the last frame, as far as a small made-up program shows on GitHub's computers, with a script pressing the buttons in a real window. On Windows itself that's with Chrome and with Edge, on an account with no administrator's rights as well as on one with them, from a folder and with a copy whose names have spaces and letters from other languages, and `codemap` and `find` gave the same results too. Nobody has tried them there by hand, with a controller or with a real game. `share` hasn't published anything from any of them, and `team` hasn't gone past its first check.

## What you need

You need Node.js and the repository's packages, as [running the site on your computer](../CONTRIBUTING.md#run-the-site-on-your-computer) explains, and Google Chrome, Chromium or Microsoft Edge. `share`, `find` and `team` also need the [GitHub CLI](https://cli.github.com), signed in with `gh auth login`. If the tools don't find your browser, set `CHROME` to where it is. To build the reference emulator you also need git, CMake and a C compiler: on Debian or Ubuntu, `sudo apt install git cmake build-essential` installs them, and on a Mac, `xcode-select --install` and `brew install cmake`.

On Windows you need only [git](https://git-scm.com), and the Edge that comes with Windows is browser enough. `setup` gets a compiler, [w64devkit](https://github.com/skeeto/w64devkit), and [CMake](https://cmake.org) by itself, about 120 MB, each from the people who make it, at a fixed version and checked against its hash. It builds in `C:\ProgramData\dreamports-build`, since the compiler can't read a path with some languages' letters in it, which takes about a gigabyte for those minutes. Then it keeps the two programs it made and deletes the rest, so nothing gets installed. If PowerShell says running scripts is disabled when you run `npm`, write `npm.cmd` in its place.

You can also run the tools on Windows inside WSL 2 (Windows Subsystem for Linux), which `wsl --install` sets up, with everything above installed inside it, as on Linux, and Chrome from Google's own package. `play`'s window opens through WSL's own display. Keep the folder in Linux's home: under `/mnt/c` the tools work too, but installing and building take several times as long. WSL 1 can't run the browser.

A game written in C needs nothing more: `npm ci` brings a compiler that builds it to WebAssembly, the same on every computer, and `npm run test:c-kit` also builds it for your computer with its own C compiler ([the kits in C](../kit/c/README.md)).

And you need your own copy of the game, made from your own cartridge: the version the Dreamport is built from, such as the USA version.

## Getting ready

`npm run dp -- setup` downloads the source code of [mGBA](https://mgba.io) 0.10.5 with git and builds it, along with two small programs of the tools' own: [`gba/original.c`](gba/original.c), which runs the original a frame at a time, and [`gba/read.c`](gba/read.c), which prints its instructions for `read`. They go in `.dreamports/gba/`, and it takes a few minutes the first time. A third, [`gba/call.c`](gba/call.c), calls one function of the original at a time for `twin`, and plays a recording to take the memory each function starts from, which builds it by itself if `setup` ran before it existed. If you already have mGBA 0.10.5's source code, `MGBA_SOURCE=<its folder> npm run dp -- setup` builds that instead of downloading it. `prove` runs the setup by itself if it hasn't been done.

It also downloads [agbcc](https://github.com/pret/agbcc), the Game Boy Advance's own compiler, about 13 MB, with git, at one fixed commit, and builds its two compilers, `agbcc` and `old_agbcc`, in under a minute. `match` builds a game's C with one of them. It needs only git and a C compiler, as it does agbcc's build steps itself, with no make and no shell ([`gba/agbcc.mjs`](gba/agbcc.mjs)). `AGBCC_SOURCE=<its folder>` builds a copy you already have. agbcc is GCC, under the GNU General Public License: it's built and run on your computer, and no part of it is in the repository, in a Dreamport or on dreamports.net. `match` builds the one it needs by itself if `setup` hasn't.

And it gets [Binaryen](https://github.com/WebAssembly/binaryen) 132.0.0, a download of 23 MB from npm's registry, checked against its hash, of which it keeps one file of 15 MB, for a game whose C waits from inside a function ([The same-memory build](#the-same-memory-build)). Binaryen is under the Apache License 2.0: it runs on your computer as the game is built, and no part of it is in the repository.

mGBA is the reference: the original runs in it, on your computer only, so there's something to compare against. It's never part of a Dreamport and never runs on dreamports.net. It starts the game with its own stand-in for the console's start-up program, so no BIOS file is needed.

`npm run dp -- rom <file>` checks your copy. It says which game it is, which version, and whether it's the copy a Dreamport's proof uses, and it remembers where the file is, in `.dreamports/copies.json`, so the other tools find it. It only reads the file: it never copies it, changes it or sends it anywhere. Give it a folder and it checks every `.gba`, `.agb` or `.bin` file in it, but names only the copies a Dreamport here measures against, and sums up the rest in one line. `--game "<name>"` names the copies of the game you're starting too, such as `npm run dp -- rom <folder> --game "Sonic Battle"`, when no Dreamport measures against it yet: a copy is that game when its header says the same name, or the start of it when the name is too long for a header's twelve characters, or when its file's name has the name's words in a row, not followed by a number, so Sonic Advance doesn't pick out Sonic Advance 2. It says which of the two it went by, along with what `original.json` needs. On its own, `npm run dp -- rom` lists the copies it remembers.

## Recording play

`npm run dp -- play <game> --record <name>` opens the game in a browser window, ready to press Play. Nothing is saved in that window, so the game starts from power-on, the way the original does. Play with the keyboard or a controller, then close the window, and the buttons you held at every frame are written to `games/<game>/proof/recordings/<name>.json`. A recording's name has lowercase letters, numbers and single dashes, such as `act-1`. Without `--record`, `play` just opens the game with your copy, and keeps its saves for next time.

`--from <recording>` starts the new recording with another recording's presses, so a part later in the game can be recorded without playing everything before it again. Press Play and the game first plays them, at its own speed and with your buttons doing nothing, then it's your turn, and the terminal says when. `--from <recording>:<frame>` plays them up to that frame only, so `--from act-1:2100` takes over at frame 2100 of `act-1`. The new recording keeps those presses, and the stretches only the original has among them, so it still starts from power-on and `prove` plays it like any other.

A recording can also come from anyone playing: a Dreamport's settings have **Report a problem**, which sends the buttons held since the game started to the site ([Players' reports](../docs/REPORTS.md)). `npm run dp -- reports` fetches those sent since the last time, with the owner's key, writes each as a recording in `.dreamports/reports/<game>/`, and plays each next to the original by itself, as `prove --quick` does, saying the frame where the Dreamport and the original part ways or that they never do: it's how what a player saw go wrong gets played again, and how play nobody planned gets proven. `reports --replay` plays those kept again, all or the ones named, and `--no-replay` only fetches. A report keeps the address's start point when there was one, and the save its game began from, as `<name>.<key>.sav` beside it and under `saves` in its recording: both games start from it, the original where the save is its cartridge's save memory. A save is a player's own, so a report stays in `.dreamports/`, and a recording in a game's `proof/recordings/` can't name one: to keep what a report found, record the same play from a start point, or from power-on.

A recording can also be written by hand, as a list of presses, which is how `/dreamport` makes them, as nobody plays there, and which suits a part played with nothing pressed, such as logos and an intro left alone. For a part where the character has somewhere to get to, such as a whole act, `route` finds the presses instead ([Finding a route](#finding-a-route)). Sonic Advance Dreamport's [logos and intro](../games/sonic-advance/proof/recordings/logos-and-intro.json) is one: A on the language screen, then nothing.

A recording holds nothing from the game, only button presses, so it lives in the game's folder and goes in a commit, and anyone with their own copy can play it again. Write what it plays in its `about`. Its other fields:

- `frames`: how many frames it lasts.
- `held`: the buttons held, as a list of changes. `[120, ["A"]]` means A is held from frame 120 until the next change. Buttons have the console's names (`A`, `B`, `SELECT`, `START`, `RIGHT`, `LEFT`, `UP`, `DOWN`, `R` and `L`), or the Dreamport's own name for a button the console doesn't have, after which the original can't match.
- `onlyInOriginal` (optional): stretches of play the original has and the Dreamport doesn't have yet, such as a menu nobody has made. Each gives `at`, the Dreamport's frame where it goes in, its length in `frames`, the buttons `held` during it, counted from its own start, and an `about`. The original plays them and the Dreamport skips them, so the frames after still line up. It can also have `sets`, as [Start points](#start-points) says.
- `start` (optional): what the Dreamport's address adds, as [Start points](#start-points) says.
- `clip` (optional): the frames the clip shows, from frame `at`, for `frames` frames: at least 300, five seconds, or all of a shorter recording's, which `share` refuses until it runs on further. Leave it out unless the moment to show is somewhere `prove` wouldn't start, as `prove` starts the clip a second before the first frame the step changed.
- `players` and `others` (optional, for games with a link between consoles): `players` is how many consoles are linked, 2 to 4, and `others` lists, for each console after the first, its own `held` list. `held` is then the first console's, and `start` says how many the page runs (`vs=3`). `prove` runs one original core for each console in lockstep over the link (`tools/gba/linked.c`) and compares every player's picture with the page's screen for that player, frame by frame, holding each player's buttons by the names the page's `dreamportsProof.buttons` gives them; a first difference's picture has one pane per player, the page's on top row and the original's below. Such a recording counts towards gameplay proven: the program that runs linked copies writes what ran on every console and the cartridge's data each used, as the one-console program does (`gba/ran.h`, `gba/used.h`), each console's memory followed by itself, and an instruction, a branch's way or a cell of data counts once any console did it in a frame where every screen matched. The functions that started in those frames are the ones its row lists as found running, for code ported.

Sonic Advance Dreamport's [first act](../games/sonic-advance/proof/recordings/neo-green-hill-act-1.json) is an example: it skips the character select, which the Dreamport doesn't have yet.

## Start points

A late part doesn't have to wait for everything before it. A recording can have a **start point**, so that the Dreamport opens right at the part and the original gets there by itself. Two things make one, and either can go without the other:

- `start` is what the Dreamport's address adds, such as `level=2&character=1`: words and values, which the game's own page reads. `prove` opens the game with them, and so does `npm run dp -- play <game> --record <name> --start level=2`.
- `sets`, in a stretch of `onlyInOriginal`, writes values to the original's work RAM as that stretch runs, such as which levels are unlocked: `[{ "frame": 9, "address": "03005168", "bytes": 1, "value": 2 }]`, with `frame` counted from the stretch's start, `address` in hexadecimal, as the code map has it, and `bytes` 1, 2 or 4. They can't reach the cartridge, and `prove` stops if one tries.
- `sets` beside `held` does the same as the original plays the recording's own frames, with `frame` one of the recording's. It's for a recording the Dreamport plays all of, its menus too, where the original still needs what the start point gives the Dreamport, such as progress: then the Dreamport runs every screen the original does, and nothing either of them leaves behind for later goes missing.

Write the presses and values that take the original to the part's first frame as a stretch of `onlyInOriginal`, at the frame where the Dreamport opens at the part, which is 0 when it opens there straight away. Then run `prove` and change the stretch's length until the frames line up. Its list of frames where the original's screen is one colour shows where each screen ends.

It's still all compared: every frame of the part, against the original, the same as any other. A part proven this way counts towards gameplay proven, and `prove`, `find`, the game's page and its progress map mark it as proven from a start point, as it could still differ once the game's real path reaches it. Once that path exists, a recording with no `start` or `sets` proves it again from power-on, and the mark goes.

**A start point only skips the way there.** What it plays has to be what a player could see at that place, and a match can't tell you that: the original does the same as the Dreamport when it's given the same values, so every frame can be the same in a recording nobody could ever play. Sonic Advance 2's first spring recordings left Sonic in the air as a stage opened, so its countdown ran while he fell and bounced, with its crouch on him in mid-air, its machine and its numbers following him, and on one spring the crouch covered his whole flight. So:

- The character starts where a player could have them: on the ground, unless the game's opening has gone and they're in the middle of something a player could be doing, such as a jump. To find the ground, try a height and see where they land.
- The game's own opening ends before they meet what the recording proves. That's anything that holds the buttons or sets an animation, such as a countdown or a title card.
- Look at it the way a player would, with `--stills` every second or so, before you call it done.

The tools hold a game to this where it can say so. In a frame no player could ever see, a game's code writes why to `dreamportsProof.neverInPlay`, as Sonic Advance 2's countdown does for a character a start point has left in the air. `prove` names those frames and fails, however they compare, it keeps them in `progress.json`, and `npm run check` and the build stop until the recording is played again without them, so a pull request with one can't pass its checks. Only a game's own code knows what its opening does, so a game whose opening holds its character adds this line itself ([the kit's README](../kit/gba/README.md#for-the-proof-tools) shows how). Until it does, `prove` reminds it in one line whenever a recording it plays has a start point and the game's code never names `neverInPlay`, which doesn't change whether the recording passes. A game with no such opening can end the reminder with a comment naming it that says why. Keep it to what a start point can cause, as a real start must never be flagged.

A recording's start point is only words and numbers, so it goes in a commit and anyone can replay it. Save states stay out of this: they hold the game's memory, so they can't go in a commit, and nobody else could replay them.

## Finding a route

`npm run dp -- route <game> <name> --goal <goal>` finds a recording's presses when nobody plays. It's for a part where the character has somewhere to get to, such as a whole act and its boss. It searches the original itself, in the reference emulator, for the buttons that take it from where a recording leaves it to the goal, and writes them as `games/<game>/proof/recordings/<name>.json`, a recording like any other, which `prove` then compares with the Dreamport. It needs none of the Dreamport's code, so a part's recording can be there before a line of the part is written, and every round of work after that is `prove`.

The way there comes from a recording. `--from <recording>[:<frame>]` starts the new one with another's presses, up to a frame or to its end, as `play --record` does, and keeps its start point and the stretches only the original has. Without `--from`, `<name>` is a recording that's already there, and it grows from its last frame.

The goal is one the game names in its `proof/route.json`, such as `act-end`, or a condition written out: one of the game's values, a sign and a number, such as `"x>=9000"`, with commas between several that all have to hold, as in `"x>=9000,y<700"`. The signs are `=`, `!=`, `<`, `<=`, `>`, `>=`, `&` for a value that has one of those bits, and `!&` for one that has none.

```sh
npm run dp -- route sonic-advance angel-island-act-2 --from angel-island-act-2-opening --goal angel-island-act-2
```

**How it searches.** It never plays from the start twice. It keeps a copy of the console's state at every new place the game reaches, a place being a cell of a grid over a few of the game's own values, such as where the character is. Then it picks a place, brings its state back, holds some buttons for a few frames, and keeps whatever new places that reaches, again and again, on several consoles at once that share what they find. The newest places and the ones tried least are picked most, so it spreads through a stage like water, and play that can't go on, such as a life lost, is dropped. Nothing is drawn as it searches, which the game can't tell, so the original runs at 2,000 to 3,000 frames a second on each console.

**What it prints.** Every few seconds, a line with how many places it has reached and where the newest is. It stops by itself. At the goal it plays the whole list of presses once more from power-on, straight through, and writes the recording only if they still reach the goal. When nothing new has turned up for a long while, or its time is over, it says so, with how far each value got, and leaves a map of every place it reached and pictures of where it stopped in `.dreamports/routes/<game>/<name>/`. Those show the game, so they stay on your computer. What it found is kept there too, and the same command goes on from it. A `--goal` that names a place it already reached writes the recording that gets there at once, to look at with `prove`'s `--stills` or to go on from another way.

**When it's stuck**, the map and the pictures say where. Most often the grid doesn't tell apart two states that lead to different things, so the search throws one of them away. A place that can only be passed with speed needs the character's speed under `apart`. A fight needs how far it has got, such as the boss's health, in its `cells`, and the game's clock under `apart`, as what a boss lets you do depends on when. A place where the way only opens later, such as a platform that moves, needs the search to wait there, which `wait` lets it do. A value the grid doesn't have is added to `route.json`, and `--cells`, `--apart` and `--wait` try another grid for one search, such as `--cells x:16,y:16` or `--wait 90:3`.

| Flag | What it does |
| :--- | :--- |
| `--from <recording>[:<frame>]` | Starts the new recording with another's presses |
| `--goal <goal>` | Where to get to: one of the game's goals, or a condition |
| `--minutes <how long>` | How long it may search, 10 unless told. The same command goes on from where it stopped |
| `--cells <value>:<size>,…` and `--apart <value>:<size>,…` | Another grid for this search |
| `--wait <frames>:<states>` | Each place also keeps a state for each stretch of that many frames after the search first reached it, up to that many, so it can wait there |
| `--then <frames>` | Frames with nothing held after the goal, such as an act's results |
| `--at-once <how many>` | How many consoles search at the same time: as many as the computer has idle cores unless told, up to 12 |
| `--seed <number>` | Other dice. With `--at-once 1`, the same seed finds the same presses every time |
| `--fresh` and `--replace` | Forgets what it found before, and writes over a recording that's already there |

### What a game says of its original

The search knows nothing of any game. A game tells it where its original keeps the few values it reads, in `games/<game>/proof/route.json`, which every version of the game shares. Like a recording's `sets` it holds only addresses and numbers, so it goes in a commit. [Sonic Advance's](../games/sonic-advance/proof/route.json) is the example.

- `values`: each value's name, with its `address` in the work memory, in hexadecimal as the code map has it, its `bytes`, 1, 2 or 4, `signed` when it can be negative, and `per`, how many of its units make one of what people count in, such as 256 to a pixel. Conditions and grids are then written in pixels.
- `cells`: the grid, each value in it with how much of it one cell covers, such as `{ "x": 32, "y": 32 }`.
- `apart` (optional): what tells two states of one place apart, the same way, such as `{ "speedX": 4 }`. A place then keeps a state for each.
- `wait` (optional): `{ "frames": 90, "states": 3 }` has each place also keep a state for each stretch of 90 frames after the search first reached it, up to 3, so it can wait there for what only comes later. It costs memory, as every place keeps that many more states.
- `lost`: conditions for play that can't go on, such as a life being lost. Without them the search wastes its tries on falls.
- `goals`: the goals the game names, each a condition, which a part in `parts.json` can also name as [what it reaches](#what-a-part-reaches). One can be written as `{ "when", "cells", "apart", "wait" }` to have a grid of its own, and with `"after"` it names the goal to reach first: an act's end after the place its boss comes in, so one command does both, each with its own grid.
- `buttons` (optional): the sets of buttons the search may hold, such as `"RIGHT A"`. Without it, each direction alone and with each of the console's other buttons, but Start and Select.

A value the game keeps in memory it hands out as it goes, such as a boss's health, has no address of its own. It has `found` in place of `address`: the stretch of memory to look through (`from`, `to`, `step`), the `mark` that's beside it, such as the address of a function its record points to, and from the mark where the record's own address is (`pointer`, `pointerBytes`, `base`) and where in the record the value is (`offset`). It reads -1 while no record is there, which makes "the boss has come" a goal, `boss>=0`.

To find where a game keeps something, look in its notes (`npm run dp -- notes <game>`) and its decompilation's names first. Then check it: `npm run dp -- route <game> <recording> --at <frames>` prints the game's values at those frames of a recording, and with `--memory <from>-<to>` every value in that stretch of work memory that isn't the same at all of them, which is how a value that changes when something happens is found.

### What nobody has played yet

`npm run dp -- untouched <version> --why <address>` says what a branch went by, before anyone searches for its other way. It plays a recording that ran the branch, the first that did or the one `--in <recording>` names, follows where each register's value came from as the original runs, and prints the comparison the branch went by: the instruction that set the flags, each side's value, and where it came from, which is a place in the game's memory, a number in the code, or something worked out from more than one thing. It says how many times the branch went each way with each set of values, and the first frame it did. A line such as `Taken 11 times, first in frame 3257: at 080549D2, 3, from the byte at 03005084, changed on the way, against 2, a number in the code` says the branch tests a byte of the work RAM against 2, and that it held 3 in that recording. What the byte is comes from the decompilation, or from `route <game> <recording> --at <frames> --memory <from>-<to>`, which shows how it changes. A value the buttons change is found by playing or by `route`; one they don't, such as the character or the game's mode, needs a recording that starts differently. It follows a value through moves, shifts and sums with numbers, and loses it across a call or where two values from memory meet. The first time it was asked, on 16 November 2026, of six of Sonic Advance Dreamport in C's smallest branches still to play, five tested the game's mode or the character and one a count the player changes.

`npm run dp -- untouched <version> --sort` does that for every branch gone one way only, to show what the work left is made of. It plays each recording that ran any of them once, several at a time, reading all the branches it ran, and sorts each branch by what it compared, the pair of values, whatever they were worked out from: a place plus a size sorts as well as a value read straight from memory. A branch **moves** when what it compared was more than one thing within one recording, so playing differently, or a search, can reach its other way. It **differs** when it was one thing in each recording but not the same in all, which is how a choice made before the part looks, such as the character, and also what play had left at a moment tested once. It's the **same** when it was the same in every recording that ran it, so no recording has ever shown another: often the game's mode or a setting, which only a recording that starts differently changes. And it goes by the **path** when both sides were numbers the code had set on the way there, the same every time, such as a flag set earlier in the function or what a function gave back: the way it goes depends on the path that led to it, so another path has to be played first. A value read from the cartridge's data, such as a level's table, isn't a number in the code. Once it has been run, `npm run dp -- tasks <version>` writes beside each branch of a task for what's left what it found of it, and how many of the task's branches are of each kind, and `tasks <version> --update --yes` writes the tasks already open again, each keeping what it says of who took it. For the two middle kinds it lists the values of the work memory the most branches test, with what they held between them, as one new recording that changes one of them can open many branches; `--all` lists every value with its branches, and the whole result goes in `.dreamports/untouched/<version>.json`, on your computer. `--at-once <how many>` says how many recordings to play at a time, half the computer's threads by default. On 16 November 2026 Sonic Advance Dreamport in C had 5,053 branches gone one way only: 1,762 moved, 179 differed by recording, 2,475 were the same everywhere, 621 went by the path and 16 didn't run as branches, with 539 functions that had never run. Sorted first by where one side came from alone, 1,954 of them couldn't be sorted at all ([#1422](https://github.com/NahuelGenchi/dreamports/issues/1422)).

`npm run dp -- untouched <version> --decided` lists the branches the code itself decides, one way of which can't happen. It's worked out from the cartridge alone, with nothing played ([`lib/decided.mjs`](lib/decided.mjs)): for each conditional branch of the Thumb code, the straight run of instructions before it is read forward with every register and flag unknown, each instruction changing what's known as the processor would, and the branch is decided only if the flags its condition reads are all known when it's reached, set from numbers in the code. The run starts after the last place anything else could arrive at: no instruction of the cartridge branches or calls into it, and no word of the cartridge holds an address in it, whatever that word is. A value read from memory, what a call leaves, and where the code is, as a game runs copies of its functions from its work RAM, are never known. It then checks that no recording of any version of the game has ever played a way it calls impossible, and stops if one has. `--write` puts them in the game's `unreachable.json`, under `"ways"`, each as `[address, "taken" or "not taken", why]`, for a person to read before they go in: gameplay proven then counts that branch's instruction and its other way only. On 16 November 2026 it found 6 in Sonic Advance, each a setting fixed when the game was built. The 621 branches `--sort` had seen compare numbers in the code were first taken for such branches; all but 3 of them go by the path, and their other way can be reached ([#1424](https://github.com/NahuelGenchi/dreamports/issues/1424)).

An aimed search steers by what its branch tests. Before it starts, `--goal untouched:<address>` asks what the branch went by in a recording that ran it, as `untouched --why` does, and each side that is a value of the work memory becomes a side of the search's grid, `tested1` and `tested2`, in bands a sixteenth of the way from what it held to what it was against. So the search keeps a state for each step towards the other way and goes on from the nearest. `frames`, how long the console has played, is a value any search can name, for a part of a game its `route.json` gives no place values for, such as a special stage: `--cells frames:120` spreads the search over time alone. `--lost <condition>` adds play that can't go on, such as `--lost "frames>5300"` when the branch is tested by a frame and play past it is wasted. A search for untouched code picks both of those by itself when they aren't given. It reads the game's place values through the recording it starts from, from its starting frame on, and where none of them changes it spreads over `frames` in their place. And where the branch it aims at ran three times or fewer in that recording, it's tested at set moments, so play two seconds past the last of them is lost. It says so when it does either, and `--cells` and `--lost` say otherwise. On 16 November 2026 `npm run dp -- route sonic-advance/c special-stage-1-quota --from special-stage-1:2800 --goal untouched:08029A3C --cells frames:120 --lost "frames>5300"` found, in 1 minute 28 seconds, presses that collect the 60 rings special stage 1's first checkpoint asks for, a branch no recording had played. Without the ring count in its grid the same search had found nothing, and without `--lost` it reached 48 rings in 8 minutes, most of them spent past the checkpoint. With neither `--cells` nor `--lost` given, the search worked both out and found the same branch in 1 minute 50 seconds.

`--goal untouched` searches for code the version hasn't played in a frame that matched, in place of a goal the game names: the tools give the program what's been played of the cartridge's code, from the version's `played.json`, and it counts, each frame, the instructions and branch ways not among them, which the search reads as a value of its own. It ends at the first frame with any, so the recording it writes reaches something new; prove it, port what it stops on, and search again from it. That way it looks only at the cartridge's code. `--goal untouched:<address>` aims at one thing alone, in the cartridge or in code a game runs from its work RAM: the branch at that address going the way nobody has played, as `untouched` lists it, or an instruction that never ran running. A search spreads over the values the game's `route.json` gives it, so one for a place those values don't move in, such as a menu or Tiny Chao Garden, needs values of that place there first. `npm run dp -- untouched <version>` lists everything that's left: the functions never played, those with branches gone one way only, with each branch's address and the way to play, and the stretches of the cartridge's data never used, the biggest first, or all of them with `--all`.

A game's `proof/unreachable.json` lists what nothing can reach, as `{ "about", "code": [[first, last, why]], "content": [[first, last, why]], "ways": [[address, way, why]] }`, with addresses in the cartridge as the code map writes them, and under `ways` the branches one way of which can't happen. Those stretches don't count towards gameplay proven while they stay unplayed ([Done](../docs/STANDARD.md#done)).

A game's `proof/saves.json` lists the bytes of its save memory that aren't its save, as `{ "about", "leftover": [[first, last, why]] }`, with bytes counted from the start of the save memory in eight hexadecimal digits. `prove` leaves them out when it compares what a Dreamport saved with the cartridge's ([Saves](../docs/STANDARD.md#saves)), and when a save differs it says the first byte that does and what each side holds there.

### What it can't do

It searches for a way, not for a good one: the presses it finds look like nobody's play, with hops that do nothing, and it takes hits. A part with nothing to reach, such as a menu, is still written by hand. It needs the reference emulator to copy its state out and bring it back, which mGBA does and nearly every libretro core does, and on those other consoles it searches with one console at a time. It has been run on the Game Boy Advance and on the made-up console of the tools' tests only.

## What a recording shows

A recording named for a character has to play that character, and a match can't tell you that either: the original plays whoever its values pick, and the Dreamport does the same, so every frame can be the same in a recording of the wrong one. Sonic Battle's first recordings of Shadow, Amy and Chaos played Cream, Rouge and another fighter, as their start points gave numbers someone had guessed, and nothing looked at who was playing.

So the original's own memory says who it is. A game whose recordings can be named for a character, or for anything else a value in the original picks, lists it in its `original.json` under `shows`: for each kind, the work RAM's address where the original keeps it, how many bytes, and the name of each value.

```json
"shows": {
  "fighter": { "address": "03001634", "bytes": 1, "names": { "0": "Sonic", "3": "Shadow", "6": "Cream" } }
}
```

`prove` reads each kind from the original as a recording's last frame ends, says what it found, and keeps the name in `progress.json`. A recording whose name names one of a kind's names, as a whole word, such as `shadow` in `shadow-moving` or `amy` in `amy-x-zone`, fails unless the original shows that one, however its frames compare, and `npm run check` and the build stop on it too, so a pull request with one can't pass its checks. Name a recording for what it shows, and leave a name out of it when it shows someone else, as Sonic Advance's `x-zone-the-normal-ending` plays Sonic in the zone Amy hasn't reached yet.

Each name in the list is checked once by a person against the original's pictures, with a recording that picks that value, before it goes in: a guessed name would only move the mistake into the list. A value the list doesn't name fails any recording named for that kind. Sonic Battle lists its fighters and Sonic Advance its characters.

## What a part reaches

A part named for an act has to play the act to its end, and a match can't tell you that: a recording that stops halfway matches the original just as well as one that gets there. Sonic Advance's Neo Green Hill Zone act 2 once counted as proven, "through its boss", on a recording that never beat the boss, with every frame the same.

So the original's own memory says whether it got there. A part in `parts.json` can name what it reaches, one of the goals the game lists in its [`route.json`](#what-a-game-says-of-its-original):

```json
{ "name": "Neo Green Hill Zone act 2", "recording": "neo-green-hill-act-2", "frames": [0, 8411], "reaches": "act-end" }
```

`prove` reads the goal's values in the original as each frame of the recording ends, and keeps in `progress.json` the frames over which the goal held, as `"reached": { "act-end": [[8102, 8380]] }`. The part is proven only when the goal comes true within its frames, so one that held already before the part's first frame says nothing of it. When it doesn't, `prove` fails the recording, however its frames compare, with `--quick` too, and says where the original did get to the goal, if anywhere: past the part's last frame, before its first, or never. The two numbers, the game's page, `npm run check` and the build count the part the same way, and `check` stops on a part that names a goal no proof has measured yet.

The way out is always in the recording: play on until the original gets there, with [`route`](#finding-a-route) for a part nobody plays, and give the part the frames that take it in. A part's goal is the game's lead's to write, when the parts are listed, and a task doesn't take it away.

A goal a part names reads values that each have an `address`. One that reads a value only the search can find, such as a boss's health, is for `route` alone. A recording that links several consoles can't prove such a part yet. Sonic Advance's acts name `act-end`, the flag the game sets when an act is cleared.

## A game's capture

Every game's card in the launcher shows a few seconds of real play. `npm run dp -- capture <game>` makes a Dreamport's from the original, so a game can have one before its Dreamport has anything to play. It opens a window where you play your own copy, from power-on, with the keyboard or a controller, and hear it as you go. `/dreamport` opens it for you as soon as it starts on a game with no capture, and you can also ask your agent, so you run nothing yourself.

Press Finish, or `Esc`, or View and Menu together on a controller, and it picks out the best stretches of what you played: lively and colourful, with buttons held, and with no fades, logos, menus or text. They come up moving. Press the one you want with the mouse, with the arrows and `Z`, or with a controller's d-pad and A. `Esc` or B goes back to playing where you left off, and the next list comes from all of it.

What you choose becomes a few seconds that loop, as near to seamless as the game allows, in `public/media/`: `<game>-dreamport.h264.mp4` and `.av1.mp4`, silent, `-still.webp` and `-share.png`. The game's entry names them, as `screen` and `share`. Choose play, with no logos or title screens: these go in a commit, on to dreamports.net, and the Dreamports team looks at them in the game's pull request ([the rule](../docs/STANDARD.md#a-games-capture)).

With nobody playing for 30 seconds the window rests: the game waits, drawing and playing nothing, until a button is pressed, as `--open` can leave it open for as long as a game takes to make. What it keeps is only what was played.

Your presses stay in `.dreamports/captures/<game>/`, so `npm run dp -- capture <game> --choose` shows the same moments again, if the window closed first or you change your mind. The pictures come from running the original again with those presses, and it stops if any frame comes out differently from what you played. A coding agent can start it for you, but the choice is yours: it never looks at the pictures.

Making a Dreamport never waits for this, so three more ways of running it keep the work going. `--open` starts the window in a process of its own and returns at once. `--pick` ends it, waiting while someone is using it, and keeps what they chose. If they played and didn't choose, it takes the moment the tool ranks first, by those same numbers, in a browser nobody sees. If nobody played it says so, and `--from <file>` plays a list of presses, as a [recording](#recording-play) has them, and takes the first of what they lead to, or says in numbers what each stretch led to: how much of the screen moved, how many colours and how often buttons were held. Values written to the original's memory aren't play, so `--from` stops at them. With any of these, `--yes` also sends what's kept as a pull request of its own, on the latest `main`, which is the game's [card](../docs/TEAMS.md#a-games-first-files-and-its-card) when it has none. A game whose first files aren't on `main` yet has nowhere for it to go, so it says the capture goes in with the branch's pull request. It leaves the branch you're on alone, so what it wrote still shows in this folder to commit there too.

## Proving

`npm run dp -- prove <game>` plays every recording of the game in the original and in the Dreamport, both from power-on, and compares every frame: its picture, pixel for pixel, in the console's own colours, and its sound, as [How sound is compared](#how-sound-is-compared) explains. A frame matches when both are the same, and for a game that keeps its memory at the console's addresses, when its work memory is too ([The same-memory build](#the-same-memory-build)). Add recordings' names after the game's to play only those. The Dreamport runs in a browser you don't see, a frame at a time, through its kit's proof mode ([the Game Boy Advance kit's](../kit/gba/README.md#for-the-proof-tools)), as fast as your computer goes rather than at the console's speed, and one browser plays all the recordings. Sonic Advance Dreamport's first act, 3,300 frames, takes a few seconds. Several recordings play at the same time, each in a page of its own, as many as your computer has idle cores and free memory for as it starts, eight at most, so two people or agents proving on one computer each get fewer and neither waits for the other. `--at-once <how many>` sets it yourself. Each recording still prints everything it found in one piece, in the usual order. A proof of the whole game says in full only what's news: the recordings that came out as when last proven, and that the step changed nothing in, are summed up at the end, by name, those with every frame the same and those that differ from the same frame as before. `--all` prints each of those in full too, as naming a recording does. A game written in C is built once, before anything plays, and not at all when none of its C changed since it was last built. `--paced` holds it to the console's speed, for a game whose code goes by the clock, one recording at a time.

`prove` ends with 0 when every frame of every recording matches. When frames differ it ends with 3 if none of them matched in the last commit, and says so, and with 1 if one did, naming the recording and the frame: a recording nothing proved before has to match in every frame (`tools/lib/as-before.mjs`). `ready` passes only on 0, and `update` on 3 as well.

`prove <game> <recording> --quick` is for while you work: it stops at the first frame that differs, says why, and writes nothing but a picture of that frame and the stills you asked for, with no clip and no numbers, so it's the cheapest way to see whether a change did what it should. Run it plainly before the step goes out, which `npm run dp -- ready <game>` does.

For each recording it says how many frames were the same and which first differs: the frame, how many pixels differ, and the box they're in, or that it's the frame's sound, and then the first picture that differs too. It lists every stretch of frames that differs, then those whose sound differs, with the first of them: the band of pitches where it's furthest from the original's, and how loud each one is there, in the console's steps. It says so when the Dreamport makes no sound at all. It also lists the stretches where the original's screen is one colour, as it is between one screen and the next, which helps find where each of the game's parts starts and ends. For each part the recording proves in `parts.json`, it says whether every frame of it matched, and it names any [note](../docs/NOTES.md) on a part it didn't prove or on a recording that differs. At the end it gives the game's two numbers as they are now. It also compares with the last time the recording was proven: frames that differ now where they matched then are listed apart, with the first of them, which is usually the one a change just broke. If any frame differs, `prove` ends with an error, so a script that runs it stops. Frames are numbered as the Dreamport counts them. The console shows each frame's work one frame later, and `prove` lines the two up. A game that reads its buttons just after the V-blank, rather than just before it as most do, reads each frame's buttons in the frame `prove` counts as the next one: `"keysAfterVBlank": true` in its `original.json` gives the original its buttons a frame later, so the two still line up. Sonic Battle is one.

For a game proven by draw lists, as a 3D game on the PlayStation 2 is, it also says which write of the first frame whose list differs isn't the original's: its place in the frame's list, what the original wrote there and what the Dreamport did, each a register's name and its 64 bits, and the writes before it that both made, so the place to look in the game's code is plain. For that it plays the original to that frame once more, with its lists written out, and removes them after. `report.json` has the same under `drawListApart`. It can't say when the Dreamport's list of that frame is too long for the kit to keep, more than 16 MB, and says so.

A Dreamport that throws, as a game does on a path it hasn't ported yet, such as a version in C behind its JavaScript, stops its recording there: `prove` says at which frame and what it threw, counts that frame and every one after as differing, keeps it under `stopped` in `report.json`, and goes on to the next recording.

At the first picture that differs, and with `--state <frames>` at any others, such as `--state 782,1099`, up to 20 at a time, it says what the console holds as it draws that frame, where the original and the Dreamport differ: its display registers, its colours, its sprites and its video memory, with what on the screen uses each stretch of it. That's why a picture differs, which a picture can't say: a layer's scroll, a sprite's place, a stretch of a map. When all of it is the same, the picture differs because of how it's drawn. A register changed between lines shows its last line's value in the original and its first in the Dreamport. For every frame `--stills` or `--state` names, it says how many pixels differ and the box they're in.

Of video memory it prints only where it differs and how each stretch of a map starts, never a tile. What it prints goes only to the terminal and `report.json`, and, as with `read`, to the company that runs your agent's model when an agent reads it.

Its results go in `.dreamports/results/<game>/<recording>/`:

- `report.json`: everything it found, with what it heard under `sound`: whether the Dreamport made any, the stretches whose sound differs, and the first of them, and under `neverInPlay` any frames no player could ever see, as [Start points](#start-points) says.
- `first-difference.png`: the first frame that differs, as the original, the Dreamport, and the original in grey with every pixel that differs in magenta. When it's only the frame's sound that differs, the pictures are the same.
- `first-picture-difference.png`: the same, for the first frame whose picture differs, when a frame before it differs only by its sound.
- `first-new-difference.png`: the same, for the first frame that differs where it matched last time.
- `clip.mp4`, with `clip-start.png`, `clip-middle.png` and `clip-end.png`, pictures of its first, middle and last frames.
- `dreamport.mp4`, the same frames of the Dreamport on its own, with nothing of the original, and `dreamport.png`, its middle frame. `share` posts only `clip.mp4`, never this one, as a pull request's clip shows the original next to the Dreamport ([#1039](https://github.com/NahuelGenchi/dreamports/issues/1039)), and never a video made another way.
- `stills/`, a picture of both at each frame `--stills` names, such as `--stills 249,250` or `--stills 900-905`, up to 600 at a time, and at each part's first and last frames, with the one before and the one after. Each is `frame-<frame>.png`, with where the two differ when they do.

The clip shows the original and the Dreamport side by side, with the frame's number, and *differs* over frames whose picture doesn't match, or *sound differs* over those where only the sound doesn't. It has no sound itself. It holds every frame, about 60 a second, made inside the browser rather than filmed from a screen, so it's smooth. It shows the frames the recording's `clip` names, or else five seconds from a second before the first frame this step changed, ending before the first frame that differs, as every frame of a clip matches. A recording that changed nothing shows its last five seconds, or the time around its first difference. A frame where only the sound changed, on main or now, starts the clip only when no frame's picture changed, as a clip has no sound: `prove` then says the change is only heard ([#1194](https://github.com/NahuelGenchi/dreamports/issues/1194)). The first frame a step changed is told from main's proof as the branch started from it: in a recording main proved the same, the first frame that matches now and didn't on main, or the other way round, and in one it didn't, the first frame whose original runs code main's proof doesn't count. A part `parts.json` names for the recording that main didn't prove, and that matches now, comes first from its own first frame, as other recordings can count its code already, which would leave the clip at its end ([#1258](https://github.com/NahuelGenchi/dreamports/issues/1258)). `prove` prints it as *What this step changed*, and says at once what `share` would refuse. It's an H.264 MP4 video, which phones and browsers play, at the console's own size, 480 by 180 with both sides and the bar. Twice that size took about twice the bytes, and more than the 2 MB limit in fast play. It's encoded in the mode browsers have for screens, at up to 2 Mbps. A calm clip stops well short of that, at about 0.1 to 0.3 MB, and five seconds of fast play comes to about 1 MB. A clip that stays over 2 MB is encoded again without that mode, which goes lower. The stills stay at twice the size, with every pixel sharp.

The clips and the pictures show the game, so they stay in `.dreamports/`, which the ignore rules keep out of commits. [Clips](../docs/STANDARD.md#clips) in the standard says where they may be shared: clips of the original in pull requests and nowhere else, and clips of the Dreamport alone anywhere. The original's sound stays there too: `prove` only keeps how loud each frame is, in `report.json`.

## How sound is compared

Both make the console's own sound for each frame: the mix of its four Game Boy channels and its two DirectSound channels, 65,536 samples a second, in its 10-bit steps, before the console's volume and filter. The original's comes from mGBA, through [`gba/original.c`](gba/original.c). The Dreamport's comes from its kit's sound engine, which runs on the page while the tools play the game, a frame of sound after each of the game's frames ([the Game Boy Advance kit's](../kit/gba/README.md#for-the-proof-tools)). A game that doesn't play its sound through the kit is silent to the tools.

The two never match sample for sample, even when the game is right. The console makes each frame's sound at its own moment in the frame, where the game's sound library runs, and the kit at the frame's start, so the two are a fraction of a frame apart, and the parts of a sound by different fractions: in Sonic Advance Dreamport, from 128 to 345 of the 1,097 samples a frame has. So `prove` compares how loud each frame is, pitch by pitch:

- The sound is split into eight bands of pitches, each an octave wide, around 125 Hz, 250 Hz and so on up to 16 kHz, on the left and on the right, and measured over the frame with the one before and the one after.
- A frame's sound is the same when every band is within 10 dB of the original's, which listeners hear as twice or half as loud. A band quieter than one of the console's steps counts as silent.
- When one is silent in every band and the other isn't, the frame differs, however quiet the sound. Two silent frames are the same.
- The original's sound is taken from as far as a frame before or after, wherever it's closest, so a sound may start or end up to a frame apart.
- A dip counts as the same. When two of the console's voices play the same note, such as a square wave and a sampled instrument, they cancel each other for a moment, and when they do depends on the exact cycle of every write to the square wave since the console was switched on, which a Dreamport can't have. So one note's band, alone or with the bands next to it, may be as far as 16 dB away for up to 8 frames in a row, an eighth of a second. A longer run differs from its ninth frame, and a dip only counts after 8 frames that were the same, so the frames around a sound that is wrong aren't taken for dips. `prove` lists the frames it took for dips.
- The sound of the two frames either side of a stretch only the original has (`onlyInOriginal`) isn't compared, as the original's runs into or out of the screen the Dreamport skips. `prove` says which frames those are.

This catches a Dreamport that is silent where the original plays, or plays where it's silent, plays another sound, or plays it far louder or quieter. It can't tell a sound a frame early or late, a quiet sound missing under a loud one, a difference inside one band, such as a note a little out of tune, or, since dips count as the same, a sound shorter than 8 frames that is missing or wrong while something else within 16 dB of it plays in its band. On Sonic Advance Dreamport's recordings, 98 in every 100 frames with sound are within 3 dB of the original in every band, and none is more than 6.8 dB away but in its dips, which are at most 14.4 dB away for 6 frames, while Sonic Battle Dreamport, which makes no sound yet, is silent wherever its original plays. [`lib/sound.mjs`](lib/sound.mjs) holds the comparison and its numbers.

## The code map and the two numbers

The code map, `games/<game>/proof/code-map.json`, lists every function in the original program with its address and its size, and nothing of its code. It's the first thing a new Dreamport needs, before any of its code, as [the standard](../docs/STANDARD.md#how-progress-is-measured) asks: write the game's `original.json` from what `rom` says about your copy, run `rom` again so the tools know it's the copy the proof uses, then make the code map, and commit both with the game's first files. `npm run dp -- codemap <game>` makes one by finding the functions in your copy itself, following the code from where the game starts, in a Game Boy Advance or an NES game. An NES game's program is in banks, so the code map numbers each of its functions by its offset in the program, and its code names one with its bank, as `sub_04_923F` ([NES addresses](../docs/CONSOLES.md#whats-different-from-the-game-boy-advance)). A decompilation knows its functions better, and `npm run dp -- codemap <game> --from <list>` takes them from a list: what `nm -S` prints from the decompilation's ELF file, or a CSV with a column for the address and one for the size, such as the list of functions Ghidra exports, or for the end, the address just after the function's last byte, as decompilations list their functions' extents. A function listed without either gets the space up to the next one. A list can stop short, as when it didn't follow a function's switch or leaves out what nothing calls, so the tools also follow the code from every function it lists, in your copy, and add what they find beyond them. A listed function keeps its start and its name and grows over the rest of its code, up to the next one listed, and anything else becomes a function of its own, without a name. A list can also name data as a function, as when it takes a switch's table or the words a function loads for the start of another, so a listed function that starts in the data of the code before it is left out, the tools say which, and the function before it grows over what it held. `npm run dp -- codemap <game> --fill` does the same to the code map the game already has, keeping its names, which a list doesn't always have.

A game can also run code from its work RAM: code it copies there from the cartridge, such as Sonic Advance's sound mixer, or code it makes there, such as Tiny Chao Garden, the program Sonic Advance unpacks into memory. A code map lists that code too, as the standard asks. In a Game Boy Advance game, `codemap --fill` plays each of the game's recordings in the original, lists the code that ran in the work RAM, reads it back and finds its functions from there, following its calls and branches, and `codemap --memory` does only that, leaving the rest of the map as it is. A stretch that's a copy of the cartridge's code goes in the map's `copies`, as where it runs, from where in the cartridge and how long, and counts as the cartridge's functions, which the copy can split where it shows one starts, as can a function copied whole onto the stack. Code identical to the cartridge's counts as the cartridge's, as Tiny Chao Garden's sound library, the same as Sonic Advance's, does. The rest are functions of their own, each written as its address and its first 8 bytes, as `"020090E8/F0B557464E464546"`, the garden's card game, since a game can put other code at the same address at another time, as the garden's routines take Sonic Advance's place at `0x03000000`. `prove` counts a function in the work RAM only while its bytes are there, and the port map counts a name in the work RAM, such as `0x020090E8`, as each function the game puts at that address. Code the recordings never run, and isn't called from code they run, isn't found, so recordings that play more of the game find more of it. On the other consoles the tools play through libretro, nothing says which functions run yet.

**On the NES.** The tools see an NES game's instructions run too. [FCEUmm](https://github.com/libretro/libretro-fceumm), like every libretro core, says nothing of them by itself, and has no debugger left in it to ask, so `setup` builds it with a change of the project's own, [`libretro/fceumm.patch`](libretro/fceumm.patch): between reading an instruction and running it, the processor calls the program that plays the original ([`libretro/host.c`](libretro/host.c), [`libretro/ran.h`](libretro/ran.h)) with the instruction's address, where that is in the cartridge's program whatever bank is switched in there, its first byte and the registers. It only looks, so every frame's picture and sound are the same with it or without, which `npm run test:real-console` checks, sample for sample. FCEUmm is under the GNU General Public License version 2: it's built and run on your computer, and nothing of it is in the repository but the lines of its own the change sits between. [The function check's processor](#the-function-check-on-the-nes) is built from the same source, so it has the two lines of the change that are in `x6502.c`, with nothing for them to call.

From that, `prove` lists the functions that ran in each recording's matching frames, in `progress.json`, as on the Game Boy Advance, and says how many instructions ran outside every function of the code map. `codemap --fill` plays each recording in the original and adds the functions play sends the processor to that following the code didn't find. A place a `JSR` called starts a function wherever it is, cut from the function it was in if it was in one. A place a `JMP ($xxxx)` jumped to, or an `RTS` returned to that isn't just after a `JSR`, as an address a routine pushed is, starts one only outside every function of the map: inside one it's that function's own code, as a switch's case is. An interrupt between two instructions is told apart by the three bytes it leaves on the stack. The code is then followed from each new function, as from a listed one. `prove` also keeps what the processor held as each function started, A, X, Y, the stack pointer and the flags, up to 16 different sets for a function, in `registers.json` beside the recording's results in `.dreamports/results/`, for the function check to try a twin with what play really gave it. Nothing reads them yet.

Each Dreamport shows two numbers, code ported and gameplay proven, which [the standard](../docs/STANDARD.md#how-progress-is-measured) explains. The tools write what both are measured with.

`prove` notes which of the original's functions ran in each frame, keeps those that ran in frames that matched, picture and sound, and writes them to `games/<game>/proof/progress.json`, with each recording's results: how many frames it has, which ones differ, and of those which differ by their sound, as `soundDiffers`, and the share of the code map's size those functions make. Recordings it didn't play this time count as they were last proven. It also says how many of the original's instructions ran outside every function of the code map, in the cartridge or in the console's work RAM: code the map is missing, which `codemap --fill` adds.

`npm run dp -- portmap <game>` writes the port map, `games/<game>/proof/port-map.json`: each function of the original that the game's code names, with the first file and line that names it, and every name that lands inside a function of the code map but not at its start, which is usually a mistake. A name is an address in the cartridge, written as a number, such as `0x08029E78`, or as a label, such as `sub_8029E78`, or `FUN_08029E78` as Ghidra writes them. On the NES it's always a label with the bank switched in at $8000, in two hexadecimal digits, as `sub_04_923F`, or with none for the last bank, which is always at $C000, as `sub_C39C`. An address outside every function of the code map is the game's data, such as a picture the code copies, and isn't counted or listed. The port map also lists the version's [stops](../docs/STANDARD.md#stops), the paths of the original its code says it hasn't ported: the words `dp:stop` in a line, in a comment where the path would be, and after them the address of what isn't ported, written as a name is, as in `// dp:stop 0x0800486C`. Every name after the words on that line is a stop and none of them a name, so they go last on the line. Each stop is listed with the function of the original its address is in, anywhere in it, or with none when the code map has no function there, and `portmap` says how many it found. A number is an address in the copy the proof uses. A label is one in the release the game's labels come from, and when that's another release, the game's `proof/names.json` says how far each stretch of its code is from the copy's. Sonic Advance Dreamport's code uses the labels of a decompilation built from the European release, and [its `names.json`](../games/sonic-advance/proof/names.json) gives the shifts to the USA release. Run it after changing the game's code; `npm run check` says when a port map is out of date.

Code ported is the size of the functions the port map names, but those with a stop in them, divided by the size of every function in the code map. A function `prove` found running in matching play counts only once the code names it, since [#1452](https://github.com/NahuelGenchi/dreamports/issues/1452), and until then `prove` says how many there are. It also compares what the game saves ([Saves](../docs/STANDARD.md#saves)): with `DP_SAVES` the program that plays the original gives the cartridge's save memory each time a frame changed it, the Dreamport's page gives what the game wrote through the kit's `cartridgeSave` (`kit/gba/save.js`), changes no more than 60 frames apart count as one write, as a flash takes a sector over some twenty frames, and a write is the same only byte for byte (`tools/lib/saves.mjs`). For a recording where they differ it names the first write that does, with the original's frame and the first byte, and `progress.json` keeps the counts, never the bytes. After the two numbers `prove` says what keeps a version from done whatever they are: how many of the original's writes of its save came out the same, how many stops it has, in how many functions, and how many functions of the code map no code names yet. Gameplay proven is the share of the original's code played in frames that matched: every instruction of the code map's functions counts once it has run in one, and every conditional branch once for each of its two ways. The program that plays the original writes what ran, with the stretches of frames each thing happened in (`DP_PLAYED` in `tools/gba/original.c`), and `prove` keeps what fell in each recording's matching frames in `games/<version>/proof/played.json` (`tools/lib/played.mjs`), with where each function's instructions and branches are: found by following its bytes from its start and from every place that ran, through both ways of each branch, as a switch's cases show only once they run. Its total is in `progress.json`, under `played`. The cartridge's data counts beside it, under `content`: with `DP_CONTENT` the program watches every read and write the processor, the BIOS and DMA make, and writes the cells of 32 bytes the game used something of, with their stretches of frames. Data is used when it's read and anything is done with it but writing it as it is into the work RAM; a copy there, or what a BIOS call unpacks there, is followed, and counts where it came from once it's read from the work RAM and used, an unpacked byte as the place as far through the packed data as it is through what came out. Data a game unpacks with code of its own counts as it's read. The cells that count are those with a byte outside every function of the code map, but those whose bytes are all the same. Gameplay proven is the lower of the two shares. The parts in `games/<game>/proof/parts.json` are still proven one by one, each when a recording plays it with every frame from its first to its last matching, picture and sound, with none the Dreamport doesn't have, and on a console whose instructions the tools don't see run, their share is still gameplay proven. On the NES the tools see the instructions run, and an NES game's gameplay proven is still its parts' share. The number is the lower of the code played and the content used, and the cartridge's data isn't followed on the NES yet, so the code's share alone must not become it: `prove` writes what ran to the game's `played.json`, every instruction and each way of every branch, counted a byte at a place, with a function's instructions those the function finder reaches by following its code, so the addresses of a table aren't taken for code, and leaves `played` and `content` out of its `progress.json`, which is what the game's card reads. That waits on following the data on the NES. `untouched` lists what hasn't been played, and its `--why`, `--sort` and `--decided`, like `route --goal untouched`, are still the Game Boy Advance's alone. The game's page, the launcher's Make row and `docs/STATUS.md` show both, and the site checks that they add up with the files before it shows them, so they only ever come from the tools. The tools also draw each game's progress map from the same files, with [`src/lib/progress-map.mjs`](../src/lib/progress-map.mjs): a picture of every function in the code map and every part, green once it counts. It's kept in `.github/readme/progress/<game>.svg`, which the table in `docs/STATUS.md` links, and the Readme workflow writes both on `main`, every three hours, from what's merged, so pull requests never conflict over them. It's only shown on GitHub, never on the site.

## Starting a game

`npm run dp -- new <game>` starts a Dreamport that someone has claimed and mapped: it needs its [New Dreamport](../docs/TEAMS.md#start-a-dreamport) issue, `proof/original.json` and its code map. It writes `index.html`, `src/main.js`, `LICENSE` and `entry.md` in its folder, then its port map and the table in `docs/STATUS.md`. Its [capture](#a-games-capture) then gives it its place in the Make row. The game's code starts as the kit's start for its console, [`gba/new-game/`](gba/new-game/), with the controller, the touch screen, the settings and the start screen already working, and it shows only a blue screen until someone writes the game. The first three files say the same for anyone with the same `original.json`, so nothing has to be reviewed in them. `new` writes over nothing. A pull request of only these comes in with no review and merges by itself ([A game's first files and its card](../docs/TEAMS.md#a-games-first-files-and-its-card)): `--commit` commits them in the words that needs, and with it `--yes` sends a whole new game's as that pull request, beside the branch you're on, which stays as it is.

`npm run dp -- new <game>/c` starts the game's [version in C](../games/README.md#versions-in-other-languages), on any console: `index.html`, `src/main.c` and `src/main.js` in `games/<game>/c/`, which show the same blue screen, then its port map. In a game that hasn't started, it also writes `LICENSE` and `entry.md` in the game's folder, and no JavaScript version, as a new game starts in C: its version in C is its main one, and `--commit` commits them as the game's first files, which `--yes` sends and which come in with no review of their code like a JavaScript game's. `npm run dp -- new <game>` adds a JavaScript version to it later. Its C stands on its console's [kit in C](../kit/c/README.md), the Game Boy Advance's own or, on any other console, what every console's shares. Every tool takes a version by that name, as in `prove <game>/c` and `play <game>/c`. A version's recordings are the game's, and it keeps only its own `progress.json` and `port-map.json`. The tools build its `src/game.wasm` before they open it, and so does the site.

## Reading the original's instructions

A Dreamport rewrites each of the original's functions from how the original does it, usually from its decompilation's C. When a function has none, because the decompilation hasn't reached it or its C doesn't match, or the game has no decompilation, `npm run dp -- read <game> <function>` prints the function's own instructions, the machine code the console runs, from your copy. It knows the Game Boy Advance's instructions, which this section starts with, and the NES's, [further down](#on-the-nes). On the Game Boy Advance the function is an address, such as `0x08016078`, a name in the code map, such as `FUN_08016078`, or a label of the release the game's labels come from, such as `Task_803775C`, which `names.json` moves to the copy's address as it does for `portmap`. It prints the whole function, as the code map has it. When a label doesn't land where a function starts, it says so first, since `names.json` may not say how far that label moved, and it may be the wrong function.

mGBA's own decoder reads the instructions. The library `setup` builds leaves out the part that writes them as text, so `setup` builds that part on its own, with [`gba/read.c`](gba/read.c), and each line is the one mGBA's debugger shows for the same address. On 1 November 2026, for every function in Sonic Battle's and Sonic Advance's code maps, all 381,615 lines it printed as instructions were the same as mGBA 0.10.5's `disassemble` command printed. An automated player then ran 1,860 of those functions, for 198 hours of the games' time: none of the addresses they ran fell on a line printed as data or in the other kind of instructions, and none of the words they read from their own code fell on a line printed as an instruction. For the 82 Sonic Advance functions whose assembly its decompilation keeps, all 24,197 instructions and 1,695 words of data came out the same. Beyond what mGBA's debugger shows, `read`:

- Writes the numbers the code keeps beside itself, its literal pool, as `.word`, and a switch's jump table, the address of each of its cases, the same way, with any padding before them as `.hword`. It finds them by following the game's code from every function in the code map, since a code map entry can start partway into a function and keep its numbers in the next entry. What none of that code reaches still reads as instructions, as it does in mGBA's debugger.
- Follows code that changes from Thumb to ARM or back partway through a function, as a game's sound driver does, and a line such as `@ ARM from here` says where.
- Adds the code map's name of each function a line calls or loads the address of, after `@`.
- Reads the function as ARM or Thumb, the console's two kinds of instructions, as the tools found it by following the game's code, or else from how its first instructions look. `--arm` or `--thumb` reads it the other way, following the code only from that address.
- Reads `--bytes <n>` bytes from the address instead of the whole function. A function the code map doesn't list gets as much as the tools can follow of it, or else its first 256 bytes.
- Reads code at `0x02000000` or `0x03000000`, which the game copies into the console's memory to run there, as it is 60 frames after power-on, or `--frame <n>` frames after, following the code only from that address.

What it prints comes from your copy of the game. It goes to the terminal and to `.dreamports/read/<game>/<address>.txt`, and never in a commit, an issue or a pull request, not even a few lines. A coding agent that reads it sends it to the company that runs the agent's model, as it does with everything it reads, so agents reach a copy only through the tools, a function at a time. The Dreamport's code says which function it rewrites, and that's enough.

A line such as `08001234:  4801  ldr r0, =0x03000010  @ 0x0800123C`, made up for this guide, is an address, the bytes there and the instruction they make. A Thumb instruction takes 2 bytes, or 4 for a call, and an ARM one 4. Most of a game's code is Thumb. A short guide to the rest:

- **Registers.** `r0` to `r12` hold numbers, `sp` points to the stack, where a function keeps what doesn't fit in them, `lr` holds where a call returns to, and `pc` the instruction running. A function gets its first four arguments in `r0` to `r3`, gives its result back in `r0`, and leaves `r4` to `r11` as it found them.
- **In and out.** `stmdb sp!, {r4-r6,lr}`, which other tools write as `push`, saves registers as a function starts, and `ldmia sp!, {r4-r6}`, or `pop`, puts them back before it returns with `bx` or by loading `pc`.
- **Calls and branches.** `bl` calls a function. `b` jumps, and `beq`, `bne`, `bhi` and the like jump only when the `cmp` before found the two equal, not equal, greater and so on: `lt`, `gt`, `le` and `ge` compare numbers that can be negative, and `lo`, `hi`, `ls` and `hs` those that can't.
- **Numbers.** `ldr r0, =0x03000010` loads a number from the literal pool, at the address after `@`. `mov` and `add` with `#` use a number written in the instruction itself.
- **Memory.** `ldr` and `str` read and write 32 bits, `ldrh` and `strh` 16, `ldrb` and `strb` 8, and `ldrsh` and `ldrsb` read numbers that can be negative. `[r1, #8]` is the address in `r1` plus 8, often a field of a structure.
- **Addresses.** `0x02000000` and `0x03000000` are the console's work memory, where the game keeps its variables, `0x04000000` its registers, which drive the screen, sound, buttons and copies (`0x040000D4` is DMA 3), `0x05000000` the palettes, `0x06000000` video memory, `0x07000000` the sprites and `0x08000000` the cartridge.
- **The BIOS.** `swi` calls the console's built-in program: `swi #11` is CpuSet, `swi #12` CpuFastSet, `swi #5` waits for the next frame and `swi #6` divides.

[GBATEK](https://problemkaputt.de/gbatek.htm) describes every instruction, register and BIOS call. Rewrite what the function does, not each instruction: readable JavaScript, with names that say what things are, and every number taken from the instructions. Name the function in a comment, by its address or its name in the code map, so the port map counts it, and prove the step. Sonic Battle Dreamport's `newScreen`, in [`games/sonic-battle/src/core.js`](../games/sonic-battle/src/core.js), rewrites `0x08016078`, which its decompilation has no C for.

### On the NES

On an NES game `read` prints the 6502's instructions, the NES's processor. The function is a bank and an address, such as `04:923F`, a label as a game's code names it, such as `sub_04_923F`, or `sub_C39C` in the last bank, an address in the last bank, such as `$C39C`, or an offset in the program as the code map numbers it, such as `0001123F` ([NES addresses](../docs/CONSOLES.md#whats-different-from-the-game-boy-advance)). `--bytes <n>` is its only option. It goes to `.dreamports/read/<game>/<offset>.txt`, by the same rules.

Nothing is built for it. The instruction set is fixed and small, so the tools read it with a table of their own, [`nes/6502.mjs`](nes/6502.mjs): every documented instruction, and the undocumented ones by the names assemblers give them, each marked `undocumented`. The function finder reads the code with the same table. On 17 November 2026, on Ghosts'n Goblins (USA) and Mega Man (USA), every function of both code maps read whole, 831 functions and 57,722 bytes. All 26,391 instructions the finder reached in them by following the games' code came out as instructions of the same length. Of 2,180 calls, 2,053 went to where a function of the code map starts, 104 into one past its start, 22 into a switched bank the finder had followed them into, and 1 to code the map doesn't list. The addressing mode of 181 opcodes is the one [FCEUmm](https://github.com/libretro/libretro-fceumm)'s processor reads them with. Nobody has compared the text with another disassembler's, line by line.

Which bank is where matters on this console, so `read` takes it from the finder ([`nes/functions.mjs`](nes/functions.mjs)), and from the instructions it can't tell more:

- A function in a switched bank is read from that bank, each address after its bank, and the addresses it names at `$8000-$BFFF` are its own bank's. Those at `$C000-$FFFF` are the last bank's.
- A call from the last bank to `$8000-$BFFF` goes to whichever bank is switched in then. The line names the bank the finder followed it into, which it knows when the code switches the bank with a number of its own, or else every bank where the code map has a function at that address, and says which of the two it is.
- A table of addresses the finder saw the code jump with is data: `.word` for a whole address, with its function's name, and `.byte` for a table of low or high bytes. A `JMP` through a pointer, or an `RTS` that jumps, is given the functions the finder followed it to.
- Bytes no code reaches say so where they start. They're written as instructions when they read as documented ones, and as `.byte` when they don't: data the finder doesn't know, or code only a table it doesn't follow leads to.
- A branch that lands inside another instruction, as when a `BIT` hides the instruction after it, is read both ways, and so is one whose last bytes are the next function's first.
- It can't know what a register holds, so not where `JMP ($0004)` goes when the finder didn't follow it, nor which bank an MMC1 cartridge has switched in, which it sets a bit at a time. It reads the cartridge only: code a game copies into the console's memory isn't read, and a function the code map lists that no code leads to gets a line that says so first.

A line such as `04:923F:  20 9C C3  JSR $C39C  ; sub_C39C`, made up for this guide, is the bank and the address, the bytes there, the instruction they make, and the name of what it calls. An instruction takes 1 to 3 bytes: the first says what it does and how the rest is read. A short guide to the rest:

- **Registers.** There are three, each 8 bits: `A`, where sums and logic happen, and `X` and `Y`, which count and index. `LDA`, `LDX` and `LDY` load them, `STA`, `STX` and `STY` store them, and `TAX`, `TYA` and the like copy one to another. A function has no fixed way of being given values: read what it uses before it sets it, which may be any of the three, a flag, or a byte in memory.
- **Operands.** `#$10` is the number 0x10 itself. `$10` is the byte at address 0x10, and `$0300` the byte at 0x0300. `$0300,X` is the byte at 0x0300 plus `X`, an entry of a table. `($10),Y` reads a 16-bit address from 0x10 and 0x11, low byte first, and adds `Y`: a pointer. `($10,X)` adds `X` first and then reads the address. `A` alone, as in `ASL A`, is the register.
- **Zero page.** Addresses 0x00 to 0xFF take one byte to name, so games keep their busiest variables and every pointer there. `$10,X` wraps round within it: 0xF8 plus 0x10 is 0x08, not 0x108.
- **Flags.** Each instruction that loads or works out a value sets `Z` when it's zero and `N` when its top bit is set. `CMP`, `CPX` and `CPY` subtract without keeping the result: `BEQ` and `BNE` then jump on equal and not equal, and `BCS` and `BCC` on greater-or-equal and less, for numbers that can't be negative. `BMI` and `BPL` test `N`, `BVS` and `BVC` test `V`, which a signed sum that overflowed sets. A function often gives its answer in a flag, the carry most of all: `SEC` or `CLC` before `RTS`, and `BCS` after the call.
- **Sums.** Everything is 8 bits and wraps round at 256. `ADC` adds with the carry and `SBC` subtracts with its opposite, so `CLC` comes before an addition and `SEC` before a subtraction, and a 16-bit number is added a byte at a time, the carry going from the low byte to the high. `ASL` and `LSR` shift, `ROL` and `ROR` shift through the carry, and `INC`, `DEC`, `INX`, `DEY` and the like add or take one. The NES's processor has no decimal mode, so `SED` changes nothing.
- **The stack.** It's the page at 0x0100 to 0x01FF, and `S` points into it. `JSR` pushes where to come back to, less one, and `RTS` pulls it and goes on after the call. `PHA` and `PLA` push and pull `A`, `PHP` and `PLP` the flags, and `TSX` and `TXS` copy `S` from and to `X`. Games jump with it too: two bytes pushed and an `RTS` is a jump to that address plus one, and a routine that pulls two bytes as it starts is reading the list of addresses after the `JSR` that called it.
- **Jumps.** `JMP $C39C` goes there, and `JMP ($0004)` goes to the address kept at 0x0004 and 0x0005. A `JMP` to another function as a function's last instruction is a call that never comes back here. `RTI` ends an interrupt, such as the one at each V-blank.
- **Addresses.** 0x0000 to 0x07FF is the console's work memory. 0x2000 to 0x2007 are the picture's registers: 0x2000 and 0x2001 its settings, 0x2002 its status, which says the V-blank has started, 0x2005 the scroll, and 0x2006 and 0x2007 the address in video memory and the byte written there. 0x4000 to 0x4015 are the sound's, 0x4014 copies a page to the sprites, and 0x4016 and 0x4017 read the controllers. 0x6000 to 0x7FFF is the cartridge's own memory, if it has any, and 0x8000 to 0xFFFF the program. A write there switches a bank. The last six bytes of the last bank are the three vectors: the V-blank interrupt, the reset and the other interrupt.

The [NESdev Wiki](https://www.nesdev.org/wiki/) describes every instruction, register and cartridge. Each sum that wraps round, each byte the function writes and what it leaves in `A`, `X`, `Y` and the carry is part of what it does, so a rewrite keeps them. Name the function in a comment by its label, such as `sub_04_923F`, so the port map counts it.

## Matching the original's bytes

The strongest proof a function has is that it comes out as the original's own bytes. `npm run dp -- match <version>` builds a Game Boy Advance game's C with the compiler the original was built with, compares each function with the original's, and says for each `The same` or `Differs`, with how many of its halfwords differ, whether it's longer or shorter, and the address of the first that differs. It ends with a total, such as `10 of 12 functions the same, 966 of 1,294 bytes.` The version is a game's version in C, such as `sonic-advance/c`. `npm run dp -- match <version> <file>` builds one file, and `npm run dp -- match <version> <function>`, with an address or a name, builds the file with that function's twin and keeps each of the original's instructions beside the twin's in `.dreamports/match/<version>/<address>.txt`, a `!` before each line that differs.

It prints nothing of the original: a name, an address, a length and a count are all it says. The file it keeps does hold the original's instructions, so it stays in `.dreamports/` and never goes in a commit, an issue or a pull request, as with what `read` prints. `match` reaches your copy only through the program `read` uses, [`gba/read.c`](gba/read.c).

**Which function a twin is.** A function says which function of the original it's the twin of the way `portmap` reads it, so the port map and `match` agree: the comment just above it names the address, as in `/** TaskCreate, 0x08001588: a task after every task of its priority. */`, and the first address in that comment is the one. A function whose own name is a label, such as `sub_8001588`, needs no comment. A label is moved by the game's `names.json`, as `portmap` moves it. A function with neither is listed as `No address` and compared with nothing.

**The names a file uses.** A linker would give every call and every value its address, and `match` does that with the original's addresses, so no linker runs. A function defined in another file of the version has the address its comment gives it. A name that is a label says its own, such as `gUnknown_03004C54`. Every other name is in the game's `proof/addresses.json`, which holds names and addresses and nothing of the game's code:

```json
{
  "about": "Where the names come from",
  "addresses": { "gTasks": "030006B0", "_call_via_r0": "08099844" }
}
```

An address is written as the code keeps it, in eight capital hexadecimal digits: a Thumb function whose address is kept as a value is odd there, as `080977D9`, and a call doesn't mind which. A function that uses a name with no address can't be the same, and `match` names each one. `--addresses <file>` adds another file of the same shape, for trying a file from anywhere before the game has its names: `npm run dp -- match <version> <any file.c> --addresses <file>`.

**The compiler.** Which compiler built the original, and how it was asked, is the game's, in its `original.json`: `"compiler": { "name": "agbcc", "flags": ["-mthumb-interwork", "-O2", "-fprologue-bugfix"] }`, as Sonic Advance has it. A game was often given the console's libraries already built, another way: Sonic Advance's flash library was built with `-O1`, and its sound library with `old_agbcc`. Each such part of the cartridge goes in the compiler's `stretches`, with its first and last address, as in `"stretches": [{ "from": "08098C00", "to": "080997DF", "name": "agbcc", "flags": ["-mthumb-interwork", "-O1", "-fprologue-bugfix"] }]`. Each file is then built with the compiler of the code its twins are the twins of, so a file holds twins of one way only, and `match` says so of a file that doesn't. The name is `agbcc` or `old_agbcc`, and the flags only those that say how the code is made, never one that names a file. Finding them is trying: a function that is certainly right comes out the same with the right ones and not with others. The file is first run through the preprocessor `npm ci` brings, with `MATCHING` defined, so a file can say `#ifdef MATCHING` where the console's build and a Dreamport's differ, as where one writes to the console's hardware and the other calls the kit. It includes from its own folder and from the version's `src/`. A file written on the kit doesn't build with the console's compiler, and `match` says how many didn't in one line.

**The assembler.** agbcc writes assembly, and nothing every computer has turns that into bytes: the clang `npm ci` brings has no ARM target, and a computer's own assembler isn't the same on Linux, a Mac and Windows. So the tools have a small one of their own, [`gba/thumb.mjs`](gba/thumb.mjs), for exactly what agbcc writes, every Thumb instruction of the console written the way the assemblers of the time read it. It makes the choices GNU's assembler made, which the original's bytes hold: a low register moved to a low register is an add of zero, and a number added to a register in place takes the 8-bit form. On 17 November 2026 it gave the same bytes as clang 21 for every form of every instruction, 1,214 lines kept in [`test/match/forms.s`](test/match/forms.s), and for the 18,542 bytes of four files agbcc wrote from twins of Sonic Advance, of which `match` then found 10 of 12 functions the same as the cartridge's, as the trial in [#1449](https://github.com/NahuelGenchi/dreamports/issues/1449) had with clang. A line it doesn't know stops it with the line's number, never a guess.

**What it compares.** A function runs as far as the compiler says it does, with the numbers it keeps beside itself. The original's is as long as the code map says, less the zeros that line up the function after it, and where the code map has no function starting, `match` says so and compares the twin's own length. Now and then the code map holds one routine as several functions, each running on into the next, as where a branch lands in the middle of it. A twin of the whole routine then names the run in its comment, from its first function to its last, as in `/** VBlankIntr, 0x08001AA4 to 0x0800258E: … */`, and `match` compares it with all of them together and keeps each one's proof, so `proofs` and tasks count every one. The port map still counts only the two addresses the comment names. It checks that each starts where the one before ends, and compares nothing when they don't. A twin that names no run and comes out longer than its function, with the bytes after it the same as the next functions', proves only the first, and `match` says to name the run. `twin` still calls the first function only. Only functions in the cartridge are compared, not yet those a game copies into the console's memory.

`npm run test:match` tries all of it with a program of the project's own, [`test/match/program.c`](test/match/program.c), against a cartridge it makes up from it, and it runs on every pull request. Building the compiler and `match` have been run only on Linux. The assembler and the rest of `match` are JavaScript, the same everywhere, but nobody has built agbcc with these steps on a Mac or on Windows yet.

## Checking a twin against the original's memory

Where no compiler gives the original's bytes back, a twin's proof is that it leaves the same memory as the original's function. `npm run dp -- twin` is that check on every console that has one, and the console is the game's: this is the Game Boy Advance's, and [the NES's](#the-function-check-on-the-nes) is below. `npm run dp -- twin <version> <function>` calls one function of the original in mGBA and its twin, built as a Dreamport, from the same memory, with the same arguments, 2,000 times, each call from the memory the one before left, and after every call compares the console's work memory, its palette, its video memory, its sprites' list and what the function gave back, byte for byte. `npm run dp -- twin <version>` checks every twin the version has, a file at a time, calling a file's functions in turn so that what one leaves is what the next starts from. The version is a game's version in C, such as `sonic-advance/c`, and the function an address or a name, as for `match`.

It says of each function `The same memory`, or what kept it from that. For one that `Differs` it says the call, what it was given, the values that were changed for it, the first address that differs and what each side left there, as the test's own program has it in `call 56, Fall(), after 0x03000104 was set to 0x0000: at 0x03000106, in the work memory, the twin left 0xCB and the original 0xCA`. A twin that is still going after 2 seconds `Never came back`: it's stopped, said, and the rest are checked. It ends with a total, and with 3 in place of 0 when a twin differed, stopped or never came back. The same seed makes the same calls, so a difference can be had again after a fix. `--calls <n>` compares that many calls of each function, `--seed <n>` makes up other calls, `--frames <n>` plays the original that many frames from power-on before the first call, 600 unless said, `--seconds <n>` gives a twin longer, `--addresses <file>` adds names as it does for `match`, and `--memories` has the calls start from [memories of play](#memories-of-play).

**The same C as `match` builds.** A twin needs nothing added to keep the console's memory. The check builds the file with the compiler `npm ci` brings, without `MATCHING` defined, and then gives what it built the console's addresses, as a linker would if WebAssembly's could ([`lib/wasm-addresses.mjs`](lib/wasm-addresses.mjs)): every value the C names and doesn't define sits where the console has it, at the address its label, the game's `proof/addresses.json` or `--addresses` gives, a function's address kept as a value is its address in the original, odd for Thumb, and a call through a pointer finds the twin of the address it holds. The cartridge is where the console has it too, from your copy, so a twin reads the game's data from there.

**On the kit.** A twin is built on its console's kit, with the folders and sources the game's own build takes ([`lib/c.mjs`](lib/c.mjs)), so one that includes `gba.h` builds, and its hardware work is the kit's: `gba_vram_write8()` writes a byte to video memory as the console does, where the test once had a stand-in. The video memory, the colours and the sprites a twin on the kit leaves are the kit's own, `gba_vram`, `gba_pal` and `gba_oam`, so those are what the check gives each call and compares with the original's, at the addresses the console has them, and a value the check changes in one of them before a call goes there too ([#1497](https://github.com/NahuelGenchi/dreamports/issues/1497)). The kit is told the copy is the cartridge, for a twin that reads it as `gba_rom`. The two builds ask the compiler the same things from one place: how the C is worked out, what a build to WebAssembly needs, and what the console's compiler takes for granted, a `char` with no sign and code that reads through any pointer, which the game's build asks too for a game that includes `"twins.h"`. The check adds GNU C, which C written for the console's compiler is, and asks for no warnings, which are the game's build's to give.

**A file at a time.** Each file of the version is built once, by itself, however many checks use it. A file's check links it with the files that define what it names, functions and values, and with those that define what they name, found by what each file built says it defines and not by reading the C. A value the console has an address for is the console's, and one a file of the version defines is that file's, as a game not yet written as twins keeps its own. A function it calls that nothing built defines stops the call, and the check says which. A twin that takes or gives a struct as it is, not through a pointer, can't be called with whole words, so it's `Not checked` and the rest of its file is. A twin written with the build's `twins.h`, `TWIN_ADDRESS` and `TWIN`, is checked as it is.

**What it gives a function.** Which paths of a function run depends on what it's given and on what it reads, so the check learns as it goes. The program that calls the original says which values each call read from memory and which values it compared, and the calls after it change a few of those, mostly to what they were compared with and the numbers beside it. That's what finds a `>` written as `>=`: nothing tells the two apart but the one value where they meet, and a function is never given it by chance. A function is also given what earlier calls gave back, the addresses of the things the code names, and the arguments of calls that could be compared. What a function's code keeps for itself is never changed: a constant it loads through the program counter, from beside its code, and the code a call ran from the work memory, where a game copies code to run it faster, as the Game Boy Advance's sound engine does with its mixer, are the code's and not values it was given ([#1518](https://github.com/NahuelGenchi/dreamports/issues/1518)).

<a id="memories-of-play"></a>**Memories of play.** Most of a game's functions read what only play sets up: the task that is running, the level's things, a heap. From the memory of power-on they find nothing, the original leaves for an address near 0, and the function is `Not checked`. `npm run dp -- twin <version> [<function>] --memories` plays the game's recordings in the original first, or only those named after it, as `prove` plays them, and each time the processor reaches a function the version has a twin of, keeps the console's memory as it was just then, with what the registers and the stack held ([`gba/twin-memories.mjs`](gba/twin-memories.mjs)). A memory is taken as the function starts, and not at the end of a frame it ran in, because that is the one moment the memory is what the function was really given, and its arguments and its caller's stack are there too. A function that runs every frame starts millions of times, so its 1st, 3rd, 9th start and so on, by threes, are looked at in each recording, and four are kept for a function, no two the same bytes, chosen by a number made from the recording's name and the start's count: the same recordings give the same memories, in whatever order they're played, which is several at once. A recording of several consoles on a link is left out.

A function's calls then start from its own memories, on both sides: the work memory, the colours, the video memory and the sprites as they were, the arguments play gave it, and the stack it had, so a pointer to something of its caller's still points at it. Half of those calls are the call play made and nothing else. The other half change what the function reads, as every call does without memories, and now and then one argument, and a function goes on a few calls from what its last one left, as one called every frame does, before another has its turn. A function that never started in any recording starts from the memory of power-on or from another function's memory, one or the other. A call that differs says the memory it started from, or how many calls on from it, as in `call 164, Shine(0x00000000), 6 calls on from the memory of made-up-play at frame 23`. The same seed and the same recordings make the same calls again.

The memories are the game's own, from your copy, so they're kept only in `.dreamports/twin/<version>/`, packed, and never in a commit, an issue or a pull request. They're taken again only when the copy, the version's functions or a recording changes. Without `--memories` nothing is played and every call starts as it did before.

On 17 November 2026, on Sonic Advance (USA) in C, whose 617 functions aren't written as twins yet: from the memory of power-on 210 were checked, 3 the same, 171 that differ and 36 stopped, and 407 weren't, in 1 minute 40 seconds. With `--memories`, from its 101 recordings one console plays, 771,042 frames, 1,818 memories of 502 functions were kept in 39 seconds, 113.7 MB, and 489 were checked, 4 the same, 394 that differ, 85 stopped, 2 that never came back and 4 with too few calls, and 128 weren't, in 2 minutes 8 seconds with the play, and the same lines came out when the memories were taken again. Of those 128, 40 never start in any recording, and 59 call the BIOS.

**Aiming at a path.** A branch that needs a few values each just so at once is one made-up calls almost never take, and a function isn't proven until its calls take every path. So the check aims some of its calls ([#1501](https://github.com/NahuelGenchi/dreamports/issues/1501)). The program that calls the original follows where each register's value came from: an argument, or a value read from the image, and the steps it took since, a number added, a shift or a mask. At each comparison of the function's own it says the two values and where each came from. Now and then the check works out which of the function's branches its calls have taken only one way, keeps a few calls that made the comparison just before each as witnesses, and makes a third of its calls aimed ones: a witness again, from the memory it started from, with the one value that comparison read set so the branch goes the other way. For a byte or a halfword that's the nearest value that does it, worked out through the steps; for a word, one the steps of adding alone give. A branch the aimed calls take opens the next one, which is aimed at in turn. An aimed call is compared like any other, so a proof still needs every path taken and every call the same, and its line says how many calls were aimed. What one value can't do, such as a branch that needs two values that agree, is left to the made-up calls. `--changes false` turns aiming off with the rest of the changes.

**What it sets aside.** A call isn't compared, and is taken back on both sides, when the original doesn't come back within 500,000 instructions, when it goes where a twin can't follow, which is the BIOS, unless a `swi` took it there, the save memory, memory that isn't there, a halfword or a word at an address none starts at, which the console moves and C doesn't, or a stack 8 KB deep, when the twin calls something nothing built defines, and when a call through a pointer meets a function that takes or gives something else, which WebAssembly stops and the console doesn't. A function with fewer calls compared than asked for is `Too few calls`, with the reasons and how many calls each cost, and one with none is `Not checked`. Neither counts as the same memory.

**The BIOS, when a game calls it.** A game asks the BIOS for some work with a `swi`, as Sonic Advance divides through its stubs `Div` and `Mod`, and the twin does that work itself, as the kit or the version's own hardware file has it. mGBA works most of them out at once and then, as the console takes time over them, runs a few instructions of its own BIOS before it comes back, so the check follows the original there: from the `swi`'s entry at `0x00000008` until it's back in the game's code, the BIOS's code runs, reads its own memory, and the stack it keeps in its own mode is the original's own, put back after the call as the call's stack is ([#1493](https://github.com/NahuelGenchi/dreamports/issues/1493)). A function that reaches the BIOS's memory any other way, as by reading near address 0, is still set aside.

**What a function gives back.** The check compares what a twin gives back only as far as its C says it gives back something: a twin of `void` has nothing to compare. So it reads the original's callers too: every call to the function in the code map's Thumb code, and the caller's instructions after it, until one reads r0, writes it, or leaves. The console's compiler reads r0 after a call only when the function gives back a value, so a twin of `void` whose original's caller reads r0 `Differs` at once, and the line names the call, as in `the call at 0x080177F0 reads r0 after it`. The pilot of [#1455](https://github.com/NahuelGenchi/dreamports/issues/1455) had such a twin, of Sonic Advance's `0x08011DBC`, kept as proven by the same memory until its bytes were compared.

**What it doesn't see.** The stack a call uses is the original's own, and the hardware's registers aren't compared: a twin does the hardware's work through the kit, and when a call that differs used a register the check says which. Each call of the original starts from the same hardware, as the emulator's state is put back after it, so each call of a twin does too: what the twin's module keeps for itself, the kit's registers and what a version's own hardware file keeps, such as a DMA channel's state, is put back before every call, and only the memories of the image go on from one call to the next ([#1499](https://github.com/NahuelGenchi/dreamports/issues/1499)). A twin has no clock, so a call in which a DMA the console starts at a V-blank, an H-blank or the sound's time writes to the image, as a long call that reaches the next V-blank can have, is set aside: `a DMA the console's clock started wrote memory in the middle of the original's call`. One that writes only the hardware's registers, as a game's H-blank DMA for its scrolling does, leaves the call to be compared. The kit's registers start each run empty and aren't given the original's, so `gba_vram_write8()` takes the sprites' tiles to start where they do in the tile modes. A function that waits for the next frame, which a game asks the BIOS for too, isn't checked. Without `--memories`, every call starts from the memory the original has 600 frames after power-on with nothing pressed, or `--frames` frames, so a function that reads what only play sets up finds nothing there, and the original leaves for an address near 0. With them, only the image is play's: the hardware's registers, the sound and the save memory are still as they are after those frames, so a function that reads one of them reads that, and a function no recording reaches has no memory of its own. A path that needs a state the made-up calls never reach isn't run, so thousands of calls the same are strong evidence and not every path: on 17 November 2026 the twelve twins of [#1449](https://github.com/NahuelGenchi/dreamports/issues/1449)'s trial, of Sonic Advance's task list, gave eleven the same over 2,000 calls each on three seeds, in 13 seconds a seed, and the twelfth the same on each of the 1,800 or so calls that could be compared, as it frees memory and most made-up addresses aren't memory it could free. Of five comparisons then changed in them, one at a time, four were found, at calls 3, 5, 9 and 124, and one, which needs a free stretch of memory of exactly no bytes, wasn't in 1,500. And the two compilers lay some things out differently, which the check shows as a difference: the console's compiler makes every struct a multiple of 4 bytes long, so `struct { u8 a; u8 b; }` is 4 bytes there and 2 here, until the twin says the padding itself.

`npm run test:twin` tries all of it with a program of the project's own, [`test/twin/program.c`](test/twin/program.c), which the console's compiler builds into a made-up cartridge that mGBA runs as the original, and it runs on every pull request: every twin the same, a `>` turned to `>=` found only once what the function reads is changed, a byte written to a background tile and to a sprite's tile, a byte of video memory read with what it holds changed, a register of the hardware read and written changed, a call a DMA of the V-blank writes in, set aside, a function reached only through a pointer, a branch made-up calls almost never take, missed without aiming and taken with it, a twin that gives back nothing of a function whose caller uses what it gives back, one that divides through the BIOS and a wrong twin of it, a twin over two files, one written with `twins.h`, a twin that never comes back, one that takes a struct as it is, and a twin that calls something nothing built defines. Then the cartridge is given a game to play, [`test/twin/play.c`](test/twin/play.c), which makes a stage once A is held and has a function that reads a lamp through it: from the memory of power-on that function isn't checked and a wrong twin of it isn't found, from its memories of play it's the same over every call and the wrong twin is found, the same recording gives the same memories and the same calls, a twin that never comes back from a memory is stopped, and nothing the repository tracks has changed. It has been run only on Linux. The check itself is JavaScript and one small program built as `read`'s is, but nobody has run it on a Mac or on Windows yet.

## The function check on the NES

The NES has no compiler that gives a game's bytes back, as its games were written by hand in the processor's own language. So a twin's proof there is the function check alone ([the standard](../docs/STANDARD.md)): one function of the original and its twin run from the same memory and the same registers, thousands of times, and must leave the same. `npm run dp -- twin <version>` runs it on every twin of an NES game's version in C that has a contract, such as `ghosts-n-goblins/c`, and `npm run dp -- twin <version> <function>...` on those named, one or several, by the original's function, such as `sub_F321`, or by the twin's own name. It says for each `the same on all 10,000 calls` or `differs`, with what differs and the first call that showed it, and ends with a total, and with 3 in place of 0 when a twin isn't the same, as on the Game Boy Advance. It's the same tool: [`twin.mjs`](twin.mjs) sees that the game is the NES's and hands the command, as it was typed, to [`nes/twin.mjs`](nes/twin.mjs), which reads its own options. `--calls` and `--seed` mean what they do on the Game Boy Advance, and `--seconds <n>` is how long one call may take, which `--limit` says in milliseconds. `--frames` and `--addresses` are the Game Boy Advance's, and the NES's check refuses them.

**The two sides.** The original's function runs in [FCEUmm](https://github.com/libretro/libretro-fceumm)'s own processor, the one the proof's emulator runs every game on: its `x6502.c`, built by itself, from the source the tools fetch for the reference emulator at the commit [`consoles.mjs`](consoles.mjs) names. It's as its makers wrote it but for the two lines the tools add so the emulator can tell them what ran ([`libretro/fceumm.patch`](libretro/fceumm.patch)), which do nothing here, as the check gives them nothing to call. FCEUmm is GPL-2.0, so nothing of it is in the repository: the tools copy five of its files into `.dreamports/twin/` on your computer and build them there, beside two small headers of their own that stand in for the rest of the emulator ([`nes/twin/core/`](nes/twin/core/)). The twin's side is the game's C, built for your computer as it is, on a stand-in for the kit that draws and plays nothing ([`nes/twin/kit.c`](nes/twin/kit.c)). Both get the same 2 KB of work memory, and [`nes/twin/check.c`](nes/twin/check.c) compares what each leaves:

- Every byte of the work memory. In the stack's page, what the original pushed and left behind isn't the game's memory, so a byte there counts only if the original stored to it or the twin changed it.
- What the contract says the twin gives back.
- Each store to the picture's and the sound's registers, and each read of them, in order. A read gets the same made-up value on both sides.
- The bank the original leaves at `$8000`, when the game says where it keeps that.
- The time, when the twin counts it: what it gives `nes_spend` against the original's cycles, from its first instruction to the end of its `RTS`.

**The contract.** A function of the original takes and gives values in the processor's three registers, `A`, `X` and `Y`, and in its flags, `N`, `V`, `Z` and `C`, and nothing in C says which. So each twin has one line beside it, in a comment, which the check reads:

```c
// dp:twin sub_F321 show_object(X)
// dp:twin sub_F68E arthur_touches(X) -> C if X < 25
// dp:twin sub_02_8416 zombies_come(&X)
// dp:twin sub_F5F9 +6 weapon_that_touches(X) -> C ? Y : 0
```

After `dp:twin` comes the original's function, named as the game's code names it for `portmap`, and then the call of the twin, in C, with the registers and flags it's given written as themselves. A register given with `&` is one the twin changes, and it's compared with the original's afterwards. After `->` comes what the twin's result has to equal, in C, of the original's registers and flags once it has returned: `-> C` for a result that is the carry, `-> !Z`, `-> C ? Y : 0`. After `if` comes what the game gives it, in C, of the registers and the work memory: the check calls it with nothing else, as a twin needn't do what the original does with an object that isn't there. A number before the call, such as `+6`, is how many cycles the twin counts beyond the function's own: 6 for one that counts the `JSR` that calls it.

It's one line because the twin's own declaration already says the rest, and it's C because the compiler then reads it against that declaration: a name the game doesn't have, or one argument too many, stops the build with the line's number. The check tries every word of it. A register the contract doesn't name gets any value, so a function that takes one the contract leaves out differs, and so does a result looked for in the wrong flag. Each contract is built after its own file's code, in the same unit, so it can call a twin no other file sees.

A game that keeps the number of the bank switched in at `$8000` in its work memory says where, once: `// dp:bank $C7`. The original then starts with that bank, or with its own when the function is in a switched one, and has to leave the one the twin's memory says.

**Time and the hardware.** The game's C is built with `DP_TWIN_CHECK` defined. What it spends and writes reaches the check through the kit, `nes_spend`, `nes_write` and `nes_read`. A game that keeps its own time, to run its interrupt partway through a function as Ghosts'n Goblins Dreamport does, passes them straight on under `DP_TWIN_CHECK`.

**The memories.** With none, each call starts from random bytes. `--memories` plays the game's recordings in the original, or those named after it, and keeps its work memory every so many frames, about 2,000 in all, in `.dreamports/twin/<game>/memories.bin`. They come from your copy, so they stay on your computer. With memories, each twin gets `--calls` calls, 5,000 unless you say, from a memory as it was, and as many "changed": the original runs once to say which bytes it reads, a few of those get other values, some of them at the edges where a sum wraps round, and it runs again. Without memories every call is a changed one. `--seed` draws other calls.

**When a twin goes wrong.** One that falls over is counted and the check goes on. One that doesn't return within `--limit` milliseconds, 200 unless you say, is stopped, and after three the check of that twin ends. A call in which the original reads where nothing answers on the cartridge is left out and counted, as it isn't one the game makes.

**Finding out more.** `--without 23,9F` leaves those bytes of the work memory out of what's compared, to see what else differs: it changes what's printed, never what a twin has to do. `--from <folder>` reads the game's C from another folder than its own `src/`, to try contracts before they're in the game.

**What it can't check yet.** The registers a call starts with are drawn, not taken from play, so `if` has to say what the game gives. The stack always starts in the same place. It lays out the program of a cartridge that switches nothing and of UNROM, and no other yet. A function that waits for the picture, or for an interrupt, can't be checked across the wait. On Windows nothing stops one call that never returns, so the whole check of that twin is stopped instead, and that hasn't been tried.

`npm run test:nes-twin` tries all of it with a program of the project's own and its twins ([`test/nes-twin/game.c`](test/nes-twin/game.c)), on every pull request: every twin the same, then one line changed at a time, a wrong number, a wrong flag in a contract, a register a contract leaves out, a place in a table that doesn't wrap round at 256, a wrong time, a twin that falls over and one that never returns. Then it makes the program a game of its own for as long as the test takes and runs `npm run dp -- twin` on it: every twin, some by name, an option before the version, a twin that differs, which has to end the tool with 3, and an option of the Game Boy Advance's, which has to be refused.

On 17 November 2026 it ran on Ghosts'n Goblins (USA), with 2,032 memories from the game's 39 recordings and a contract for each of the 22 twins the trial in [#1451](https://github.com/NahuelGenchi/dreamports/issues/1451) tried, written in a copy of the game's C outside the repository: 5,000 calls each from a memory as it was and 5,000 changed. Every contract's registers and flags held. 12 twins left the same memory, result and hardware as the original on every call from a real memory, where the trial, with 1,720 memories from four recordings, had 15: this check also counts a call in which the original reads the picture's registers through a pointer, which the trial left out, and the wider memories reached one more difference. 7 were the same in everything, the changed memories and the time too.

## A function's proof, and a game made a function at a time

`match` and `twin` say whether a function is proven, and a version that keeps its proofs holds what they found in `games/<version>/proof/proofs.json`, a function to a line ([`lib/proofs.mjs`](lib/proofs.mjs)):

```json
{
  "original": "the copy's SHA-1",
  "from": "who writes it",
  "functions": [
    ["080001C4", "bytes", "1f0c2ab94e77d310", "9a3e0c5512f8b6aa"],
    ["0800024C", "memory", "77b2910c4dd0e2f1", "c41d7e02ab9935c8", 2000]
  ]
}
```

A line is a function of the code map, the kind of proof, `bytes` for the same bytes and `memory` for the same memory, a mark of the twin as it was written then, a mark of the original's function as the copy had it, and for `memory` how many calls were compared. A mark is the start of a SHA-1, so the file holds nothing of the game. **Only `match` and `twin` write a line**, each for what it found the same, and a function either finds differs loses its line of that kind. The same bytes are the stronger proof, so `twin` leaves such a line as it is. Neither keeps anything found with `--addresses`, with another folder's C or with bytes left out, and `twin` keeps nothing from fewer than 1,000 calls.

**A proof goes stale by itself.** The twin's mark is of its own code, of what its file holds outside every function, such as its `#define` lines and declarations, and of the game's own headers its file includes, without their comments and with every run of spaces as one. So a comment can change freely, and once the code of a twin changes, or a line of its file outside the functions, or a header of its file, or the contract beside an NES twin, its line no longer counts and the tool has to prove it again. The same goes for the original's side when a code map gives the function other bytes. `npm run dp -- proofs --check`, which `npm run check` runs for every version that keeps its proofs, fails on a line that doesn't hold, and on one written by hand: on a computer with no copy of the game it looks at the twin's side, and with one at the original's too.

**A path left out is never proven.** A twin with a [stop](../docs/STANDARD.md#stops) in it isn't kept, even when it comes out the same, and a line from before the stop was written stops counting. The same memory is a proof only of the paths the calls took, so `twin` also asks the program that runs the original which of the function's own instructions each call ran and which way each branch went. A function is `The same memory` and proven only when every instruction of the original's ran in the calls compared and each of its branches went both ways, but for a way the game's `unreachable.json` rules out. One whose calls left some out is said to be the same as far as they went, with the first few it missed, such as `0x0800020E always taken`: more calls, another `--seed`, or on the NES memories from play, reach them. On the Game Boy Advance a switch's cases are found from each word of the function that holds an address inside it, as its table does.

**A version that keeps its proofs is made a function at a time**, and one that doesn't is made a part at a time, as every game was before [#1454](https://github.com/NahuelGenchi/dreamports/issues/1454): nothing here touches it, and `match` and `twin` say what they find and keep nothing. `npm run dp -- proofs <version> --start` writes the file with no line in it, for a version in C on the Game Boy Advance or the NES. That is its lead's to decide for a game that has tasks already, and `/dreamport` does it for a whole new game. From then on:

- `npm run dp -- proofs <version>` says how many functions have each proof and lists the version's tasks, and with a function's address or a task's name, each of its functions with its twin and where it stands.
- `npm run dp -- tasks <version>` opens its tasks from its code map: each a group of functions that sit together, at most 12 and two kilobytes of code, never over more than a kilobyte of the cartridge's data, and on the NES in one bank. A task is named for its first and last function, `Task: Functions 080001C4 to 0800024C in C`, and lists every function with the name the code map gives it, its twin, and whether it's proven and how. Twenty are open at once, the first in the map's order, and the next open as those close. `--update` writes the open ones again from where their functions stand, with a new title for one whose group ends elsewhere since the code map found more functions. GitHub holds 100 issues under one, so the claims bot puts each under the issue of its stretch of the game's code, 64 KB of addresses, such as *Sonic Advance Dreamport in C, code 08000000 to 0800FFFF*, itself under the version's issue ([Where a big game's tasks go](../docs/TEAMS.md#where-a-big-games-tasks-go)). `find`, `tasks` and the Make pages read a game's tasks from its game's issue down, wherever they are.
- `npm run dp -- find <game> --take` goes by each function's proof: a task whose functions are all proven in the folder isn't handed out, and it says what the task is made of and when it's done.
- `npm run dp -- ready <version> --task <a function's address or the task's name>` passes only when every proof kept holds and each function of the task has one, beside what it asks of every step. A game with no recording yet, as a new one has while its first functions are proven, has nothing to play, and it says so in place of failing.
- A Dreamport isn't [done](../docs/STANDARD.md#done) while a function has no proof, which `prove` says with what else is left.

Its parts stay as names for people and as what its recordings are for, and get no tasks. Two kinds of function are in no task, as neither proof reaches one yet, and each still counts as not proven: a function the game makes in its work memory, and a Game Boy Advance cartridge's start, which is the jump at its first address, part of its header, and the code right after the header that it goes to. Those run once, before any function is called, and never come back, so no call of them can be compared, and in a Dreamport that work is the kit's.

`npm run test:function-tasks` tries all of it through the tools as they're typed, with the function check's own program as a game in `games/` for as long as it takes and a stand-in for GitHub, and it runs on every pull request. `npm run test:function-homes` does the same for a big game's tasks: a made-up game of 1,720 functions and 400 groups, with `tasks` opening them twenty at a time to the last, the claims workflow's own script putting each under its stretch's issue, and a stand-in for GitHub that keeps GitHub's limits (`tools/test/stand-in/github.mjs`), so it fails if any issue would hold more than 100. It needs no compiler and nobody's copy, and runs on every pull request too.

## Shared libraries

Many games of a console have code none of them wrote: the console maker's libraries, such as the Game Boy Advance's sound engine, sound drivers and other middleware, and the helpers its compiler adds. Each such function needs a twin and a proof in every Dreamport that has it, so it's written once, in the kit, and each version takes it from there and proves it on its own copy ([#1508](https://github.com/NahuelGenchi/dreamports/issues/1508)).

**Where a library lives.** A library of one console's games is a folder of its kit, `kit/<console>/c/lib/<name>/`, such as `kit/gba/c/lib/m4a/`, and C that several consoles' games share, as the C library of every console with a MIPS processor, is in `kit/c/lib/<name>/`. Its id is `<console>/<name>`, or `c/<name>`. Beside its C, its `NOTICE.md` names each source its twins were written from, by repository and commit, and its `library.json` says what it is, the consoles whose games have it (only in `kit/c/lib/`), the compiler and flags that built it on each console where `match` can build it, its variants, when games have more than one version of it, each as the files it's made of, and each of its twins with the size in bytes of the original's function and its file, or `null` for a function of the library nobody has written yet, named as a public source names it, so all that's known of the library counts:

```json
{
  "about": "Nintendo's sound engine, MusicPlayer2000",
  "compilers": { "gba": { "name": "old_agbcc", "flags": ["-mthumb-interwork", "-O2"] } },
  "variants": { "a": ["engine.c", "mixer-a.c"], "b": ["engine.c", "mixer-b.c"] },
  "functions": [["SoundMain", 1172, "engine.c"], ["SoundMix", 820, "mixer-a.c"]]
}
```

A twin in a library names no address and nothing of any game. It's named as the library's own function, a version of it that differs is a file of its own, never a game's name in an `#if`, and a stop in it is the words `dp:stop` alone, which holds back the function it's in, in every game that has it. Every function its files define is listed, and the files' names are their own among everything a game of its console is built with. `npm run dp -- libraries --check`, part of `npm run check`, holds every library and every version that takes one to these rules, and asks each library for its notice.

**How a version takes one.** Its `proof/libraries.json` names each library it takes, with the variant, and where its copy has each of the library's functions and each value their C names, as the code map's keys, eight capital hexadecimal digits:

```json
{
  "about": "Where the copy has each library's functions",
  "libraries": { "gba/m4a": { "variant": "a", "at": { "SoundMain": "080976BC", "gMPlayTable": "0809B000" } } }
}
```

Every tool then takes the library's twins as the version's own, at those addresses: the build links its C, the port map counts each of them and names it by its place in the kit, as `kit/gba/c/lib/m4a/engine.c:12`, `match` builds its files with the library's own compiler from its folder alone, and `twin` checks them as any twin, on the Game Boy Advance and on the NES, where a contract in a library names the library's own function. A function the version gives no address to isn't in its copy, and isn't checked. `libraries --check` asks that each function a version takes starts where its code map has one of the library's size.

**Finding a library in a new game.** `npm run dp -- libraries <version> --find` looks for every library of the version's console in its copy and writes where it found each into the version's `libraries.json`, so nobody looks for a function by hand. On the Game Boy Advance a library's functions were built once by its maker and linked into each game as they were, the same bytes but where an address goes. So a function the library's compiler rebuilds, as `match` proves it, is found by building the library's C with that compiler, as `match` does, and comparing it with each function of the code map of the library's size, every byte but where a linker fills one. What sits there in the copy then gives where the game has everything the function calls and reads, which go in `libraries.json` too, and a function the code map has twice is told apart by where another function calls it. Nothing of any game is kept for this, as what's compared is built from the library's C. A function no compiler rebuilds, such as a routine written in assembly or a BIOS stub, is found by its short hash in `library.json`: the first 16 digits of a SHA-1 of its bytes with every address masked. `npm run dp -- libraries <version> --hash` writes it, for each function the version proves by the same memory and no version by the same bytes, and `libraries --check` refuses one a version proves by the same bytes, as a compiler rebuilds it. Either way `--find` only says where a function is: `match` or `twin` then proves it on the copy. `npm run dp -- libraries --shared <game> <game>` lists the functions two games on this computer share with every address masked, each by its address in each game and its size, which is how a new library is found. On the NES, whose games were written by hand, no compiler rebuilds a library, so every function is found by its short hash, its bytes with each address of an instruction masked, of the work memory's first page or anywhere. A developer's routine copied into another of its games is the same instructions, with its work memory elsewhere, so where the new game keeps each value the library names comes from another version that takes the library and whose copy is on this computer: what its instruction names at a place, the new game's names at the same place. The NES's build then gives each value to the library's C as `ADDRESS_<name>`, as it reads them. Other consoles find theirs once their tools do ([#1508](https://github.com/NahuelGenchi/dreamports/issues/1508)).

**A proof never carries over.** A version's `proofs.json` gets a line for a library's function only when `match` or `twin` proves it on that version's own copy, at its own addresses, as for any twin. Its mark is of the library's C, so it's the same in every game, and a change to the library makes its proofs stale in every version that takes it at once, which `npm run dp -- proofs --check` says. What carries over is the C: a proof by the same bytes is a build and a compare on the next game, seconds, and one by the same memory is `twin` run again there.

**The number.** `npm run dp -- libraries` says, for each console with a library, how much of its known shared code is proven: every function its libraries list, written or not, by the size of the original's, and proven once it has a proof that holds in a version on that console that takes it. As `proofs --check` does without the game's copy, it goes by the twin's mark alone. The number can fall as a library is added, as it's a share of what's known. With a version, it lists the libraries the version takes and where each of their functions stands.

**The map.** `docs/STATUS.md` shows each console's shared code below the table of Dreamports, as a map in `.github/readme/progress/shared.<console>.svg`, the way AnyPS5's progress map shows its system libraries: the console's number first and largest, with how many games take its libraries, then each library a block in rows that wrap, as wide in its row as it has functions so a row's blocks come out about as tall, with its name, how many of its functions are written and a thin bar of how much of it is proven, and each function a cell, green once proven by the same bytes, blue by the same memory, amber while written and not proven, grey while nobody has written it. Every cell is on one grid, a label is never cut, as a block is never narrower than its name and count, and the map follows the reader's light or dark theme, each colour at least 3:1 against what it's on. `readme` draws it with the games' maps, from the same count as `libraries` ([`src/lib/shared-map.mjs`](../src/lib/shared-map.mjs)), so the Readme workflow redraws it after merges and nobody types a number. Its names come from the libraries' `library.json`, never from a game's files.

A step that only proves functions shows those proofs in a clip's place in a game with no recording yet ([Clips](../docs/STANDARD.md#clips)), and the twins of a library aren't counted that way yet: a version that takes a library shows a clip.

`npm run test:libraries` tries all of it with a made-up library in `kit/gba/c/lib/` and two made-up games in `games/`, each for as long as it takes, the library's two functions at addresses of each game's own and its values elsewhere: both port maps count it, the game's build links its C, `match` proves it on one copy and `twin` on the other, a change to it makes both stale, a stop in it holds both back, `readme` draws the console's map with each function's state, `--hash` keeps a short hash only of a function no version proves by the same bytes, `--find` finds the library in a third game, where nothing says where it is and one of its functions is there twice, and `--shared` lists what two of them share, and `libraries --check` refuses a library that names an address or a function it doesn't list and a version that puts a function where its code map has another. Then every library the kit has is built as `match` builds it, with its own compiler from its folder alone, and to WebAssembly on its console's kit, as a Dreamport that takes it is, so none breaks before a game takes it. It runs on every pull request. `npm run test:nes-libraries` does the same on the NES, with a routine of the project's own in two made-up programs, at another place and work memory in each: `twin` proves it in the first, `--hash` keeps its hash, `--find` finds it in the second by that hash alone, with where that one keeps its values, and not the routine of its size beside it, and `twin` proves it there. It runs on every pull request too.

## The same-memory build

A Dreamport made [the stricter way](../docs/STANDARD.md) keeps every value where the console keeps it, so a function and its twin leave the same memory behind, and an address kept in memory means the same in both. The build does three things for that on the Game Boy Advance, each only for a game whose C asks for it by what it uses. A game that uses none of them builds to the same bytes as before.

**Memory at the console's addresses.** `gba_console_memory(0)`, first thing in `game_start`, makes the console's work memory real where the console has it: 256 KB from `0x02000000` and 32 KB from `0x03000000`, zeroed ([`kit/gba/c/memory.c`](../kit/gba/c/memory.c)). The game's WebAssembly memory grows to reach it, about 50 MB of addresses, of which the browser gives real memory only to what the game touches. Its C then names a value by its address, as in `#define gFrame (*(u32 *)0x03000000)`. With `gba_console_memory(1)` the player's copy is at `0x08000000` too, for a game that reads the cartridge's data by the addresses it's known by, which takes the addresses up to 168 MB for the largest cartridge. Video memory, the colours, the sprites and the registers stay the kit's, and `gba_vram_write8()` writes one byte to video memory as the console does: into both halves of its halfword, or nowhere among the sprites' tiles.

**From an address to its twin.** A function kept in memory, such as the one a sprite runs each frame, is kept as its address in the original, not as whatever the Dreamport's own build makes of it. A game that includes `"twins.h"` gets that file written by the build, and nothing of it is kept in the repository. It comes from the comment above each function, which names the function of the original it's the twin of, as [`portmap`](#the-code-map-and-the-two-numbers) and [`match`](#matching-the-originals-bytes) read it, and from the names in the game's `proof/addresses.json`. A value the game's C names and doesn't define, such as `extern const u16 gWave[8];` for data of the cartridge's, is put at the address `proof/addresses.json` gives its name, by the pass the function check places addresses with ([`lib/wasm-addresses.mjs`](lib/wasm-addresses.mjs)), so the same line of C names it for the console's compiler, for the check and for the game. A name nothing defines and no address is given for stops the build, as a linker would. The header holds `ADDRESS_<name>` for each, as memory keeps it, odd for Thumb code in the cartridge, `TWIN_ADDRESS(function)` for the value to keep, `TWIN(pointer)` for the twin to call, and `TWIN_TABLE`, which a game writes once, in a file that declares every twin, to define the table. A call to an address with no twin stops the game, which `prove` reports as it does any stop. The game's build does what the function check does with plain C too: a function's address the C takes is its address in the original, a call through a pointer goes through the table to the twin, and a name that is a label, such as `gUnknown_03004C54`, is at its own address. A function of the original the C calls by name and doesn't define yet, such as one a later step will write, is left for the page, which stops the game with its name if it's ever called: `The game called CreateTitleScreen, which has no code in it yet.`

**Waiting from inside a function.** A console's game waits for the screen from wherever it is, as a fade written as a loop does, and its main loop never returns. `kit_wait_frame()` ends the frame there, and `kit_run(function)`, called once from `game_start` and once from each `game_step`, goes on from where the game last waited ([`kit/c/pause.c`](../kit/c/pause.c)). WebAssembly can't leave a function halfway, so a game that calls them gets one more pass over what the compiler built: Asyncify, from [Binaryen](https://github.com/WebAssembly/binaryen), which gives every function on the way to a wait a way to put its values away and come back to them. The page needs nothing new. In the trial of [#1451](https://github.com/NahuelGenchi/dreamports/issues/1451) the pass made Sonic Advance in C 6% larger than the same module tidied, and no slower. Binaryen is a download of 23 MB, and few games need it, so it isn't among what `npm ci` installs: the first build that needs it gets version 132.0.0 from npm's registry, checks it against its hash, and keeps the one file of it the pass needs, 15 MB of JavaScript, in `.dreamports/binaryen/`. The site's own build would get it the same way for a game that waits this way, and none does yet. A game with these waits or this memory runs as WebAssembly only, not as a program for your computer.

**What `prove` compares.** A game lists the work memory to compare in its `original.json`, or a [trial](../games/README.md#versions-in-other-languages) in its own, which says nothing else, so the game's other versions compare no memory:

```json
"workMemory": [{ "address": "02000000", "bytes": 262144 }, { "address": "03000000", "bytes": 32256 }]
```

Each stretch is its first address, in eight capital hexadecimal digits, and how many bytes, in order. A game leaves out what the two can't share, such as the top of the fast work memory, where the console's processor keeps its stack and a Dreamport's C keeps its own elsewhere. `prove` then compares every byte of them after every frame, in the original and in the Dreamport, beside the picture and the sound, and a frame matches only when all three are the same. Both sides hash the same bytes as each frame ends, so only hashes cross from the browser. At the first frame whose memory differs it plays the original to that frame once more and says how many bytes differ, the first one's address and what each side holds there, and where the rest are, and `report.json` has it under `memory`. It reads the work memory and nothing of the cartridge.

`npm run test:same-memory` tries all of it with a program of the project's own, [`test/same-memory/cart.c`](test/same-memory/cart.c), and it runs on every pull request. The program is built twice from the same C: as a cartridge, with agbcc, the tools' assembler and a few lines of a linker, and as a Dreamport. `prove` has to find all 600 frames and all 294,400 bytes of work memory the same, and then find five lines written wrong: a number that shows on the screen, a count only the work memory shows, a wait a frame short, a byte written to video memory as to any other memory, and a function kept in memory as the Dreamport's own. It has been run only on Linux, and with no real game yet.

## Counting what a game draws

On the PlayStation 2, where a 3D game is proven by its draw list, `draws` says what a game's lists hold, before any of it is written again:

```
npm run dp -- draws <copy> [--frames <n>] [--from <presses.json>] [--between <first>-<last>]
```

It plays the original from power-on for `--frames` frames, 600 unless said, with nothing held, or with the presses in `--from`, a file like a recording: `{ "frames": 4200, "held": [[0, []], [1850, ["START"]], [1880, []]] }`. Then it counts what the game gave the console's graphics chip, in the frames `--between` names or all of them after the first: how many things a frame, the shapes and how they're drawn, the textures' formats, palettes and sizes, the blending, the depth and alpha tests, what it's all drawn into, the pictures moved, and which path the register writes came by. Writes that come from vector unit 1 mean the game's shapes are made by a program on that unit, which its Dreamport has to do the sums of.

It prints counts and nothing else, and keeps nothing: the lists' file it reads is removed as it ends. It takes the copy's path, so it works before the game has a folder here.

## Proving a part

A part, such as a game's logos or one of its acts, is proven by a recording that plays the whole of it, from its first frame to its last, so a recording that skips any of it with Start doesn't prove it. It may end with a press that moves the game on, the way a player leaves it: Sonic Advance Dreamport's title screen is frames 902 to 1252 of `neo-green-hill-act-1`, which ends it with Start. These steps prove one:

1. Make a recording that plays the whole part and a little of what comes after it, with `play --record`, with `play --record --from` to start where another recording reaches the part, or by hand.
2. Run `npm run dp -- prove <game> <recording>` and read the stretches where the original's screen is one colour. A part usually starts as one of them ends and ends as the next one does. Where the screen is one colour between two parts, as when one fades out and the next fades in, those frames go with the part before, so the next part starts on the first frame that isn't one colour.
3. Check the frames you picked with `--stills`, such as `--stills 253,254,932,933`, and look at the pictures in `stills/`.
4. Write the part's `recording` and `frames` in `parts.json`, and run `prove` again. It says whether the part is proven, which for a part that names [what it reaches](#what-a-part-reaches) also takes the original getting there within those frames, and keeps pictures of its first and last frames, with the one before and the one after, so the lead can check them once more.

Sonic Advance Dreamport's logos are frames 254 to 932 of [`logos-and-intro`](../games/sonic-advance/proof/recordings/logos-and-intro.json): the language screen fades to white until frame 253, and the Sonic Team logo fades to black, which stays until 932.

A part the game can't reach yet is proven the same way, from a [start point](#start-points).

A recording made for something else can come to play a whole part, as one made for a foundation does: Ghosts'n Goblins Dreamport's `stage-clear`, made for its enemies, played all of its first stage with every frame the same, and the stage didn't count until `parts.json` named it. So when a recording the step changed matches on every frame, no part names it and the game has parts with no recording yet, `prove` says so, with those parts' names, under the stretches where the screen is one colour. If it plays one of them whole, steps 2 to 4 name it, in the same pull request, which then closes the part's task too. If it plays only some of a part, it names none.

## Bringing a branch up to date

`npm run dp -- update <game>` merges the latest `main` into the branch, before a pull request goes out or when one conflicts. A conflict in `docs/STATUS.md`'s table, a progress map, a port map or a `progress.json` settles by itself, with `main`'s table and maps and both sides' recordings. Then it runs `ready` on the result, for every game both sides proved, and only commits if that passes, so pushing is all that's left. A merge passes when the check and the build do and no frame that matched before differs: what matched is what each side's last commit has, and of the two the one that matched more. So a version that doesn't match every recording yet, such as one in C behind its JavaScript, is brought up to date too, and a merge that breaks a frame either side had isn't committed, however often it's run. It needs your copy of the game, as a `progress.json` can only be measured again with it.

A conflict in anything else stops it, with the merge left open, and names the files, since someone has to read both sides. Settle them, `git add` them, and run it again. If `ready` fails, the merge stays open too, so fix what it found and run it again. It exits with 2 for conflicts it can't settle and 1 for anything else that stops it. `--base <branch>` merges that branch instead of `main`, for a pull request built on another.

A branch [built on a pull request in review](../docs/TEAMS.md#building-on-a-piece-in-review) gets that pull request's newest commits first, the same way, each time `update` runs: while it's open, and its last ones once it has merged. A branch left behind what it stands on conflicts with `main` in every file the two share, as a squashed merge has none of the commits the branch took. `update` knows what a branch is built on from the merge that brought it in, and from the `Builds on #<number>` lines of the branch's own pull request, and needs the GitHub CLI to ask which pull request that was. Without it, it says so and brings in `main` alone.

Once that pull request is in `main`, `update` merges `main` as a commit that says it holds it: `main`'s own files, with `main` and the pull request's last commit as its parents. git then compares from that last commit, where a squashed merge alone made it compare from before either began, so only what the branch itself changed is left to settle. That commit stays in the branch's history, named `main, which holds #<number>`, and changes no file.

## Sharing a preview

`npm run dp -- share <game>` publishes a preview of the game as it is in your last commit, on GitHub Pages from your own fork, at `https://<you>.github.io/dreamports/<game>/`, so anyone can play it with their own copy without waiting for a review. `--as <name>` names the preview, to keep more than one. `--about "<what changed>"` puts a sentence of what changed on the preview's first page. Beside the preview, apart from it, go the side-by-side `clip.mp4`s that `prove` made of what this step changed (or the one `--clip` names, which is a `clip.mp4` too), each with its measures beside it, and `share` prints the lines that show them in the step's pull request: a frame of each clip that links the video, and a link. `share` keeps every clip's lines for the branch in `.dreamports/share/clips.md` as soon as they're pushed, before it waits for Pages, to paste under Clips as they are, and `npm run dp -- share --check <file>` refuses a pull request's text that leaves out a clip's frame or link, or that links a clip `share` didn't make for the branch, printing the lines to put there. `share` also writes the pull request's text itself, `.dreamports/share/pull-request.md`, from the repository's template, with all it knows filled in: the issue the branch is for and its milestone, the pull requests in review the branch starts on top of, what `--about` says, the game's lead when it's someone else, the clips, the game's two numbers where the branch left main and now, the titles of the notes the step adds, and the preview. What only whoever made the step can say, such as its sources, stays as the template's own words in `<angle brackets>`, and `--check` refuses a text with any of those left. Shared again from the same branch, it keeps what was written in and writes only its own lines again. A pull request's own check, *Clips*, reads every clip its text links with the measures beside it, and fails the same way (`tools/clips-check.mjs`).

Only a clip `prove` made goes, and only when it keeps the rules of [Clips](../docs/STANDARD.md#clips), which `prove` measures into each `report.json` and says as it ends (`tools/lib/clips.mjs`). It lasts at least 300 frames, five seconds. At least half of it, 150 frames, comes from the first frame the step changed on, so a recording that proves only a few frames of a new place after a menu runs on in that place, rather than moving its `clip` back into the menu. Every frame of it matches the original's, in picture and sound, since [#1039](https://github.com/NahuelGenchi/dreamports/issues/1039): a run-on whose frames differ shows a step that isn't done, so port what those frames need until they match. `share` takes only the side by side `clip.mp4`, never the Dreamport's video on its own, `dreamport.mp4`, and the Clips check refuses one. It shows a recording the step changed: one whose every frame main played the same, such as the title screen in a step about a fighter, is left out. One the step changed only in sound, such as a menu whose sound a fix to the sound engine made match, is left out too whenever another clip shows a change that can be seen, and the *Clips* check refuses it beside one: a clip has no sound, so it would show a place the step isn't about with nothing to see. A step that changes sound only keeps its clips. A step that changes the game's code or recordings has at least one clip, so when no recording shows anything it changed, as when nothing plays the new code yet, `share` refuses and says to add a recording that plays it, or run one on until it does. A team build's preview, which `team add` updates, needs none of its own. The Dreamport's picture is one colour in no more than a quarter of it, and the same as the frame before in no more than nine frames in ten. Side by side, no more than a quarter of the frames differ from the original's in more than half their pixels, as when the recording takes the original somewhere else, which `share` says apart. Its recording is committed as it was proven, against main as the branch starts from it, so a merge of main means proving again. A clip `share` kept from before that breaks a rule now leaves the branch's clips. For a version in C, as in `share sonic-battle/c`, it builds the game's WebAssembly from the C in your last commit, which has to be committed, as no commit holds the built file. It posts nothing. It asks before it publishes and before it switches Pages on for your fork the first time, and `--yes` answers yes for you. [Previews](../docs/PREVIEWS.md) explains what a preview holds, what it risks for players, and where the clip goes.

A step that changes a game's code and no frame, such as one that only moves code, has no clip, as every recording comes out as `main` has it. Its proof stands in for one. `prove <game>` with no recording named plays every recording and keeps a record of that whole proof in `.dreamports/proofs/`: how many recordings it played, its `progress.json`, and the game's folder and the kits' as they were, each as a hash. When the commit's `progress.json` is `main`'s own file and the record is of the very files the commit holds, `share` publishes the record beside the game's clips, and gives its line for the pull request, in `.dreamports/share/clips.md` like a clip's. So prove the game whole, commit, and share: files changed after the proof, or a merge of `main` that changed the game or its kit, mean proving it again, and a merge of `main` that changed neither doesn't. The pull request's check reads the record and holds it to what would merge, for each version whose code the step changes. A step that changes the game's recordings always shows a clip (`tools/lib/same-proof.mjs`).

A step that only proves functions, in a game made a function at a time that has no recording yet, has neither: nothing of the game plays, so there's no frame and no whole proof to record. Its functions' proofs stand in. `share` writes, in the same `.dreamports/share/clips.md`, a line for each function the step adds or changes, with its twin's name, its address and its kind of proof, and publishes nothing for it, as `proofs.json` is in the commit. The pull request's check works the same out again from what would merge, with no copy of any game, and asks for those lines in the text. The proofs stand in only when all of this holds (`tools/lib/proven-step.mjs`):

- the game has no recording, on `main` or in the step. Once it has one, a step shows a clip, or the record above when no frame changed;
- every function the step adds or changes in the version's code is a twin whose line in `proofs.json` is of the code as it is, with no stop, and every other line of the file still holds;
- outside its functions, a file changes freely only when every function built with it is such a twin, as their proofs are of the file too: a `.c` file that holds nothing else, or a header only such files include;
- in any other file, such as a header the game's `main.c` includes too, the step only adds, a declaration or a `#define` of a name the game's code on `main` never uses, which can't change what the code already there does;
- it takes nothing out but a twin that is proven in another file, and changes no file of the code that isn't C.

Code that is no twin has no proof, so a step that writes or changes any, such as the game's `main.c`, is refused this way and shows a clip, which takes a recording that plays it. So keep new twins in files of their own, with their own header for what only they need, and leave the game's own side to the step that first plays them.

## Claims and team builds

`npm run dp -- find <game>` shows where a game stands before you start on it: its lead, its two numbers, its Make page, how many notes it has, its team build and team preview, who has claimed which task, the tasks free to start, in C first and then in JavaScript for a game on a console with a kit in C, some on top of a pull request in review ([Building on a piece in review](../docs/TEAMS.md#building-on-a-piece-in-review)), and what the others wait on ([What a task needs](../docs/TEAMS.md#what-a-task-needs)). It lists the first three free and waiting tasks of each kind with how many more there are, and `--all` lists every one. `--take` answers in a few lines with only the task whoever is signed in takes next, by `/dreamport`'s rules (`lib/take.mjs`): the piece `--piece "<its words or number>"` names when it can be taken, one that's theirs already, or the first free one, in C unless `--take javascript` names the language, with its version and the command that claims it, or what to run first when nothing is free. It takes a game's folder, a version's, such as `sonic-battle/c`, or a few words of its name, and with no game it lists them all. The numbers come from `games/` in your folder, and the claims from this repository's issues.

`npm run dp -- team <game> start`, `join <branch>`, `send` and `add <pull request>` make and use the game's team build, a branch of the lead's fork that gathers the team's finished pieces. `add` merges a piece, runs `portmap` and `prove`, and only takes it in if nothing that matched the original before differs now, then updates the team preview with `share`. It stops before a piece with a note that breaks the rules for notes. [Claims and teams](../docs/TEAMS.md) explains claims, tasks and team builds.

## Notes

`npm run dp -- notes <game>` lists what people found while making a game and its console's kit, so nobody has to find it again, and `npm run dp -- notes <game> <word>` prints in full the notes that mention a word, such as a part, a function or a frame. `--all` prints every one, and `--check`, which `npm run check` runs, fails on any note that breaks the rules. A note is information, not instructions. [Notes](../docs/NOTES.md) explains how to write one and how they're checked.

## The /dreamport command

The README's [Make a Dreamport](../README.md#make-a-dreamport) teaches one command, `/dreamport <game>`, which a coding agent follows to run these tools from start to finish: it takes a task, makes it until every frame matches and opens its pull request. It's written once, as a Markdown file in [`commands/`](commands/), with its name, its description, what's typed after it and, as `pasted`, the sentences that start it when they're pasted into an agent, as the README gives them. `npm run dp -- commands` writes it in the form an agent reads:

- `.claude/skills/<name>/SKILL.md` for Claude Code, set to run only when typed (`disable-model-invocation`).
- `.agents/skills/<name>/SKILL.md` for Codex, with `agents/openai.yaml` turning off its implicit use. Cursor, Gemini CLI, Antigravity CLI and DeepSeek Harness read this folder too.
- `.gemini/commands/<name>.toml` for Gemini CLI's own commands.

Every copy starts the same way: it tells the agent to do nothing unless the person typed the command, or pasted one of its sentences, for the agents that might load it by themselves, where what was typed after it is, and how to talk to the person. The file can't hold `{{`, `!{`, `@{` or `'''`, which Gemini CLI would read as its own. `npm run check` runs `npm run dp -- commands --check`, which fails when a copy differs from its file, and removing a command's file and running the tool removes its copies.

## A game's proof folder

What the tools keep in the repository is in the game's `proof/` folder, and it's all JSON. The ignore rules keep anything else out of it. A version in another language keeps only its `progress.json`, `port-map.json` and, when it's made a function at a time, `proofs.json` in its own, such as `games/sonic-battle/c/proof/`.

| File | What it holds |
| :--- | :--- |
| `original.json` | The copy the proof uses: its console, its name, the title and code in its header, and its SHA-1 checksum, `keysAfterVBlank` for a game that reads its buttons just after the V-blank, `workMemory` for one that keeps its memory at the console's addresses, the stretches `prove` compares ([The same-memory build](#the-same-memory-build)), `screen` for a game on another console that [chooses its own size](../docs/CONSOLES.md#how-a-console-is-known), `provenBy` for a game compared another way than its console's games are, by its draw lists (`"draw lists"`, as a PlayStation 2 game is unless it says otherwise, [The PlayStation 2](../docs/CONSOLES.md#the-playstation-2)) or by its pictures (`"pictures"`), `shows` for what a recording can be named for, as [What a recording shows](#what-a-recording-shows) says, and `compiler` for the compiler that built the original and its flags, which `match` builds the game's C with ([Matching the original's bytes](#matching-the-originals-bytes)) |
| `recordings/` | Recorded play, one file per recording |
| `route.json` | Optional: where the original keeps the few values `route` reads as it searches, and the goals the game names, as [Finding a route](#what-a-game-says-of-its-original) says. A part can name one of those goals as what it reaches |
| `code-map.json` | The code map |
| `progress.json` | Each recording's results and the code that ran in matching play, written by `prove` |
| `unreachable.json` | Optional: the stretches of the cartridge nothing can reach, each with why, which don't count towards gameplay proven, read by a person before it goes in |
| `saves.json` | Optional: the bytes of the save memory that aren't the game's save, each stretch with why the original never reads them, which `prove` doesn't compare, read by a person before it goes in |
| `played.json` | What of the original's code was played in each recording's matching frames, and where its instructions and branches are, as sets of places in the code map's functions, written by `prove`; nothing of the code itself |
| `libraries.json` | Only in a version that takes a shared library from the kit: which, its variant, and where its copy has each of the library's functions and values ([Shared libraries](#shared-libraries)) |
| `proofs.json` | Only in a version made a function at a time: each function's proof, by the same bytes or the same memory, with a mark of the twin and of the original's function it's a proof of, written by `match` and `twin` alone ([A function's proof](#a-functions-proof-and-a-game-made-a-function-at-a-time)) |
| `port-map.json` | The port map: the functions the game's code names, the names that land inside one but not at its start, and the stops, each a path the code says it hasn't ported, written by `portmap` |
| `names.json` | Optional: how far the release the game's labels come from is from the copy's, stretch by stretch, for `portmap` and `read` |
| `addresses.json` | Optional: the names the game's C gives the original's values and functions that it doesn't define, each with its address, for `match`; nothing of the code itself |
| `parts.json` | The game's parts, each with the recording and frames that prove it once there are some, and what it has to reach when it names that ([What a part reaches](#what-a-part-reaches)), written by the game's lead |

## What stays on your computer

Everything else the tools keep is in `.dreamports/`, in the repository's folder, which the ignore rules keep out of commits: where your copies are, the reference emulator, every result with its pictures and clips, what `route` found and the pictures of where it stopped, what `read` prints, the NES's processor and the memories the function check takes from play, the registers `prove` keeps of an NES game's functions as they start, the compiler `match` builds with, what it builds and the instructions it keeps side by side, Binaryen and each game's `twins.h`, what you played for `capture`, and the browser profiles the tools use. Deleting it is safe, as `setup` and `rom` make it again. Only what you send leaves it, such as a clip in a pull request. A coding agent is different: whatever it reads, such as what `read` prints, goes to the company that runs its model, unless that model runs on your computer too.

## For a game on the Game Boy Advance kit

A game made on [the Game Boy Advance kit](../kit/gba/README.md) works with the tools when its page calls `proof?.watch(screen, input)`, as the kit's guide shows, and keeps the kit's start screen, where the tools give it the copy and press Play. Its screen has to be the console's 240 by 160 pixels while the tools play it, and the tools hear its sound when it plays through the kit's `createSound()`. Games with more than one player on a page aren't supported yet.
