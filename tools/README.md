# The proof tools

[Back to README](../README.md) · [Contribution workflow](../CONTRIBUTING.md) · [The Dreamport standard](../docs/STANDARD.md) · [Written in: #77](https://github.com/NahuelGenchi/dreamports/issues/77)

The proof tools show that each step of a Dreamport plays like the original game, so its progress is measured instead of guessed. They play the same button presses in the original and in the Dreamport, compare every frame, what it shows and what it sounds like, work out the game's [two numbers](../docs/STANDARD.md#how-progress-is-measured), code ported and gameplay proven, and make short clips of both side by side. They run on your own computer, with your own copy of the game, and everything they take from the game stays there.

You start each one from a terminal in the repository's folder, with `npm run dp -- <tool>`. `npm run dp` on its own lists them.

| Tool | What it does |
| :--- | :--- |
| `setup` | Builds the reference emulator the original runs in |
| `rom` | Checks a copy of a game, says which game and which version it is, and remembers where it is |
| `play` | Opens a game in a browser with your copy, and with `--record` keeps what you play as a recording, after another recording's presses with `--from` |
| `route` | Finds the presses that take the original from where a recording leaves it to a goal, such as an act's end, and writes them as a recording, with nobody playing ([Finding a route](#finding-a-route)) |
| `prove` | Plays each recording in the original and in the Dreamport, compares every frame, its picture and its sound, says what the console holds that differs, updates the numbers, and with `--stills` keeps pictures of the frames you name |
| `capture` | Lets you play the original in a window, and keeps a real moment of it for the game's card, or with `--open`, `--pick` and `--from` does that while the game is being made, with nothing waiting for anyone |
| `codemap` | Makes the code map: every function in the original, with its address and size |
| `new` | Writes a claimed game's first files: its page, its code on the kit with everything wired in, its license and its entry |
| `portmap` | Makes the port map: each function of the original the Dreamport's code names, and where |
| `read` | Prints one of the original's functions, its instructions, from your copy, for code its decompilation has no C for |
| `share` | Publishes a preview of a game on GitHub Pages from your own fork, with the clips of what the step changed for its pull request |
| `find` | Shows where a game stands: its lead, its two numbers, its team build, who has claimed which task, the tasks free to start, and what the others wait on |
| `tasks` | Opens a Task issue for each of a game's foundations and parts that has none yet, its foundations first and then in the order a player meets them |
| `notes` | Shows what people found while making a game or its console's kit, so nobody has to find it again |
| `team` | The game's team build, the lead's branch with the team's finished pieces: `start` makes it, `join` starts a piece from it, `send` sends a piece to the lead, and `add` proves a piece and takes it in |
| `readme` | Writes the table of Dreamports in `docs/STATUS.md`, with each one's numbers and lead, from their [entries](../games/README.md#the-entry), and each one's progress map. A workflow runs it on `main`, so a pull request doesn't need it |
| `commands` | Writes the `/dreamport` command, from `tools/commands/`, in the form each coding agent reads |
| `ready` | Everything a step has to pass before it goes out, in one go: the port map, every recording, `npm run check` and the build, printing only what's wrong |
| `update` | Brings a branch up to date with `main`, and with any pull request it's built on: merges it, settles conflicts in files the tools write, runs `ready` and commits ([Bringing a branch up to date](#bringing-a-branch-up-to-date)) |
| `help` | Prints one section of these documents, the ones whose headings have the words you give, so that nobody has to read a whole one |

They've been used with real games only on the Game Boy Advance, and they work the same way for any other console, each in a small emulator built on your computer, as far as [Other consoles](../docs/CONSOLES.md) says. They've been used with real games only on Linux. On a Mac, Apple silicon or Intel, on Windows with only Node.js and git added, and on Windows inside WSL 2, `setup`, `rom`, `notes`, `read`, `play --record`, `prove` and `portmap` work as they do on Linux, with the same results to the last frame, as far as a small made-up program shows on GitHub's computers, with a script pressing the buttons in a real window. On Windows itself that's with Chrome and with Edge, on an account with no administrator's rights as well as on one with them, from a folder and with a copy whose names have spaces and letters from other languages, and `codemap` and `find` gave the same results too. Nobody has tried them there by hand, with a controller or with a real game. `share` hasn't published anything from any of them, and `team` hasn't gone past its first check.

## What you need

You need Node.js and the repository's packages, as [running the site on your computer](../CONTRIBUTING.md#run-the-site-on-your-computer) explains, and Google Chrome, Chromium or Microsoft Edge. `share`, `find` and `team` also need the [GitHub CLI](https://cli.github.com), signed in with `gh auth login`. If the tools don't find your browser, set `CHROME` to where it is. To build the reference emulator you also need git, CMake and a C compiler: on Debian or Ubuntu, `sudo apt install git cmake build-essential` installs them, and on a Mac, `xcode-select --install` and `brew install cmake`.

On Windows you need only [git](https://git-scm.com), and the Edge that comes with Windows is browser enough. `setup` gets a compiler, [w64devkit](https://github.com/skeeto/w64devkit), and [CMake](https://cmake.org) by itself, about 120 MB, each from the people who make it, at a fixed version and checked against its hash. It builds in `C:\ProgramData\dreamports-build`, since the compiler can't read a path with some languages' letters in it, which takes about a gigabyte for those minutes. Then it keeps the two programs it made and deletes the rest, so nothing gets installed. If PowerShell says running scripts is disabled when you run `npm`, write `npm.cmd` in its place.

You can also run the tools on Windows inside WSL 2 (Windows Subsystem for Linux), which `wsl --install` sets up, with everything above installed inside it, as on Linux, and Chrome from Google's own package. `play`'s window opens through WSL's own display. Keep the folder in Linux's home: under `/mnt/c` the tools work too, but installing and building take several times as long. WSL 1 can't run the browser.

A game written in C needs nothing more: `npm ci` brings a compiler that builds it to WebAssembly, the same on every computer, and `npm run test:c-kit` also builds it for your computer with its own C compiler ([the kits in C](../kit/c/README.md)).

And you need your own copy of the game, made from your own cartridge: the version the Dreamport is built from, such as the USA version.

## Getting ready

`npm run dp -- setup` downloads the source code of [mGBA](https://mgba.io) 0.10.5 with git and builds it, along with two small programs of the tools' own: [`gba/original.c`](gba/original.c), which runs the original a frame at a time, and [`gba/read.c`](gba/read.c), which prints its instructions for `read`. They go in `.dreamports/gba/`, and it takes a few minutes the first time. If you already have mGBA 0.10.5's source code, `MGBA_SOURCE=<its folder> npm run dp -- setup` builds that instead of downloading it. `prove` runs the setup by itself if it hasn't been done.

mGBA is the reference: the original runs in it, on your computer only, so there's something to compare against. It's never part of a Dreamport and never runs on dreamports.net. It starts the game with its own stand-in for the console's start-up program, so no BIOS file is needed.

`npm run dp -- rom <file>` checks your copy. It says which game it is, which version, and whether it's the copy a Dreamport's proof uses, and it remembers where the file is, in `.dreamports/copies.json`, so the other tools find it. It only reads the file: it never copies it, changes it or sends it anywhere. Give it a folder and it checks every `.gba`, `.agb` or `.bin` file in it, but names only the copies a Dreamport here measures against, and sums up the rest in one line. `--game "<name>"` names the copies of the game you're starting too, such as `npm run dp -- rom <folder> --game "Sonic Battle"`, when no Dreamport measures against it yet: a copy is that game when its header says the same name, or the start of it when the name is too long for a header's twelve characters, or when its file's name has the name's words in a row, not followed by a number, so Sonic Advance doesn't pick out Sonic Advance 2. It says which of the two it went by, along with what `original.json` needs. On its own, `npm run dp -- rom` lists the copies it remembers.

## Recording play

`npm run dp -- play <game> --record <name>` opens the game in a browser window, ready to press Play. Nothing is saved in that window, so the game starts from power-on, the way the original does. Play with the keyboard or a controller, then close the window, and the buttons you held at every frame are written to `games/<game>/proof/recordings/<name>.json`. A recording's name has lowercase letters, numbers and single dashes, such as `act-1`. Without `--record`, `play` just opens the game with your copy, and keeps its saves for next time.

`--from <recording>` starts the new recording with another recording's presses, so a part later in the game can be recorded without playing everything before it again. Press Play and the game first plays them, at its own speed and with your buttons doing nothing, then it's your turn, and the terminal says when. `--from <recording>:<frame>` plays them up to that frame only, so `--from act-1:2100` takes over at frame 2100 of `act-1`. The new recording keeps those presses, and the stretches only the original has among them, so it still starts from power-on and `prove` plays it like any other.

A recording can also be written by hand, as a list of presses, which is how `/dreamport` makes them, as nobody plays there, and which suits a part played with nothing pressed, such as logos and an intro left alone. For a part where the character has somewhere to get to, such as a whole act, `route` finds the presses instead ([Finding a route](#finding-a-route)). Sonic Advance Dreamport's [logos and intro](../games/sonic-advance/proof/recordings/logos-and-intro.json) is one: A on the language screen, then nothing.

A recording holds nothing from the game, only button presses, so it lives in the game's folder and goes in a commit, and anyone with their own copy can play it again. Write what it plays in its `about`. Its other fields:

- `frames`: how many frames it lasts.
- `held`: the buttons held, as a list of changes. `[120, ["A"]]` means A is held from frame 120 until the next change. Buttons have the console's names (`A`, `B`, `SELECT`, `START`, `RIGHT`, `LEFT`, `UP`, `DOWN`, `R` and `L`), or the Dreamport's own name for a button the console doesn't have, after which the original can't match.
- `onlyInOriginal` (optional): stretches of play the original has and the Dreamport doesn't have yet, such as a menu nobody has made. Each gives `at`, the Dreamport's frame where it goes in, its length in `frames`, the buttons `held` during it, counted from its own start, and an `about`. The original plays them and the Dreamport skips them, so the frames after still line up. It can also have `sets`, as [Start points](#start-points) says.
- `start` (optional): what the Dreamport's address adds, as [Start points](#start-points) says.
- `clip` (optional): the frames the clip shows, from frame `at`, for `frames` frames: at least 300, five seconds, or all of a shorter recording's, which `share` refuses until it runs on further. Leave it out unless the moment to show is somewhere `prove` wouldn't start, as `prove` starts the clip a second before the first frame the step changed.
- `players` and `others` (optional, for games with a link between consoles): `players` is how many consoles are linked, 2 to 4, and `others` lists, for each console after the first, its own `held` list. `held` is then the first console's, and `start` says how many the page runs (`vs=3`). `prove` runs one original core for each console in lockstep over the link (`tools/gba/linked.c`) and compares every player's picture with the page's screen for that player, frame by frame, holding each player's buttons by the names the page's `dreamportsProof.buttons` gives them; a first difference's picture has one pane per player, the page's on top row and the original's below.

Sonic Advance Dreamport's [first act](../games/sonic-advance/proof/recordings/neo-green-hill-act-1.json) is an example: it skips the character select, which the Dreamport doesn't have yet.

## Start points

A late part doesn't have to wait for everything before it. A recording can have a **start point**, so that the Dreamport opens right at the part and the original gets there by itself. Two things make one, and either can go without the other:

- `start` is what the Dreamport's address adds, such as `level=2&character=1`: words and values, which the game's own page reads. `prove` opens the game with them, and so does `npm run dp -- play <game> --record <name> --start level=2`.
- `sets`, in a stretch of `onlyInOriginal`, writes values to the original's work RAM as that stretch runs, such as which levels are unlocked: `[{ "frame": 9, "address": "03005168", "bytes": 1, "value": 2 }]`, with `frame` counted from the stretch's start, `address` in hexadecimal, as the code map has it, and `bytes` 1, 2 or 4. They can't reach the cartridge, and `prove` stops if one tries.

Write the presses and values that take the original to the part's first frame as a stretch of `onlyInOriginal`, at the frame where the Dreamport opens at the part, which is 0 when it opens there straight away. Then run `prove` and change the stretch's length until the frames line up. Its list of frames where the original's screen is one colour shows where each screen ends.

It's still all compared: every frame of the part, against the original, the same as any other. A part proven this way counts towards gameplay proven, and `prove`, `find`, the game's page and its progress map mark it as proven from a start point, as it could still differ once the game's real path reaches it. Once that path exists, a recording with no `start` or `sets` proves it again from power-on, and the mark goes.

**A start point only skips the way there.** What it plays has to be what a player could see at that place, and a match can't tell you that: the original does the same as the Dreamport when it's given the same values, so every frame can be the same in a recording nobody could ever play. Sonic Advance 2's first spring recordings left Sonic in the air as a stage opened, so its countdown ran while he fell and bounced, with its crouch on him in mid-air, its machine and its numbers following him, and on one spring the crouch covered his whole flight. So:

- The character starts where a player could have them: on the ground, unless the game's opening has gone and they're in the middle of something a player could be doing, such as a jump. To find the ground, try a height and see where they land.
- The game's own opening ends before they meet what the recording proves. That's anything that holds the buttons or sets an animation, such as a countdown or a title card.
- Look at it the way a player would, with `--stills` every second or so, before you call it done.

The tools hold a game to this where it can say so. In a frame no player could ever see, a game's code writes why to `dreamportsProof.neverInPlay`, as Sonic Advance 2's countdown does for a character a start point has left in the air. `prove` names those frames and fails, however they compare, it keeps them in `progress.json`, and `npm run check` and the build stop until the recording is played again without them, so a pull request with one can't pass its checks. Only a game's own code knows what its opening does, so a game whose opening holds its character adds this line itself ([the kit's README](../kit/gba/README.md#for-the-proof-tools) shows how). Until it does, `prove` reminds it in one line whenever a recording it plays has a start point and the game's code never names `neverInPlay`, which doesn't change whether the recording passes. A game with no such opening can end the reminder with a comment naming it that says why. Keep it to what a start point can cause, as a real start must never be flagged.

A recording's start point is only words and numbers, so it goes in a commit and anyone can replay it. Save states stay out of this: they hold the game's memory, so they can't go in a commit, and nobody else could replay them.

## Finding a route

`npm run dp -- route <game> <name> --goal <goal>` finds a recording's presses when nobody plays. It's for a part where the character has somewhere to get to, such as a whole act and its boss. It searches the original itself, in the reference emulator, for the buttons that take it from where a recording leaves it to the goal, and writes them as `games/<game>/proof/recordings/<name>.json`, a recording like any other, which `prove` then compares with the Dreamport. It needs none of the Dreamport's code, so a part's recording can be there before a line of the part is written, and every round of work after that is `prove`.

The way there comes from a recording. `--from <recording>[:<frame>]` starts the new one with another's presses, up to a frame or to its end, as `play --record` does, and keeps its start point and the stretches only the original has. Without `--from`, `<name>` is a recording that's already there, and it grows from its last frame.

The goal is one the game names in its `proof/route.json`, such as `act-end`, or a condition written out: one of the game's values, a sign and a number, such as `"x>=9000"`, with commas between several that all have to hold, as in `"x>=9000,y<700"`. The signs are `=`, `!=`, `<`, `<=`, `>`, `>=`, `&` for a value that has one of those bits, and `!&` for one that has none.

```sh
npm run dp -- route sonic-advance angel-island-act-2 --from angel-island-act-2-opening --goal angel-island-act-2
```

**How it searches.** It never plays from the start twice. It keeps a copy of the console's state at every new place the game reaches, a place being a cell of a grid over a few of the game's own values, such as where the character is. Then it picks a place, brings its state back, holds some buttons for a few frames, and keeps whatever new places that reaches, again and again, on several consoles at once that share what they find. The newest places and the ones tried least are picked most, so it spreads through a stage like water, and play that can't go on, such as a life lost, is dropped. Nothing is drawn as it searches, which the game can't tell, so the original runs at 2,000 to 3,000 frames a second on each console.

**What it prints.** Every few seconds, a line with how many places it has reached and where the newest is. It stops by itself. At the goal it plays the whole list of presses once more from power-on, straight through, and writes the recording only if they still reach the goal. When nothing new has turned up for a long while, or its time is over, it says so, with how far each value got, and leaves a map of every place it reached and pictures of where it stopped in `.dreamports/routes/<game>/<name>/`. Those show the game, so they stay on your computer. What it found is kept there too, and the same command goes on from it. A `--goal` that names a place it already reached writes the recording that gets there at once, to look at with `prove`'s `--stills` or to go on from another way.

**When it's stuck**, the map and the pictures say where. Most often the grid doesn't tell apart two states that lead to different things, so the search throws one of them away. A place that can only be passed with speed needs the character's speed under `apart`. A fight needs how far it has got, such as the boss's health, in its `cells`, and the game's clock under `apart`, as what a boss lets you do depends on when. A place where the way only opens later, such as a platform that moves, needs the search to wait there, which `wait` lets it do. A value the grid doesn't have is added to `route.json`, and `--cells`, `--apart` and `--wait` try another grid for one search, such as `--cells x:16,y:16` or `--wait 90:3`.

| Flag | What it does |
| :--- | :--- |
| `--from <recording>[:<frame>]` | Starts the new recording with another's presses |
| `--goal <goal>` | Where to get to: one of the game's goals, or a condition |
| `--minutes <how long>` | How long it may search, 10 unless told. The same command goes on from where it stopped |
| `--cells <value>:<size>,…` and `--apart <value>:<size>,…` | Another grid for this search |
| `--wait <frames>:<states>` | Each place also keeps a state for each stretch of that many frames after the search first reached it, up to that many, so it can wait there |
| `--then <frames>` | Frames with nothing held after the goal, such as an act's results |
| `--at-once <how many>` | How many consoles search at the same time: as many as the computer has idle cores unless told, up to 12 |
| `--seed <number>` | Other dice. With `--at-once 1`, the same seed finds the same presses every time |
| `--fresh` and `--replace` | Forgets what it found before, and writes over a recording that's already there |

### What a game says of its original

The search knows nothing of any game. A game tells it where its original keeps the few values it reads, in `games/<game>/proof/route.json`, which every version of the game shares. Like a recording's `sets` it holds only addresses and numbers, so it goes in a commit. [Sonic Advance's](../games/sonic-advance/proof/route.json) is the example.

- `values`: each value's name, with its `address` in the work memory, in hexadecimal as the code map has it, its `bytes`, 1, 2 or 4, `signed` when it can be negative, and `per`, how many of its units make one of what people count in, such as 256 to a pixel. Conditions and grids are then written in pixels.
- `cells`: the grid, each value in it with how much of it one cell covers, such as `{ "x": 32, "y": 32 }`.
- `apart` (optional): what tells two states of one place apart, the same way, such as `{ "speedX": 4 }`. A place then keeps a state for each.
- `wait` (optional): `{ "frames": 90, "states": 3 }` has each place also keep a state for each stretch of 90 frames after the search first reached it, up to 3, so it can wait there for what only comes later. It costs memory, as every place keeps that many more states.
- `lost`: conditions for play that can't go on, such as a life being lost. Without them the search wastes its tries on falls.
- `goals`: the goals the game names, each a condition, which a part in `parts.json` can also name as [what it reaches](#what-a-part-reaches). One can be written as `{ "when", "cells", "apart", "wait" }` to have a grid of its own, and with `"after"` it names the goal to reach first: an act's end after the place its boss comes in, so one command does both, each with its own grid.
- `buttons` (optional): the sets of buttons the search may hold, such as `"RIGHT A"`. Without it, each direction alone and with each of the console's other buttons, but Start and Select.

A value the game keeps in memory it hands out as it goes, such as a boss's health, has no address of its own. It has `found` in place of `address`: the stretch of memory to look through (`from`, `to`, `step`), the `mark` that's beside it, such as the address of a function its record points to, and from the mark where the record's own address is (`pointer`, `pointerBytes`, `base`) and where in the record the value is (`offset`). It reads -1 while no record is there, which makes "the boss has come" a goal, `boss>=0`.

To find where a game keeps something, look in its notes (`npm run dp -- notes <game>`) and its decompilation's names first. Then check it: `npm run dp -- route <game> <recording> --at <frames>` prints the game's values at those frames of a recording, and with `--memory <from>-<to>` every value in that stretch of work memory that isn't the same at all of them, which is how a value that changes when something happens is found.

### What it can't do

It searches for a way, not for a good one: the presses it finds look like nobody's play, with hops that do nothing, and it takes hits. A part with nothing to reach, such as a menu, is still written by hand. It needs the reference emulator to copy its state out and bring it back, which mGBA does and nearly every libretro core does, and on those other consoles it searches with one console at a time. It has been run on the Game Boy Advance and on the made-up console of the tools' tests only.

## What a recording shows

A recording named for a character has to play that character, and a match can't tell you that either: the original plays whoever its values pick, and the Dreamport does the same, so every frame can be the same in a recording of the wrong one. Sonic Battle's first recordings of Shadow, Amy and Chaos played Cream, Rouge and another fighter, as their start points gave numbers someone had guessed, and nothing looked at who was playing.

So the original's own memory says who it is. A game whose recordings can be named for a character, or for anything else a value in the original picks, lists it in its `original.json` under `shows`: for each kind, the work RAM's address where the original keeps it, how many bytes, and the name of each value.

```json
"shows": {
  "fighter": { "address": "03001634", "bytes": 1, "names": { "0": "Sonic", "3": "Shadow", "6": "Cream" } }
}
```

`prove` reads each kind from the original as a recording's last frame ends, says what it found, and keeps the name in `progress.json`. A recording whose name names one of a kind's names, as a whole word, such as `shadow` in `shadow-moving` or `amy` in `amy-x-zone`, fails unless the original shows that one, however its frames compare, and `npm run check` and the build stop on it too, so a pull request with one can't pass its checks. Name a recording for what it shows, and leave a name out of it when it shows someone else, as Sonic Advance's `x-zone-the-normal-ending` plays Sonic in the zone Amy hasn't reached yet.

Each name in the list is checked once by a person against the original's pictures, with a recording that picks that value, before it goes in: a guessed name would only move the mistake into the list. A value the list doesn't name fails any recording named for that kind. Sonic Battle lists its fighters and Sonic Advance its characters.

## What a part reaches

A part named for an act has to play the act to its end, and a match can't tell you that: a recording that stops halfway matches the original just as well as one that gets there. Sonic Advance's Neo Green Hill Zone act 2 once counted as proven, "through its boss", on a recording that never beat the boss, with every frame the same.

So the original's own memory says whether it got there. A part in `parts.json` can name what it reaches, one of the goals the game lists in its [`route.json`](#what-a-game-says-of-its-original):

```json
{ "name": "Neo Green Hill Zone act 2", "recording": "neo-green-hill-act-2", "frames": [0, 8411], "reaches": "act-end" }
```

`prove` reads the goal's values in the original as each frame of the recording ends, and keeps in `progress.json` the frames over which the goal held, as `"reached": { "act-end": [[8102, 8380]] }`. The part is proven only when the goal comes true within its frames, so one that held already before the part's first frame says nothing of it. When it doesn't, `prove` fails the recording, however its frames compare, with `--quick` too, and says where the original did get to the goal, if anywhere: past the part's last frame, before its first, or never. The two numbers, the game's page, `npm run check` and the build count the part the same way, and `check` stops on a part that names a goal no proof has measured yet.

The way out is always in the recording: play on until the original gets there, with [`route`](#finding-a-route) for a part nobody plays, and give the part the frames that take it in. A part's goal is the game's lead's to write, when the parts are listed, and a task doesn't take it away.

A goal a part names reads values that each have an `address`. One that reads a value only the search can find, such as a boss's health, is for `route` alone. A recording that links several consoles can't prove such a part yet. Sonic Advance's acts name `act-end`, the flag the game sets when an act is cleared.

## A game's capture

Every game's card in the launcher shows a few seconds of real play. `npm run dp -- capture <game>` makes a Dreamport's from the original, so a game can have one before its Dreamport has anything to play. It opens a window where you play your own copy, from power-on, with the keyboard or a controller, and hear it as you go. `/dreamport` opens it for you as soon as it starts on a game with no capture, and you can also ask your agent, so you run nothing yourself.

Press Finish, or `Esc`, or View and Menu together on a controller, and it picks out the best stretches of what you played: lively and colourful, with buttons held, and with no fades, logos, menus or text. They come up moving. Press the one you want with the mouse, with the arrows and `Z`, or with a controller's d-pad and A. `Esc` or B goes back to playing where you left off, and the next list comes from all of it.

What you choose becomes a few seconds that loop, as near to seamless as the game allows, in `public/media/`: `<game>-dreamport.h264.mp4` and `.av1.mp4`, silent, `-still.webp` and `-share.png`. The game's entry names them, as `screen` and `share`. Choose play, with no logos or title screens: these go in a commit, on to dreamports.net, and the Dreamports team looks at them in the game's pull request ([the rule](../docs/STANDARD.md#a-games-capture)).

With nobody playing for 30 seconds the window rests: the game waits, drawing and playing nothing, until a button is pressed, as `--open` can leave it open for as long as a game takes to make. What it keeps is only what was played.

Your presses stay in `.dreamports/captures/<game>/`, so `npm run dp -- capture <game> --choose` shows the same moments again, if the window closed first or you change your mind. The pictures come from running the original again with those presses, and it stops if any frame comes out differently from what you played. A coding agent can start it for you, but the choice is yours: it never looks at the pictures.

Making a Dreamport never waits for this, so three more ways of running it keep the work going. `--open` starts the window in a process of its own and returns at once. `--pick` ends it, waiting while someone is using it, and keeps what they chose. If they played and didn't choose, it takes the moment the tool ranks first, by those same numbers, in a browser nobody sees. If nobody played it says so, and `--from <file>` plays a list of presses, as a [recording](#recording-play) has them, and takes the first of what they lead to, or says in numbers what each stretch led to: how much of the screen moved, how many colours and how often buttons were held. Values written to the original's memory aren't play, so `--from` stops at them. With any of these, `--yes` also sends what's kept as a pull request of its own, on the latest `main`, which is the game's [card](../docs/TEAMS.md#a-games-first-files-and-its-card) when it has none. A game whose first files aren't on `main` yet has nowhere for it to go, so it says the capture goes in with the branch's pull request. It leaves the branch you're on alone, so what it wrote still shows in this folder to commit there too.

## Proving

`npm run dp -- prove <game>` plays every recording of the game in the original and in the Dreamport, both from power-on, and compares every frame: its picture, pixel for pixel, in the console's own colours, and its sound, as [How sound is compared](#how-sound-is-compared) explains. A frame matches when both are the same. Add recordings' names after the game's to play only those. The Dreamport runs in a browser you don't see, a frame at a time, through its kit's proof mode ([the Game Boy Advance kit's](../kit/gba/README.md#for-the-proof-tools)), as fast as your computer goes rather than at the console's speed, and one browser plays all the recordings. Sonic Advance Dreamport's first act, 3,300 frames, takes a few seconds. Several recordings play at the same time, each in a page of its own, as many as your computer has idle cores and free memory for as it starts, eight at most, so two people or agents proving on one computer each get fewer and neither waits for the other. `--at-once <how many>` sets it yourself. Each recording still prints everything it found in one piece, in the usual order. A proof of the whole game says in full only what's news: the recordings that came out as when last proven, and that the step changed nothing in, are summed up at the end, by name, those with every frame the same and those that differ from the same frame as before. `--all` prints each of those in full too, as naming a recording does. A game written in C is built once, before anything plays, and not at all when none of its C changed since it was last built. `--paced` holds it to the console's speed, for a game whose code goes by the clock, one recording at a time.

`prove` ends with 0 when every frame of every recording matches. When frames differ it ends with 3 if none of them matched in the last commit, and says so, and with 1 if one did, naming the recording and the frame: a recording nothing proved before has to match in every frame (`tools/lib/as-before.mjs`). `ready` passes only on 0, and `update` on 3 as well.

`prove <game> <recording> --quick` is for while you work: it stops at the first frame that differs, says why, and writes nothing but a picture of that frame and the stills you asked for, with no clip and no numbers, so it's the cheapest way to see whether a change did what it should. Run it plainly before the step goes out, which `npm run dp -- ready <game>` does.

For each recording it says how many frames were the same and which first differs: the frame, how many pixels differ, and the box they're in, or that it's the frame's sound, and then the first picture that differs too. It lists every stretch of frames that differs, then those whose sound differs, with the first of them: the band of pitches where it's furthest from the original's, and how loud each one is there, in the console's steps. It says so when the Dreamport makes no sound at all. It also lists the stretches where the original's screen is one colour, as it is between one screen and the next, which helps find where each of the game's parts starts and ends. For each part the recording proves in `parts.json`, it says whether every frame of it matched, and it names any [note](../docs/NOTES.md) on a part it didn't prove or on a recording that differs. At the end it gives the game's two numbers as they are now. It also compares with the last time the recording was proven: frames that differ now where they matched then are listed apart, with the first of them, which is usually the one a change just broke. If any frame differs, `prove` ends with an error, so a script that runs it stops. Frames are numbered as the Dreamport counts them. The console shows each frame's work one frame later, and `prove` lines the two up. A game that reads its buttons just after the V-blank, rather than just before it as most do, reads each frame's buttons in the frame `prove` counts as the next one: `"keysAfterVBlank": true` in its `original.json` gives the original its buttons a frame later, so the two still line up. Sonic Battle is one.

A Dreamport that throws, as a game does on a path it hasn't ported yet, such as a version in C behind its JavaScript, stops its recording there: `prove` says at which frame and what it threw, counts that frame and every one after as differing, keeps it under `stopped` in `report.json`, and goes on to the next recording.

At the first picture that differs, and with `--state <frames>` at any others, such as `--state 782,1099`, up to 20 at a time, it says what the console holds as it draws that frame, where the original and the Dreamport differ: its display registers, its colours, its sprites and its video memory, with what on the screen uses each stretch of it. That's why a picture differs, which a picture can't say: a layer's scroll, a sprite's place, a stretch of a map. When all of it is the same, the picture differs because of how it's drawn. A register changed between lines shows its last line's value in the original and its first in the Dreamport. For every frame `--stills` or `--state` names, it says how many pixels differ and the box they're in.

Of video memory it prints only where it differs and how each stretch of a map starts, never a tile. What it prints goes only to the terminal and `report.json`, and, as with `read`, to the company that runs your agent's model when an agent reads it.

Its results go in `.dreamports/results/<game>/<recording>/`:

- `report.json`: everything it found, with what it heard under `sound`: whether the Dreamport made any, the stretches whose sound differs, and the first of them, and under `neverInPlay` any frames no player could ever see, as [Start points](#start-points) says.
- `first-difference.png`: the first frame that differs, as the original, the Dreamport, and the original in grey with every pixel that differs in magenta. When it's only the frame's sound that differs, the pictures are the same.
- `first-picture-difference.png`: the same, for the first frame whose picture differs, when a frame before it differs only by its sound.
- `first-new-difference.png`: the same, for the first frame that differs where it matched last time.
- `clip.mp4`, with `clip-start.png`, `clip-middle.png` and `clip-end.png`, pictures of its first, middle and last frames.
- `dreamport.mp4`, the same frames of the Dreamport on its own, with nothing of the original, and `dreamport.png`, its middle frame. `share` posts only `clip.mp4`, never this one, as a pull request's clip shows the original next to the Dreamport ([#1039](https://github.com/NahuelGenchi/dreamports/issues/1039)), and never a video made another way.
- `stills/`, a picture of both at each frame `--stills` names, such as `--stills 249,250` or `--stills 900-905`, up to 600 at a time, and at each part's first and last frames, with the one before and the one after. Each is `frame-<frame>.png`, with where the two differ when they do.

The clip shows the original and the Dreamport side by side, with the frame's number, and *differs* over frames whose picture doesn't match, or *sound differs* over those where only the sound doesn't. It has no sound itself. It holds every frame, about 60 a second, made inside the browser rather than filmed from a screen, so it's smooth. It shows the frames the recording's `clip` names, or else five seconds from a second before the first frame this step changed, ending before the first frame that differs, as every frame of a clip matches. A recording that changed nothing shows its last five seconds, or the time around its first difference. The first frame a step changed is told from main's proof as the branch started from it: in a recording main proved the same, the first frame that matches now and didn't on main, or the other way round, and in one it didn't, the first frame whose original runs code main's proof doesn't count. `prove` prints it as *What this step changed*, and says at once what `share` would refuse. It's an H.264 MP4 video, which phones and browsers play, at the console's own size, 480 by 180 with both sides and the bar. Twice that size took about twice the bytes, and more than the 2 MB limit in fast play. It's encoded in the mode browsers have for screens, at up to 2 Mbps. A calm clip stops well short of that, at about 0.1 to 0.3 MB, and five seconds of fast play comes to about 1 MB. A clip that stays over 2 MB is encoded again without that mode, which goes lower. The stills stay at twice the size, with every pixel sharp.

The clips and the pictures show the game, so they stay in `.dreamports/`, which the ignore rules keep out of commits. [Clips](../docs/STANDARD.md#clips) in the standard says where they may be shared: clips of the original in pull requests and nowhere else, and clips of the Dreamport alone anywhere. The original's sound stays there too: `prove` only keeps how loud each frame is, in `report.json`.

## How sound is compared

Both make the console's own sound for each frame: the mix of its four Game Boy channels and its two DirectSound channels, 65,536 samples a second, in its 10-bit steps, before the console's volume and filter. The original's comes from mGBA, through [`gba/original.c`](gba/original.c). The Dreamport's comes from its kit's sound engine, which runs on the page while the tools play the game, a frame of sound after each of the game's frames ([the Game Boy Advance kit's](../kit/gba/README.md#for-the-proof-tools)). A game that doesn't play its sound through the kit is silent to the tools.

The two never match sample for sample, even when the game is right. The console makes each frame's sound at its own moment in the frame, where the game's sound library runs, and the kit at the frame's start, so the two are a fraction of a frame apart, and the parts of a sound by different fractions: in Sonic Advance Dreamport, from 128 to 345 of the 1,097 samples a frame has. So `prove` compares how loud each frame is, pitch by pitch:

- The sound is split into eight bands of pitches, each an octave wide, around 125 Hz, 250 Hz and so on up to 16 kHz, on the left and on the right, and measured over the frame with the one before and the one after.
- A frame's sound is the same when every band is within 10 dB of the original's, which listeners hear as twice or half as loud. A band quieter than one of the console's steps counts as silent.
- When one is silent in every band and the other isn't, the frame differs, however quiet the sound. Two silent frames are the same.
- The original's sound is taken from as far as a frame before or after, wherever it's closest, so a sound may start or end up to a frame apart.
- A dip counts as the same. When two of the console's voices play the same note, such as a square wave and a sampled instrument, they cancel each other for a moment, and when they do depends on the exact cycle of every write to the square wave since the console was switched on, which a Dreamport can't have. So one note's band, alone or with the bands next to it, may be as far as 16 dB away for up to 8 frames in a row, an eighth of a second. A longer run differs from its ninth frame, and a dip only counts after 8 frames that were the same, so the frames around a sound that is wrong aren't taken for dips. `prove` lists the frames it took for dips.
- The sound of the two frames either side of a stretch only the original has (`onlyInOriginal`) isn't compared, as the original's runs into or out of the screen the Dreamport skips. `prove` says which frames those are.

This catches a Dreamport that is silent where the original plays, or plays where it's silent, plays another sound, or plays it far louder or quieter. It can't tell a sound a frame early or late, a quiet sound missing under a loud one, a difference inside one band, such as a note a little out of tune, or, since dips count as the same, a sound shorter than 8 frames that is missing or wrong while something else within 16 dB of it plays in its band. On Sonic Advance Dreamport's recordings, 98 in every 100 frames with sound are within 3 dB of the original in every band, and none is more than 6.8 dB away but in its dips, which are at most 14.4 dB away for 6 frames, while Sonic Battle Dreamport, which makes no sound yet, is silent wherever its original plays. [`lib/sound.mjs`](lib/sound.mjs) holds the comparison and its numbers.

## The code map and the two numbers

The code map, `games/<game>/proof/code-map.json`, lists every function in the original program with its address and its size, and nothing of its code. It's the first thing a new Dreamport needs, before any of its code, as [the standard](../docs/STANDARD.md#how-progress-is-measured) asks: write the game's `original.json` from what `rom` says about your copy, run `rom` again so the tools know it's the copy the proof uses, then make the code map, and commit both with the game's first files. `npm run dp -- codemap <game>` makes one by finding the functions in your copy itself, following the code from where the game starts, in a Game Boy Advance or an NES game. An NES game's program is in banks, so the code map numbers each of its functions by its offset in the program, and its code names one with its bank, as `sub_04_923F` ([NES addresses](../docs/CONSOLES.md#whats-different-from-the-game-boy-advance)). A decompilation knows its functions better, and `npm run dp -- codemap <game> --from <list>` takes them from a list: what `nm -S` prints from the decompilation's ELF file, or a CSV with a column for the address and one for the size, such as the list of functions Ghidra exports, or for the end, the address just after the function's last byte, as decompilations list their functions' extents. A function listed without either gets the space up to the next one. A list can stop short, as when it didn't follow a function's switch or leaves out what nothing calls, so the tools also follow the code from every function it lists, in your copy, and add what they find beyond them. A listed function keeps its start and its name and grows over the rest of its code, up to the next one listed, and anything else becomes a function of its own, without a name. A list can also name data as a function, as when it takes a switch's table or the words a function loads for the start of another, so a listed function that starts in the data of the code before it is left out, the tools say which, and the function before it grows over what it held. `npm run dp -- codemap <game> --fill` does the same to the code map the game already has, keeping its names, which a list doesn't always have.

Each Dreamport shows two numbers, code ported and gameplay proven, which [the standard](../docs/STANDARD.md#how-progress-is-measured) explains. The tools write what both are measured with.

`prove` notes which of the original's functions ran in each frame, keeps those that ran in frames that matched, picture and sound, and writes them to `games/<game>/proof/progress.json`, with each recording's results: how many frames it has, which ones differ, and of those which differ by their sound, as `soundDiffers`, and the share of the code map's size those functions make. Recordings it didn't play this time count as they were last proven. It also says how many of the original's instructions ran outside every function of the code map: code the map is missing, in the cartridge, which `codemap --fill` adds, or code the game copies into the console's memory before running it, which the map normally lists once already, where it sits in the cartridge.

`npm run dp -- portmap <game>` writes the port map, `games/<game>/proof/port-map.json`: each function of the original that the game's code names, with the first file and line that names it, and every name that lands inside a function of the code map but not at its start, which is usually a mistake. A name is an address in the cartridge, written as a number, such as `0x08029E78`, or as a label, such as `sub_8029E78`, or `FUN_08029E78` as Ghidra writes them. On the NES it's always a label with the bank switched in at $8000, in two hexadecimal digits, as `sub_04_923F`, or with none for the last bank, which is always at $C000, as `sub_C39C`. An address outside every function of the code map is the game's data, such as a picture the code copies, and isn't counted or listed. A number is an address in the copy the proof uses. A label is one in the release the game's labels come from, and when that's another release, the game's `proof/names.json` says how far each stretch of its code is from the copy's. Sonic Advance Dreamport's code uses the labels of a decompilation built from the European release, and [its `names.json`](../games/sonic-advance/proof/names.json) gives the shifts to the USA release. Run it after changing the game's code; `npm run check` says when a port map is out of date.

Code ported is the size of the functions the port map names and those `prove` found running in matching play, divided by the size of every function in the code map. Gameplay proven is the share of the parts in `games/<game>/proof/parts.json` that a recording proves: every frame from the part's first to its last matched, picture and sound, with none the Dreamport doesn't have. The game's page, the launcher's Make row and `docs/STATUS.md` show both, and the site checks that they add up with the files before it shows them, so they only ever come from the tools. The tools also draw each game's progress map from the same files, with [`src/lib/progress-map.mjs`](../src/lib/progress-map.mjs): a picture of every function in the code map and every part, green once it counts. It's kept in `.github/readme/progress/<game>.svg`, which the table in `docs/STATUS.md` links, and the Readme workflow writes both on `main`, every three hours, from what's merged, so pull requests never conflict over them. It's only shown on GitHub, never on the site.

## Starting a game

`npm run dp -- new <game>` starts a Dreamport that someone has claimed and mapped: it needs its [New Dreamport](../docs/TEAMS.md#start-a-dreamport) issue, `proof/original.json` and its code map. It writes `index.html`, `src/main.js`, `LICENSE` and `entry.md` in its folder, then its port map and the table in `docs/STATUS.md`. Its [capture](#a-games-capture) then gives it its place in the Make row. The game's code starts as the kit's start for its console, [`gba/new-game/`](gba/new-game/), with the controller, the touch screen, the settings and the start screen already working, and it shows only a blue screen until someone writes the game. The first three files say the same for anyone with the same `original.json`, so nothing has to be reviewed in them. `new` writes over nothing. A pull request of only these comes in with no review and merges by itself ([A game's first files and its card](../docs/TEAMS.md#a-games-first-files-and-its-card)): `--commit` commits them in the words that needs, and with it `--yes` sends a whole new game's as that pull request, beside the branch you're on, which stays as it is.

`npm run dp -- new <game>/c` starts the game's [version in C](../games/README.md#versions-in-other-languages), on any console: `index.html`, `src/main.c` and `src/main.js` in `games/<game>/c/`, which show the same blue screen, then its port map. In a game that hasn't started, it also writes `LICENSE` and `entry.md` in the game's folder, and no JavaScript version, as a new game starts in C: its version in C is its main one, and `--commit` commits them as the game's first files, which `--yes` sends and which come in with no review of their code like a JavaScript game's. `npm run dp -- new <game>` adds a JavaScript version to it later. Its C stands on its console's [kit in C](../kit/c/README.md), the Game Boy Advance's own or, on any other console, what every console's shares. Every tool takes a version by that name, as in `prove <game>/c` and `play <game>/c`. A version's recordings are the game's, and it keeps only its own `progress.json` and `port-map.json`. The tools build its `src/game.wasm` before they open it, and so does the site.

## Reading the original's instructions

A Dreamport rewrites each of the original's functions from how the original does it, usually from its decompilation's C. When a function has none, because the decompilation hasn't reached it or its C doesn't match, or the game has no decompilation, `npm run dp -- read <game> <function>` prints the function's own instructions, the machine code the console runs, from your copy. The function is an address, such as `0x08016078`, a name in the code map, such as `FUN_08016078`, or a label of the release the game's labels come from, such as `Task_803775C`, which `names.json` moves to the copy's address as it does for `portmap`. It prints the whole function, as the code map has it. When a label doesn't land where a function starts, it says so first, since `names.json` may not say how far that label moved, and it may be the wrong function.

mGBA's own decoder reads the instructions. The library `setup` builds leaves out the part that writes them as text, so `setup` builds that part on its own, with [`gba/read.c`](gba/read.c), and each line is the one mGBA's debugger shows for the same address. On 1 November 2026, for every function in Sonic Battle's and Sonic Advance's code maps, all 381,615 lines it printed as instructions were the same as mGBA 0.10.5's `disassemble` command printed. An automated player then ran 1,860 of those functions, for 198 hours of the games' time: none of the addresses they ran fell on a line printed as data or in the other kind of instructions, and none of the words they read from their own code fell on a line printed as an instruction. For the 82 Sonic Advance functions whose assembly its decompilation keeps, all 24,197 instructions and 1,695 words of data came out the same. Beyond what mGBA's debugger shows, `read`:

- Writes the numbers the code keeps beside itself, its literal pool, as `.word`, and a switch's jump table, the address of each of its cases, the same way, with any padding before them as `.hword`. It finds them by following the game's code from every function in the code map, since a code map entry can start partway into a function and keep its numbers in the next entry. What none of that code reaches still reads as instructions, as it does in mGBA's debugger.
- Follows code that changes from Thumb to ARM or back partway through a function, as a game's sound driver does, and a line such as `@ ARM from here` says where.
- Adds the code map's name of each function a line calls or loads the address of, after `@`.
- Reads the function as ARM or Thumb, the console's two kinds of instructions, as the tools found it by following the game's code, or else from how its first instructions look. `--arm` or `--thumb` reads it the other way, following the code only from that address.
- Reads `--bytes <n>` bytes from the address instead of the whole function. A function the code map doesn't list gets as much as the tools can follow of it, or else its first 256 bytes.
- Reads code at `0x02000000` or `0x03000000`, which the game copies into the console's memory to run there, as it is 60 frames after power-on, or `--frame <n>` frames after, following the code only from that address.

What it prints comes from your copy of the game. It goes to the terminal and to `.dreamports/read/<game>/<address>.txt`, and never in a commit, an issue or a pull request, not even a few lines. A coding agent that reads it sends it to the company that runs the agent's model, as it does with everything it reads, so agents reach a copy only through the tools, a function at a time. The Dreamport's code says which function it rewrites, and that's enough.

A line such as `08001234:  4801  ldr r0, =0x03000010  @ 0x0800123C`, made up for this guide, is an address, the bytes there and the instruction they make. A Thumb instruction takes 2 bytes, or 4 for a call, and an ARM one 4. Most of a game's code is Thumb. A short guide to the rest:

- **Registers.** `r0` to `r12` hold numbers, `sp` points to the stack, where a function keeps what doesn't fit in them, `lr` holds where a call returns to, and `pc` the instruction running. A function gets its first four arguments in `r0` to `r3`, gives its result back in `r0`, and leaves `r4` to `r11` as it found them.
- **In and out.** `stmdb sp!, {r4-r6,lr}`, which other tools write as `push`, saves registers as a function starts, and `ldmia sp!, {r4-r6}`, or `pop`, puts them back before it returns with `bx` or by loading `pc`.
- **Calls and branches.** `bl` calls a function. `b` jumps, and `beq`, `bne`, `bhi` and the like jump only when the `cmp` before found the two equal, not equal, greater and so on: `lt`, `gt`, `le` and `ge` compare numbers that can be negative, and `lo`, `hi`, `ls` and `hs` those that can't.
- **Numbers.** `ldr r0, =0x03000010` loads a number from the literal pool, at the address after `@`. `mov` and `add` with `#` use a number written in the instruction itself.
- **Memory.** `ldr` and `str` read and write 32 bits, `ldrh` and `strh` 16, `ldrb` and `strb` 8, and `ldrsh` and `ldrsb` read numbers that can be negative. `[r1, #8]` is the address in `r1` plus 8, often a field of a structure.
- **Addresses.** `0x02000000` and `0x03000000` are the console's work memory, where the game keeps its variables, `0x04000000` its registers, which drive the screen, sound, buttons and copies (`0x040000D4` is DMA 3), `0x05000000` the palettes, `0x06000000` video memory, `0x07000000` the sprites and `0x08000000` the cartridge.
- **The BIOS.** `swi` calls the console's built-in program: `swi #11` is CpuSet, `swi #12` CpuFastSet, `swi #5` waits for the next frame and `swi #6` divides.

[GBATEK](https://problemkaputt.de/gbatek.htm) describes every instruction, register and BIOS call. Rewrite what the function does, not each instruction: readable JavaScript, with names that say what things are, and every number taken from the instructions. Name the function in a comment, by its address or its name in the code map, so the port map counts it, and prove the step. Sonic Battle Dreamport's `newScreen`, in [`games/sonic-battle/src/core.js`](../games/sonic-battle/src/core.js), rewrites `0x08016078`, which its decompilation has no C for.

## Proving a part

A part, such as a game's logos or one of its acts, is proven by a recording that plays the whole of it, from its first frame to its last, so a recording that skips any of it with Start doesn't prove it. It may end with a press that moves the game on, the way a player leaves it: Sonic Advance Dreamport's title screen is frames 902 to 1252 of `neo-green-hill-act-1`, which ends it with Start. These steps prove one:

1. Make a recording that plays the whole part and a little of what comes after it, with `play --record`, with `play --record --from` to start where another recording reaches the part, or by hand.
2. Run `npm run dp -- prove <game> <recording>` and read the stretches where the original's screen is one colour. A part usually starts as one of them ends and ends as the next one does. Where the screen is one colour between two parts, as when one fades out and the next fades in, those frames go with the part before, so the next part starts on the first frame that isn't one colour.
3. Check the frames you picked with `--stills`, such as `--stills 253,254,932,933`, and look at the pictures in `stills/`.
4. Write the part's `recording` and `frames` in `parts.json`, and run `prove` again. It says whether the part is proven, which for a part that names [what it reaches](#what-a-part-reaches) also takes the original getting there within those frames, and keeps pictures of its first and last frames, with the one before and the one after, so the lead can check them once more.

Sonic Advance Dreamport's logos are frames 254 to 932 of [`logos-and-intro`](../games/sonic-advance/proof/recordings/logos-and-intro.json): the language screen fades to white until frame 253, and the Sonic Team logo fades to black, which stays until 932.

A part the game can't reach yet is proven the same way, from a [start point](#start-points).

A recording made for something else can come to play a whole part, as one made for a foundation does: Ghosts'n Goblins Dreamport's `stage-clear`, made for its enemies, played all of its first stage with every frame the same, and the stage didn't count until `parts.json` named it. So when a recording the step changed matches on every frame, no part names it and the game has parts with no recording yet, `prove` says so, with those parts' names, under the stretches where the screen is one colour. If it plays one of them whole, steps 2 to 4 name it, in the same pull request, which then closes the part's task too. If it plays only some of a part, it names none.

## Bringing a branch up to date

`npm run dp -- update <game>` merges the latest `main` into the branch, before a pull request goes out or when one conflicts. A conflict in `docs/STATUS.md`'s table, a progress map, a port map or a `progress.json` settles by itself, with `main`'s table and maps and both sides' recordings. Then it runs `ready` on the result, for every game both sides proved, and only commits if that passes, so pushing is all that's left. A merge passes when the check and the build do and no frame that matched before differs: what matched is what each side's last commit has, and of the two the one that matched more. So a version that doesn't match every recording yet, such as one in C behind its JavaScript, is brought up to date too, and a merge that breaks a frame either side had isn't committed, however often it's run. It needs your copy of the game, as a `progress.json` can only be measured again with it.

A conflict in anything else stops it, with the merge left open, and names the files, since someone has to read both sides. Settle them, `git add` them, and run it again. If `ready` fails, the merge stays open too, so fix what it found and run it again. It exits with 2 for conflicts it can't settle and 1 for anything else that stops it. `--base <branch>` merges that branch instead of `main`, for a pull request built on another.

A branch [built on a pull request in review](../docs/TEAMS.md#building-on-a-piece-in-review) gets that pull request's newest commits first, the same way, each time `update` runs: while it's open, and its last ones once it has merged. A branch left behind what it stands on conflicts with `main` in every file the two share, as a squashed merge has none of the commits the branch took. `update` knows what a branch is built on from the merge that brought it in, and from the `Builds on #<number>` lines of the branch's own pull request, and needs the GitHub CLI to ask which pull request that was. Without it, it says so and brings in `main` alone.

Once that pull request is in `main`, `update` merges `main` as a commit that says it holds it: `main`'s own files, with `main` and the pull request's last commit as its parents. git then compares from that last commit, where a squashed merge alone made it compare from before either began, so only what the branch itself changed is left to settle. That commit stays in the branch's history, named `main, which holds #<number>`, and changes no file.

## Sharing a preview

`npm run dp -- share <game>` publishes a preview of the game as it is in your last commit, on GitHub Pages from your own fork, at `https://<you>.github.io/dreamports/<game>/`, so anyone can play it with their own copy without waiting for a review. `--as <name>` names the preview, to keep more than one. `--about "<what changed>"` puts a sentence of what changed on the preview's first page. Beside the preview, apart from it, go the side-by-side `clip.mp4`s that `prove` made of what this step changed (or the one `--clip` names, which is a `clip.mp4` too), each with its measures beside it, and `share` prints the lines that show them in the step's pull request: a frame of each clip that links the video, and a link. `share` keeps every clip's lines for the branch in `.dreamports/share/clips.md` as soon as they're pushed, before it waits for Pages, to paste under Clips as they are, and `npm run dp -- share --check <file>` refuses a pull request's text that leaves out a clip's frame or link, or that links a clip `share` didn't make for the branch, printing the lines to put there. `share` also writes the pull request's text itself, `.dreamports/share/pull-request.md`, from the repository's template, with all it knows filled in: the issue the branch is for and its milestone, the pull requests in review the branch starts on top of, what `--about` says, the game's lead when it's someone else, the clips, the game's two numbers where the branch left main and now, the titles of the notes the step adds, and the preview. What only whoever made the step can say, such as its sources, stays as the template's own words in `<angle brackets>`, and `--check` refuses a text with any of those left. Shared again from the same branch, it keeps what was written in and writes only its own lines again. A pull request's own check, *Clips*, reads every clip its text links with the measures beside it, and fails the same way (`tools/clips-check.mjs`).

Only a clip `prove` made goes, and only when it keeps the rules of [Clips](../docs/STANDARD.md#clips), which `prove` measures into each `report.json` and says as it ends (`tools/lib/clips.mjs`). It lasts at least 300 frames, five seconds. At least half of it, 150 frames, comes from the first frame the step changed on, so a recording that proves only a few frames of a new place after a menu runs on in that place, rather than moving its `clip` back into the menu. Every frame of it matches the original's, in picture and sound, since [#1039](https://github.com/NahuelGenchi/dreamports/issues/1039): a run-on whose frames differ shows a step that isn't done, so port what those frames need until they match. `share` takes only the side by side `clip.mp4`, never the Dreamport's video on its own, `dreamport.mp4`, and the Clips check refuses one. It shows a recording the step changed: one whose every frame main played the same, such as the title screen in a step about a fighter, is left out. A step that changes the game's code or recordings has at least one clip, so when no recording shows anything it changed, as when nothing plays the new code yet, `share` refuses and says to add a recording that plays it, or run one on until it does. A team build's preview, which `team add` updates, needs none of its own. The Dreamport's picture is one colour in no more than a quarter of it, and the same as the frame before in no more than nine frames in ten. Side by side, no more than a quarter of the frames differ from the original's in more than half their pixels, as when the recording takes the original somewhere else, which `share` says apart. Its recording is committed as it was proven, against main as the branch starts from it, so a merge of main means proving again. A clip `share` kept from before that breaks a rule now leaves the branch's clips. For a version in C, as in `share sonic-battle/c`, it builds the game's WebAssembly from the C in your last commit, which has to be committed, as no commit holds the built file. It posts nothing. It asks before it publishes and before it switches Pages on for your fork the first time, and `--yes` answers yes for you. [Previews](../docs/PREVIEWS.md) explains what a preview holds, what it risks for players, and where the clip goes.

A step that changes a game's code and no frame, such as one that only moves code, has no clip, as every recording comes out as `main` has it. Its proof stands in for one. `prove <game>` with no recording named plays every recording and keeps a record of that whole proof in `.dreamports/proofs/`: how many recordings it played, its `progress.json`, and the game's folder and the kits' as they were, each as a hash. When the commit's `progress.json` is `main`'s own file and the record is of the very files the commit holds, `share` publishes the record beside the game's clips, and gives its line for the pull request, in `.dreamports/share/clips.md` like a clip's. So prove the game whole, commit, and share: files changed after the proof, or a merge of `main` that changed the game or its kit, mean proving it again, and a merge of `main` that changed neither doesn't. The pull request's check reads the record and holds it to what would merge, for each version whose code the step changes. A step that changes the game's recordings always shows a clip (`tools/lib/same-proof.mjs`).

## Claims and team builds

`npm run dp -- find <game>` shows where a game stands before you start on it: its lead, its two numbers, its Make page, how many notes it has, its team build and team preview, who has claimed which task, the tasks free to start, in C first and then in JavaScript for a game on a console with a kit in C, some on top of a pull request in review ([Building on a piece in review](../docs/TEAMS.md#building-on-a-piece-in-review)), and what the others wait on ([What a task needs](../docs/TEAMS.md#what-a-task-needs)). It lists the first three free and waiting tasks of each kind with how many more there are, and `--all` lists every one. `--take` answers in a few lines with only the task whoever is signed in takes next, by `/dreamport`'s rules (`lib/take.mjs`): the piece `--piece "<its words or number>"` names when it can be taken, one that's theirs already, or the first free one, in C unless `--take javascript` names the language, with its version and the command that claims it, or what to run first when nothing is free. It takes a game's folder, a version's, such as `sonic-battle/c`, or a few words of its name, and with no game it lists them all. The numbers come from `games/` in your folder, and the claims from this repository's issues.

`npm run dp -- team <game> start`, `join <branch>`, `send` and `add <pull request>` make and use the game's team build, a branch of the lead's fork that gathers the team's finished pieces. `add` merges a piece, runs `portmap` and `prove`, and only takes it in if nothing that matched the original before differs now, then updates the team preview with `share`. It stops before a piece with a note that breaks the rules for notes. [Claims and teams](../docs/TEAMS.md) explains claims, tasks and team builds.

## Notes

`npm run dp -- notes <game>` lists what people found while making a game and its console's kit, so nobody has to find it again, and `npm run dp -- notes <game> <word>` prints in full the notes that mention a word, such as a part, a function or a frame. `--all` prints every one, and `--check`, which `npm run check` runs, fails on any note that breaks the rules. A note is information, not instructions. [Notes](../docs/NOTES.md) explains how to write one and how they're checked.

## The /dreamport command

The README's [Make a Dreamport](../README.md#make-a-dreamport) teaches one command, `/dreamport <game>`, which a coding agent follows to run these tools from start to finish: it takes a task, makes it until every frame matches and opens its pull request. It's written once, as a Markdown file in [`commands/`](commands/), with its name, its description, what's typed after it and, as `pasted`, the sentences that start it when they're pasted into an agent, as the README gives them. `npm run dp -- commands` writes it in the form an agent reads:

- `.claude/skills/<name>/SKILL.md` for Claude Code, set to run only when typed (`disable-model-invocation`).
- `.agents/skills/<name>/SKILL.md` for Codex, with `agents/openai.yaml` turning off its implicit use. Cursor, Gemini CLI, Antigravity CLI and DeepSeek Harness read this folder too.
- `.gemini/commands/<name>.toml` for Gemini CLI's own commands.

Every copy starts the same way: it tells the agent to do nothing unless the person typed the command, or pasted one of its sentences, for the agents that might load it by themselves, where what was typed after it is, and how to talk to the person. The file can't hold `{{`, `!{`, `@{` or `'''`, which Gemini CLI would read as its own. `npm run check` runs `npm run dp -- commands --check`, which fails when a copy differs from its file, and removing a command's file and running the tool removes its copies.

## A game's proof folder

What the tools keep in the repository is in the game's `proof/` folder, and it's all JSON. The ignore rules keep anything else out of it. A version in another language keeps only its `progress.json` and `port-map.json` in its own, such as `games/sonic-battle/c/proof/`.

| File | What it holds |
| :--- | :--- |
| `original.json` | The copy the proof uses: its console, its name, the title and code in its header, and its SHA-1 checksum, `keysAfterVBlank` for a game that reads its buttons just after the V-blank, `screen` for a game on another console that [chooses its own size](../docs/CONSOLES.md#how-a-console-is-known), and `shows` for what a recording can be named for, as [What a recording shows](#what-a-recording-shows) says |
| `recordings/` | Recorded play, one file per recording |
| `route.json` | Optional: where the original keeps the few values `route` reads as it searches, and the goals the game names, as [Finding a route](#what-a-game-says-of-its-original) says. A part can name one of those goals as what it reaches |
| `code-map.json` | The code map |
| `progress.json` | Each recording's results and the code that ran in matching play, written by `prove` |
| `port-map.json` | The port map: the functions the game's code names, and the names that land inside one but not at its start, written by `portmap` |
| `names.json` | Optional: how far the release the game's labels come from is from the copy's, stretch by stretch, for `portmap` and `read` |
| `parts.json` | The game's parts, each with the recording and frames that prove it once there are some, and what it has to reach when it names that ([What a part reaches](#what-a-part-reaches)), written by the game's lead |

## What stays on your computer

Everything else the tools keep is in `.dreamports/`, in the repository's folder, which the ignore rules keep out of commits: where your copies are, the reference emulator, every result with its pictures and clips, what `route` found and the pictures of where it stopped, what `read` prints, what you played for `capture`, and the browser profiles the tools use. Deleting it is safe, as `setup` and `rom` make it again. Only what you send leaves it, such as a clip in a pull request. A coding agent is different: whatever it reads, such as what `read` prints, goes to the company that runs its model, unless that model runs on your computer too.

## For a game on the Game Boy Advance kit

A game made on [the Game Boy Advance kit](../kit/gba/README.md) works with the tools when its page calls `proof?.watch(screen, input)`, as the kit's guide shows, and keeps the kit's start screen, where the tools give it the copy and press Play. Its screen has to be the console's 240 by 160 pixels while the tools play it, and the tools hear its sound when it plays through the kit's `createSound()`. Games with more than one player on a page aren't supported yet.
